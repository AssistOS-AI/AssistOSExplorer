RoboWork

RoboWork runs the robots controlled through RoboTeam. It keeps native accounts and files in separate persistent homes, starts resident ALA runs, and provides Browser, Desktop, terminal and selected-image environments.

Persistent homes and resident runs

A robot keeps its home under workspace .data/.private/roboWorkAgent. Programs see /home/<id> with matching HOME and USER. RoboTeam stores registry, conversations and workflows; RoboWork stores homes, native configuration, run metadata, tool generations and nested image state. Ploinky hides the private store from other agents.

A run starts through the internal run_start tool. Only the exact verified RoboTeam agent acting for itself may invoke RoboWork tools. Robot programs receive no Ploinky credential. Their own home, admitted project folder, the folders passed for the run, read-only skills and per-run callbacks cross the boundary. The rest of the workspace is not mounted, and private project history stays masked in runs, terminals, model discovery, Browser and Desktop. Cwd under .data or .ploinky, and the workspace root itself, is refused. A task that spans several projects uses a common parent folder below the root.

A path check cannot protect a later path mount while a robot can write that path. RoboWork records each granted folder's device and inode. A container's first process compares its mounts with them before anything a robot controls starts, and native ALA binds each folder through a descriptor it opened and compared. A swapped folder ends the run with FOLDER_REFUSED.

Run and GUI starts return starting promptly while the resident service prepares tools, images and launch. Run reads report progress and failures; robot status reports GUI readiness. RoboTeam polls while waiting. Stopping a starting run cancels its owned preparation and prevents a late launch. Shared preparation continues for other consumers. Static Bubblewrap warms after readiness. A selected-agent terminal reports that preparation is in progress and asks the user to retry Open.

RoboTeam restart reattaches to the same resident runs and GUI containers. RoboWork restart interrupts runs; Resume continues the native conversation. Output replays from sequence zero and replayed phase progress is suppressed. A run stops with an error at the 64 MiB log cap. Ended unreleased runs older than seven days are removed at startup only.

Interactive execution

Browser and Desktop mount the same home at /config and /home/<id>. Without a folder they start at the home. Session HTTP and WebSocket traffic use the authenticated RoboWork port-3001 route. Box bindings are 17000:7000 and 13001:3001; the routed container port stays 3001.

Administrator robot terminals launch only the verified RoboWork discovery row. The card starts at the home; Open Terminal Here keeps the clicked folder. A default terminal and its task have separate localhost networks. Plain terminals retain their normal behavior, including an administrator's ability to access all homes through a plain RoboWork terminal.

Closing a robot terminal ends its private process namespace, including children that ignore hangup and termination signals. The inner launcher detects TTY hangup without consuming shell input; live-terminal job control and resize stay with the shell.

An Environment starts a new container from the chosen agent's image. Editors available in an Environment terminal come from that image. It has no target credentials, programs installed after target startup or target localhost. Listing checks image presence and cached errors without pulling all images. Only the selected step downloads its image, without a fixed 120-second limit; an explicit retry can recover a cached pull failure. Private-data agents, RoboWork and RoboTeam are excluded.

Network and accepted limits

Private pasta networks block RoboWork loopback and sibling GUI ports. Only a GUI task's own MCP port is forwarded. Explicit RoboTeam or RoboWork loopback MCP addresses no longer work; non-loopback addresses remain usable. Soul Gateway inference uses the mounted robot-specific socket, with credentials retained in the service.

Workflows do not accept a target robot, but robot-written prompts can indirectly influence another robot. This boundary prevents direct home and credential access. Administrator plain-terminal authority remains. Proxy administration stays in RoboTeam while RoboWork owns leases, relays and firewall resources.

Checks

Provider-free checks live in tests/. Explicit live probes live in tests/e2e/ and the RoboWork smoke specification. Live acceptance requires command-produced evidence, positive controls, exact source and container identities, and the full selected apparatus suite. Local source checks alone do not establish namespace isolation or sustained eight-run polling fairness.
