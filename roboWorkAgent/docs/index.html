RoboWork

RoboWork runs the robots controlled through RoboTeam. It keeps native accounts and files in separate persistent homes, starts resident ALA runs, and provides Browser, Desktop, terminal and selected-image environments.

Persistent homes and resident runs

A robot keeps its home at workspace .data/robots/<id>/home. Programs see /home/<id> with matching HOME and USER. RoboTeam stores registry, conversations and workflows; RoboWork stores homes, native configuration, run metadata, tool generations and nested image state. Ploinky mounts service state from .data/agents/roboWorkAgent at /root and the declared robot volume at /robots. Each robot has home, run, runs/<runId> and terminal directories. RoboTeam accesses these through RoboWork tools and has no robot-volume mount. At startup, before the service listens, RoboWork removes superseded tool generations and its former shared npm cache, as DS002 specifies; they accumulate until the next start.

A run starts through the internal run_start tool. Only the exact verified RoboTeam agent acting for itself may invoke RoboWork tools. Robot programs receive no Ploinky credential; the only credential a robot can use is its own git credential, served on demand. Their own home, admitted project folder (writable), the workspace (read-only, at its canonical path), the folders passed for the run, read-only skills and per-run callbacks cross the boundary. RoboWork adds the workspace itself; a caller cannot grant, widen or remove it. .data, .ploinky, .ploinky-box and the root .env are empty read-only masks in runs, terminals, model discovery, Browser, Desktop and Environments, and the project's own .roboteam records, which RoboTeam reads back, stay masked as well. An entry that is absent when a session starts has no mask. Where the filesystem opens a hidden entry under another spelling, as APFS does through a Mac Box, the masks cannot hold and no workspace is shown, though a project skill link can still mount another project read-only. One check decides every cwd: it must lie below the workspace root, and the root itself, .data, .ploinky and .ploinky-box are refused. Browser, Desktop and terminals also refuse a folder inside .roboteam. A task that spans several projects uses a common parent folder below the root.

A path check cannot protect a later path mount while a robot can write that path. RoboWork records each granted folder's device and inode. A Browser or Desktop container's first process compares its mount with it before anything a robot controls starts, and ALA, in a native run, an Environment and a terminal's sandbox, compares each folder first and binds it through a descriptor it opened. A swapped folder ends the run with FOLDER_REFUSED.

Robots that share a folder

There is no read isolation between project folders: a robot can read every other project, including its .roboteam, nested .env and .git/config, and other robots' working files. Write isolation and home isolation remain: a robot writes only its cwd and home and cannot reach another robot's home. Robots that share a folder, or where one works in a parent of the other's folder, must trust each other, and no code tries to prevent that. This is a stated exception to home isolation: a robot runs what sits in its working folder, so a plugin, script, hook or skill that another robot planted there runs with the home of the robot that runs it open, credentials included. Coding agents also load configuration, plugins and instructions from ancestors of their cwd, so what a robot writes in a parent folder can reach a child's sandbox. OpenCode stops when it cannot prepare an ancestor's .opencode, so RoboWork shows each one above the working folder as a read-only prepared empty directory at each start, and nothing inside it loads. This keeps robots running and is not a trust boundary: an ancestor's opencode.json can still name a plugin, and other coding agents still read their ancestors' files. Sibling folders are not ancestors and are not loaded. Put robots that must not trust each other in folders where neither lies inside the other.

Run and GUI starts return starting promptly while the resident service prepares tools, images and launch. Run reads report progress and failures; robot status reports GUI readiness. RoboTeam polls while waiting. Stopping a starting run cancels its owned preparation and prevents a late launch. Shared preparation continues for other consumers. Static Bubblewrap warms after readiness. A selected-agent terminal reports that preparation is in progress and asks the user to retry Open.

RoboTeam restart reattaches to the same resident runs and GUI containers. RoboWork restart interrupts runs; Resume continues the native conversation. Output replays from sequence zero and replayed phase progress is suppressed. A run stops with an error at the 64 MiB log cap. Ended unreleased runs older than seven days are removed at startup only. Deleting a stopped robot removes its home, sockets, terminal state and credential record but preserves its run history. Startup recovers retained runs by run ID from their metadata, even after the robot is deleted.

Nested Podman keeps images at /root/podman/images. Installation and startup select /root/server-state/podman-storage.conf through CONTAINERS_STORAGE_CONF. A separately launched outer WebTTY process must use the same configuration when starting an Environment through nested Podman. Writable container layers and run state stay on the disposable /var/lib/roboteam-podman tmpfs. The migrated image cache is preserved without rebuilding the runtime image or resetting storage.

Interactive execution

Browser and Desktop mount the same home at /config and /home/<id>. Without a folder they start at the home. Session HTTP and WebSocket traffic use the authenticated RoboWork port-3001 route. Box bindings are 17100:7000 and 13101:3001; the routed container port stays 3001.

Robot-card terminals use the verified RoboWork discovery row and start at the home. Open Terminal Here defaults to eligible running agents and keeps the clicked folder and original robot home. Ordinary processes in the selected agent can access that home and may retain files or open descriptors after the terminal ends. A default terminal and its task have separate localhost networks. Plain terminals retain their normal behavior, including an administrator's ability to access all homes through a plain RoboWork terminal.

A coding agent terminal opens one of the robot's enabled coding agents in place of its shell, with the same sandbox, home and folder. New and resumed coding sessions use ALA's full-access policy for all seven agents. ALA supplies native permission flags and environment values after the login profile, while Bubblewrap continues to enforce the directory grants and private process namespace. One-shot robot runs use the same full-access policy by default. Ploinky lists and opens them from the command line with ploinky cs (ploinky coding-sessions) in the current folder, through the administrator-only coding session API that the manifest declares under webtty.codingSessions: the person picks a robot (the robot named default first), one of its enabled coding agents, then a running terminal to attach, an earlier conversation to resume or a new one. Catalogs that support persisted conversation bindings return sessionBindingSupported and per-conversation sessionBinding metadata. Callers can match their unique Session binding: <uuid> system instruction to the native conversation. Earlier conversations are the ones a person started with that agent in that folder; RoboWork reads them from ALA's interactive session catalog inside the confined home helper. The terminal is a WebTTY session, so it also appears among the Live Sessions. The administrator coding-session launch API accepts optional systemPrompt, arbitrary text without NUL of at most 16384 UTF-8 bytes. It does not accept a role field. Nonempty instructions get an immutable .p-<uuid> terminal profile and a private service-owned descriptor, so concurrent launches of the same robot and coding agent cannot overwrite each other. Re-preparing that returned profile retains its native session arguments and instructions. The descriptor, including the instructions, survives service restart until normal descriptor expiry; API responses do not return the instruction text. RoboWork passes systemPrompt unchanged to ALA's native launch builder, which applies the selected agent's native instruction mechanism without typing or submitting a user prompt. Callers pass the instructions again when resuming a conversation through a new launch request; Ploinky supervised sessions do this automatically. Supervisor and worker semantics belong to Ploinky and its workspace skills, not RoboWork or ALA. Both Live Sessions and ploinky cs admit the workspace root as the working folder. A root terminal can write ordinary workspace files; existing private workspace entries and the root .roboteam remain masked. Project terminals retain the read-only view of the rest of the workspace.

Closing an isolated RoboWork robot terminal ends its private process namespace, including children that ignore hangup and termination signals. The inner launcher detects TTY hangup without consuming shell input; live-terminal job control and resize stay with the shell.

An Environment starts a new container from the chosen agent's image. Editors available in an Environment terminal come from that image. It has no target credentials, programs installed after target startup or target localhost. Listing checks image presence and cached errors without pulling all images. Only the selected step downloads its image, without a fixed 120-second limit; an explicit retry can recover a cached pull failure. Private-data agents, RoboWork and RoboTeam are excluded.

Each time the service starts, it pulls the Browser and Desktop images again in the background, together with the agent images it already holds. Ploinky restarts RoboWork on update, so a newer image published under the same tag reaches robots. A running Browser, Desktop or Environment keeps its image until it is started again. If a download fails, the local image stays in use.

Network and accepted limits

Private pasta networks block RoboWork loopback and sibling GUI ports. Only a GUI task's own MCP port is forwarded. Explicit RoboTeam or RoboWork loopback MCP addresses no longer work; non-loopback addresses remain usable. Soul Gateway inference uses the mounted robot-specific socket, with credentials retained in the service.

Workflows do not accept a target robot, but robot-written prompts can indirectly influence another robot. This boundary prevents direct home and credential access. Administrator plain-terminal authority remains. Proxy administration stays in RoboTeam while RoboWork owns leases, relays and firewall resources.

Git credentials

RoboTeam can give a robot a GitHub token with git user name and email. RoboWork keeps the token encrypted under /robots/.credentials, outside the robot directory that launches bind, and never writes it to the home. The confined home helper writes ~/.config/roboteam/git/config with the name, email and a credential helper for https://github.com, and includes that file once from ~/.gitconfig. When git needs a password the helper asks RoboWork over the robot's own socket /workspace/roboteam-soul/git-credentials.sock; RoboWork answers only https github.com requests and logs each use without the token. Anyone with access to the robot can use the credential. The default robot's token is kept only in Ploinky's encrypted workspace git credential file at .data/dpu-data/git-credentials/credentials.json, mounted into RoboWork through /git-credentials, which RoboWork serves to that robot and Ploinky reads so ploinky update and other Ploinky git operations can reach private repositories; RoboWork keeps only its non-secret record, and removal deletes that file first. Deleting the credential or the robot removes the record and closes the socket. DS002 holds the contract.

CSV Mail reuses the default robot GitHub connection over a separate Unix socket. RoboWork forwards Git traffic only to the CSV Mail repository and keeps the token in the service.

OpenCode V2 migration

Deploy V2-compatible ALA together with RoboWork. Startup resolves the current @opencode/cli release, unless the operator explicitly pins a version, then upgrades existing homes under a kernel lock. OpenCode requires version 2 or newer, with no upper major-version limit; ALA checks protocol compatibility. OpenCode 2 supplies @opencode/plugin and effect to its plugins from its own executable and installs nothing into the configuration directory, so RoboWork prepares and copies no plugin dependency tree. The service remains reachable while robot operations return OPENCODE_MIGRATING; each robot is released when its own step ends. Status includes the migration state. Each original home state snapshot and journal lives under server-state/migrations/opencode-v2-1/<robot-id> in RoboWork's service home; a snapshot omits a managed plugin dependency tree and records the exclusion in snapshot.json. Before ordinary cache cleanup the OpenCode 1 executable generation is moved into v1-tool-cache there, with a current.json naming it; no OpenCode 2 generation is copied, nothing under it is removed automatically, and if the move fails every OpenCode generation stays in the cache and the failure is logged at every start. Migration checks session and message IDs, API-visible sessions and stored credentials before enabling a robot; failures block that robot with OPENCODE_MIGRATION_FAILED. A home's step needs the bytes its snapshot copies plus its database and the larger of 1 GiB and that need beyond it, and the tool cache refuses a real installation of a coding agent with less than 5 GiB free where it lives (reusing a usable generation never checks), so only robots that truly need a download wait; a robot that does not fit is paused with OPENCODE_MIGRATION_PAUSED and its journal and home untouched, retried every ten minutes and by a guarded request (at most once a minute), and resumes without a restart.

Restart RoboWork to retry an interrupted or failed migration after fixing its cause. Completed journals are not migrated again and the original snapshot is never replaced; every start only removes a plugin dependency tree that RoboWork or OpenCode 1 left in a home, when its manifest declares exactly the one plugin dependency, its lock lists nothing else, plugin/ and plugins/ hold only RoboWork's soul-gateway.js and no OpenCode configuration document names a plugin, and logs one [opencode-plugin] summary line. A home with other plugins or plugin keys (authored), other dependencies (customized) or a link or shared file in the way (unsafe) is left alone; a customized or unsafe home needs manual review and blocks that robot, while a removal failure for a completed robot is only logged. The snapshot covers OpenCode configuration, data, state, .opencode and home .ala; project transcripts and RoboTeam's registry are retained in place, not copied. For rollback, stop RoboTeam and RoboWork and all robot terminals, save any newer work, restore exactly the snapshot paths listed in snapshot.json (remove newly created migration-state paths that were originally absent), restore the retained OpenCode 1 generation from v1-tool-cache (OpenCode 1 reinstalls its plugin dependency tree itself from the restored manifest and lock), and deploy the matching V1 RoboWork/ALA revision before restarting. Keep the migration backup; rolling back discards V2 conversation changes from the restored native database. The service waits up to ten minutes for the migration lock when another process holds it. The operator scripts scripts/robot-storage-report.mjs (read-only) and scripts/prune-opencode-migration.mjs (an advisory dry run by default; with --apply it holds the lock and must not overlap a RoboWork start or deploy) report sizes and, after every journal is complete, remove snapshot plugin trees (per robot, only where snapshot.json reads as a plain object), snapshots and the retained V1 backup; --normalize-v1-tools only rewrites the backup descriptor. Running the prune script ends rollback.

Checks

Provider-free checks live in tests/. Explicit live probes live in tests/e2e/ and the RoboWork smoke specification. Live acceptance requires command-produced evidence, positive controls, exact source and container identities, and the full selected apparatus suite. Local source checks alone do not establish namespace isolation or sustained eight-run polling fairness.

Coding-agent terminal profiles use ALA’s native launch builder and runner. RoboWork supplies the validated robot home, working directory, workspace masks and tool paths; ALA constructs and starts Bubblewrap while retaining the controlling terminal. Ploinky owns the session menus and WebTTY attachment.

Interactive worker control

Supervised interactive terminals use a separate, narrowly scoped worker-control MCP channel, implemented in `server/worker-control.mjs` and `scripts/worker-mcp.mjs`. The administrator-authorized coding-session API adds `control-create {}`, `control-poll {id, results, profile, validateOnly?}` and `control-close {id}`. Channels belong to the authenticated principal and can be claimed by only one immutable supervisor launch profile through optional `launch.controlId`. The service mounts that channel directory read-only at `/run/robowork-worker` only in the supervisor, including container launches. A stdio MCP adapter uses the private Unix socket; Pi and OMP use the same adapter as a native extension. No user token or service credential enters a robot, and the existing RoboTeam-only internal tools remain unchanged.

The server exposes only `worker_status`, `worker_send {message}` and `worker_interrupt`. The Ploinky Router relay binds these operations to the worker terminal of the selected pair; tools accept no terminal identifier, robot identifier or arbitrary command. Status reports whether the process runs, its last output time, silence duration and a terminal-output tail bounded to 100 lines and 16 KiB, without attach state. The tail is untrusted terminal text, not a structured conversation history. Send writes a bounded message into the interactive terminal and starts the output-silence monitor. Interrupt sends the agent descriptor's native cancellation key and explicitly does not claim that execution stopped.

The supervisor appends assignments and corrections to `tasks.md` as a user-visible history and explicitly calls `worker_send`; file edits never automatically submit prompts. The Ploinky Router monitors new output after delivery and notifies the supervisor after ten minutes of silence. Changes to `results.md` notify the supervisor. Both files are append-only histories, not current task state or a queue. Existing results are baselined on delivery so old reports are not announced as new. No completion marker or other history content changes monitoring state; the supervisor judges progress from its current instructions, worker output and actual code. Silence is a reason to inspect, not evidence of a deadlock. The Router owns the relay and monitor for the lifetime of the supervised terminals; detaching or closing the CLI does not stop them. Registration requires ownership of both terminals in the same folder and provider, and every poll verifies the claimed supervisor profile. A validation-only poll does not dequeue commands. User tokens are not retained or forwarded; the Router signs each provider call with the admitted owner identity and the exact request body, through the current private relay and route policy. Stale routing fails closed until the pair is re-registered. Router shutdown closes WebTTY terminals and drops the corresponding grants; process restoration across restart is not supported. After five seconds without polling the MCP reports it offline; queued calls time out after fifteen seconds and are dispatched at most once. A timed-out mutation can have an unknown outcome and must not be blindly repeated. Channels are ephemeral, revoked on pair removal or supervisor replacement, and must be recreated after a service restart. Existing supervisors must be reopened to acquire their native tool configuration.

RoboWork maintains a persistent per-folder coding-session index under its private server-state/coding-session-index directory. Rows retain the native conversation ID, robot ID and name, coding agent, title and native timestamps. The index coding-session route accepts only {directory} and requires the same verified administrator as the launch routes. Reads return cached rows immediately and indicate an active background update. A first import scans all robot/agent catalogs through the existing confined helper; later reads serve the saved snapshot without starting or upgrading scans. Post-launch jobs update known catalogs. Launches from both CLI and browser persist their source and schedule targeted updates after 2, 30 and 120 seconds to discover identifiers assigned by the native agent. Explicit native history reads also update the index. A single service queue deduplicates folder jobs and bounds helper traffic. Successful reads merge rows by native conversation ID, retaining earlier entries absent from a partial catalog; failures retain its previous rows and expose a source warning. Deleted robots are removed during reconciliation. The index survives service restart, including empty-folder imports. Automatic reconciliation runs every fifteen minutes for previously visited folders and discovers histories created outside the launch flow, including catalogs previously found empty. Reading an old index after restart does not start a scan; service timers own subsequent reconciliation. Failed updates are retried in the background, preserving cached rows; no manual rebuild route or button is exposed. Atomic private-file replacement, directory checks and no-follow file reads protect index storage; no prompts, credentials or terminal logs are indexed.

The coding-session robots response includes the shared coding-agent catalog. Browser creation forms allow selecting robot and coding agent in either order without fetching a separate agent list per robot.

The administrator-only sync-history route accepts the same robot, codingAgent and directory fields as history and reads the complete native catalog through the confined helper before merging it into the index. Browser Kill synchronizes this catalog before and after stopping the selected terminal. Complete index imports bypass recent-menu scan and result limits and include untitled native session records when the agent has persisted enough metadata to resume them. Process exit is never an index deletion.
