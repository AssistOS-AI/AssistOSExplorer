## Introduction

RoboWork is a resident global Ploinky agent on the existing roboteam-agent runtime image. RoboTeam calls its internal synchronous MCP tools.

## Core Content

Every tool requires an AgentServer-verified invocation naming exactly `agent:AchillesIDE/roboTeamAgent`, acting for itself with no delegated user. An `internal` tag alone does not establish this authority. Tools call the resident loopback service with a per-launch capability. Users cannot invoke these tools directly.

RoboTeam declares the waiting dependency `roboWorkAgent global`. Explorer keeps `roboTeamAgent global no-wait` and does not declare RoboWork directly. RoboTeam startup waits for RoboWork readiness. Startup-only retries accept exact typed 503 TARGET_INACTIVE and connection failures, using five delays totaling 5.75 seconds, and stop before RoboFlow initialization. An unavailable RoboWork returns a clear retryable error. Workflow interruption reconciliation waits for the first successful `run_list` answer. Explorer startup ordering and unchanged RoboWork container identity across RoboTeam restart require deployment evidence.

The persistent bind `.data/.private/roboWorkAgent` becomes `/data`. Ploinky masks `.data/.private` from other agents and from RoboWork's workspace view. Homes are `robots/<id>/home`; run metadata, logs and callback sockets are service-owned siblings under `runs/<runId>`. Tool generations, image storage, proxy state and model-catalog cache stay service-owned. Empty terminal stubs under `.data/roboWorkAgent/terminal` carry no secrets. No migration from old robot homes is provided.

Robot processes see their home at `/home/<id>` with matching HOME and USER. Browser and Desktop mount the same folder at `/config` and `/home/<id>`. Their default cwd and Desktop shell cwd are the home. Project turns keep their admitted project cwd. Cwd and folder grants are realpath-checked and refuse `/data`, private storage, its descendants and ancestors. Both kinds also refuse the workspace root, workspace `.data`, `.ploinky-box` with its quarantined `.ploinky-box.*` siblings, and the root `.env`; a folder may lie below `.ploinky/repos/<name>`, the registered repository sources, and nowhere else in `.ploinky`. One check decides every cwd, whether it comes from a run, a Browser or Desktop, or a terminal: it must lie below the workspace root, and the workspace root itself, workspace `.data`, `.ploinky` and `.ploinky-box` are refused. Browser, Desktop and terminals also refuse a cwd inside project `.roboteam`; a run may start there, in the folder RoboTeam prepares for graph generation.

A path check followed by a path mount cannot be safe while a robot can write any part of the path, and nested Podman resolves a volume source in RoboWork's namespace, where every home is visible. RoboWork therefore refuses a grant whose path is not already canonical, records the `dev:ino` of each cwd and folder at grant time, walking the canonical path without following a link, and gives Podman the directory itself: it opens the path again, compares the identity and passes `/proc/<service pid>/fd/<n>` as the volume source, keeping the descriptor open until the container has started or the run has ended. As a backstop, the first process of a Browser or Desktop container compares its mount targets with these identities before anything a robot controls can start: OpenCode loads plugins from the robot-writable home, so a check after launch would lose that race. A mismatch exits 78 and the session ends `CWD_REFUSED`. An Environment starts ALA directly, and ALA makes the same comparison first, from the `--expect-dir` identity of the cwd and of every folder; a mismatch exits 78 before ALA reads its configuration, and the run ends `FOLDER_REFUSED`. A `.roboteam` in the cwd that is a link or not a directory is refused the same way before ALA starts. Native runs and Environments pass the identity to ALA, and a terminal passes it to ALA's sandbox before the shell starts; each opens the directory once, compares it and binds it by descriptor. The robot home, Soul socket, callback channels, tool cache and the workspace keep path mounts: their path components are service-owned and no robot can write them, and the workspace root is refused as a cwd, so every writable mount lies strictly below it. The check relies on a bind mount keeping the `st_dev` and `st_ino` of its source, as Bubblewrap's own descriptor bind does; a storage that broke this would refuse every run rather than expose anything.

In every path a robot sees its home, its cwd, writable, the workspace read-only at its canonical path, and the service mounts. RoboWork adds the workspace itself; a caller cannot grant, widen or remove it, and a folder grant still refuses the root. A folder grant inside the workspace becomes a read-only export over the workspace at its own path. `.data`, `.ploinky`, `.ploinky-box` with its quarantined `.ploinky-box.*` siblings, and the root `.env` are empty read-only masks in every path, and do not depend on Ploinky's masks. Native runs, model discovery and native terminals mask through ALA and Bubblewrap, whose bind makes every submount read-only. Browser, Desktop and Environment containers mask through Podman, whose `ro` covers only the top mount, so RoboWork also rebinds each writable submount of the root read-only, reading `/proc/self/mountinfo` for it, and mounts the working folder after the root. A masked directory is an empty tmpfs that cannot copy up what it covers; a masked file reads as nothing or is refused with `EACCES`, and no write to it persists: it is refused, or goes to `/dev/null` itself, which Podman's bind of the device may accept. An entry absent at start has no mask, because a robot cannot create one in a read-only root; one an administrator creates later stays visible to a session until its next start. A link among the masked entries is followed when it leads inside the root and shows nothing when it dangles or leaves the root; a link to the root or above, or an entry that is neither a file nor a directory, refuses the start with `WORKSPACE_UNAVAILABLE`, as does a root at `/workspace`, one that overlaps the robot's home, or an unreadable mount table, and nothing launches. A task that spans several projects uses a common parent folder below the root as its cwd. Opening a robot terminal at the workspace root is refused with a message and the terminal ends.

There is no read isolation between project folders: a robot can read every other project, including its `.roboteam`, nested `.env` and `.git/config`, and other robots' working files. Write isolation and home isolation remain: a robot writes only its cwd and home and cannot reach another robot's home. Robots that share a folder, or where one works in a parent of the other's folder, must trust each other, and no code tries to prevent that. This is a stated exception to home isolation. A robot runs what sits in its working folder: a plugin, script, hook or skill that another robot planted there runs with the home of the robot that runs it open, credentials included. Coding agents also load configuration, plugins and instructions from ancestors of their cwd, so what a robot writes in a parent folder runs in a child's sandbox. Sibling folders are not ancestors and are not loaded. Robots that must not trust each other therefore work in folders where neither lies inside the other.

ALA runs under a private pasta network with gateway mapping disabled and a mount namespace where `/data` includes only the current robot, current run and read-only tool cache. The coding agent retains one Bubblewrap sandbox with private procfs and dropped capabilities. Service helpers use a separate confined helper with only the selected home and no network. Project `.roboteam` holds the records RoboTeam reads back and acts on, such as a conversation's working folder and the task records it continues, and the session skills directory. A robot must not rewrite them, so it is an empty read-only mask in every path: runs, terminals, model discovery, Browser and Desktop. Robots that share a folder see each other's conversations in RoboTeam, so privacy between them is not the reason. RoboTeam also takes a conversation's or a task's folder from where its record sits and refuses a saved path that differs, so a record a robot rewrote cannot move a run to another folder. ALA runs outside its sandbox and keeps writing `ALA_SESSIONS` below the real `.roboteam`; only the coding agent's view is masked. An Environment container leaves it visible to ALA for the same reason and masks it inside Bubblewrap. Browser and Desktop mount it with `notmpcopyup`, because a tmpfs otherwise copies the contents of the path it covers. Terminals and model discovery create the directory when it is missing, because a mask needs an existing target and a robot must not be able to create it first. Only the cwd's own `.roboteam` is masked: one below a cwd used as a common parent or inside a read-only granted folder stays visible, and the `.roboteam` of every other project, like the root `.roboteam` seen from a project, is visible read-only through the workspace. Skill sources use read-only aliases. Callback channels expose only the current run. No Ploinky environment copy or SDK credential enters robot code. The Soul Gateway socket lives outside the writable home and is mounted at `/workspace/roboteam-soul`.

Only the run's own GUI MCP port is forwarded. Explicit MCP URLs on RoboTeam or RoboWork loopback, including `http://127.0.0.1:7000/mcp`, are unreachable; non-loopback services remain usable over the private network. A robot terminal and its task have different localhost networks. Browser session HTTP and WebSocket traffic uses the authenticated route `/base-agent-additional-server/roboWorkAgent/3001/api/robots/<id>/session/`. Box bindings are `17100:7000` and `13101:3001`; the routed container port stays 3001.

`run_start` validates and persists a run, then immediately returns `starting`. The resident service prepares tools, static Bubblewrap, the selected image and native launch in the background. `run_read` carries preparation progress and terminal failure. Inputs received before native launch are ordered and bounded. Stopping a starting run cancels its preparation and owned pull or builder, prevents late launch, and discards queued input; cancelling one consumer does not stop a shared build that another consumer or startup warmup still needs. Static Bubblewrap warms after the service listens, without holding readiness. `gui_ensure` also returns `starting`; `robot_status` reports readiness or failure and RoboTeam polls to preserve its existing wait behavior. A selected-agent terminal returns a clear preparing/retry answer while its runtime and image are prepared, within the modal timeout. `run_start` is idempotent on run ID. `run_read` returns sequence-numbered stdout/stderr and unanswered callbacks, holds at most 100 ms and caps each response at 1 MiB. Clients poll at 100 to 250 ms while active and back off to about two seconds while idle. Sustained fairness requires the live eight-run acceptance check. A 64 MiB run log stops the run with an error. At service startup, ended unreleased runs older than seven days are removed; no periodic retention sweep is implied.

RoboTeam restart leaves RoboWork runs and GUI containers alive. Reattachment uses authoritative `run_list`, matches robot/session/turn identity and replays output from sequence zero with replayed progress marked. Robot-writable project records never authorize a run. RoboWork restart marks live runs interrupted; Resume continues through RoboTeam. An asynchronous RoboTeam MCP queue caller can fail across restart even while its resident run continues. Replayed phase progress is not duplicated; the final unwritten phase-log tail may be absent.

An Environment is a new short-lived container from an enabled global agent's declared image, never the live target. It inherits neither target credentials nor programs installed after target startup nor target localhost. Node is required for ALA. Discovery excludes RoboTeam, RoboWork and private-data agents; persistentStorage alone is not private. Listing checks image presence and cached failures without pulling all images. Only a chosen step prepares its image, without a fixed 120-second cap. A cached pull failure stays visible and an explicit selection retries it.

Administrator robot terminals use RoboWork's profile source and only its verified writable discovery row. The second-prompt launcher enters the sandbox after Ploinky identity capture and exits the terminal when the sandbox exits. Plain terminals in every agent retain their ordinary behavior. An administrator can access all homes through a plain RoboWork terminal. A robot can indirectly influence another robot through workflow prompts; workflows do not accept a target robot. These accepted limits do not grant direct sibling-home or credential access.

The inner robot-terminal launcher checks its inherited TTY without consuming input and exits when that TTY hangs up. Its private PID namespace then ends, including foreground and detached children that ignore hangup and termination signals. Live-terminal input, job control and resize remain with the interactive shell.

Proxy assignments and release retain RoboTeam's administrator HTTP routes. RoboWork owns leases, relays and firewall setup. Releasing an active GUI robot is refused; orphan assignments are released. The tools add no robot credentials, ports or mounts.
