# Live acceptance probes

Run these commands inside the selected robot's actual sandbox on the exact apparatus candidate. Use dedicated robots A and B. An administrator creates `marker-B` in B's home and records its tree hash and modes before testing. Keep operator controls and artifacts outside robot-writable projects. Never substitute a model's refusal for command output.

`isolation.mjs --probe <name> --robot <A> --victim <B> --workspace <absolute-root>` emits `ROBOWORK_COMMAND_PROBE_V1` only after every selected assertion succeeds. Missing prerequisites and unsupported controller-only scenarios exit non-zero. Transport the exact checked script through an admitted read-only skill folder; a model must execute the command and return its produced sentinel. Provider-free tests use synthetic inputs and do not establish live isolation.

`persistence.mjs --robot <A> --marker /home/<A>/<owned-marker> --sha256 <expected> --stage <stage>` checks exact bytes, rejects symlinks and emits a command receipt. The operator invokes it at `initial`, `restart`, `recreate` and `box-recreate`, pairing each receipt with actual lifecycle command and container-generation evidence. The script itself performs no restart and does not prove one occurred.

`opencode-plugin-free.mjs --binary <opencode> [--offline] [--keep]` shows that OpenCode 2 starts in a home with no plugin dependency tree, loads a plugin that imports the modules its host provides, and creates no tree of its own. It needs only Node and the executable, so copy the single file into the RoboWork container's `/tmp` and run it there against the deployed cache binary, with network and then offline: `node /tmp/opencode-plugin-free.mjs --binary /root/tool-cache/shell-selections/shell/bin/opencode`, and the same with `--offline`. The networked run is the one that discriminates, because offline a failed install would also leave nothing behind. Run it on the apparatus host and on an x64 host before a candidate that stops seeding plugin trees is deployed there, since the cache binary differs by architecture. It creates a new scratch home with its own XDG directories, writes only a recorder plugin under `.config/opencode/plugins` (an OpenCode 2 default export whose `setup` imports `@opencode/plugin` and `effect`, calls the `Provider` and `Model` constructors that `server/plugins/soul-gateway.js` uses and writes a record), starts `opencode serve` on a free loopback port there and waits for `/api/info` and the legacy-history migration. It then requires `/api/model` to answer (an empty list counts, because the scratch home has no provider), polls `/api/plugin` every 250 ms, because OpenCode loads plugins in the background and answers an empty list at first, until it lists the recorder as `active` (`--plugin-wait-ms`, default 30000; a `failed` plugin at any poll fails at once), and requires the record to exist with every export usable. After it stops the server it fails if `node_modules`, `package.json`, `package-lock.json`, `bun.lock` or `bun.lockb` exists under `.config/opencode`, or if `.cache/opencode/npm` holds any entry. It removes the scratch home on every exit; `--keep` leaves it and prints its path. `--timeout-ms` (default 120000) bounds server readiness and `--record-wait-ms` (default 15000) bounds the wait for the record. `--offline` runs the whole probe in a new network namespace. It tries `unshare -rn` first and `bwrap --dev-bind / / --unshare-net` second, and runs the script's own check (`--netns-selfcheck`) inside each: loopback up, no non-loopback interface, and a connect to a documentation address refused for lack of a route. A bare `unshare` namespace has its loopback down and the probe raises it with `ip` or `ifconfig`, so a container without those tools (the RoboWork container has `unshare` and `bwrap` but neither) falls through to `bwrap`, which raises loopback itself. The first wrapper that passes runs the probe; when none passes the probe fails and never falls back to a run with network. On Explorer QA the offline run passed through the `bwrap` path, because `unshare` could not raise loopback there. The selection logic is covered by `probes.test.mjs`, the namespaces themselves only by a live run. On success it prints one line `ROBOWORK_OPENCODE_PLUGIN_FREE_V1 <json>` (OpenCode version from `--version`, plugin count, recorder evidence, offline flag, elapsed milliseconds) and exits 0. A failure prints its reason, and for a plugin failure the server output tail, to stderr and prints no sentinel. The sentinel proves that this OpenCode build, with this scratch home and this network condition, supplies `@opencode/plugin` and `effect` to a local plugin and writes no plugin tree. It does not prove that robot homes can have their trees removed, that third-party packages hoisted into an existing tree are unused, that a model turn works, or the behavior of any other OpenCode version or architecture. `probes.test.mjs` runs the probe against stub executables: a correct stub must print the sentinel, and a stub that creates `.config/opencode/node_modules`, one that reports the recorder `failed`, one that never runs the recorder, one with an unusable host export, one that writes `bun.lock` and one that fills the package cache must each fail with no sentinel. Those tests cover the probe's logic only; the stub's `/api/plugin` shape follows OpenCode 2.4.2's `Plugin.Info` schema as read from its binary, and only a run against the real binary shows the real server agrees.

`controller-scenarios.mjs --config <private-json> --scenario W1 [--baseline]` creates a new owned robot and owned folders and runs a fresh model discovery and a real OpenCode turn with the free model. A canary plugin in a sibling folder's `.opencode/plugin` must stay silent, and so must the same canary in the working folder's parent, whose `.opencode` lacks the `.gitignore` OpenCode would need to write; the same canary in the working folder must write its marker, which proves the canary runs. A recorder plugin in the robot's own home must have run, in the discovery and in the turn, must have listed an empty workspace `.data`, and must have imported `@opencode/plugin` and `effect` and found their exports usable. A recorder that never ran, or one that could not use the host modules, fails the scenario. After the discovery and again after the turn, the new robot's `.config/opencode` must hold no `node_modules`, `package.json`, `package-lock.json`, `bun.lock` or `bun.lockb`. The canaries and the recorder are OpenCode 2 default-export plugins (`export default { id, setup }` with a distinct `id` each; OpenCode 2.4.2 reports a named-export plugin as failed, and a failed plugin makes model discovery refuse the catalog), the shape the live probe above proved. Before this change the scenario planted OpenCode 1 named-export plugins. The base revision still seeds a plugin tree, so the absence assertions cannot pass there: run `--baseline` (W1 only) on the base revision first. It skips only those two absence assertions, still requires the canaries, the recorder and the usable host modules, and prints `baseline: true` with the list of what it skipped, so that run is never mistaken for a candidate run. Then run W1 without the option on the candidate.

Controller orchestration is required for planted-home symlink helper calls, other-agent masks and Explorer API, enabled-manifest agentExec inventory, refused grants, deletion, capability callbacks, home mount inode identity, image selection, real TTY controls, proxy/network effects and restart continuity. These checks must retain the approved Acceptance IDs, negative controls and exact prerequisites; none is represented by a skipped sandbox probe.

`controller-scenarios.mjs --config <private-json> --scenario I10` retains eighteen exact cwd/folder refusals, among them the workspace-private `.data/roboTeamAgent` and `.ploinky-box`, which the scenario first proves to exist from the RoboWork service, and checks an actual read through the planted public-workspace link in a newly provisioned robot's default terminal. It uses the normal RoboWork profile preparation, the unique writable RoboWork discovery row and the canonical WebTTY client. Install the existing smoke dependencies and Chromium using `tests/smoke/`'s documented setup before running; the helper loads `@playwright/test` only for I10. The private `explorer.storageState` must authenticate the same direct administrator as the controller. Config accepts identities and private state paths, with no command or result overrides.

I10 joins the actual 201 launch, profile and immutable RoboWork generation to a private recovery receipt and a held native command with exact nonce/argv, HOME, cwd, TTY, PID/start and private namespace evidence. A privileged read of the same link must resolve B's marker; the native read must produce a filesystem denial without printing B's bytes. The controller releases the command only after its process identity is observed, requires the captured exit status to be zero and the terminal to close normally, then checks exact receipt/process/ExecID/session absence and the unchanged empty terminal stub. B's tree hash and modes must remain unchanged. Missing native prerequisites or unproven cleanup fail without a success sentinel. A failed terminal gets a normal exit attempt through its exact owned 201 session; unproven cleanup retains the owned robot/project identities for recovery and never forces WebTTY DELETE or erases a recovery record. Provider-free tests exercise synthetic identities and real temporary file reads; Linux terminal isolation remains a separate apparatus gate.
