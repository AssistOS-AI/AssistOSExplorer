LiveKit Server terminology

LiveKit Server

LiveKit Server carries live WebMeet meeting media and supplies the signaling and room-control API. The AchillesIDE/liveKitServerAgent supervisor starts it from a pinned image after Ploinky verifies the mounted topology. It advertises the topology-selected IPv4 and owns the Box's single UDP 7882 mux. Public signaling and authenticated private administration pass through Ploinky Router; local deployment without a media stanza is bounded to a reachable host or LAN and cannot satisfy cross-network release evidence.

Egress

Egress is the LiveKit process that records meeting media for authorized room workflows. The supervisor runs Egress and PulseAudio as the image's unprivileged egress user, with a private temporary configuration and the recordings mount. Its template listener and semantic health listener are distinct loopback services; health must prove the expected process and socket ownership. Recordings persist under .data/liveKitServerAgent/recordings/. Release evidence requires connected publisher media, EGRESS_COMPLETE, and a non-empty output file; open listeners alone do not prove recording.

Topology

Topology is the immutable Ploinky runtime descriptor that identifies the current publication generation and permitted media address. Configuration generation reads the mounted snapshot only after Router authority attestation. A media stanza requires a canonical globally routable IPv4, UDP 7882, and an accepted address mode; local environment overrides cannot replace it. When topology explicitly omits media, the generator selects bounded local deployment using the configured host address or a usable interface. Pre-attestation hooks receive no Router locator or topology environment.

TURN

TURN is an external relay service that helps meeting participants connect when a direct media path is unavailable. Ploinky describes the relay through non-secret topology and brokers short-lived credentials to exact authorized consumers. liveKitServerAgent neither starts a relay daemon nor receives its long-term secret. The relay UDP and TLS fallback lanes are separate release checks, alongside the native architecture and cross-network direct-UDP lanes; a successful local meeting does not replace them.
