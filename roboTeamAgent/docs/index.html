RoboTeam Documentation

Product vision

A robot is a durable virtual employee with a visible workstation. Its desktop or browser can be replaced without losing its home, account configuration, or work files.

RoboTeam gives each workspace a shared catalog of named robots. An administrator creates the records, and workspace agents can assign work to them. A graphical task runs in a disposable Desktop or Browser container. The same Selkies session shows both automated actions and the final state, so a person can watch the work and open the workstation afterward.

Robot identity and state survive container replacement. RoboTeam keeps the robot home, selected working directory, downloads, logs, and coding-agent configuration outside the graphical container. Runtime tools are installed into a shared versioned cache on first use instead of being copied into each robot.

System boundary

RoboTeam is one globally enabled Ploinky agent. It owns robot records, container lifecycle, MCP bridges, the authenticated Selkies proxy, and task status. A robot is not another Ploinky agent. It is a workspace-scoped record with persistent directories and, when needed, one active Desktop or Browser container.

Advanced Language Agent, abbreviated ALA, is RoboTeam's LLM execution layer. RoboTeam starts ALA as a separate process for each task. ALA reads the prompt and selects the requested coding-agent backend. ALA currently supports Codex, OpenCode, and Pi. The selected executable must be available, and its authentication and configuration must exist in the robot directory passed through --home. RoboTeam prepares Codex automatically; OpenCode and Pi require their CLI executables to be provisioned in the outer runtime. RoboTeam's current Desktop and Browser MCP injection is implemented for Codex, so GUI automation tasks must use Codex for now.

Execution modes

ModeRuntime and use
desktopLinuxServer Webtop, Selkies, and computer-use-linux. ALA controls the same full desktop that the user watches.
browserLinuxServer Chromium, Selkies, and Playwright MCP. ALA controls the visible Chromium session through CDP.
simpleALA runs against the selected working directory without starting a graphical container.

Each start is a native asynchronous Ploinky task. One ALA process runs per robot, while later Desktop, Browser, and Simple tasks wait in that robot's FIFO queue. ALA messages appear in the Ploinky task log, and ALA process exit sets the final task state. A completed GUI task leaves one container running so the final state remains available. The matching session-URL tool returns its live Selkies link.

AchillesCLI integration

AchillesCLI includes two built-in C-Skills for RoboTeam. list-robots calls RoboTeam's internal robot_list MCP tool and prints the workspace robot catalog. launch-robot calls startDesktopTaskForRobot or startBrowserTaskForRobot, attaches the native task to AchillesCLI's background-task observer, passes the active AchillesCLI directory as cwd, waits for the GUI and MCP bridge, and returns the live Selkies link. The observer continues to publish intermediate messages and the terminal result after the launcher returns.

/exec list-robots
/exec launch-robot desktop analyst: inspect the application and report any UI problems
/exec launch-robot browser researcher: open the site and verify the login flow
