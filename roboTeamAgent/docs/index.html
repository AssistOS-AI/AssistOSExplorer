RoboTeam Documentation

New robots enable only OpenCode. Administrators can select Codex, OpenCode, Pi or Claude Code instead, using the same setting for conversations, delegated tasks and manual workstation tools. See coding-agent configuration.

Product vision

A robot is a durable virtual employee with a visible workstation. Its desktop or browser can be replaced without losing its home, account configuration, or work files.

RoboTeam gives each workspace a shared catalog of named robots. Administrators create and delete ordinary records, and workspace agents assign work to them. At startup, RoboTeam creates the ordinary robot named exactly default only if it is missing; an existing one keeps its identity and home. A graphical task runs in a disposable Desktop or Browser container. The same Selkies session shows both automated actions and the final state, so a person can watch the work and open the workstation afterward.

Robot identity and state survive container replacement. RoboTeam keeps the robot home, selected working directory, downloads, logs, and coding-agent configuration outside the graphical container. At service startup, runtime tools are prepared in a shared versioned cache in the background. Robots reuse the prepared tools; an immediate request waits for any preparation it needs.

The Explorer RoboTeam button opens a waiting page while the agent starts, then opens the dashboard automatically once its HTTP service, MCP and Router routes are ready. Startup failures remain visible with a retry control.

System boundary

Workflow cards are clickable View/Edit links without a separate action bar. Hover gently highlights the card and its title, with the tooltip View workflow. Mouse navigation and return-focus restoration do not leave selection outlines; keyboard navigation keeps a visible focus indicator.

In Robots, the total beside the heading is muted text, without a badge background or border. The compact + Create robot button opens a small name dialog; Cancel, Escape and the backdrop dismiss it without discarding a draft. A pending creation cannot be submitted twice or dismissed, and errors stay inside the dialog. Robot cards show a subtle status below the avatar, the ID beside the name and coding-agent/mode metadata beneath. Logs is an underlined, link-styled toggle in that metadata area, without a background or border, not in the action bar. Open and an active workstation's Stop control remain visible. Manage skills and Coding agent are grouped under More actions. Administrator-only Delete robot remains separated at the bottom of that menu and retains its confirmation. The Logs toggle uses the accent text color when hovered or expanded and opens logs below the card; closing the panel restores focus to that toggle. Other robot operation errors remain visible in the tab.

The dashboard, including when opened in the Explorer modal, has three tabs. Robots contains creation and all robot controls. Workflow types contains workflow creation, management and Flows history. Kron jobs is reserved for future functionality and currently has no scheduling controls. Robots opens by default; switching tabs preserves the existing forms and lists. The tabs support keyboard arrows, Home and End.

Workflow types matches the Robots tab's unboxed heading, plain total, compact + Create control and card layout. Each workflow card shows initials with Built-in/Custom beneath, name and ID together, then its full description, task/connection counts and any coverage warning. Click the card to open View/Edit; a small More actions control at the corner of custom cards retains administrator-only deletion, with the existing confirmation and preservation of run history. That control is separate from the card link and never opens the workflow editor. Flows history is a secondary text link. Creation and editing still open their existing dedicated pages.

Workflow pages provide Back to Workflow types even inside the Explorer modal, outside its hidden embedded header. The editor's Close works for read-only workflows too. Opening View/Edit, Create workflow or Flows history preserves the source tab, list scroll, invoking link and robot-name draft. Close, Save or the return link restores that source, including through generation and editing; browser Back restores it as well. Direct page entry falls back to Workflow types without changing the default tab for fresh dashboard visits.

RoboTeam is one globally enabled Ploinky agent. It owns robot records, container lifecycle, MCP bridges, the authenticated Selkies proxy, and task status. A robot is not another Ploinky agent. It is a workspace-scoped record with persistent directories and, when needed, one active Desktop or Browser container.

Advanced Language Agent, abbreviated ALA, is RoboTeam's LLM execution layer. RoboTeam starts ALA as a separate process for each task. ALA reads the prompt and selects Codex, OpenCode, Pi, or Claude Code. RoboTeam prepares the current CLI packages in its shared cache and puts the selected executable on ALA's PATH. Authentication and configuration remain in the robot directory passed through --home. A Desktop exposes the selected commands for robot-specific setup. An administrator logs Claude Code in by running claude in the robot's Terminal, and RoboTeam never sees those credentials. RoboTeam's Desktop and Browser MCP injection is implemented for Codex, OpenCode and Claude Code, so GUI automation tasks resolve to one of those backends; Pi runs only Simple tasks.

Robot conversations and the default copilot

Opening or refreshing a robot chat prepares its coding-agent tools without printing routine cache messages into the conversation. Preparation failures are still reported.

Explorer's Open Copilot here opens roboTeamAgent with robot=default and the selected cwd. Every robot card has Open → Copilot, which opens achilles-cli/ below the Ploinky workspace. The copilot creates that folder if missing and reuses it otherwise. The former AchillesCLI wrapper now lives in copilot/ inside RoboTeam; there is no separate AchillesCLI agent or image. The wrapper creates .roboteam/ inside the selected folder for conversations and task history; its .gitignore excludes everything in it from the project's repository. ALA writes the conversation text there, under .roboteam/.ala/sessions/. Each folder has its own session list. Conversations and task records belong to that folder rather than to a robot, so deleting a robot leaves them intact.

A robot owns its home and configured accounts. A conversation owns its cwd, ALA session, transcript and selected skill catalog. Each message executes another turn in that conversation. Independent CLI conversations and Simple tasks run concurrently, including while a GUI task runs. Desktop and Browser still share one container and one graphical task queue.

Use /session, /session new, /session resume <id>, /tasks, /model and /permissions. Codex, OpenCode and Claude Code support native approvals; Pi rejects ask-for-approval. The bundled copilot repository is available only to default; its direct chat initially selects only the copilot skillset. Every robot opened in WebChat also receives the required, read-only list-workflows and launch-workflow skills. RoboTeam does not scan the workspace for skills. Manage repositories in RoboTeam and conversation skill selection on RoboTeam's Conversation skills page (WebChat menu). Each external continuation captures current configured source files. Use /list robots to list workspace robots; the CLI does not administer repositories or skills.

Execution modes

Delegated tasks have their own WebChat cards, logs, and final results, attached to the originating conversation. The launcher's short confirmation and live URL may appear in the parent's activity; the child execution log stays in its task card. A chat-publication failure is reported diagnostically and does not stop task polling or restart the remote task.

Use each robot’s Manage skills dialog to add Anthropic repositories and inspect optional named combinations in skillsets.md. The default robot selects from descriptions; RoboTeam saves a conversation policy and captures current selected files at each execution boundary. See Skills & Skillsets for the format, examples and execution diagram.

Each start is a native asynchronous Ploinky task. Independent CLI conversations run concurrently per robot. Desktop and Browser share one graphical ALA slot and FIFO queue. ALA messages appear in the Ploinky task log, and ALA process exit sets the final task state. Stopping a live GUI task from its WebChat task card leaves the container active and pauses that robot's queue for manual work. Resume uses the task's opaque continuation handle, continues the saved native conversation with a fresh-screen instruction, and then releases the queue. A completed GUI task also leaves one container running so the final state remains available. The matching session-URL tool returns its live Selkies link. The RoboTeam dashboard keeps that link on the robot card while the session is ready, so closing the workstation window does not lose the entry point.

RoboFlow team workflows

In the task editor, Add skill or skillset opens a repository picker. Expanding a repository reveals its entries and extends the list, which scrolls inside the popup while the search field and footer stay visible.

RoboFlow workflows are global directed graphs of tasks. The editor keeps the task list at left and opens General or Graph in the right pane; selecting a task opens its details, and + immediately adds a new task named New Task at the top of the list with the terminal execution type. Generation is a separate first step that creates a draft, then opens the editor on the graph. Drag a centered left or right node port to another node's port to create a directed edge. Use Start node in the task editor to choose the highlighted entry point; select an edge on Graph and press Delete or Backspace to remove it. Save persists the graph and layout. The server warns when no robot covers a task's skillsets; warnings do not block saving or starting. RoboFlow randomly selects an available matching robot for each visit. Desktop and browser tasks share each robot's GUI queue. Branching tasks return an outgoing edge; zero or one outgoing edge needs no routing prompt. The protected Standard development workflow (id default) has one node, uses the default robot and requires a caller-selected execution mode. SQLite stores global definitions and run snapshots; logs and final responses stay in the working folder. See DS007.

A task that allows sub-flows can delegate to sequential sub-flows. The shared Run workflows node waits for their completion and follows the creator-selected edge. Inspect children in the phase’s Sub-flows tab and use parent Pause or Resume to control the group. See Robots & Runs for state and continuation rules.

AchillesCLI integration

AchillesCLI's front copilot automatically mounts the builtin bash and launch-gpt-researcher skills. In WebChat it also receives list-workflows and launch-workflow, both with directly executable scripts. Its turn context carries no workflow catalog. It runs list-workflows to get the current workflow ids, then launch-workflow calls roboflow_start_flow through the CLI-owned authenticated runtime channel. The parent attaches the native task to its background observer and returns immediately; the task carries the link to the flow page at /flows?flowId=<runId>, which shows the graph, the phases and their live logs. The copilot cannot launch individual robots or control a flow after starting it.

/exec launch-workflow {"action":"start","workflowTypeId":"default","executionType":"browser","objective":"Inspect the application and report UI problems"}

Human input

Enable Allows human input in an ordinary task to let its robot request a business decision missing from the prompt and context. The internal require-human-input skill submits a question with three suggestions, then the robot ends execution and the workflow stays paused. In Explorer Observability → Requires human input, select the workflow and choose a suggestion or Other answer, then Send answer. RoboFlow continues the same task and native session with the answer before resuming graph traversal. The tab also includes other paused and failed flows. Pending questions survive a service restart.
