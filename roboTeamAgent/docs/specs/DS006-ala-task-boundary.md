## Introduction

ALA is the task executor started by RoboTeam; it is not responsible for creating desktop or browser containers.

## Core Content

The AchillesCLI wrapper owns project persistence. Opening a folder creates its `.achilles-cli/` directory. `sessions/` contains conversations, and `tasks/` contains one directory per task. Each `tasks/<task-id>/` holds `task.json` with the request and its robot, `logs/` with the observed output and cursor, and `executions/` with one record per attempt or continuation. Settings, REPL history and mutation/execution leases use the same project root. CLI and WebChat commands share this storage. The root cannot be replaced by a symlink or redirected by a robot environment variable.

RoboTeam stores only project-location references in its shared `projects/` registry to find saved conversations and execution records after restart. Records themselves stay in the project and are never read from robot-scoped or workspace-wide locations. Missing records and duplicate copied identifiers fail explicitly. A saved execution must match its robot ID; a recreated robot with the same name cannot inherit it. Native session bindings record the robot ID and reject continuation through another robot.

PLOINKY_WORKSPACE_ROOT is mandatory at RoboTeam startup and CLI entry. It must identify an accessible absolute directory. Missing, empty, relative or unavailable values must fail explicitly; neither cwd nor `/workspace` is a fallback. The validated root must survive native environment filtering as an explicit engine configuration value and determine the read-only parent mount.

Manual terminal and workstation preparation must use the robot’s scoped defaults policy reference. Robot record IDs are not skill policy IDs. Preparation must retain saved selection and policy version; conversational execution continues to use its own conversation policy.

Copilot WebChat and CLI conversations must default to full-access inside the ALA sandbox when no valid workspace permission selection exists. Explicit execution overrides and saved workspace selections remain authoritative, including ask-for-approval. Reading the default must not write settings or require per-folder setup. The engine fallback must also use full-access. This native execution policy does not change Router authorization or Bubblewrap filesystem isolation.

WebChat task records preserve the executing `robotName` through observation, persistence and protocol publication. Runtime-state envelopes report the current robot for the chat header, including default launches without a robot query parameter. Inline task cards show identity, status and duration with always-visible detail/live-session links and no collapse control; logs and continuation remain on the task details page.

RoboTeam must not initialize knowledge-unit storage, retrieve memory into prompts, persist provider results as memory or return cached provider responses. Every conversation turn executes through the native ALA session. Persisted UI messages and task receipts remain presentation and lifecycle records, not a prompt-memory system.

RoboTeam sends the current request and caller-supplied system instructions to ALA by prepending those instructions to the user prompt; ALA has no separate system-instruction option. Normal conversations supply workflow selection instructions and the current workflow catalog. Generation supplies graph authoring instructions. Branching tasks supply routing instructions with the full graph and current node; tasks with zero or one outgoing edge receive no routing system prompt. No role is inferred from the robot name. Only the default workflow accepts a caller-selected execution mode. Native Codex, OpenCode or Pi continuation owns conversation context; missing bound continuation fails without replaying UI transcripts. Each workflow visit has its own conversation and task id and receives only prior final responses plus graph context.

A skill repository contains self-contained Anthropic skills and may define root `skillsets.md`. The skillsetMDParser reads each level-one heading as a unique skillset name and requires level-two Description and Skills sections containing non-empty prose and a non-empty hyphen bullet list of exact SKILL.md names from that repository. Descriptions may span multiple lines; subsection labels are case-insensitive. Repeated sections, unknown headings and unknown members must fail import. Names may contain spaces and have at most 100 characters. Descriptions are limited to 4000 characters, files to 100 sets and sets to 100 listed members. There is no version field or JSON wrapper. Missing or empty skillsets.md publishes no implicit whole-repository set. Overlapping sets form a deduplicated union; different selected skills with the same native name must fail.

Administrators add and remove repositories through each robot's Manage skills dialog. It displays an expandable row per repository with individual skill names only, and skillset names, descriptions and members. Individual skill descriptions remain available in discovery metadata but are not displayed in this dialog. Addition accepts an HTTPS Git URL or a recommended source from the authenticated Ploinky marketplace. Recommendations must include Git repositories directly in the workspace with a nonempty skills/ folder and valid named, described SKILL.md descriptors when present, including repositories without remotes. Subdirectories missing SKILL.md must produce visible recommendation warnings without excluding the repository; those subdirectories are not selectable skills. Skill recommendations prefer a workspace Git checkout, then `.ploinky/repos`, then the registered URL. Local recommendations retain their canonical source for live resolution. Remote registrations and managed .ploinky/repos registrations must prefer the same-name workspace checkout on registration and subsequent live resolution without pulling or changing branches. Skill links expose current source bytes, including edits during execution. Recommendations already registered on the current robot display a disabled Added button. Match the preferred source or registered Git URL, ignoring trailing slashes and the URL .git suffix. Manual submission of that recommended URL also refuses duplicates. Removing the registration enables the recommendation again. Removal targets the stored repository ID. The UI sends DELETE with the repository ID in the name query parameter and no request body. Registration validates the repository and saves metadata without copying its skills. Ploinky owns the shared checkout and updates. Legacy imported repositories without stored definitions expose their individual skills but no inferred skillsets.

RoboTeam assigns internal repository and skillset IDs; descriptions are the selection authority presented to the model. Backward-compatible explicit repository names remain accepted, but registration atomically rejects duplicate names, canonical local sources and collisions between repository names and generated skillset IDs. Ambiguous bare selectors in an existing registry fail on policy creation and live continuation; qualified individual skills remain selectable. robot_list aggregates the declared skillsets for each robot. The front conversation receives the current workflow catalog with graph tasks and the default workflow supported modes. Workflow tasks resolve canonical repository-source/skillset identities to robot-local selectors through skillSets; IDs are selectors, not task descriptions. The built-in copilot collection declares its groups using the same file format.

New tasks resolve their conversation selection through RoboTeam. Before execution, RoboTeam calls the shared Ploinky repository client to install selected live symlinks under the working directory `.agents/skills` and prepare `.claude -> .agents`. Install is additive. RoboTeam records links it installs and explicitly removes only unchanged owned links on deselection or source replacement. Existing ordinary files and conflicting links must remain intact and produce an error. Local skills already at the selected path need no additional link.

The robot command catalog must accept an optional conversation `sessionId` and discover model completions through ALA using that robot's home and selected conversation. A missing session id must use a non-persisted preview, not another saved conversation. Model discovery must not bind a backend or create conversation state. Discovery errors must be returned explicitly. WebChat must refresh the catalog when the selected conversation or backend changes and must not let an earlier request replace a later conversation's catalog.

Graphical launch scripts must publish their ready session as structured `liveSession` metadata with `mode` and a bounded same-router `url` through the existing task receipt channel. The parent must verify the task through the authenticated MCP client before persisting or publishing its presentation. Duplicate or reordered receipts must not reset task lifecycle or create duplicate observers. Task polling and snapshot reads must preserve the metadata. The stdout result supplied to the coding agent must include startup confirmation, task id and the exact live-session Markdown link. WebChat owns the fixed English live-session button labels and validates the URL independently; no optional agent identity may be hardcoded in Ploinky for this feature.

Only the default robot registers the bundled copilot catalog; other robots cannot select that built-in source. The bundled copilot catalog must contain bash, launch-gpt-researcher and launch-workflow. RoboFlow routing uses structured final responses and caller-supplied system prompts; it needs no injected decision MCP tools. Codex, OpenCode and Pi are ALA backends, not standalone Ploinky workers. Provider names in ordinary prompts must not force selection of removed launcher skills. Installed skill files remain live. A later external turn or continuation resolves the current conversation policy again.

Copilot startup must suppress routine tool-cache diagnostics on its conversation output channels. Cache preparation, reuse, and fallback behavior remain unchanged; preparation failures must still propagate as errors rather than being hidden.

Every new task validates its requested `skillSets`, `skillset` alias, and qualified `skills`, then stores a reference to one authoritative conversation policy before enqueueing. MCP values are comma-separated strings; HTTP also accepts arrays. Named skillset IDs, explicit whole sources and individual source-qualified skills form a union. Named combinations select only their declared members, bound to the owning repository generation. Direct chat omission selects `launch-workflow` for the front copilot (robot `default`) and no skills for other robots, unless scoped defaults were saved. Delegated task omission selects no skills, including for default. Explicit empty arrays and `use none` stay empty. Administrator imports remain optional; both local and HTTPS registrations resolve the current Ploinky checkout.

`workspace` skill sources are not scanned. RoboTeam resolves task skills only from the bundled catalog and from repositories registered on the robot whose sources resolve through the authenticated Ploinky marketplace endpoint. RoboTeam does not discover conventional `.agents/skills`, `.claude/skills` or package `skills` catalogs under the workspace or its projects. Registered source generations are validated and captured as before; a required invalid or missing registered source fails execution.

A policy saves canonical discovery scope, live selectors, source bindings, exclusions, overrides, mode and an optimistic `policyVersion` in the robot's private `runtime/skill-policies`. Existing policy state wins over copied task requests. Legacy explicit empty selections remain empty. The historically indistinguishable nonempty default copilot-only case keeps the bundled catalog. A local or remote import whose original generation cannot be proven requires explicit reselection or explicit recovery-catalog pinning. Old snapshots remain recovery evidence and are never an implicit live fallback. Legacy path manifests are recovered only on explicit pinning: validate the saved permitted paths and identities, require canonical robot-owned or bundled sources, capture their current bytes into a digest-protected catalog, and preserve the original manifest. Missing or corrupt recovery sources fail visibly.

After queue and tool preparation, the conversational wrapper takes its existing session execution lease and prepares live links from current source resolution. Execution metadata records policy version, selected entries and a link revision. The revision identifies the installation, not an immutable content snapshot. Source edits remain immediately visible. Historical capture and retention helpers remain available for recovery records but are not called by live execution.

RoboTeam starts ALA with `--cwd <cwd>` and the full Ploinky workspace as a read-only `--folder`, both preserved at their canonical absolute paths. The working directory must be strictly below the workspace root. ALA mounts exactly what it is given: it must not discover, copy, mount or overlay task skills and receives no skill options. RoboTeam owns the initial skill instruction. The robot home is mounted writable and used directly as the native home; RoboTeam prepares no per-project copy, so concurrent tasks share one native home per robot. GUI containers use the same workspace read-only and working-directory writable mounts.

Pinned recovery catalogs cannot execute through the live installation path. They fail explicitly until the user restores a live selection. Scoped settings and terminal continuation retain their conversation policy; execution metadata must not replace a newer saved selection. Policy mutations retain optimistic version checks and source-qualified identity validation.

Identity and source exclusions, applicable native-name exclusions, and source overrides suppress required-selection validation. A disabled individual may become invalid, disappear, or outlive removal/replacement of its imported source without blocking an empty execution. Exclusion tombstones remain after removal and suppress a returning identity; explicit re-enabling validates the current descriptor and imported-source binding. Non-excluded required identities and sources still fail visibly when unavailable.

Workspace identities encode folder paths, which may differ from native skill names. Name exclusions retain validated identity/name associations learned during `deny-name`, explicit selection, Settings toggles, or legacy policy creation. Missing or invalid descriptors use those associations without guessing a name from their folder. Valid renamed descriptors use their current name, and `allow-name` removes the corresponding association. Inventory and capture never write this metadata. Legacy identities already missing before their names can be proven remain explicit errors. Registered source names beginning with `workspace`, such as `workspace-tools`, retain ordinary imported-source generation bindings.

For local imports, registered metadata proves the initial native name at each relative skill directory. Explicit mutations retain later valid names in optional `importedSkillNames` metadata bound to the exact source path and generation; those observations supersede registration names for live additions and renames. The empty relative directory represents a source-root `SKILL.md`. Missing or malformed descriptors retain applicable exclusions, while an invalid unproven folder cannot inherit an identity or name exclusion from its spelling. Valid current names always win. The metadata is validated on read and bounded to 32 registered sources and 5,000 observed directories; an over-budget mutation fails before persistence. Stored observations from another source generation are never reused.

RoboTeam publishes a Conversation skills action with its current, selected, and updated WebChat session envelopes using the resolved robot name and saved session UUID. Generic WebChat displays this optional action only for the selected session and validates same-origin navigation. A user click opens Explorer Copilot Settings for that exact conversation. Those catalog requests omit cwd and use the conversation's saved scope. Explorer consumes the context query once; invalid or incomplete context reports an error instead of falling back to defaults. Ordinary Settings continues to edit defaults for future conversations.

Successful completion must remain structured task status, not a synthetic sentence in the task log or assistant response. The final `outputText` must contain only ALA's result, with no generated completion fallback when that result is empty.

The copilot wrapper must attach delegated tasks to their originating assistant message using the session returned inside the task-insertion result. Child progress and final output belong to the delegated task record, not the parent's intermediate-message history. Once the task record is persisted, failure to attach or publish its chat presentation must emit a diagnostic but must not prevent status polling, task-start notification, or terminal-result persistence. The observer must never relaunch the remote task to recover its presentation.

Every ALA invocation must include `--session-id <uuid> --control-stdin`. A continuation must preserve the original session UUID and add `--resume-session`. RoboTeam must persist the task-to-session mapping and request settings under `<cwd>/.achilles-cli/tasks/<task-id>/` so a service restart does not require reconstruction from logs. ALA owns the native session reference, pins the first selected backend, and requires the same home and cwd. Stop must not delete this metadata. Missing state must produce an explicit failure, including for tasks created before persistent sessions were supported.

The internal `sendMessageToRobotTask` tool must accept a validated task handle and a nonempty bounded prompt. It must report `delivered` only after ALA acknowledges native steering, or `queued` for execution-local follow-up. Codex and Pi use their native control protocols; the current OpenCode adapter queues messages until its active invocation finishes. Stop discards pending messages. A message received after task termination must be rejected with an instruction to continue the task instead. Simple continuation must not add screen instructions.

RoboTeam launches ALA from the outer agent runtime after the required GUI, tool-cache generation, and MCP bridge are ready, or after coding-agent preparation for a simple task. It passes `--home` using the robot's persistent home, `--cwd` using the caller-selected workspace directory, `--folder` for the containing workspace and runtime socket, `--taskFile` using a private runtime prompt file, and `--ca` using the selected coding agent. The canonical mounts preserve the prepared live workspace; optional `--model` is forwarded.

A Desktop task must produce an invocation equivalent to `ala --home /data/robots/<robot-id>/home --cwd /workspace/<project> --taskFile /data/robots/<robot-id>/runtime/<task-id>.prompt --ca codex --MCPServers desktop=http://127.0.0.1:<port>/mcp`. A Browser task uses the `browser` MCP name. A Simple task omits `--MCPServers`. Concrete robot ids, cwd values, task ids, coding-agent choices, and loopback ports vary per request.

`--home` selects persistent coding-agent authentication and configuration. `--cwd` selects the writable work tree and disables ALA's temporary workspace. `--taskFile` supplies the prompt without placing its full text in process arguments. `--ca` selects `auto`, `codex`, `opencode`, or `pi`. `--MCPServers` supplies task-local Streamable HTTP MCP endpoints. RoboTeam resolves MCP `skillSets` and `skills` into installed links before launching ALA; neither selection option is passed to ALA. `--model` optionally overrides the selected backend's native model.

For GUI work RoboTeam passes `--MCPServers name=http://127.0.0.1:<random>/mcp`. The random port is the outer loopback mapping of fixed inner port `8100`. ALA translates that value into the selected backend's transient mechanism: Codex command-line `mcp_servers` overrides or OpenCode process-only remote `mcp` entries. Saved configuration and authentication under the robot home remain authoritative and are not rewritten. Desktop and Browser tasks must select Codex or OpenCode. Pi has no ALA-managed MCP injection, so RoboTeam must resolve GUI work to Codex or OpenCode and reject an explicit Pi selection instead of starting a GUI task that cannot control the visible session.

The ALA child is cancellable. Cancelling a graphical native task for human takeover sends termination to ALA while preserving the GUI container and puts that robot into manual-control mode. The explicit MCP stop tools stop ALA without entering manual-control mode. No existing queued graphical ALA request may start for that robot while a human controls the visible session. After all previous graphical requests are terminal, a new explicit graphical task must clear the manual-control pause and run once the previous process has exited. Queued status must expose manual-control as its blocking reason and task logs must explain the pause; independent CLI conversations remain available. Resume must use the opaque continuation handle returned by the cancelled native task, select the exact interrupted request, place its replacement ahead of existing queued work, and clear manual-control mode. The replacement prompt must contain the custom continuation or a short Continue instruction and an explicit instruction to inspect the current visible state with the available MCP tools, discard stale element or focus assumptions, preserve the human's changes, and continue. Only one graphical ALA process may run per robot. Desktop and Browser share one FIFO queue; independent Simple/CLI conversations run concurrently, and cancelling one queued request must not terminate the active request.

The three start tools must be native asynchronous Ploinky tools. Their command processes must remain active while the corresponding RoboTeam request waits and while ALA runs. RoboTeam must set `ALA_EVENT_STREAM=1`, parse `coding-agent-message` records from ALA standard error, and forward their message text to the command's standard error. Ploinky records that channel as live task progress. RoboTeam must collect ALA standard output separately and return it as the command's final `outputText`; ALA process exit determines whether the native task completes or fails. Desktop, Browser, and Simple starts, together with `resumeTaskForRobot`, must declare `resumeTaskForRobot` as their continuation tool. Every start and continuation must publish a validated version-1 handle during execution and return it on completion or cancellation. The handle supports completed, stopped, or failed Desktop, Browser, and Simple tasks. Live prompts use the declared sendMessageToRobotTask tool.

When `--ca` selects a concrete backend, RoboTeam prepares that backend's current cached generation and prepends its binary directory to the ALA child `PATH`. Omitted `ca` and `auto` prepare only the robot's configured coding agents, allowing ALA to select among them. Explicit selection must belong to that list. WebChat preparation uses the same list; inherited overrides and managed cache paths for other agents are removed. Executables are shared across robots. Account and configuration state for every backend remains under the robot-specific `--home`.

ALA owns the coding-agent sandbox even when it runs inside RoboTeam's outer container. It must first probe its normal user-namespace and private-procfs path. The current bounded nested runtime rejects the procfs mount inside that additional user namespace, so ALA may use its capability-assisted private-proc path: Bubblewrap omits the extra user namespace, retains private PID, IPC, and UTS namespaces and the private procfs, constructs the mounts using the outer admitted capability, and drops all capabilities before starting Codex. Codex must disable its redundant native sandbox inside this boundary. Neither this Codex setting nor ALA's private-proc fallback permits execution outside the ALA Bubblewrap filesystem and environment boundary.

## Decisions & Questions

### Question #1: Can a robot run several conversations?

Response: Independent Simple/CLI conversations run concurrently. Desktop and Browser retain one shared graphical queue and container. One conversation uses one ALA session and permits only one active turn. The shared copilot wrapper persists UI messages under the robot's copilot directory and invokes ALA with that robot's home.

### Question #2: Does this change migrate AchillesCLI state?

Response: No. The default robot starts with its own state. Existing robot homes are retained, and old AchillesCLI files are left untouched.

RoboTeam must not implement conversation commands for skill selection, live updates or pinning. ALA owns the single initial instruction about mounted .agents/skills; continued turns must not repeat that instruction.

## Conclusion

RoboTeam owns robot and GUI lifecycle; the shared conversational wrapper preserves session and task state, and ALA owns native coding-agent execution.

Repositories without declared skillsets expose each skill’s name and description, grouped by repository ID, in robot discovery and the default robot’s turn context. Individual selections use `repository-id/skill-name` in `skills` and combine with selected skillsets. Delegated tasks never receive copilot automatically; the front copilot's direct default chats initially select only `launch-workflow` and honor explicit empty selections. Resume captures current source files unless pinned.

RoboTeam must prepare a private per-turn ploinky-runtime directory with version-2 context.json, SDK client/lib files, the selected AgentLib JWT modules and package identity, a byte-preserved signed Router descriptor and tasks.sock. SDK dependencies must be real files inside this folder, not symlinks into unmounted locations. Descriptor locator and AgentLib paths point inside /workspace/ploinky-runtime; signed descriptor mirror fields must remain unchanged. ALA receives only --folder <directory> as ploinky-runtime and mounts it read-only. No Ploinky-specific ALA option or configuration parsing remains.

Task-start and live-session notifications use newline-delimited JSON over the Unix socket, with a per-turn capability token, stable notification UUID and a 1 MiB limit. RoboTeam must acknowledge only after authenticated task observation succeeds. Concurrent or repeated messages with the same ID and payload share one observation; reusing an ID with different content fails. The client retries a failed notification up to three times with the same ID, never repeating the MCP launch. New live-session metadata uses a new notification ID. Invalid messages must not affect other tasks. On completion or cancellation, RoboTeam drains accepted notifications, closes the socket and removes its private runtime directory. No event files or polling are used. Task logs and progress still use the existing Ploinky task observer.

Skillset discovery visibility is administrator-controlled per robot through PATCH /api/robots/:id/skillsets with an id and boolean enabled. Persist disabledSkillsets in robot metadata; absent entries are enabled. The management catalog includes disabled sets and their enabled state. Default turn catalogs and robot_list omit them, including nested repository definitions. A repository with disabled definitions must not become an individual-skill fallback. Existing execution selections and continuations are unaffected.
