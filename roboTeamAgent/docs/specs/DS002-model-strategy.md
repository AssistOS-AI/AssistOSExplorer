## Introduction

RoboTeam's current robot and container control path does not require an LLM.

## Core Content

Robot creation, listing, browser or desktop start, stop, log retrieval, authorization, persistence, HTTP proxying, and WebSocket proxying work without a model provider.

Advanced Language Agent, abbreviated ALA, is RoboTeam's LLM execution layer. Every AI execution runs in the RoboWork worker (DS005, Execution cutover): RoboTeam starts no ALA of its own, has no local execution path, and refuses an AI task, turn or model call with `worker_not_configured` while `ROBOTEAM_WORKER_COORDINATOR_BASE` is unset. The paragraphs below describe what ALA does inside the worker. RoboTeam owns deterministic robot, task, container, and proxy lifecycle. ALA reads the task prompt, selects a coding-agent backend, runs it inside ALA's Bubblewrap sandbox, and gives it any task-local MCP server configuration.

ALA currently supports `codex`, `opencode`, `pi`, `claude`, and `auto`. With `auto`, RoboTeam omits `--ca` and ALA uses the `codingAgent` saved in the robot's `.ala/config.json`, falling back to the first available agent. RoboTeam resolves the current official npm package for each backend (unless an operator pins that backend to an exact version with `ROBOTEAM_CODEX_VERSION`, `ROBOTEAM_OPENCODE_VERSION`, `ROBOTEAM_PI_VERSION` or `ROBOTEAM_CLAUDE_VERSION`), installs it in a separate shared tool-cache generation, validates its CLI, and places the requested backend on ALA's `PATH`. Automatic selection prepares only the robot's configured coding agents. New robots configure only OpenCode. Explicit backend requests must name an enabled agent; the server retains support for multiple enabled agents. The executable cache is workspace-wide, while account and configuration state comes only from the robot home supplied through `--home`.

The ALA `--MCPServers` adapter injects task-local URL configuration into Codex, OpenCode and Claude Code. Desktop and Browser tasks without an explicit caller override omit `--ca`, leaving coding-agent selection to ALA and the robot home configuration. RoboTeam must not substitute a GUI-compatible backend. Pi has no ALA-managed MCP injection; selecting Pi in the Coding agent dialog displays a yellow warning that it is not compatible with Browser and Desktop executions.

RoboTeam asks the worker to run ALA with the selected backend (`auto` for a robot with several coding agents) and may forward an optional model override; the robot's HOME, which owns authentication and backend configuration, is the worker's, and RoboTeam neither reads nor binds it. RoboTeam passes task-local MCP URL overrides. When the user chose no model, a one-agent OpenCode robot is configured with the free default `opencode/glm-5.3-flash-free`, marked `modelSource: default` and shown as the default, never as the user's choice. A `soul-gateway/<id>` model is served to OpenCode only, through the worker's Soul Gateway model channel; the other backends refuse it with `model_unavailable_in_worker` before admission. The local Soul Gateway provider below serves the robot's interactive Terminal and workstation containers. Model names, tiers and prices must come from the gateway catalog rather than a vendor-specific list in RoboTeam. Claude Code does not use Soul Gateway and runs only Claude's own models with Anthropic credentials from its own login; `/model` lists them from ALA, which reads them from the installed CLI, so RoboTeam keeps no Claude model list.

### Soul Gateway model catalog

RoboTeam must install the same repository-owned JavaScript plugin in each robot's global OpenCode plugin directory. OpenCode's asynchronous `config` hook must fetch the local Soul Gateway `/v1/models` catalog and populate `provider.soul-gateway.models` in memory. No generated `opencode.json` or wrapper-supplied `OPENCODE_CONFIG_CONTENT` is required for the gateway. Existing unrelated provider and permission settings must remain intact.

Discovery occurs when native OpenCode initializes its provider configuration, including a new model-list process or execution. There must be no periodic polling or 60-second catalog cache. Existing native instances retain their initialized model list until reinitialization; a new OpenCode process reads the current catalog. Discovery failures must produce an explicit service-unavailable error rather than silently selecting another provider.

Model listing and coding-agent status come from admitted, robot-scoped worker utilities. RoboTeam loads no ALA, starts no coding-agent CLI and reads no old robot HOME for these operations. The coordinator operations `robots/models` and `robots/agent-status` use the same verified coordinator and workspace-robot rule as `robots/get`, checked before every cache read. Native model discovery runs protocol-mode ALA in the orchestration domain, with coding-agent commands in the worker HOME workload. Status uses a fixed workload helper without an execution provider. Its projection contains each agent's availability, login boolean and optional version token. Login detection is passive and does not prove a credential is still valid.

The worker's OpenCode picker includes all Soul Gateway models permitted to the worker at the latest bounded catalog refresh. It merges them with native models using the existing Router upstream and channel catalog validation. Native HOME plugin entries under the gateway prefix are replaced by the worker-owned list. Other coding backends receive no gateway models. This picker catalog does not widen inference: each execution channel still exposes and accepts only the selected model. No gateway effort choices are invented when the catalog mapping advertises none, so a nondefault effort for those entries is rejected by the existing exact-effort validation. An unavailable or invalid gateway catalog refuses the whole listing without caching a partial result.

Utilities have a twelve-second deadline, a combined 512 KiB output limit, and atomic caps of one open utility per robot and four per worker. They use the normal execution resource ledger and recovery path. The worker caches sanitized projections for fifteen seconds by robot, configuration revision and operation, with at most 128 entries. Failed utilities are not cached. RoboTeam reports login status as `"unknown"` when the worker cannot supply it.

`GET /api/robots/<id>/coding-agents` reads the saved selection from RoboTeam's own robot record. Saving an agent or model selection without an effort needs no model listing. When an effort is supplied and the worker robot is available, `PATCH /api/robots/<id>/coding-agents` checks it against that exact model's advertised efforts, including a previously saved effort. Unsupported choices return 400. A save without an `effort` field keeps the saved effort of an unchanged model, and `null` clears it. When a robot has no worker binding, model listing returns 409 `model_listing_unavailable`; the settings dialog still loads and saves selections, using the static Claude Code or Pi effort levels where known. The model picker retains the configured model while a list is unavailable.

Exact gateway model IDs, available context/output limits and token prices must map to OpenCode metadata. Absent limits and reasoning-effort choices must not be invented. Manual terminal launches, Desktop launches, WebChat autocomplete and ALA execution must use the same installed plugin from the robot home. WebChat model discovery must run OpenCode in the same canonical cwd/home sandbox as execution so the robot-home gateway socket resolves; a model-list process must not use a sandbox that hides the robot home. The selector presents `soul-gateway/<gateway-model-id>`; inference forwards the exact gateway ID. Reading the currently selected model must not fetch the catalog. This integration must not switch the coding backend or add gateway entries to a Codex or Pi catalog.

### Model and effort selection

The robot chat `/model <model-id> [effort|default]` command validates effort against ALA native model metadata before saving. A native model ID may contain spaces; the command resolves the longest known ID and treats a single trailing token as the effort. `/model` lists models and their supported efforts; WebChat autocomplete first offers models as subcommands, then the selected model's supported efforts and `default` as argument completions, and the terminal picker asks for effort when supported. RoboTeam saves the selection atomically for the conversation's agent in the robot home `.ala/config.json` under `models` and `efforts`. That config is the single source of the robot's coding agent, models and efforts; `.roboteam/settings.json` holds no coding-agent models. RoboTeam pre-populates it with the OpenCode default, the free model `opencode/glm-5.3-flash-free` served by OpenCode's native provider, when the robot enables OpenCode and no OpenCode model is set, so headless runs do not fall back to whatever model OpenCode picks on its own. A model the user chose is never overwritten. Through the worker the same default is sent in the robot's configuration when the user picked no model, marked `settings.modelSource: 'default'` (a chosen model carries no marker), and `getModel` reports `modelSource` so the UI shows it as the default; the worker writes it into the robot's managed ALA configuration, and RoboTeam writes no provider credential into any worker HOME. A model served through Soul Gateway (`soul-gateway/…`, the prefix matched case-insensitively) runs in worker mode on OpenCode only, through the worker-hosted Soul Gateway model channel: the worker calls Soul Gateway with its own identity (`agent:AchillesIDE/robo-work`, one shared billing and budget row) through the canonical AchillesAgentLib Router transport, serves exactly the one gateway model that execution uses (the conversation or task override, else the robot's configured model) to the OpenCode workload over a loopback relay in the execution's network namespace, and hands OpenCode a read-only generated configuration (`OPENCODE_CONFIG`) with a placeholder key; no gateway credential is written to any worker HOME or passed to ALA, the coding agent or the workload, and the worker, not RoboTeam, owns the channel. If the worker cannot serve the model the attempt fails with `model_unavailable` (the model is not in the gateway catalog) or `model_channel_unavailable` (the gateway cannot be reached) and the user reads a plain message; an attempt that ends for inactivity includes the last error the channel saw (status and a short sanitized message). For Codex, Claude and Pi, which have no such channel, worker mode refuses a Soul Gateway model before admission with `model_unavailable_in_worker`; it is never replaced by the free default. `/model default` clears both overrides for the current backend. Selecting a model without effort clears its old effort. Every execution snapshots this configuration; a running turn keeps its captured selection.

Models without effort metadata must not open an effort menu. Selecting an effort must insert `/model <model-id> <effort>`; the autocomplete catalog must not enumerate model/effort combinations at the model-selection stage.

WebChat runtime state must carry the model and optional effort together at startup, session selection, model changes, and turn selection. The header must display a configured effort beside the model in the same badge. Resetting effort must clear the previous displayed value. Turn-selection events must use the effort captured for that execution, not a later configuration read.
