## Introduction

RoboTeam stores credential-bearing GUI state and operates a nested engine, so public access and runtime authority remain explicit.

## Core Content

Coding-agent configuration is administrator-only through robot creation and `PATCH /api/robots/<id>/coding-agents`, behind the existing authenticated Router route and browser mutation proof. It configures available managed tools, not a security sandbox or a single-agent server restriction.

Only authenticated administrators may add or remove a robot's skill repositories through POST or DELETE `/api/robots/<id>/skillsets`. Internal agents and non-admin users must be denied; existing Router identity and browser mutation proof remain required. Imports accept credential-free HTTPS Git URLs or canonical directories inside the workspace, excluding robot private data. Repository imports must reject symbolic links, special files, excessive size and malformed SKILL.md descriptors; they must never run repository setup scripts. Imported code remains a trusted administrator-selected supply-chain input, not validated safe code.

Robot deletion from the dashboard must require confirmation and the same administrator authorization as `robot_delete`. It must refuse queued or active work, pending container transitions, and retained containers. The runtime must prevent late starts from recreating a deleted robot. Deletion removes that robot's home, runtime records, skillset imports and task catalogs, without deleting source repositories or the shared tool cache.

Canonical identity remains `agent:AchillesIDE/roboTeamAgent`. Port `7000` is reserved for AgentServer/MCP; only the RoboTeam HTTP/WebSocket service on port `3001` has an authenticated browser route. Inner Podman, Selkies loopback ports, bridge port 8100, and Chromium CDP port 9222 are never public.

Browser identity comes only from Router-injected `x-ploinky-auth-info`; mutations require Ploinky proof. AgentServer listens on port `7000`; MCP callbacks use a cryptographically random 32-byte internal token generated by the launcher on every start, plus the authenticated user id, without logging either. The launcher must overwrite any inherited token and share the generated value only through the internal service/AgentServer environment. It must not be a manifest setting, persisted credential or source constant. Task and Copilot execution must remove it before starting ALA.

Robots belong to the workspace rather than individual users and retain separate mounts. Creation and deletion require an authenticated `admin` role; internal Ploinky agents may use the explicitly internal list, task-start, and task-status tools without a delegated user identity.

All administrator-only HTTP operations require the authenticated actor's roles, after trimming and lower-casing, to include `admin` and exclude `guest`. This covers robot creation, deletion, model and coding-agent settings, skill repository mutations, and workflow definition and generation mutations. Usernames, display names and the `local:admin` id do not grant administrator authority. The local CLI supplies `user` and `admin` roles. Internal-token calls require forwarded non-guest administrator roles for these operations; the token alone grants no administrator role.

Workspace robot listing through `GET /api/robots` is a directory read and is decided before the unsigned compatibility header is consulted. Only the exact `GET /api/robots` path uses this rule; robot-specific paths such as `/api/robots/<id>/session` are decided by the family gate described below. A browser request is decided only on the Router-signed request in `x-ploinky-auth-info`, verified with the Agent helper loaded from `${PLOINKY_AGENT_RUNTIME_ROOT:-/Agent}/lib/invocationAuth.mjs` against the exact method, path, query, empty body, tool, audience and replay cache. The signed actor must be a direct user: kind `user`, an actor id equal to a non-empty `user:` subject, and no delegated user or delegation claim. After trimming and lower-casing roles, the actor must not hold `guest` and must hold `admin` or the signed `explorer.access` capability. Usernames, the `local:admin` id alias and the unsigned header grant nothing. A missing helper, agent secret or agent id returns 503; a missing or failed verification returns 401; a verified but non-entitled actor, including guests, returns 403. The response's `canAdmin` is true only for a verified non-guest `admin` role.

Every other route on the service port, apart from internal-token calls, requires the same signed entitlement. This covers the pages, static assets, `/config.js`, the robot session HTTP proxy, every `/api/*` route including `/api/roboflow*`, unknown paths, and the WebSocket upgrade of the robot session. The exempt routes are internal-token calls, `GET /status`, the AgentServer passthrough (`/mcp`, `/task`, `/getTaskStatus`, `/health`, whose own secure-wire verification applies) and `GET /api/robots` with its own rule above. The gate verifies the Router-signed request once, over the exact method, path, query and raw body bytes, with the Agent helper and replay cache described above; an upgrade is verified over an empty body, as the Router signs it. The signed actor must be a direct user without `guest` who holds `admin` or the `explorer.access` capability. A missing or failed verification, an unsigned header, a replayed or tampered request returns 401 with `authenticated Ploinky user is required`. A missing helper, agent secret or agent id, or a verifier fault, returns 503 with `request verification is unavailable`. A verified but non-entitled actor, including a `selfRegistered` account, a guest or a user without the capability, returns 403 with `Explorer access permission is required to use RoboFlow` under `/api/roboflow*` and `Explorer access permission is required to use RoboTeam` everywhere else; the listing keeps `Explorer access is required to list robots`. The refusal precedes body parsing, so a malformed body from a non-entitled caller is also 403, while a body over 64 KiB returns 400 first. The gate only admits: the existing per-route administrator checks still apply to the forwarded roles, and the unsigned header never grants entitlement. A refused WebSocket upgrade receives the same status with a JSON body and logs only its status and path. Static assets are still revalidated with ETag on every request, each revalidation being a signed request.

An internal-token `GET /api/robots` lists robots only when it carries `x-roboteam-listing-origin: agent` and no `x-roboteam-user-*` header; any other internal listing request returns 403 and the response's `canAdmin` is false. The `robot_list` tool sets that header only after checking the AgentServer-verified grant: an `agent` actor whose id equals an `agent:` subject, with no `usr`, `user` or `delegation` claim and no forwarded `metadata.user`. Any other caller, including a direct or delegated user and a permissive persisted tool policy, is rejected before an HTTP request is made. Other internal operations keep the service-token path unchanged.

Every outward robot view, from listing, creation, coding-agent updates and run get/start/stop, uses a restricted projection unless that exact request is verified as coming from a non-guest `admin`. The listing uses its own verification; every other view reuses the signed `admin` decision of the family gate and never verifies a request a second time. The unsigned compatibility header, usernames and internal-token calls never widen it. In the restricted view, each repository `source` becomes a credential-free display URL: the scheme, host, optional port and plain path of a remote Git origin, or `git@host:path` reduced to `host:path`. Userinfo, query strings and fragments are dropped, and local paths, `file:` URLs and malformed or ambiguous values become empty. The run's task `cwd` becomes a workspace-relative reference, or is omitted when it is outside the workspace. The rule mirrors Ploinky's marketplace display projection. Stored robot configuration, repository sources and task requests stay unchanged, and task and log APIs are outside this projection. The skills dialog labels and removes repositories by their stable id when the display source is empty. The outer RoboTeam container remains on Ploinky's managed network. Its admitted `nestedPodman` capability adds only `SYS_ADMIN`, `NET_ADMIN`, `/dev/fuse`, `/dev/net/tun`, label disablement, and the fixed nested-Podman seccomp profile. The listing's `codingAgentLogins` reveals which outer accounts a robot holds, so it is included only for a verified non-guest administrator listing; it contains booleans and never a credential value.

RoboTeam's startup-only creation of an absent ordinary robot named `default` is an internal registry operation, not a new externally callable administrative tool. It must not weaken administrator-only create/delete policy, internal workspace-agent task access, authenticated GUI routes or credential separation. The default is workspace-owned like every other robot, has no special marker or fixed identity, and remains subject to ordinary deletion guards.

The inner engine runs as uid 0 inside the outer container's user namespace; it is not physical-host root. `SYS_ADMIN` still makes the outer container a weak security boundary, so this remains a controlled experiment. Inner runs disable Podman's private IPC setup to avoid a nested mqueue mount that the bounded capability intentionally cannot create; GUI runs add only their own `/dev/shm` tmpfs. No host Podman socket or public inner API exists, and cleanup uses exact labels and names. Robot homes and browser sessions are credential-bearing data; operators must protect `/data` and backups.

The current nested runtime cannot mount a private procfs inside the additional user namespace used by ALA's normal Bubblewrap path. ALA must probe that normal path first. When only that nested mount is rejected, ALA may omit the additional user namespace while retaining private PID, IPC, and UTS namespaces, a private procfs, its read-only filesystem boundary, controlled writable mounts, isolated temporary storage, and its filtered environment. The admitted outer `SYS_ADMIN` capability may be used only while Bubblewrap constructs those mounts, and Bubblewrap must apply `--cap-drop ALL` before starting the coding agent. The coding agent must not inherit the capability. Failure of both private-proc paths must stop execution; an unsandboxed fallback is forbidden.

Current npm and GitHub releases are external supply-chain inputs. An operator pin (`ROBOTEAM_CODEX_VERSION`, `ROBOTEAM_OPENCODE_VERSION`, `ROBOTEAM_PI_VERSION`, `ROBOTEAM_CLAUDE_VERSION`) is also an operator-supplied supply-chain input: it must be an exact version, the exact version is recorded in the generation stamp, and a pinned agent never falls back to a generation of another version. RoboTeam must stage and probe candidates before activation, record exact resolved versions, verify computer-use-linux bytes against the available upstream digest, mount generations read-only, and fall back only to a stamped valid generation. Cache metadata and logs must not contain robot credentials.

### Local Soul Gateway access

The RoboTeam service owns one UNIX socket per robot under that robot's `.config/opencode` directory. Startup prepares existing robots; creation, terminal and task/container preparation provision new robot connections. The socket is mode 0600, its parent directories must be validated without following symlinks, and an existing live listener or non-socket file must never be replaced. A filesystem shared from a macOS host (virtiofs) cannot store a socket's mode: chmod fails with EINVAL, the socket stays 0666, and that filesystem does not enforce the parent directory's mode either. There the listener still starts and the service logs that the socket is not owner-only, because socket access already follows robot-home access; any other failure to set the mode stops the listener. Robot deletion and service shutdown close the owned listeners and cancel pending requests. No new public TCP port or Router route is exposed.

The service must validate the generated-local Router descriptor before reading its credential and must use AgentLib's certified Router transport for both model discovery and chat. The generated credential must stay in RoboTeam. The private socket accepts only `GET /v1/models` and `POST /v1/chat/completions`, with a 2 MiB chat request limit. Socket access follows existing robot-home filesystem access; robots are workspace-controlled identities, not a new tenant security boundary.

The native OpenCode plugin must connect through the mounted robot-home socket. It must create a process-local loopback chat endpoint protected by a random ephemeral capability, forwarding only the chat completion route to the socket. The capability must never authorize MCP, filesystem or lifecycle operations. Plugin disposal closes the local endpoint, and client disconnects cancel upstream requests. Neither persistent provider configuration nor a Ploinky credential is written to the home. Plugin and helper files are installed atomically without overwriting unrelated settings.

The certified local Router transport advertises buffered chat only. The service must request `stream: false` upstream and translate a completed response into SSE when OpenCode requests streaming, preserving content, tool calls, finish reason and usage. This is completion delivery, not token-by-token streaming. Errors must preserve useful HTTP status without forwarding credential-bearing upstream error text.

### Local skill scope

Trusted local-skill launch scope is carried from Ploinky as a canonical path inside the existing workspace grant and persisted per conversation. It is discovery metadata, not a new filesystem grant. Saved scope cannot be widened by resolving a retargeted alias; selected source trees are validated and mounted through ALA's existing read-only catalog delivery. Multiple bounded CLI scopes may share one already-authorized Box.

### Conversation skill settings

RoboTeam serves the Conversation skills page and `GET` and `PATCH <publicBasePath>api/robots/<robotId>/conversations/<sessionId>/skills` under its existing authenticated Router route. Anonymous requests receive 401, and the internal-token actor receives 403 because no internal caller needs these endpoints. Robots belong to the workspace and conversations carry no owner, so any Explorer-entitled signed-in user who names a robot and one of its registered conversations may read or change that conversation's skill selection. This is no wider than the `list_achilles_skills` and `set_achilles_skill_enabled` tools. The endpoints take no query parameters and no directory, accept only `identity`, `enabled` and `policyVersion` in a `PATCH` body, and never create or change a robot-defaults policy. A conversation bound to another robot, or whose saved policy reference is not its own conversation policy, is refused. Browser mutations rely on the Router's mutation proof and exact Origin check, and RoboTeam adds no second check. The page renders every dynamic value as text.

### Live Sessions

Live Sessions routes run inside the signed-entitlement gate and refuse every internal-token caller with 403, even with forwarded or signed user headers. Authority is only the signed principal (`verified.payload.actor.id`) and the signed administrator decision of the same request; forwarded identity and caller-supplied owner fields are ignored. Runs a viewer may not see answer 404. Only the verified owner may message a run; the owner or an administrator may stop it. Rows without a verified owner (`system`, `unverified`) are visible to administrators only. Transcripts are read only from server-bound run metadata after authorization, never from container logs or caller paths, and are served as `text/plain` with `nosniff`. The view page renders text only and cannot be framed. Streams end after 25 minutes so a reconnect is authorized again, which bounds how long a revoked administrator keeps watching.

Copilot processes publish over a private Unix socket on the container's `/dev/shm`. Its invisibility from ALA sandboxes was observed with a diagnostic harness and listener; the same check against the production listener is pending. The service binds each run to the publisher incarnation that opened it and accepts an owner only from a Router-signed WebChat token that it verifies itself over the full request tuple, its own audience, expiry and replay. Publisher-declared identity is ignored. The publisher keeps the raw token only until it sends the claim and never logs it. ALA binds the directory of a coding-agent binary without a reserved-path guard; a robot that falls back to a binary in its writable home could project a host directory such as `/dev/shm` into a later sandbox. This residual risk remains open until investigated in ALA and RoboTeam. DS008 owns the full contract.

### Terminal profiles

The terminal profile endpoints `GET /api/terminal-profiles`, `POST /api/terminal-profiles/<id>/prepare` and `POST /api/terminal-profiles/resolve` serve Explorer's Open Terminal Here dialog and Ploinky's profile resolution. They decide only on the signed route authentication already verified for the request: a signed-in `user:` principal with the signed administrator decision. They refuse every internal-token caller and never consult the compatibility actor or forwarded role headers. Prepare also requires the browser mutation proof, and resolve is read-only and answers `{allowed: false}` for a well-formed request it cannot prove; a malformed body answers 400 and a caller without the signed administrator decision 403 (a request whose signature cannot be verified is refused earlier with 401). The selected robot's home folder becomes HOME for a shell on the target the administrator chose. It is executable configuration under that target's authority, and logins, history and files the administrator creates there are readable by the robot. Explorer discloses this beside the selection; the disclosure is not a control, and the terminal remains an administrator shell, not a sandbox. Robots stay workspace identities, not a tenant boundary.

### Workflow graph authoring

roboflow_generate_workflow requires the administrator role, like workflow creation, update and deletion. The browser uses the native Ploinky MCP client and Router task polling and cancellation. HTTP mutations retain browser CSRF proof checks. Graph generation passes system instructions to a default robot terminal task and returns a validated unsaved draft. The retired decision tools have no MCP definitions or HTTP endpoints.

### Worker coordinator callers

RoboTeam calls the RoboWork worker's coordinator API over the Router's private listener; it is transport only and starts no local execution. The existing local launch paths (`/api/control`, WebChat turns, RoboFlow dispatch, the robot MCP tools) are unchanged and do not advertise worker protection. Each hop goes to `<ROBOTEAM_WORKER_COORDINATOR_BASE>/v1/coordinator/<route>` at the private Router location of the verified generated descriptor, with a private agent assertion over the exact body bytes. A missing selector base, descriptor, Agent library or private identity refuses with 503 `worker_coordinator_unavailable` before any I/O. Callers never fall back to a local path. Every row has exactly one carrier:

| Row | Evidence on the hop | Refusals |
| --- | --- | --- |
| Browser API: `POST /api/worker/admissions`, `/lookup`, `/bindings`, `/references/<id>/read`, `/events`, `/control` | The `providerAdmission` grant the Router mints only for the dedicated `/base-agent-additional-server/roboTeamAgent/3001/api/worker/*` route, which the manifest declares before the broad route (the broad route mints nothing). It is sent as `x-ploinky-user-delegation`. | Internal-token callers, requests without a grant, and a grant whose user is not the request's signed principal get 403 `owner_evidence_unavailable`. Bodies are exact JSON objects (400 `invalid_request`). Session and flow work get 400 `logical_kind_unavailable`. |
| WebChat | The grant inside the envelope's own Router-signed `__webchat_message__` token, after RoboTeam verifies the token over the rebuilt signed arguments, including `runtimeScope` and `event`. It is held in memory only. | Unverifiable, guest, shared-scope and tampered-`event` envelopes make no hop. A verified envelope for a second user in the same runtime is refused (`runtime_principal_mismatch`, diagnostics only). |
| Background (RoboFlow, Cron) | Root bindings: the owner's grant through `/api/worker/bindings`. Derived bindings: the coordinator alone, with the parent binding in the signed body. | A schedule binding `cron_<id>.r<n>` needs the signed administrator decision, the schedule's recorded `bindingRevision` equal to `n` (otherwise 409 `binding_revision_unavailable`, checked before the owner) and the schedule owner (otherwise 403 `binding_owner_mismatch`). A flow binding needs a root flow owned by the caller, and an administrator for a run-now flow. Cron-fired and child flows bind only as derived bindings. Records without binding metadata get 409 (no legacy reader). |
| MCP robot tool (`tools/worker-task-reference.mjs`) | The Router origin token (`metadata.taskRefOrigin`) and the declared tool name. It never forwards a user grant, even when the invocation metadata carries one. | No origin token: `owner_evidence_unavailable`. A failure prints `worker admission failed: <code>` and is never retried, because the origin token is single-use. |
| Operator native CLI | None. Unsigned terminal arguments are never evidence. | Every coordinator operation refuses with `owner_evidence_unavailable` and persists and sends nothing (interim, until D1 is decided). |

Worker answers map to fixed codes that never carry a token, grant or worker reason: 401 becomes 502 `worker_auth_failed`, 403 becomes `forbidden`, and a Router-marked refusal (`X-Ploinky-Refusal`) becomes 503 `worker_route_unavailable`. A connection that never reached the Router becomes 503 `worker_unreachable`. A complete response the worker never sends, such as the Router's unmarked 502 or 504 after the worker dropped a dispatched request, has an unknown outcome. A browser admission with an unknown outcome makes one lookup with the same grant and otherwise answers 503 `worker_reply_unknown` with the `originRequestId`.

The WebChat shim persists each admission in the private origin store `/data/worker-coordinator/webchat-origins.sqlite` before the first transmission. The directory is 0700, the file 0600, a symlinked location is refused, and the store holds no token or grant. Rows are `persisted`, `sent`, `unknown`, `admitted` or `refused`. The first four count toward caps of 64 per user and 4096 in total, and a full store refuses with `capacity_exceeded` without evicting anything. Refused rows are kept for ten minutes (at most 16 per user). The verified `runtime-open` envelope and any later verified envelope with a grant reattach at most 16 recovery rows plus 16 follow-up rows per envelope. Recovery rows are that user's `unknown` rows and its `persisted` or `sent` rows older than the 30-second claim window, oldest first: each is claimed by compare-and-set and looked up, and its stored bytes are sent again once if absent. Follow-up rows are that user's `admitted` rows, oldest first: each is read until a terminal snapshot (including `paused` and `human-input`), then deleted, and a kept row is re-stamped by compare-and-set so the next envelope reads the rows read least recently. WebChat turn admission (`admitTurn`, session work keyed by the conversation ID) is implemented, but the dispatcher does not call it until turn conversion. The origin store shares `/data`'s trust level; that no robot workload can write `/data/worker-coordinator` remains to be confirmed when execution moves to the worker.


#### Execution cutover

When `ROBOTEAM_WORKER_COORDINATOR_BASE` is set, `createCliRuntime` builds the worker engine (`copilot/src/lib/execution/workerEngine.mjs`) instead of the local ALA engine, and no local ALA installation is resolved. A worker failure is an explicit error; there is no fallback to a local run. With the variable unset the local engine is unchanged until the AI-task end-to-end gate passes. The worker engine builds the same native prompt and ALA inputs as the local engine, admits them as a version-2 specification (`admitTurn` for a WebChat turn, a `task` admission under the flow binding for a RoboFlow phase) and feeds the relayed `ala` records through the same record handler, so the streaming events are identical. A `truncated` row or a retention gap becomes a diagnostic event. The final text is the result of the reference.

No follow-up bearer credential exists. An interactive turn opens one NDJSON event subscription (`references/<id>/events` with `stream: true`, through `hop.stream`) with the admission grant, which authorizes it at open. If the stream drops, the engine reattaches from its cursor only with a grant the user supplies, namely a later verified envelope of the same principal, held in memory by the dispatcher; with none it ends the call with `owner_evidence_expired` and the worker keeps running the execution (`execution: may_still_run`, or `finished` when only the result read is missing, which stays retrievable by lookup). Each user control carries the grant of its own request: a stop uses the grant of the stop envelope, and a message uses the grant in the message; a control without a usable grant of its own is not delivered and is reported. The chat's stop button and Escape are such a stop (decision M-40): the Router forwards the stop as a signed WebChat envelope with event `stop` that carries its own minted grant, and RoboTeam sends the worker `stop` (one control, a deterministic operation ID) with that grant only. No earlier or later grant of the same user is borrowed. An unsigned control line (an older Router), a missing grant or an expired one is not delivered: the user is told "Stop not delivered: the worker needs your fresh authorization. The task may still be running; press stop again.", it is logged, the turn keeps running, and the next press is sent again. A page unload, navigation or shutdown only detaches and sends no stop. Every other user-initiated control follows the same rule (decision M-12 (b)): the worker `stop`, `message` and `answer` of a person's action carry the grant of that person's own request, and only a system-initiated control (a flow failure, a recovery, the startup reconciliation) uses the coordinator identity and the flow binding. A user's RoboFlow pause or terminate finds the phase's worker reference with the coordinator identity and the flow binding, because the worker records a phase origin under the binding row, which a lookup by the user's grant never searches, and then sends the `stop` on that reference with the user's own grant, which the worker accepts from the reference's owner or an administrator and refuses for anyone else. Nothing in RoboTeam changes until the worker has the stop (decision M-34): the requester must be the flow's owner or an administrator (a message, the owner alone), otherwise 403 and no state changes; then every non-terminal phase of the flow and of its child flows gets the stop, and if any stop was refused, failed, or found no worker record for a phase that had started, the request ends 409 with the "Stop not delivered…" notice and the flow is left running and still followed by reconciliation. A phase that never started needs no stop. A phase is never continued, resumed or retried while a binding lookup shows its previous attempt running on the worker, or the worker cannot answer (409), whatever marked it paused or failed (an undelivered system stop, `stop_not_confirmed`). A task child learns which kind a stop is from the `user` mark of its stdin stop record, so a user stop with no grant is never sent under the binding and is reported as not confirmed. With the worker configured, the per-flow RoboFlow pause, terminate, phase-pause and phase-message paths mint no grant and are refused with `owner_evidence_unavailable` before anything changes; the UI uses `POST /api/roboflow/control` instead (`{flowId, action: pause | terminate | pause-instance | message-instance, instanceId?, prompt?}`), which answers 409 when a worker stop was not accepted. The command-line session and the terminal REPL have no Router request and therefore no grant: in worker mode they admit no worker turn at all (`owner_evidence_unavailable`), so they have nothing to stop. A RoboFlow phase runs on the background row: the coordinator identity and its persisted flow binding authorize its reads, polling and system-initiated stop (flow cancel, pause or failure, and recovery), with no user grant.

Detaching (RoboTeam shutdown, engine close, SIGTERM of a task child) leaves the worker execution running; only a user stop, or the stdin `stop` record of a task child, is sent as a `stop` control. The hop allowlist is the admission, lookup, binding and reference operations plus `robots/provision`, `robots/configure`, `robots/get` and `operations/get`; every other operation is refused before any I/O. The manifest declares `providerAdmission` for exactly eight route patterns, each before the broad route: `/api/worker/*`, `/api/robots/*` (robot create, import and update), `/api/roboflow/flows`, `/api/roboflow/schedules/*` (flow start and run-now), `/api/control` (task start, stop, take-control and message), `/api/roboflow/human-input/answer`, `/api/roboflow/control` (a user's pause, terminate, phase pause and phase message) and `/api/live-sessions/*` (a run's stop and message). A task started through `/api/control` hands its request's grant to the robot-task child over the child's stdin only, never argv, environment or a file; the child uses it at once for its one task admission under a deterministic origin and keeps nothing. A user's stop of such a task carries the stopping request's own grant in the stop record over stdin; the task is `pausing` until the worker confirms, and any stop the worker does not confirm (no grant, a refused or failed control, a reference not found, an expired grant, or an accepted stop with no terminal state within the bound) makes the child exit 75, recorded as `stop_not_confirmed` (the execution may still be running), never as paused. The private session skills overlay and any path with a protected component are never sent as folders; only skill mount sources are. Robot create and update provision or configure the robot on the worker with that request's grant, and a flow start registers the root flow binding with it before the first phase is admitted. An administrator can also ask `POST /api/worker/robots/ensure`, and a robot without a worker record is otherwise refused with `worker_robot_not_provisioned`. The worker robot ID is recorded in the robot metadata and the worker's HOME is never read or bound by RoboTeam. The workspace root is never granted: a conversation without a project folder is admitted with no project grant, a project folder below the root is the only writable grant, extra folders (skills, the human-input channel) are explicit read-only grants below the root, and a task or phase that names the root as its working folder is refused with `workspace_root_not_granted` before admission. A flow start or run-now prepares every robot the flow's phases may use on the worker (provision, or configure when stale) with the starting request's own grant, right after it registers the binding and before the first phase, because a phase runs on the coordinator identity alone and cannot configure a robot; a phase that still finds its robot stale fails with a message naming the robot. Robot deletion (decision M-29) asks the worker first (`robots/delete`, deterministic operation ID, the deleting request's own administrator grant); a worker `robot_busy` refusal keeps RoboTeam's record with the message "the robot has running or unsettled work; stop it first", a lost reply is retried once under the same operation, and a robot the worker no longer has is success; Every local precondition (workstation and tasks, the manager's state, a live robot chat helper) is checked before the worker is asked and is a 409 that deletes nothing; RoboTeam removes its own record only after the worker accepted, retries it briefly if a precondition appeared in between, and otherwise answers a 409 that says deleting again finishes it (the worker's deletion is idempotent), never a 500. A worker task is `pausing` only while a stop awaits confirmation; every end path settles it as paused, failed or completed. An attempt the worker stops on its own ends `failed` with reason `inactive_timeout` (no activity from the model) or `deadline_exceeded` (maximum duration), shown as "Stopped: no activity from the model for N minutes" (the worker's minutes when its result carries them) or "Stopped: the task exceeded its maximum duration"; RoboFlow treats either as a phase failure, dispatches no successor and retries nothing. `ask-for-approval` stays refused in worker mode, because a native permission request has no worker control. The task-failure and human-input channels are the worker's (decision M-14): the spec sets `workflowExecution` for a workflow phase and `humanInput` only for a phase that allows human input; the bundled skill folders are read-only grants (by their managed-repository workspace path), the prompt names the granted path and the channel directory `/run/robo-work/channels/<channel>` that the skill scripts take as `--directory`, a `task-failed` event fails the turn as in the local engine, and a `human-input-request` event is passed to RoboFlow, which pauses the phase and holds the worker's reference and request ID. The user's answer (`POST /api/roboflow/human-input/answer`, the one exact path that mints the owner grant) is sent to the worker once as the `answer` control with that request's own grant, and only after the worker accepts it is the continuation dispatched as a new admission with a new deterministic origin; RoboTeam never resends an answer by itself.
