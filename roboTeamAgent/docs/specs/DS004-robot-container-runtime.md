## Introduction

RoboTeam combines durable robot state with disposable browser or desktop containers. Operating-system runtimes and automation executables have separate lifecycle and supply-chain boundaries.

## Core Content

The Explorer RoboTeam toolbar button must open Explorer's shared `#agent-runtime-wait` route in a new tab, watching `AchillesIDE/roboTeamAgent` and targeting `/base-agent-additional-server/roboTeamAgent/3001/`. It must not navigate directly to the dashboard while startup may still be pending. Explorer must probe the dashboard and MCP readiness and wait for stable Router routes before navigation. Disabled or failed runtimes must show the shared explanatory state and retry controls.

Administrator robot cards must offer Open → Terminal through Ploinky's existing WebTTY surface. Clicking a specific robot's card is the explicit robot choice. The card first calls the mutation-protected `POST /api/terminal-profiles/<id>/prepare`, which prepares the shared shell tools, the robot environment and the selected coding-agent cache, validates that the robot's root is the same directory projected beneath the workspace data mount, and returns the robot id, its name and only the workspace-relative root. The former `POST /api/robots/<id>/terminal` route no longer exists and answers 404. The browser then uses mutation-protected WebTTY discovery for that root with the profile `{provider: 'roboTeamAgent', id}`. It must select exactly one writable running RoboTeam row that carries a launch ID and whose discovery Ploinky bound to that robot, and hand off its opaque launch ID only in the URL fragment with no opener or referrer; the close policy of a card terminal is the WebTTY default, Keep running. Missing or ambiguous targets, and a RoboTeam row that Ploinky marks unavailable because the robot's home folder is unreachable or read-only, must fail rather than selecting another agent or Box. This operation must not start ALA or a GUI container. WebTTY owns terminal authorization, the existing container user and lifecycle.

RoboTeam serves three terminal profile endpoints on port 3001 for Explorer's Open Terminal Here dialog and for Ploinky: `GET /api/terminal-profiles` lists `{id, label}` for every robot sorted by name, `POST /api/terminal-profiles/<id>/prepare` is the card operation above, and `POST /api/terminal-profiles/resolve` answers Ploinky's profile resolution. The `IDE-plugins/terminal-profile-source` contribution lets Explorer find the list, and the `webtty.homeProfiles` declaration in `manifest.json` lets Ploinky find the resolve route. All three endpoints decide only on the signed route authentication that the service already verified for the very request. They require a signed-in user principal with the signed administrator decision, and they refuse every internal-token caller; the compatibility actor and forwarded role headers never grant anything. The resolve endpoint is read-only and fast. It accepts exactly `{version: 1, id}` and answers `{allowed: true, profile: {id, label, home: 'robots/<id>/home'}}` only when the robot exists, its root validates and its `home` child is a real directory, not a symbolic link, that is the direct child of the robot root; every other well-formed `{version: 1, id}` that cannot be proven answers `{allowed: false}`. A malformed body answers 400 and a caller without the signed administrator decision 403 (a request whose signature cannot be verified is refused earlier with 401). Ploinky, not the browser, then confines that relative path to RoboTeam's data directory and translates it for the target.

RoboTeam installs the fixed container hook `/etc/ploinky/webtty-env.sh`. Ploinky, not the hook, sets HOME and the `PLOINKY_WEBTTY_PROFILE_PROVIDER`, `PLOINKY_WEBTTY_PROFILE_ID` and `PLOINKY_WEBTTY_PROFILE_LABEL` variables from the resolved profile before the fixed interactive shell starts. With no profile variables the hook does nothing and the shell stays plain, and a profile of another provider is ignored. For `roboTeamAgent` the hook accepts only a valid robot id whose `/data/robots/<id>/metadata.json` exists and only a HOME that is the same inode as `/data/robots/<id>/home`, so any equivalent mount alias passes; it then sources the robot's regular `.roboteam-env.sh` from HOME. The hook never infers a robot from the working directory and never changes the folder the administrator chose: it records the physical working directory, sources the environment without exporting `ROBOTEAM_WORKING_DIRECTORY`, and returns to that directory if the file moved it. Any mismatch makes the hook fail, so the launch fails visibly instead of starting a shell for another robot. The generated robot shell exports `CLAUDE_CONFIG_DIR="$HOME/.claude"`, so an administrator logs Claude Code in by running `claude` in this terminal and completing its normal login. RoboTeam must not read, store or forward Claude credentials. The browser must not supply shell commands, hooks, environment values or a HOME path.

The robot's home folder is executable configuration under the authority of the target that opens it. Settings the robot wrote there (git, ssh, coding-agent configuration) can run commands when an administrator uses those tools in the terminal, and logins, history and files the administrator creates there are stored where the robot can read them. Bash saves interactive history to `$HOME/.bash_history` by default, so in a robot terminal the history lands in the robot's HOME, where the robot can read it; no Ploinky code sets `HISTFILE`, and the `/bin/sh` fallback may differ. Profile shells start with readline configured from the system file `/etc/inputrc` (`INPUTRC=/etc/inputrc`), so readline configuration the robot wrote is not loaded by the shell itself; tools the administrator runs may still load configuration from that HOME. On targets other than the RoboTeam container only HOME, INPUTRC (`/etc/inputrc`) and the three profile variables change and the robot's tool environment is not loaded; on a Ploinky Box target the shell sits beside the router, which controls every agent container. Explorer's dialog text beside the selection states the executable-configuration risk, the robot-readable logins, history and files, the Box sentence and the missing tool setup elsewhere; the INPUTRC and history facts are documented behavior, not dialog text. The disclosure documents an accepted tradeoff and is not a control. The terminal remains an administrator shell, not a robot-specific sandbox.

Manual Desktop, Browser and Terminal openings start at `$PLOINKY_WORKSPACE_ROOT/.data/roboTeamAgent/robots/<id>/`. The GUI mounts the containing workspace read-only and this robot root writable at the same absolute path. Native account data remains in its `home/` directory. The `home/` directory is mounted writable at `/config` and used directly as ALA `--home`; RoboTeam prepares no per-project copy. The home keeps ALA's `.ala/config.json` and coding-agent state, not conversation transcripts. Conversation and task history is stored in the opened folder under `.roboteam/`, not in the robot root. Existing conversation cwd values are preserved. Explicit task cwd values still override the default.

Robot metadata uses schema `roboteam-robot-v1`. `/data/robots/` contains each robot's persistent home, workspace, downloads, logs, and runtime files. Writes must be atomic and identifiers must be validated before filesystem access.

Startup must register the ordinary robot named exactly `default` only when absent, after initializing storage and before accepting HTTP requests. Registry lookup-and-create and ordinary creation/deletion must share an interprocess mutation lock, with exclusive acquisition, verified stale-owner recovery and owner-checked release. Existing default metadata and home must remain unchanged; registration must not download tools, copy credentials or start a graphical container. Corrupt or duplicate default records must fail explicitly without overwriting them. Deleting this robot is an ordinary administrator operation; recreation occurs only on a later startup.

The outer `docker.io/assistos/roboteam-agent:runtime` image must satisfy `roboteam-runtime-v6`. It provides the exact stable Podman 5.8.7 release, Node.js, npm, Bubblewrap, fuse-overlayfs, pasta, curl, Git, and nested storage configuration. Its Podman base and supported amd64 and arm64 platform members must be immutable digest-pinned inputs; rolling, development and release-candidate Podman bases are forbidden. Before installation and every service start, its `roboteam-podman-init` helper must establish a private, 2 GiB-limited tmpfs at `/var/lib/roboteam-podman`, without adding capabilities. Failure must stop startup. The overlay configuration must keep the persistent image store at `/data/podman/images`, use graphroot `/var/lib/roboteam-podman/storage` and runroot `/var/lib/roboteam-podman/run` on that tmpfs, enable `transient_store`, and use `force_mask="0700"`. This avoids unsupported FUSE-on-FUSE writable layers and conmon state on macOS virtiofs while allowing protected directories and merged-/usr links to be unpacked there. Tmpfs allocates memory on demand; robot homes, workspace files, images and tool generations remain persistent. GUI images must pre-create `/install` and `/opt/roboteam-tools`, the exact bind targets used by ToolCache. Deployment smoke testing must exercise writable directory creation and a complete GUI start with workspace and tool-generation mounts, GUI HTTP 200, Chromium CDP and MCP responses, without executing a workflow. The image must not bake in Codex, OpenCode, Pi, computer-use-linux, Supergateway, or Playwright MCP.

Installation must validate `/opt/roboteam-runtime/contract-v6` with content `roboteam-runtime-v6`, successful `podman --version` output equal to `podman version 5.8.7`, required commands, npm execution and `/opt/roboteam-runtime/storage.conf` before preparing data or the terminal hook. The immutable Podman stable base is recorded in the image source lock. Installation must require executable `/usr/local/bin/roboteam-podman-init` and invoke it only after all prerequisite checks, before data preparation, the terminal hook and the SQLite probe. `RuntimeManager.initialize` must await the same absolute helper through its process implementation with a 30-second timeout before Podman info or managed cleanup. Helper errors are fatal, with no fallback or configurable helper path. The producer helper mounts absent `/var/lib/roboteam-podman` as tmpfs with `size=2g,mode=0700,nosuid,nodev`, reuses existing tmpfs without resetting storage, and rejects symbolic links or existing non-tmpfs mounts.

The manifest `agent` command must be `exec sh /code/scripts/startAgent.sh`. Ploinky runs it after the profile `install` hook as `<shell> -c "cd <cwd> && sh /code/scripts/install.sh && exec sh /code/scripts/startAgent.sh"`, under its agent entrypoint. The `exec` makes the start script the main command that receives Ploinky's TERM, whichever shell Ploinky selects. The start script runs AgentServer and the RoboTeam service as children. When either one exits by itself, even cleanly, the script stops the other and exits non-zero. On TERM, the script ignores further HUP, INT and TERM, sends one TERM to each child and waits for both. It exits 0 only when both exit 0; otherwise it exits with the first non-zero status, checking the service before AgentServer. Ploinky's targeted restart, `ploinky restart roboTeamAgent`, accepts exit 0 as the acknowledgement that the drain completed and refuses every other result. Ploinky does not escalate to SIGKILL, and it refuses a drain that outlasts its bounded wait. The drain runs in the existing container, so a container started with an earlier start script keeps that script's TERM handling; this behavior is adopted by recreating the container, not by a targeted restart. The service's TERM handler closes the HTTP listener and RoboFlow. It sends TERM to the processes of queued, starting and running robot tasks, removes retained GUI containers, closes Soul Gateway connections and exits 0. A rejected shutdown step ends the service non-zero. GUI container removal errors are ignored, so exit 0 does not prove that every GUI container was removed. The start script installs its TERM handler only after both child PIDs are recorded. A TERM that arrives earlier, or before the service registers its own handler, ends that process with the signal status, which fails the drain. AgentServer fails in-flight tool calls and waits for its tool workers and task queue. A restart while tool calls or robot tasks run can therefore outlast Ploinky's wait.

The sibling image-definition repository must provide a local development installer with `agent`, `desktop`, `browser`, and `all` targets. It must build in the exact owned Ploinky Box, stream GUI images into the single running managed RoboTeam container's nested engine without a registry or host engine socket, reject ambiguous container ownership, and reinstall RoboTeam after activation. This path is native-architecture development tooling; multiarchitecture output remains a publication responsibility.

The manifest must retain `containerSecurity.nestedPodman: true`, MCP port 7000, authenticated service port 3001, `/data` persistence, and the current runtime-only desktop and browser image defaults. A workstation started with a proxy lease from proxyAgent uses `--network pasta:-T,3128:<relay port>` and mounts the managed Chromium proxy policy read-only; a proxied Browser container is created, initialized and firewalled before it starts, as defined in DS008. Every inner Podman run must use `--ipc=none` because creating a nested mqueue mount is not admitted by Ploinky's bounded capability. GUI containers must restore their required shared memory with a private `/dev/shm` tmpfs, use Podman's `k8s-file` log driver so `podman logs` works without a systemd journal in the outer container, and expose Selkies port 3000 and MCP bridge port 8100 only through random outer-loopback mappings. No host container-engine socket may be mounted.

`ToolCache` must begin preparing all shared tools at every RoboTeam service startup, after nested Podman initialization and HTTP listening. Preparation must run in the background so downloads do not consume the service readiness budget. Shell tools (Codex, OpenCode, Pi and Claude Code), desktop tools (computer-use-linux and Supergateway), and browser tools (Playwright MCP) must prepare concurrently through the same cache instance used by runtime requests. Requests arriving during preparation must share the pending work. Startup must log readiness or failure for each family; one failed family must not stop the service or prevent other families from becoming available. Failed preparation must remain retryable on demand. Startup must not create a robot GUI session; temporary installation and validation containers may fetch missing GUI images.

`ToolCache` must resolve current upstream versions during startup preparation and on demand after the bounded refresh interval, unless an operator pin is set. An operator may pin Codex, OpenCode, Pi or Claude Code to one exact version with `ROBOTEAM_CODEX_VERSION`, `ROBOTEAM_OPENCODE_VERSION`, `ROBOTEAM_PI_VERSION` or `ROBOTEAM_CLAUDE_VERSION`, declared in the manifest `env` list. An unset or empty variable means unpinned. A pin must be a canonical semantic version, `MAJOR.MINOR.PATCH` with an optional `-prerelease` suffix, with no leading zeros in numeric identifiers, no empty prerelease identifiers, no build metadata, `v` prefix, range, tag such as `latest`, or whitespace, and at most 64 characters. Any other value makes the `ToolCache` constructor throw `invalid ROBOTEAM_<AGENT>_VERSION`. Because the service and every robot CLI start construct a `ToolCache`, an invalid pin stops the RoboTeam service from starting and fails robot CLI starts, so a misconfiguration never silently unpins. A pinned agent skips the `npm view` lookup, installs exactly that version, and keeps the same `{package, version, runtime}` generation identity and the same launcher selection. A pinned agent must never fall back to a different version: only a stamped generation whose descriptor and stamp both record the pinned version may be used. Codex, OpenCode, Pi, Claude Code (`@anthropic-ai/claude-code`, executable `claude`), Supergateway, and Playwright MCP resolve through their official npm packages; computer-use-linux resolves from its current GitHub release for the active architecture. Host npm and cached-tool probes must not inherit Ploinky's `NODE_OPTIONS` symlink-preservation flags. Candidates must be installed in unique staging directories, probed before activation, recorded with exact resolved versions, and activated by replacing `current.json` atomically. The downloaded computer-use-linux bytes must have a recorded SHA-256 digest and must match an upstream asset digest when one is available.

Prepared generations live under `/data/tool-cache`. Concurrent preparation for the same tool family must coalesce in one process. A failed lookup, download, installation, or validation may use only the last stamped valid generation. If no valid generation exists, the operation must fail clearly. Exact generations must remain available while live containers can still mount them.

OpenCode installs `@opencode-ai/plugin` into `~/.config/opencode` of every robot home the first time it runs there (about 3,600 files), and every OpenCode process started meanwhile waits for it. RoboTeam prepares that dependency tree once per exact OpenCode version as the tool-cache bundle `opencode-plugin`: an `npm install --ignore-scripts` of `@opencode-ai/plugin@<the cached OpenCode version>` that keeps `package.json`, `package-lock.json` and `node_modules`. Its generation name derives from the version, platform, architecture and Node runtime, so another OpenCode version never reuses it, and it never falls back to a generation of another version. Startup preparation installs it after the coding-agent tools, then seeds every OpenCode robot. Task start, GUI container start, the Terminal and model listing wait for the template and seed the robot's home before OpenCode runs (this replaces OpenCode's own self-install, about a minute under load); robot creation answers first and schedules the seed in the background, and service startup prepares shells and sockets before it listens and seeds only afterwards, so the copy (seconds per home) never delays readiness. One seed (or shell preparation) per home runs at a time, and a task that starts sooner shares it. Deleting a robot waits for the one in flight, which checks for the deletion before it moves anything into the home and otherwise removes its own staging and reports `aborted`; anything queued afterwards does nothing, so the removal never races a copy. Only robots whose coding agents include OpenCode are seeded, even though the Terminal can start any agent; OpenCode installs for itself in the others; a spawned copilot catalog process never seeds and never runs npm, because it runs outside the server's per-robot lock and a copy there could race the deletion of the robot. Seeding copies the template into the home (never a link, because the sandbox sees the home at another path and a later OpenCode install must not write into the shared cache), writes `package.json` and the lock first and renames `node_modules` into place last, and tolerates concurrent preparation of one home. OpenCode skips its own installation when `node_modules` exists and the lock lists the dependency, but it never compares versions, so seeding also replaces a managed install whose plugin version differs from the cached OpenCode. A home whose manifest declares other dependencies, or that holds `node_modules` without a manifest, is left to OpenCode; links where the seed would read or write are refused. Without a template for the exact version, OpenCode installs for itself as before. Projects that contain their own `.opencode` directory still make OpenCode install into it on first use; RoboTeam does not write into workspaces.

Desktop and Browser containers mount their mode-specific tool generation read-only at `/opt/roboteam-tools`. They mount every coding-agent generation and the matching immutable shell directory at their cache paths, read-only. The full shared cache root must not be mounted. PATH prepends that shell directory while retaining LinuxServer's `/lsiopy/bin`. The shell directory contains relative links to complete validated coding-agent generations and is cached independently for each set of agents. Robot creation prepares configuration directories and shell initialization; repeat preparation preserves user profile content. Desktop, Browser and terminal shells expose every coding agent, whatever the robot's selection, so an administrator can log in to any agent before selecting it. Robot conversations and tasks give ALA only the selected agents. Persistent Codex, OpenCode, Pi, Claude Code and XDG state remain in the robot home regardless of selection. GUI containers receive `CLAUDE_CONFIG_DIR=/config/.claude`, the copilot engine passes `CLAUDE_CONFIG_DIR=<robot home>/.claude` to ALA, and the robot shell uses `$HOME/.claude`; all three name the same directory, which holds the Claude Code login, settings and native sessions. ALA runs separately in the outer runtime with the requested cwd and robot-specific home. Because the agent's shell is not the desktop, every Desktop task's system instructions say so, tell it to inspect the desktop only through the computer-use tools, and name the desktop's Chromium; each Desktop start also writes an executable `Desktop/chromium.desktop` launcher for `roboteam-open-browser` into the robot home, so Chromium appears as a desktop icon. Chromium is not started automatically.

Robot metadata stores `codingAgents`, a nonempty list drawn from `codex`, `opencode`, `pi` and `claude`, in that order. All robots share one Claude Code installation from the tool cache, exposed to ALA through `CLAUDE_BIN`. Creation defaults to `['opencode']`, including startup creation of default. Existing metadata without this field retains all four without rewriting the record. The dashboard creation form has no coding-agent selector and uses the OpenCode default. Existing robot cards show the configured agent names and provide an administrator-only Coding agent button that opens a single-selection dialog. The server accepts any nonempty subset through creation and `PATCH /api/robots/<id>/coding-agents`; it must not impose the dashboard's single-selection limit. Updates require a stopped workstation and no unfinished tasks. New chats and tasks use the saved selection; existing conversations retain their captured environment and native backend. Users must reopen them after changing the setting. Saved conversations must not switch backend silently: a conversation whose native agent is no longer enabled for the robot reports "This conversation used <agent>, which is not enabled for this robot. Create a new session." when it is opened or used, and WebChat stays available so a new session can be created. A retained GUI session is reusable only when its selected agents also match.

The robot's ALA config, `<robot home>/.ala/config.json`, is the single source of the robot's coding agent, models and efforts: `{ "codingAgent": "opencode", "models": { "<agent>": "<model>" }, "efforts": { "<agent>": "<effort>" } }`, one model and one effort per coding agent, with no version, priority or web-search fields. Robot shell preparation writes `codingAgent` as the robot's first selected agent and, for OpenCode robots, the free model `opencode/glm-5.3-flash-free` served by OpenCode's native provider unless an OpenCode model is already set. `PATCH /api/robots/<id>/coding-agents` saves the new first agent as `codingAgent` and keeps the models and efforts chosen for other agents. `codingAgents` in the robot metadata still decides which agent binaries RoboTeam installs. A config ALA would reject is left untouched for ALA to report.

RoboTeam must report, for each robot, whether its home holds a login for each of the four coding agents, without reading a credential value and without running a CLI. The detection is ALA's own, the one behind `ala status --home <robot home>`: `server/coding-agent-status.mjs` loads `detectCodingAgentLogin` and `codingAgentLoginFiles` from ALA's `src/coding-agents/logins.mjs` through `resolveAlaInstallation`, with an environment that points `HOME`, `CODEX_HOME`, `XDG_*`, `PI_CODING_AGENT_DIR` and `CLAUDE_CONFIG_DIR` at the robot's home and carries no credential variable of the RoboTeam server, so a server-wide key never counts as a robot's login. It checks only where each CLI keeps its login: Codex is logged in when `~/.codex/auth.json` holds any filled field besides `last_refresh` and `auth_mode`; OpenCode when `~/.local/share/opencode/auth.json` holds any typed provider entry or its `opencode.db` has an active `account_state`, an active `control_account` or any `credential` row; Pi when `~/.pi/agent/auth.json` holds an `api_key` entry with a key or environment mapping or an `oauth` entry with an access token; Claude Code when `~/.claude/.credentials.json` holds a `claudeAiOauth` access or refresh token or `~/.claude/.claude.json` holds a `primaryApiKey`. Only bounded regular files are opened, SQLite is opened read-only, and an unreadable store counts as no login. Results are cached per file by modification time and size. When ALA cannot be loaded or has no `logins.mjs`, the listing still answers and reports every login as absent, and the failure is logged once; `resolveAlaInstallation` treats that module as optional, so task execution never depends on it. A reported login may be expired or revoked, because validity can only be established by the CLI; credentials supplied through environment variables or an operating-system keyring are not detected, and RoboTeam supplies neither to robots. OpenCode runs through Soul Gateway without any login, so the absence of an OpenCode login does not mean the robot cannot run OpenCode. `GET /api/robots` adds `codingAgent`, the agent ALA uses for the robot (the configured `codingAgent` when the robot has it enabled, otherwise its first enabled agent), to every robot, and `codingAgentLogins` `{ codex, opencode, pi, claude }` as booleans only for an administrator listing.

Coding-agent selection configures the managed tool environment and mounts; it is not an access-control boundary against manually installed programs or arbitrary user commands. ALA's discovery and selection algorithm remains unchanged. Unselected managed cache paths and inherited binary overrides must be removed from the execution environment. Robot account files and unrelated user configuration must not be deleted.

RoboTeam must run in Ploinky global mode for workspace access. ALA must be declared through the manifest's `link-install` array using its Git repository URL, not as an npm dependency. Ploinky reuses an existing workspace checkout identified by Git origin, or clones it when absent, without pulling or resetting existing work. `/Agent/linked/AdvancedLanguageAgent` must be a symbolic link to the workspace repository mounted read-write for the global robot manager. Task execution, Copilot and skill discovery must resolve the real `bin/ala.mjs` through that link. Local source tests may use the sibling workspace checkout, and an explicit command override remains available. The installer must validate the ALA APIs used by Copilot before starting the service. Data and cache paths, image references, the six-hour tool refresh interval, the service's UTC timezone and public UI prefix must be internal constants, not manifest environment options. A proxied GUI container receives the timezone and locale of its proxy's exit address instead of that UTC constant, as defined in DS008. RoboTeam must pass the Ploinky-selected AgentLib path to ALA rather than installing another AgentLib copy. The fixed eight-GUI-robot limit applies only to retained graphical sessions; independent CLI conversations remain uncapped. Constructor and function injection may be retained for tests. Ploinky's Node.js symlink-preservation options must not change the base of ALA's relative imports. When ALA exits unsuccessfully, RoboTeam must preserve its bounded output tail and include that diagnostic in the internal task error.

Only active sessions and task queues are retained in memory. A robot may retain at most one GUI session. That session is reusable only for the same mode and resolved cwd. A queued request with another mode or cwd must wait for the active ALA task, remove the idle retained container by its exact managed name, and create its replacement with the new `/workspace` mount. A Simple task must leave a retained GUI session unchanged. A GUI session becomes `running` only after Selkies accepts its published connection and the MCP endpoint returns an HTTP response; the outer Pasta listener alone is not readiness evidence. Initialization may remove stale containers only when RoboTeam's managed label proves ownership. Failure and stop must remove the exact owned container. Restart does not automatically resume interrupted work or queued requests whose native Ploinky task was interrupted.

### Live Sessions IPC in the container

The RoboTeam service creates the Live Sessions socket at `/dev/shm/roboteam-live/registry.sock` on the outer container's private `/dev/shm`: the directory with mode 0700 and the socket with mode 0600, both exclusively. It never adopts, replaces or unlinks an existing path. Copilot processes started with `ploinky cli` shared the service's uid and mount namespace and reached a diagnostic listener at that path on a deployed candidate; WebChat copilots start through the same container command path and are expected to behave alike, which is not yet observed at runtime. Robot GUI containers do not mount that `/dev/shm`. The socket's invisibility from ALA sandboxes was observed with a diagnostic harness and listener (a fixture coding-agent binary and an extra test bind); the same check against the production listener is pending. Because ALA binds the directory of a coding-agent binary without a reserved-path guard, a robot that falls back to a binary in its writable home could project `/dev/shm` into a later sandbox; this residual risk stays open until investigated. An IPC startup failure is logged and leaves the HTTP service and in-process Live Sessions running. A container restart starts with a fresh `/dev/shm`, so the socket is created again. Robot task execution records keep their owner principal with an HMAC whose key derives from the per-start internal token, because robot containers can write those records. DS008 owns the protocol and ownership rules.

### Runtime tools for other agent containers

The tool cache (`/data/tool-cache`, visible to every global-mode agent as `<workspace>/.data/roboTeamAgent/tool-cache`) also holds what a phase needs inside another agent's container (DS006), each as a cache generation with `stamp.json` and `current.json` and the last valid generation as fallback (`server/runtime-bundle.mjs`): `bwrap` is a fully static Bubblewrap 0.11.0, built once in RoboTeam's nested Podman on a digest-pinned Alpine from the checksum-pinned upstream release and checked to have no dynamic dependencies; `ala` is a copy of ALA's `bin`, `src` and `package.json`, made only when ALA's package is outside the workspace, because the link-installed workspace checkout is otherwise used directly. Node.js is not shipped: ALA and the coding agents run on the `node` of the target agent's image. They are prepared when such a phase starts, not at agent start.

### Global workflow storage

RoboFlow uses embedded node:sqlite at /data/roboflow/roboflow.sqlite in the RoboTeam data volume. Installation probes SQLite support. Global execution metadata, and saved workflow definitions as JSON files in /data/roboflow/flows, are the exception to folder-scoped conversation storage; logs and final responses remain in the execution folder. See DS007 for run snapshots, matching, GUI queueing and restart recovery.
