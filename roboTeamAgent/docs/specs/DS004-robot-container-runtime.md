title: DS004-robot-container-runtime
summary: Defines persistent robot storage, runtime-only GUI images, current-version tool caching, and bounded nested Podman lifecycle.

## Introduction

RoboTeam combines durable robot state with disposable browser or desktop containers. Operating-system runtimes and automation executables have separate lifecycle and supply-chain boundaries.

## Core Content

The Explorer RoboTeam toolbar button must open Explorer's shared `#agent-runtime-wait` route in a new tab, watching `AchillesCLI/roboTeamAgent` and targeting `/base-agent-additional-server/roboTeamAgent/3001/`. It must not navigate directly to the dashboard while startup may still be pending. Explorer must probe the dashboard and MCP readiness and wait for stable Router routes before navigation. Disabled or failed runtimes must show the shared explanatory state and retry controls.

Administrator robot cards must offer Open → Terminal through Ploinky's existing WebTTY surface. RoboTeam must validate that the selected robot's root is the same directory projected beneath the workspace data mount and return only its workspace-relative directory. The browser must use mutation-protected WebTTY discovery, select exactly one writable running RoboTeam target, and hand off its opaque launch ID only in the URL fragment with no opener or referrer. Missing or ambiguous targets must fail rather than selecting another agent or Box. This operation must not start ALA or a GUI container. WebTTY owns terminal authorization, the existing container user and lifecycle. The mutation-protected POST terminal-preparation endpoint must prepare the shared shell tools and robot environment. RoboTeam installs the fixed container hook `/etc/ploinky/webtty-env.sh`, which recognizes robot-root cwd values and legacy home paths and sets HOME and coding-agent configuration before the fixed interactive shell starts. The browser must not supply shell commands, hooks or environment values. The terminal remains an administrator shell, not a robot-specific sandbox.

Manual Desktop, Browser and Terminal openings start at `$PLOINKY_WORKSPACE_ROOT/.data/roboTeamAgent/robots/<id>/`. The GUI mounts the containing workspace read-only and this robot root writable at the same absolute path. Native account data remains in its `home/` directory. The `home/` directory is mounted writable at `/config` and used directly as ALA `--home`; RoboTeam prepares no per-project copy. Conversation and task history is stored in the opened folder under `.achilles-cli/`, not in the robot root. Existing conversation cwd values are preserved. Explicit task cwd values still override the default.

Robot metadata uses schema `roboteam-robot-v1`. `/data/robots/` contains each robot's persistent home, workspace, downloads, logs, and runtime files. Writes must be atomic and identifiers must be validated before filesystem access.

Startup must register the ordinary robot named exactly `default` only when absent, after initializing storage and before accepting HTTP requests. Registry lookup-and-create and ordinary creation/deletion must share an interprocess mutation lock, with exclusive acquisition, verified stale-owner recovery and owner-checked release. Existing default metadata and home must remain unchanged; registration must not download tools, copy credentials or start a graphical container. Corrupt or duplicate default records must fail explicitly without overwriting them. Deleting this robot is an ordinary administrator operation; recreation occurs only on a later startup.

The outer `docker.io/assistos/roboteam-agent:runtime` image must satisfy `roboteam-runtime-v4`. It provides Podman 6, Node.js, npm, Bubblewrap, fuse-overlayfs, pasta, curl, Git, and nested storage configuration. The image must not bake in Codex, OpenCode, Pi, computer-use-linux, Supergateway, or Playwright MCP.

The sibling image-definition repository must provide a local development installer with `agent`, `desktop`, `browser`, and `all` targets. It must build in the exact owned Ploinky Box, stream GUI images into the single running managed RoboTeam container's nested engine without a registry or host engine socket, reject ambiguous container ownership, and reinstall RoboTeam after activation. This path is native-architecture development tooling; multiarchitecture output remains a publication responsibility.

The manifest must retain `containerSecurity.nestedPodman: true`, MCP port 7000, authenticated service port 3001, `/data` persistence, and the current runtime-only desktop and browser image defaults. Every inner Podman run must use `--ipc=none` because creating a nested mqueue mount is not admitted by Ploinky's bounded capability. GUI containers must restore their required shared memory with a private `/dev/shm` tmpfs, use Podman's `k8s-file` log driver so `podman logs` works without a systemd journal in the outer container, and expose Selkies port 3000 and MCP bridge port 8100 only through random outer-loopback mappings. No host container-engine socket may be mounted.

`ToolCache` must begin preparing all shared tools at every RoboTeam service startup, after nested Podman initialization and HTTP listening. Preparation must run in the background so downloads do not consume the service readiness budget. Shell tools (Codex, OpenCode and Pi), desktop tools (computer-use-linux and Supergateway), and browser tools (Playwright MCP) must prepare concurrently through the same cache instance used by runtime requests. Requests arriving during preparation must share the pending work. Startup must log readiness or failure for each family; one failed family must not stop the service or prevent other families from becoming available. Failed preparation must remain retryable on demand. Startup must not create a robot GUI session; temporary installation and validation containers may fetch missing GUI images.

`ToolCache` must resolve current upstream versions during startup preparation and on demand after the bounded refresh interval. Codex, OpenCode, Pi, Supergateway, and Playwright MCP resolve through their official npm packages; computer-use-linux resolves from its current GitHub release for the active architecture. Host npm and cached-tool probes must not inherit Ploinky's `NODE_OPTIONS` symlink-preservation flags. Candidates must be installed in unique staging directories, probed before activation, recorded with exact resolved versions, and activated by replacing `current.json` atomically. The downloaded computer-use-linux bytes must have a recorded SHA-256 digest and must match an upstream asset digest when one is available.

Prepared generations live under `/data/tool-cache`. Concurrent preparation for the same tool family must coalesce in one process. A failed lookup, download, installation, or validation may use only the last stamped valid generation. If no valid generation exists, the operation must fail clearly. Exact generations must remain available while live containers can still mount them.

Desktop and Browser containers mount their mode-specific tool generation read-only at `/opt/roboteam-tools`. They mount only the robot's selected coding-agent generations and the matching immutable shell directory at their cache paths, read-only. The full shared cache root must not be mounted. PATH prepends that shell directory while retaining LinuxServer's `/lsiopy/bin`. The shell directory contains relative links to complete validated coding-agent generations and is cached independently for each selected set. Robot creation prepares configuration directories and shell initialization; repeat preparation preserves user profile content. Opening a Desktop, Browser or terminal selects the same managed tools as robot conversations. Persistent Codex, OpenCode, Pi and XDG state remain in the robot home regardless of selection. ALA runs separately in the outer runtime with the requested cwd and robot-specific home.

Robot metadata stores `codingAgents`, a nonempty list drawn from `codex`, `opencode` and `pi`. Creation defaults to `['codex']`, including startup creation of default. Existing metadata without this field retains all three without rewriting the record. The dashboard creation form has no coding-agent selector and uses the Codex default. Existing robot cards show the configured agent names and provide an administrator-only Coding agent button that opens a single-selection dialog. The server accepts any nonempty subset through creation and `PATCH /api/robots/<id>/coding-agents`; it must not impose the dashboard's single-selection limit. Updates require a stopped workstation and no unfinished tasks. New chats, tasks and terminals use the saved selection; existing conversations retain their captured environment and native backend. Users must reopen them after changing the setting. Saved conversations must not switch backend silently. A retained GUI session is reusable only when its selected agents also match.

Coding-agent selection configures the managed tool environment and mounts; it is not an access-control boundary against manually installed programs or arbitrary user commands. ALA's discovery and selection algorithm remains unchanged. Unselected managed cache paths and inherited binary overrides must be removed from the execution environment. Robot account files and unrelated user configuration must not be deleted.

RoboTeam must run in Ploinky global mode for workspace access. ALA must be declared through the manifest's `link-install` array using its Git repository URL, not as an npm dependency. Ploinky reuses an existing workspace checkout identified by Git origin, or clones it when absent, without pulling or resetting existing work. `/Agent/linked/AdvancedLanguageAgent` must be a symbolic link to the workspace repository mounted read-write for the global robot manager. Task execution, Copilot and skill discovery must resolve the real `bin/ala.mjs` through that link. Local source tests may use the sibling workspace checkout, and an explicit command override remains available. The installer must validate the ALA APIs used by Copilot before starting the service. Data and cache paths, image references, the six-hour tool refresh interval, UTC timezone and public UI prefix must be internal constants, not manifest environment options. RoboTeam must pass the Ploinky-selected AgentLib path to ALA rather than installing another AgentLib copy. The fixed eight-GUI-robot limit applies only to retained graphical sessions; independent CLI conversations remain uncapped. Constructor and function injection may be retained for tests. Ploinky's Node.js symlink-preservation options must not change the base of ALA's relative imports. When ALA exits unsuccessfully, RoboTeam must preserve its bounded output tail and include that diagnostic in the internal task error.

Only active sessions and task queues are retained in memory. A robot may retain at most one GUI session. That session is reusable only for the same mode and resolved cwd. A queued request with another mode or cwd must wait for the active ALA task, remove the idle retained container by its exact managed name, and create its replacement with the new `/workspace` mount. A Simple task must leave a retained GUI session unchanged. A GUI session becomes `running` only after Selkies accepts its published connection and the MCP endpoint returns an HTTP response; the outer Pasta listener alone is not readiness evidence. Initialization may remove stale containers only when RoboTeam's managed label proves ownership. Failure and stop must remove the exact owned container. Restart does not automatically resume interrupted work or queued requests whose native Ploinky task was interrupted.
