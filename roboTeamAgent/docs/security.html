Documentation / Security

Security

Ploinky authenticates the only public route; RoboTeam enforces administrator-only lifecycle mutations and keeps nested runtime ports private.

Identity and exposure

AgentServer/MCP uses port 7000; the authenticated HTTP and WebSocket route targets port 3001. Requests require Router-injected identity and mutations retain Ploinky proof enforcement. Inner Podman, random Selkies mappings, MCP bridge mappings, and browser CDP remain loopback-only and are not public.

Administrator-only HTTP operations require an admin role and reject any actor with a guest role. Role comparison trims whitespace and ignores case. Usernames, display names and the local:admin id grant no administrator authority. The local CLI supplies user and admin roles. Internal-token calls need forwarded non-guest administrator roles for these operations.

Beyond administrator checks, every route on the service port except internal-token calls, GET /status, the AgentServer passthrough (/mcp, /task, /getTaskStatus, /health) and GET /api/robots needs a Router-signed request from a direct, non-guest user who holds admin or the explorer.access capability. This covers pages, static assets, the robot session proxy, every API route and the session WebSocket. The request is verified once over its exact method, path, query and body. A missing, unsigned, tampered or replayed request returns 401, a missing verifier returns 503, and a non-entitled caller such as a selfRegistered account returns 403 Explorer access permission is required to use RoboTeam (…to use RoboFlow under /api/roboflow). The robot listing keeps Explorer access is required to list robots.

Nested authority

Ploinky admits containerSecurity.nestedPodman and supplies only SYS_ADMIN, NET_ADMIN, /dev/fuse, /dev/net/tun, label disablement, and a fixed seccomp profile. The outer container remains on the managed network and does not use --privileged.

The current nested runtime cannot mount ALA's private procfs inside another user namespace. ALA first probes its normal user-namespace path, then may use the outer container's admitted mount capability to create only a private PID namespace and procfs. Bubblewrap applies --cap-drop ALL before Codex starts, so Codex does not inherit SYS_ADMIN or another outer capability. Filesystem and environment isolation remain active, and ALA fails closed when it cannot create a private procfs by either path. This fallback removes one additional UID namespace; it does not remove the outer Podman boundary or the ALA Bubblewrap boundary.

SYS_ADMIN remains powerful, so this is a controlled experiment rather than a hostile-tenant sandbox. Host-level or microVM isolation is required for hostile workloads.

Persistent credentials

A robot home can contain cookies, sessions, tools, and documents. Treat /data and backups as credential-bearing storage. Stopping does not revoke sessions or erase data.

Runtime tool supply chain

Current Codex and MCP releases are external npm and GitHub inputs. RoboTeam installs candidates in unique staging directories, records exact resolved versions and the computer-use-linux digest, probes them before activation, and mounts active generations read-only. Failed updates retain the last stamped generation; a first use without any valid generation fails instead of activating an unproven candidate.

Cleanup

No host Podman socket, public inner API, or broad prune operation is exposed. Authenticated administrators may delete a stopped robot through robot_delete; container cleanup targets exact managed names and labels.

Startup may create the ordinary workspace robot named default only if absent. This grants no new external authority: authenticated administrator create/delete, internal task access and authenticated GUI routing remain unchanged. The robot can be deleted under normal guards and is recreated only on a later startup; no task invocation receives automatic administration or copied credentials.

Robot views

Robot list, creation, coding-agent and run responses show repository sources and the task working directory in full only to a verified administrator. Everyone else sees a credential-free remote URL, or nothing for local paths and unrecognized values, and a workspace-relative working directory. Stored robot configuration is not changed.

Live Sessions

Live Sessions routes run under the same signed-entitlement gate and refuse every internal-token caller with 403, even with forwarded or signed user headers. Authority is only the request's signed principal and signed administrator decision. A run the viewer may not see answers 404. Only its verified owner may message a run; the owner or an administrator may stop it. Runs without a verified owner are visible to administrators only, labelled system or owner unverified. Transcripts come only from server-bound run metadata, never from container logs or caller paths. Streams end after 25 minutes and reconnect with a fresh authorization.

Copilot processes publish over a 0600 Unix socket on the container's private /dev/shm. Its invisibility from ALA sandboxes was observed with a diagnostic harness and listener; the same check against the production listener is pending. The service accepts an owner only from a Router-signed WebChat token that it verifies itself, and it ignores any identity a publisher declares. Residual risk: ALA binds the directory of a coding-agent binary without a reserved-path guard, so a robot falling back to a binary in its writable home could project /dev/shm into a later sandbox. This stays open until investigated. See DS010.

Terminal profiles

The terminal profile endpoints GET /api/terminal-profiles, POST /api/terminal-profiles/<id>/prepare and POST /api/terminal-profiles/resolve serve Explorer's Open Terminal Here dialog and Ploinky's profile resolution. They decide only on the signed route authentication already verified for the request: a signed-in user: principal with the signed administrator decision. They refuse every internal-token caller and never consult the compatibility actor or forwarded role headers. Prepare also requires the browser mutation proof, and resolve is read-only and answers {allowed: false} for a well-formed request it cannot prove; a malformed body answers 400 and a caller without the signed administrator decision 403 (a request whose signature cannot be verified is refused earlier with 401). The selected robot's home folder becomes HOME for a shell on the target the administrator chose. It is executable configuration under that target's authority, and logins, history and files the administrator creates there are readable by the robot. Explorer discloses this beside the selection; the disclosure is not a control, and the terminal remains an administrator shell, not a sandbox. Robots stay workspace identities, not a tenant boundary.

Conversation skill settings

RoboTeam's Conversation skills page and its GET and PATCH api/robots/<robotId>/conversations/<sessionId>/skills endpoints run under the authenticated Router route. Anonymous requests receive 401 and the internal-token actor receives 403. Robots are workspace-owned and conversations have no owner, so any Explorer-entitled signed-in user who names a robot and one of its registered conversations may change that conversation's selection, which is no wider than the list_achilles_skills and set_achilles_skill_enabled tools. The endpoints take no query parameters and no directory, accept only identity, enabled and policyVersion, never create or change robot defaults, and refuse a conversation bound to another robot. Browser mutations rely on the Router's mutation proof and exact Origin check.

Workflow decision callbacks

An opted-in workflow execution receives a private HTTP Unix socket and random execution-scoped capability. Its only operation submits a human-input question for that runtime task. It cannot select another flow or call the general RoboTeam API. The channel closes when the process exits, and its files are removed. User answers use the existing Router-authenticated port-3001 service and record the verified actor. No Ploinky credential is added to the callback context.

Private project history

RoboTeam supplies ALA with --ignore for the absolute cwd/.roboteam directory on every execution and continuation. The coding agent sees an empty read-only directory, including through exposed mount aliases. RoboTeam and the outer ALA process retain access outside the sandbox to persist sessions, transcripts and logs. This requires an ALA version that supports --ignore.
