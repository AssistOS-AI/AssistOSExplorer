Documentation / Security

Security

RoboTeam relies on Ploinky for public authentication and routing, then applies profile ownership, filesystem permissions, process identity, internal-token checks, and path validation inside the agent.

Public access

All application, API, noVNC asset, and desktop WebSocket traffic uses the authenticated agent-port route. The VNC server and websockify listeners bind only inside the agent container. They must not be published as direct host ports.

State-changing browser calls obtain a route- and session-bound Ploinky browser mutation proof. The Router validates that proof before the request reaches RoboTeam. WebSocket upgrades use the authenticated Ploinky session and carry Router-injected identity metadata.

Ownership and isolation

Every robot profile records one owner user id. List, start, stop, status, desktop page, and WebSocket operations require the same owner. The server returns a generic not-found response when a different user names the profile.

Each profile receives a unique numeric Linux UID. Its root, home, workspace, browser, downloads, log, and runtime directories use restrictive modes and ownership. Desktop processes run with that UID. This prevents one ordinary profile desktop process from reading another profile's private files through normal Unix discretionary access controls.

The RoboTeam control service runs as the trusted manager and can access every profile. The agent container shares one kernel and is not a virtual-machine boundary. Container compromise, root execution inside the desktop, or a kernel vulnerability can bypass per-profile Unix permissions.

Chromium runs as the profile UID with `--no-sandbox` for compatibility with the nested container runtime. The entire profile desktop must therefore be treated as one trust domain. Opening untrusted content or executing untrusted code in that desktop is outside the isolation guarantee; stronger containment belongs at the task-runtime or per-profile-container boundary.

Authenticated browser state

Chromium cookies, tokens, local storage, and saved session data are sensitive credentials. They persist in the profile browser directory and inherit the protection of the Ploinky data volume and profile filesystem permissions. RoboTeam does not provide application-level encryption at rest, credential rotation, backup encryption, or recovery-key management.

Operators must protect the workspace data volume and backups as credential stores. A profile should be stopped when it is not needed, but stopping the processes does not revoke website sessions.

Internal service calls

MCP command processes cannot impersonate an arbitrary browser user. They receive the authenticated user id from AgentServer metadata and send it to the loopback service with the generated `ROBOTEAM_INTERNAL_TOKEN`. The service compares that token without logging it. The generated token, Ploinky agent secret, Router tokens, cookies, and authentication headers must never enter source control or diagnostic output.

Operational limits

RoboTeam caps concurrent desktops to bound resource use. Profile creation serializes UID allocation. Desktop startup fails closed when a required executable, virtual display, VNC listener, or WebSocket bridge does not become ready. A critical desktop process exit triggers cleanup of the associated session.
