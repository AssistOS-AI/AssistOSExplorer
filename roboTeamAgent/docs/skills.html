Skills and skillsets

Give each robot access to the procedures it needs, then select only the skills required for a particular task. RoboTeam manages repositories and selections; Ploinky installs live skill links and ALA mounts the prepared workspace.

Add repositories to a robot

Open Manage skills on a robot card. Enter an HTTPS Git repository URL and choose Add repo. Expand a repository row to inspect skill names, plus each skillset's name, description and members. Remove unregisters the repository while preserving its shared checkout. These actions require an administrator.

Each declared skillset has a control at the top right: an administrator-only Disable or Enable button. The choice is saved per robot. Disabled skillsets remain visible here, but are omitted from the default robot's discovery catalog and robot_list. Disabling every skillset does not expose the repository as an individual-skill fallback. This controls discovery; existing task selections and continuations remain usable.

The dialog also lists recommended repositories from Ploinky's authenticated /api/marketplace endpoint, including skill repositories detected directly in the workspace as well as registered repositories. Local discovery requires a Git repository with a nonempty skills/ directory and valid SKILL.md descriptors declaring a name and description. Subdirectories missing SKILL.md produce a visible warning without excluding the repository; they are not available skills. A remote URL is optional. Choose Add repo beside a recommendation. Ploinky prefers a Git checkout directly in the workspace, such as work/DocumentationSkills, then an installed checkout in .ploinky/repos, then the registered Git URL. Recommendations already registered on this robot show a disabled Added button, matching either the local source or the Git URL, with or without its .git suffix. Removing the repository enables the button again. The UI sends DELETE with the repository ID in the name query parameter and no request body. Registered remote URLs and .ploinky/repos sources prefer a workspace Git checkout with the same repository name when present. Local checkouts are read without pulling or switching branches. Local registrations read that source live when preparing later executions; active executions also see source edits. Entering a recommended repository's exact URL uses the same preferred source.

RoboTeam uses the shared Ploinky repository client to resolve or prepare a checkout, validates its Anthropic SKILL.md descriptors and saves registration metadata. It does not make a private repository copy or run setup scripts. Ploinky supplies workspace-first sources and owns checkout updates.

Define combinations in skillsets.md

A skillset groups skills from one repository for a type of task. The optional root file skillsets.md can declare several overlapping groups. Each level-one heading names a skillset. Its level-two Description section explains when to use it, and its level-two Skills section lists exact name values from that repository's SKILL.md frontmatter. Use a hyphen followed by a space for each member.

# report-review

## Description

Use when a report needs PDF inspection and a written review.

## Skills

- read-pdf
- write-doc

# pdf-inspection

## Description

Use when only the PDF needs inspection.

## Skills

- read-pdf

The skillsetMDParser accepts multiline descriptions and case-insensitive section headings. It rejects duplicate skillset names, repeated or unknown sections, missing descriptions, empty member lists and unknown skill names. Skillset names may contain spaces. There is no version field or JSON wrapper. Empty or absent skillsets.md contributes no skillsets; a plain Anthropic skill repository remains supported.

Prompt and conversation ownership

RoboTeam sends the current request and, for the front conversation, the workflow catalog and caller-supplied system instructions to choose and start a workflow. Every turn goes to ALA; RoboTeam performs no knowledge-memory lookup or response caching. RoboTeam points the coding agent to .agents/skills once when starting the native conversation; the agent reads skill descriptors itself. Resumed turns do not repeat that instruction or replay UI transcripts; native coding-agent sessions retain conversation context. Starting a workflow creates a separate asynchronous task with its own conversation and task ID. The workflow supplies the relevant context in each node's task context with the graph and prior final responses.

What the default robot receives

At each default WebChat turn, RoboTeam supplies the available robots and their specializations. For each robot it includes its skillset names, descriptions, member names and generated selection IDs. Descriptions tell the default robot when a combination is useful; IDs distinguish selections from different repositories. For repositories without skillsets, it instead supplies each individual skill's name and description, grouped by repository ID. Discovery does not send full skill instructions.

Workflow nodes select named skillsets from the current Ploinky repository catalog. RoboFlow matches all selected sets on one robot, resolves stable repository-source/skillset identities to that robot catalog and mounts only those skills. Branching tasks receive caller-supplied routing instructions. The front copilot uses the builtin launch-workflow set.

Registration rejects duplicate repository names, equivalent local source paths and names that collide with a generated skillset ID. Existing ambiguous bare selectors report an error; select qualified individual skills or remove and register the conflicting source with a different name.

Direct default chats initially include only launch-workflow; RoboTeam does not scan the workspace for skills. Explicit exclusions or an empty selection remain authoritative. Only the default robot registers the bundled copilot skillset. Other robots cannot select it. Delegated tasks targeting default receive it only when explicitly requested. An omitted delegated selection mounts no skills. The full SKILL.md instructions become available only through the selected directories.

Prepare live skills

Opening a terminal or workstation prepares skills from the robot’s saved scoped defaults. Conversation execution uses its own saved policy. Opening a terminal does not reset the selection.

ALA receives the full Ploinky workspace read-only and the robot working directory writable at their original absolute paths. It creates no skill directories or overlays. The working directory must be below the workspace root. Native agent state is kept beneath that writable directory; existing state is preserved during migration. Desktop and terminal containers use the same workspace mounts.

Direct default chats initially select only launch-workflow; workspace scanning is disabled. Explicit empty selections remain empty. Delegated tasks without a selection mount no skills, including when their target is default. Named skillset IDs select only their declared members; repository-qualified individual skills and explicit whole-repository selectors remain supported. Each later execution resolves and installs the current selection after queue wait.

The task stores a conversation policy reference before queueing. At execution start, RoboTeam resolves selected sources and asks Ploinky to install relative links under the working folder’s .agents/skills. Ploinky also prepares .claude → .agents. Omitted entries are not removed by install; RoboTeam explicitly removes its own obsolete links. Ordinary files and conflicting links remain intact and produce a diagnostic.

Removed skills and continuation

Selected links expose current repository files, including changes during an active execution. New skills in whole-source selections are discovered at the next execution. Missing required skills fail visibly. Historical pinned catalogs cannot execute through live installation; restore a live selection first. Native conversation history remains owned by the coding agent.

Legacy copied catalogs remain recovery evidence. They are not a fallback when live sources are missing. Read local skill discovery for selection and exclusion rules.

See Robots & Runs for task controls and the ALA task boundary specification for the execution contract.

Runtime dependencies and task notifications

For each execution, RoboTeam prepares a private ploinky-runtime folder containing sdk/, agentlib/ with JWT dependencies, the signed router-descriptor.json, version-2 context.json and tasks.sock. It passes --folder /path/to/ploinky-runtime as ploinky-runtime. ALA mounts the whole folder read-only at /workspace/ploinky-runtime and knows nothing about Ploinky. Script files and configuration cannot be changed through this mount; the socket remains usable.

Skills call the real Ploinky client through the Router. A task-start notification identifies the new task; it does not contain the task logs. RoboTeam verifies and associates the task with the originating chat turn, then acknowledges the notification. Retries retain the same notification ID and are deduplicated. Live-session updates use separate IDs. The existing task observer supplies progress and results to WebChat. RoboTeam drains accepted notifications and removes the runtime folder after execution or cancellation.
