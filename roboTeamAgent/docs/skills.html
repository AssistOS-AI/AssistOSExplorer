Skills and skillsets

Give each robot access to the procedures it needs, then select only the skills required for a particular task. RoboTeam manages repositories and selections; ALA mounts the resulting immutable execution catalog.

Add repositories to a robot

Open Manage skills on a robot card. Enter an HTTPS Git repository URL and choose Add repo. Expand a repository row to inspect skill names, plus each skillset's name, description and members. Remove unregisters the repository and deletes its imported files. These actions require an administrator.

Each declared skillset has a control at the top right: an administrator-only Disable or Enable button. The choice is saved per robot. Disabled skillsets remain visible here, but are omitted from the default robot's discovery catalog and robot_list. Disabling every skillset does not expose the repository as an individual-skill fallback. This controls discovery; existing task selections and continuations remain usable.

The dialog also lists recommended repositories from Ploinky's authenticated /api/marketplace endpoint, filtered to skill repositories. Choose Add repo beside a recommendation. Ploinky prefers a Git checkout directly in the workspace, such as work/DocumentationSkills, then an installed checkout in .ploinky/repos, then the registered Git URL. Recommendations already registered on this robot show a disabled Added button, matching either the local source or the Git URL, with or without its .git suffix. Removing the repository enables the button again. The UI sends DELETE with the repository ID in the name query parameter and no request body. Local registrations read that source live when preparing later executions; the active execution keeps its captured files. Entering a recommended repository's exact URL uses the same preferred source.

RoboTeam clones the repository into staging, validates its Anthropic SKILL.md descriptors and imports its files once into private storage under robots/<robot-id>/skillsets/<generation>/, beside the robot home. It does not run repository setup scripts. Each skill must contain its resources inside its own directory. Imports reject symlinks and special files and exclude .git and node_modules. Repository updates are not implemented.

Define combinations in skillsets.md

A skillset groups skills from one repository for a type of task. The optional root file skillsets.md can declare several overlapping groups. Each level-one heading names a skillset. Its level-two Description section explains when to use it, and its level-two Skills section lists exact name values from that repository's SKILL.md frontmatter. Use a hyphen followed by a space for each member.

# report-review

## Description

Use when a report needs PDF inspection and a written review.

## Skills

- read-pdf
- write-doc

# pdf-inspection

## Description

Use when only the PDF needs inspection.

## Skills

- read-pdf

The skillsetMDParser accepts multiline descriptions and case-insensitive section headings. It rejects duplicate skillset names, repeated or unknown sections, missing descriptions, empty member lists and unknown skill names. Skillset names may contain spaces. There is no version field or JSON wrapper. Empty or absent skillsets.md contributes no skillsets; a plain Anthropic skill repository remains supported.

Prompt and conversation ownership

RoboTeam sends the current request and, for the default robot, the delegation catalog and a rule to delegate when the user hints, indicates, or explicitly requests that someone else perform the task. Otherwise, the default robot performs the task itself. Every turn goes to ALA; RoboTeam performs no knowledge-memory lookup or response caching. ALA points the coding agent to .agents/skills and requires current descriptor reads on each turn; the agent reads skill descriptors itself. RoboTeam does not repeat those instructions or replay UI transcripts; native coding-agent sessions retain conversation context. A launch-robot call creates a separate asynchronous task with its own conversation and task ID. The parent must supply the relevant context in its task description.

What the default robot receives

At each default WebChat turn, RoboTeam supplies the available robots and their specializations. For each robot it includes its skillset names, descriptions, member names and generated selection IDs. Descriptions tell the default robot when a combination is useful; IDs distinguish selections from different repositories. For repositories without skillsets, it instead supplies each individual skill's name and description, grouped by repository ID. Discovery does not send full skill instructions.

The default robot uses launch-robot with skillSets containing discovered IDs and/or skills containing qualified repository-id/skill-name selectors. Both accept arrays or comma-separated strings. RoboTeam expands the requested sets, adds individual selections and deduplicates the union. Two distinct selected skills with the same native name are rejected.

Registration rejects duplicate repository names, equivalent local source paths and names that collide with a generated skillset ID. Existing ambiguous bare selectors report an error; select qualified individual skills or remove and register the conflicting source with a different name.

Direct default chats initially include the three bundled copilot skills and live workspace skills; explicit exclusions or an empty selection remain authoritative. Only the default robot registers the bundled copilot skillset. Other robots cannot select it. Delegated tasks targeting default receive it only when explicitly requested. An omitted delegated selection mounts no skills. The full SKILL.md instructions become available only through the selected directories.

Prepare the execution catalog

Direct default chats initially select copilot and workspace skills. Explicit empty selections remain empty. Delegated tasks without a selection mount no skills, including when their target is default. Named skillset IDs select only their declared members; repository-qualified individual skills and explicit whole-repository selectors remain supported. Every later execution captures current selected bytes after queue wait, unless the conversation explicitly pins a catalog.

The task stores a conversation policy reference before enqueueing. At execution start, RoboTeam validates source identities and captures selected descriptors, scripts and resources into an immutable private catalog under runtime/skill-catalogs. The catalog includes a revision and policy version. ALA receives --skill-catalog even when selection is empty; configured repositories cannot add skills to that execution.

Removed skills and continuation

Local sources are read from their current working directories. New skills in an automatic workspace or selected whole local source are discovered without an update command. Named subsets do not automatically select new siblings. Missing required sources fail visibly; excluded identities remain excluded. Running executions retain their captured resources. Explicit /skills pin retains the last catalog, while /skills live resumes current-source capture.

Legacy copied catalogs remain intact. Legacy path manifests are recovery evidence; explicit pinning validates and captures their remaining permitted sources into an immutable catalog without rewriting the old manifest. Missing or corrupt recovery sources fail. Read local skill discovery for exclusion, migration and retention rules.

See Robots & Runs for task controls and the ALA task boundary specification for the execution contract.

Runtime dependencies and task notifications

For each execution, RoboTeam prepares a private ploinky-runtime folder containing sdk/, agentlib/ with JWT dependencies, the signed router-descriptor.json, version-2 context.json and tasks.sock. It passes --folder /path/to/ploinky-runtime as ploinky-runtime. ALA mounts the whole folder read-only at /workspace/ploinky-runtime and knows nothing about Ploinky. Script files and configuration cannot be changed through this mount; the socket remains usable.

Skills call the real Ploinky client through the Router. A task-start notification identifies the new task; it does not contain the task logs. RoboTeam verifies and associates the task with the originating chat turn, then acknowledges the notification. Retries retain the same notification ID and are deduplicated. Live-session updates use separate IDs. The existing task observer supplies progress and results to WebChat. RoboTeam drains accepted notifications and removes the runtime folder after execution or cancellation.
