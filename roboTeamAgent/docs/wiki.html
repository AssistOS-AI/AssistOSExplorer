RoboTeam Wiki

RoboTeam

The single Ploinky agent that stores robots, operates inner Podman, and proxies observable GUI sessions.

Robot

A workspace-scoped persistent record and directory tree with a unique name, home, workspace, downloads, logs and on-demand run. External creation and deletion require an administrator. Startup also creates the ordinary name default when absent and reuses it unchanged otherwise; it has no special ID or marker and remains normally deletable. Creation installs no software, copies no credentials and starts no container. “Profile” is not used for this object.

Robot home

The persistent directory mounted at /config in either GUI image and later supplied to ALA through --home. It contains robot-specific state, not private copies of executables. It holds ALA's .ala/config.json, the single source of the robot's coding agent, models and efforts, and the coding agents' own accounts and state. Claude Code keeps its login, settings and native sessions in .claude there: the robot shell, ALA and the GUI containers all set CLAUDE_CONFIG_DIR to that directory. Conversations and native continuations are not stored there; they live in the opened folder.

Robot run

The retained graphical environment for a robot. RoboTeam keeps at most one Desktop or Browser container per robot and may leave it running after ALA finishes. A queued graphical task reuses it when mode and cwd match or replaces it before execution when either value differs.

Robot task queue

The FIFO list shared by a robot's Desktop and Browser requests. Only one graphical task uses that robot's single GUI container at a time. Independent CLI conversations and Simple tasks run concurrently outside this queue. Cancelling a live graphical task from WebChat pauses the GUI queue for manual control; resuming places the interrupted request first and releases the queue. A completed task leaves the GUI container available.

Advanced Language Agent

ALA is RoboTeam's LLM execution layer. RoboTeam starts it as an outer process with the robot home, selected cwd, task prompt, coding-agent choice, and optional GUI MCP address. ALA can run Codex, OpenCode, Pi, or Claude Code when the selected CLI and its configuration are available. The task-local MCP URL adapter configures Codex, OpenCode and Claude Code, so RoboTeam GUI automation uses one of those three.

Workflow type

A global directed graph with task nodes, edges, entryTaskId and saved node positions. Tasks specify name, prompt, skillsets and execution mode. Definitions have no robot assignments. The protected Standard development graph (id default) is a single node using the default robot and a caller-selected mode.

Task flow

One execution of a saved graph for an objective and working folder. SQLite stores its immutable graph snapshot, state and distinct task instances. Logs and final responses remain in the working folder.

Task instance

One visit to a graph node. For an ordinary task, RoboFlow creates a unique runtime task, chooses a matching robot, records the final response and follows an outgoing edge. A managed coordinator visit stores child workflow references and has no native runtime task. Repeated visits in cycles create distinct instances.

Front copilot and workflows

The former AchillesCLI wrapper runs inside RoboTeam for every robot. Explorer opens the ordinary default robot. A robot owns its home; each conversation owns a cwd, transcript, selected skill catalog and ALA/native session. The default robot automatically mounts bash and launch-gpt-researcher. Every robot opened in WebChat also receives the read-only list-workflows and launch-workflow skills. The front copilot calls list-workflows for the current workflow ids, then launch-workflow starts a RoboFlow task flow through the real Ploinky MCP client. RoboFlow then runs the workflow by matching each task to an available robot and following directed edges. Its parent wrapper attaches the native task and returns immediately. The task keeps the link to the flow page, which shows the graph, the phases and their live logs and stops the flow or a single phase.

Browser mode

A custom inner image derived from digest-pinned LinuxServer Chromium, streamed through Selkies and controlled over CDP by the active cached Playwright MCP generation.

Desktop mode

A custom inner image derived from digest-pinned LinuxServer Webtop Ubuntu XFCE, streamed through Selkies and controlled by active cached computer-use-linux and Supergateway generations.

computer-use-linux

An architecture-specific Rust MCP executable resolved from the current GitHub release during startup preparation, validated, and stored in the persistent shared desktop tool cache. It is not a RoboTeam JavaScript dependency and is not baked into the image.

Codex boundary

The current Codex npm package is prepared in a persistent shared cache. ALA mounts that runtime inside Bubblewrap with robot-specific home state; a manual desktop mounts the same generation and can run Codex from its PATH.

Tool cache

The persistent, generation-based store under /data/tool-cache. Service startup prepares the coding-agent, desktop and browser tools in the background by resolving upstream versions, staging and probing executables, then atomically activating them. Robot requests share pending preparation and reuse its results. An operator can pin a coding agent to one exact version with ROBOTEAM_CODEX_VERSION, ROBOTEAM_OPENCODE_VERSION, ROBOTEAM_PI_VERSION or ROBOTEAM_CLAUDE_VERSION (set with ploinky var before start). Failed updates fall back to the last valid generation (for a pinned agent, only one of the pinned version); a family without a valid fallback logs its startup failure and retries on demand.

Ploinky agent

The outer deployable with identity agent:AchillesCLI/roboTeamAgent. Ploinky starts it, attaches storage, authenticates users, exposes MCP on port 7000, and routes the UI on port 3001.

Nested Podman

The Podman 5.8.7 engine inside the bounded RoboTeam outer container. Publication uses the immutable stable base recorded in the image source lock. Installation requires the roboteam-runtime-v6 marker and a successful exact version check. The image initializer establishes disposable tmpfs storage before installation setup and before service engine checks. It reuses existing tmpfs and rejects symbolic links or other mounted filesystems. The engine uses fuse-overlayfs and pasta and never controls host Podman.

Selkies session

The HTTP and WebSocket GUI produced by Chromium or Webtop and proxied through RoboTeam's authenticated route. While a session is ready, the robot dashboard shows its complete URL as a reusable link. Closing the workstation window does not stop the container or remove that link.

Skillset

A named combination of skills declared in a repository’s root skillsets.md, with Description and Skills sections. RoboTeam exposes each combination’s name, description and members with a generated selection ID. Registration alone does not activate skills. Conversation policies select named combinations, individual repository-qualified skills, explicit whole sources, or automatic workspace discovery. Each external execution captures current selected files; explicit pinning keeps the captured catalog. See Skills & Skillsets for the format and workflow.

Soul Gateway adapter

The RoboTeam service connects OpenCode to the local Soul Gateway through AgentLib's verified Router transport. It owns a private UNIX socket in each robot home and retains the Ploinky credential. The shared OpenCode plugin discovers models at initialization and registers them in memory. It forwards inference through a temporary loopback endpoint protected by a random capability, then through the robot socket. Service shutdown or robot deletion closes the socket; plugin disposal closes the local endpoint. There is no generated provider configuration file, periodic model polling or new public port. Buffered upstream responses are translated into SSE for OpenCode.

The opened project owns .roboteam/, which carries a .gitignore containing *. ALA writes each conversation's text to .roboteam/.ala/sessions/<sessionId>.jsonl; RoboTeam keeps its turn metadata in .roboteam/sessions/ and task records in .roboteam/tasks/. A robot supplies the execution environment and native accounts. Deleting a robot preserves project history but may prevent native continuation.

Allow sub-flows

An ordinary robot-executed workflow task marked with the Allow sub-flows option. Its robot receives the required, view-only workflow-creator skill and a catalog of eligible workflow types. It can choose an ordinary outgoing edge or return a plan for ordered children together with the continuation edge. It has a purple outline in the graph. Workflow types containing tasks that allow sub-flows are excluded from child selection, including server-side validation.

Run workflows

The shared managed node that appears in a graph containing a task that allows sub-flows. RoboFlow owns its execution; it has no robot, skill selection or ALA session. Each visit runs the selected children sequentially in array order. The next starts only after the preceding child completes successfully. Failed and paused children block continuation; later children remain pending. The creator chooses an outgoing edge from this node before the children start. Different visits keep separate child lists.

Sub-flow

A workflow execution created by a task that allows sub-flows through Run workflows. It owns a captured graph, objective, task instances and output files, and shares the parent's working folder. Parent and creator identifiers connect it to the initiating visit. Children start sequentially in array order, subject to existing robot queues. Each child receives only the final response of the preceding child’s last task as additional context; pending children have no running timer. Parent Pause pauses active children; parent Resume resumes paused children without repeating completed or failed work. A child page links back to the parent, and the creator's Sub-flows tab links to every child.
