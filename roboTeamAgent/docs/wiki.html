RoboTeam Wiki

RoboTeam

The single Ploinky agent that stores robots, operates inner Podman, and proxies observable GUI sessions.

Robot

A workspace-scoped persistent record and directory tree with a unique name, specialization, home, workspace, downloads, logs and on-demand run. External creation and deletion require an administrator. Startup also creates the ordinary name default when absent and reuses it unchanged otherwise; it has no special ID or marker and remains normally deletable. Creation installs no software, copies no credentials and starts no container. “Profile” is not used for this object.

Robot home

The persistent directory mounted at /config in either GUI image and later supplied to ALA through --home. It contains robot-specific state, not private copies of executables.

Robot run

The retained graphical environment for a robot. RoboTeam keeps at most one Desktop or Browser container per robot and may leave it running after ALA finishes. A queued graphical task reuses it when mode and cwd match or replaces it before execution when either value differs.

Robot task queue

The FIFO list shared by a robot's Desktop and Browser requests. Only one graphical task uses that robot's single GUI container at a time. Independent CLI conversations and Simple tasks run concurrently outside this queue. Cancelling a live graphical task from WebChat pauses the GUI queue for manual control; resuming places the interrupted request first and releases the queue. A completed task leaves the GUI container available.

Advanced Language Agent

ALA is RoboTeam's LLM execution layer. RoboTeam starts it as an outer process with the robot home, selected cwd, task prompt, coding-agent choice, and optional GUI MCP address. ALA can run Codex, OpenCode, or Pi when the selected CLI and its configuration are available. The current task-local MCP URL adapter configures Codex, so RoboTeam GUI automation uses Codex.

Workflow type

A global directed graph with task nodes, edges, entryTaskId and saved node positions. Tasks specify name, prompt, skillsets and execution mode. Definitions have no robot assignments. The protected default graph is a single node using the default robot and a caller-selected mode.

Task flow

One execution of a saved graph for an objective and working folder. SQLite stores its immutable graph snapshot, state and distinct task instances. Logs and final responses remain in the working folder.

Task instance

One visit to a graph node with a unique runtime task. RoboFlow chooses a matching robot, records the final response and follows an outgoing edge. Repeated visits in cycles create distinct instances.

Front copilot and workflows

The former AchillesCLI wrapper runs inside RoboTeam for every robot. Explorer opens the ordinary default robot. A robot owns its home; each conversation owns a cwd, transcript, selected skill catalog and ALA/native session. The front copilot receives the workflow catalog and the default robot automatically mounts bash, launch-gpt-researcher and launch-workflow; launch-workflow starts a RoboFlow task flow through the real Ploinky MCP client. RoboFlow then runs the workflow by matching each task to an available robot and following directed edges. Its parent wrapper attaches the native task and returns immediately. The task keeps the link to the flow page, which shows the graph, the phases and their live logs and stops the flow or a single phase.

Browser mode

A custom inner image derived from digest-pinned LinuxServer Chromium, streamed through Selkies and controlled over CDP by the active cached Playwright MCP generation.

Desktop mode

A custom inner image derived from digest-pinned LinuxServer Webtop Ubuntu XFCE, streamed through Selkies and controlled by active cached computer-use-linux and Supergateway generations.

computer-use-linux

An architecture-specific Rust MCP executable resolved from the current GitHub release during startup preparation, validated, and stored in the persistent shared desktop tool cache. It is not a RoboTeam JavaScript dependency and is not baked into the image.

Codex boundary

The current Codex npm package is prepared in a persistent shared cache. ALA mounts that runtime inside Bubblewrap with robot-specific home state; a manual desktop mounts the same generation and can run Codex from its PATH.

Tool cache

The persistent, generation-based store under /data/tool-cache. Service startup prepares the coding-agent, desktop and browser tools in the background by resolving upstream versions, staging and probing executables, then atomically activating them. Robot requests share pending preparation and reuse its results. Failed updates fall back to the last valid generation; a family without a valid fallback logs its startup failure and retries on demand.

Ploinky agent

The outer deployable with identity agent:AchillesCLI/roboTeamAgent. Ploinky starts it, attaches storage, authenticates users, exposes MCP on port 7000, and routes the UI on port 3001.

Nested Podman

The Podman 6 engine inside the bounded RoboTeam outer container. Publication resolves the rolling upstream tag to one digest per run. The engine uses fuse-overlayfs and pasta and never controls host Podman.

Selkies session

The HTTP and WebSocket GUI produced by Chromium or Webtop and proxied through RoboTeam's authenticated route. While a session is ready, the robot dashboard shows its complete URL as a reusable link. Closing the workstation window does not stop the container or remove that link.

Skillset

A named combination of skills declared in a repository’s root skillsets.md, with Description and Skills sections. RoboTeam exposes each combination’s name, description and members with a generated selection ID. Registration alone does not activate skills. Conversation policies select named combinations, individual repository-qualified skills, explicit whole sources, or automatic workspace discovery. Each external execution captures current selected files; explicit pinning keeps the captured catalog. See Skills & Skillsets for the format and workflow.

Soul Gateway adapter

The RoboTeam service connects OpenCode to the local Soul Gateway through AgentLib's verified Router transport. It owns a private UNIX socket in each robot home and retains the Ploinky credential. The shared OpenCode plugin discovers models at initialization and registers them in memory. It forwards inference through a temporary loopback endpoint protected by a random capability, then through the robot socket. Service shutdown or robot deletion closes the socket; plugin disposal closes the local endpoint. There is no generated provider configuration file, periodic model polling or new public port. Buffered upstream responses are translated into SSE for OpenCode.

The opened project owns .achilles-cli/sessions/ and .achilles-cli/tasks/. A robot supplies the execution environment and native accounts. Deleting a robot preserves project history but may prevent native continuation.
