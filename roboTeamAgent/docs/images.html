Images and dependencies

RoboTeam publishes three custom runtime images and installs fast-moving control tools into a persistent cache when they are first needed.

First-use preparation

Codex, Supergateway, and Playwright MCP are resolved through npm. Host npm calls and cached Codex probes use a sanitized child environment without Ploinky's NODE_OPTIONS symlink-preservation flags, while the parent agent environment remains unchanged. Codex uses a global-prefix cache layout so ALA can discover the binary, mount its complete runtime read-only inside Bubblewrap, and place its bin directory on the sandbox PATH. GUI npm packages are installed by short-lived inner containers based on their target GUI image, which preserves native-runtime compatibility.

computer-use-linux remains an architecture-specific Rust executable. RoboTeam resolves the latest GitHub release, selects the matching amd64 or arm64 asset, records its computed SHA-256 digest, and honors an upstream digest when GitHub provides one. The prepared desktop generation is probed in the desktop image before activation.

A manual desktop mounts the active Codex generation at /opt/roboteam-codex and exposes it on PATH. A user can therefore run codex login while the robot home is mounted at /config; ALA later uses the same home with the same cached Codex executable.

Robot creation and shared images

Creating a robot allocates metadata plus home, workspace, downloads, logs, and runtime directories. It does not copy an image or install an executable. Tool generations live under the shared /data/tool-cache root, while each robot contributes only its own state and work directories. This avoids a separate Codex or MCP installation for every robot.

Refresh, fallback, and size policy

Each tool family is resolved once per RoboTeam process and rechecked after ROBOTEAM_TOOL_REFRESH_INTERVAL_MS, six hours by default. Simultaneous requests share one in-process preparation. A resolved version and its target image identify an immutable cache generation. New content is staged and validated before current.json is replaced atomically. If resolution, download, installation, or validation fails, RoboTeam uses the last stamped generation; the very first use fails clearly when no fallback exists.

The operating-system and graphical base digests remain fixed in image definitions. Runtime tool versions are deliberately absent from those definitions, so updating a tool does not require publishing a new image.

The graphical images are large because LinuxServer Webtop and Chromium include Selkies, a window manager, browser or desktop packages, audio support, and the supporting operating-system files. The custom MCP layers are a small part of the total. Browser and desktop are separate images, but the current browser base is not substantially smaller because it carries almost the same graphical streaming stack.

Local development loop

The image-definition repository provides scripts/install-roboteam-local.mjs with agent, desktop, browser, and all targets. Run it from the workspace host while the owned Ploinky Box is active. GUI targets also require a running RoboTeam agent.

The launcher validates exact Box ownership and builds in the Box image store. Desktop and browser images are streamed directly into RoboTeam's nested Podman store, with no registry push and no temporary image archive. A final RoboTeam reinstall stops active robot sessions and activates the local images. This development loop builds only the host's native architecture; GitHub publication continues to produce the supported multiarchitecture manifests.
