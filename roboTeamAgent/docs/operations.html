RoboTeam Documentation

PLOINKY_WORKSPACE_ROOT is required and must name an existing absolute directory. RoboTeam reports a configuration error when it is missing or invalid. Desktop, Browser and ALA use that configured workspace root; they do not substitute the current directory or a default workspace path.

RoboTeam exposes robot management and task execution as MCP tools. The Ploinky Router applies the tool policy before RoboTeam receives a call.

Choose a robot's coding agent

New robots enable OpenCode only. The creation form has no coding-agent selector. On an existing robot card, administrators choose Coding agent, select Codex, OpenCode, Pi or Claude Code in the dialog, and save. Claude Code is the last choice in the dialog. The card displays the enabled agent without opening the dialog. Stop the workstation and tasks before changing the selection. Open a new chat or terminal afterward; existing conversations keep their captured backend.

The robot's ALA config, <robot home>/.ala/config.json, is the single source of its coding agent, models and efforts. It has the form { "codingAgent": "opencode", "models": { "<agent>": "<model>" }, "efforts": { "<agent>": "<effort>" } }, with one model and one effort per coding agent. Robot creation writes codingAgent as the robot's first selected agent. Saving a new agent in the dashboard (PATCH /api/robots/<id>/coding-agents) replaces codingAgent and keeps the models and efforts chosen for other agents. The robot record still keeps codingAgents, which decides which agent binaries RoboTeam installs.

The selection controls managed tools in WebChat, delegated MCP tasks, Desktop, Browser and Open → Terminal. ALA selects from those available tools. Omitted ca means auto; an explicit backend must be enabled. Account files stay in the robot home when changing agents. The setting does not restrict programs installed manually.

The dashboard permits one selection. Integrations may supply a nonempty codingAgents array containing any combination of codex, opencode, pi and claude during creation or through the administrator-only PATCH /api/robots/<id>/coding-agents endpoint. Existing robots without that field retain all four until configured. Desktop and Browser task automation depends on the selected ALA backend's MCP adapter, so it needs Codex, OpenCode or Claude Code.

Claude Code

All robots share one Claude Code installation from the tool cache: the npm package @anthropic-ai/claude-code with the executable claude, which RoboTeam hands to ALA through CLAUDE_BIN. Claude Code can drive Desktop and Browser tasks because ALA passes it the task's MCP server.

RoboTeam never handles Claude credentials. To log a robot in, an administrator opens Open → Terminal on the robot card, runs claude, and completes the normal Claude Code login. The robot shell exports CLAUDE_CONFIG_DIR="$HOME/.claude", the copilot engine passes CLAUDE_CONFIG_DIR=<robot home>/.claude to ALA, and Desktop and Browser containers get CLAUDE_CONFIG_DIR=/config/.claude. All three point at the same robot home directory, so the login, Claude Code's settings and its native sessions stay with the robot.

Claude Code does not use Soul Gateway. It runs only Claude's own models, with Anthropic credentials from its login. /model in WebChat lists Claude's models as ALA reports them from the installed CLI, so the list follows the Claude Code release instead of a list kept in RoboTeam.

Soul Gateway models in OpenCode

RoboTeam installs the shared soul-gateway.js plugin in each robot's ~/.config/opencode/plugins/ directory. OpenCode loads it automatically from the robot home, whether opened manually in the terminal or Desktop, or started through ALA. Configure upstream accounts such as SuperGrok and Openference once in Soul Gateway. No generated opencode.json is needed. When a robot enables OpenCode, RoboTeam records the built-in opencode/big-pickle model in the robot's ALA config (~/.ala/config.json) unless an OpenCode model is already set. Headless runs then use the same default as the terminal, not whatever model OpenCode would pick on its own. A model the user chose is never overwritten.

At native OpenCode initialization, the plugin reads the local gateway model catalog and registers soul-gateway/<gateway-model-id> entries in memory. WebChat's model selector and /model use that same native catalog when the conversation uses OpenCode. The plugin does not select OpenCode as the robot's backend.

There is no periodic polling. Reopen OpenCode to refresh the catalog after changing gateway providers or models. An unavailable gateway produces an explicit error. The RoboTeam service must be running: it owns the private connection in the robot home. After installing this change, restart RoboTeam and reopen existing OpenCode instances.

The Soul Gateway adapter keeps Ploinky credentials in RoboTeam. The plugin uses a private UNIX socket and an ephemeral, authenticated loopback endpoint inside its own process. On a workspace shared from a macOS host the socket's mode cannot be restricted; RoboTeam then logs that the socket is not owner-only and starts anyway. The local Router transport requires buffered responses, so text and tool calls arrive after each gateway response completes.

Tasks in WebChat

Workflow status follows this priority: active phases, including queued, starting and pausing, make the run running; otherwise a paused phase makes it paused; otherwise a failed phase makes it failed; otherwise it is completed. WebChat preserves paused workflow outcomes and follows the workflow state after continuation from the flow page, including after a chat refresh. Task and workflow timers freeze on pause and continue from the accumulated duration on resume, excluding the pause. The flow header displays the overall duration.

The chat header identifies the current robot. Task cards identify the executing robot and show status and duration. Cards always show View Task Details, which opens logs and the continuation composer in the right pane. Graphical tasks also expose Open live browser or Open live desktop. Logs and continuation inputs are not embedded in the conversation.

RoboFlow team workflows

RoboFlow workflows are global directed graphs of tasks. Describe a workflow to generate a draft on the generation page, which starts the task and streams its live log tail while it runs, or through roboflow_generate_workflow; then refine named nodes and drag positions on the drawing board. Drag a centered left or right port to a port on another node to create a directed edge; dropping elsewhere cancels the connection. Use Start node in the task editor to choose the highlighted entry point. Select an edge and press Delete or Backspace to remove it. Each task declares name, prompt, skillsets and terminal, desktop or browser execution. Save persists the graph and layout. The server warns when no robot covers a task's skillsets; warnings do not block saving or starting. RoboFlow randomly selects an available matching robot for each visit. Desktop and browser tasks share each robot's GUI queue. Branching tasks return an outgoing edge; zero or one outgoing edge needs no routing prompt. The protected Standard development workflow (id default) has one node, uses the default robot and requires a caller-selected execution mode. SQLite stores global definitions and run snapshots; logs and final responses stay in the working folder. See DS007.

Robot conversations and the default copilot

Explorer's Open Copilot here opens roboTeamAgent with robot=default and the selected cwd. Every robot card has Open → Copilot, which opens achilles-cli/ below the Ploinky workspace. The copilot validates and creates that folder before reading its settings, and reuses it on subsequent launches. The former AchillesCLI wrapper now lives in copilot/ inside RoboTeam; there is no separate AchillesCLI agent or image. The wrapper creates .roboteam/ inside the selected folder for conversations and task history; its .gitignore excludes everything in it from the project's repository. ALA writes the conversation text there, under .roboteam/.ala/sessions/. Each folder has its own session list. Conversations and task records belong to that folder rather than to a robot, so deleting a robot leaves them intact.

A robot owns its home and configured accounts. A conversation owns its cwd, ALA session, transcript and selected skill catalog. Each message executes another turn in that conversation. Independent CLI conversations and Simple tasks run concurrently, including while a GUI task runs. Desktop and Browser still share one container and one graphical task queue.

Use /session, /session new, /session resume <id>, /tasks, /model and /permissions. Codex, OpenCode and Claude Code support native approvals; Pi rejects ask-for-approval. The bundled copilot repository is available only to default; its direct chat initially selects only the copilot skillset. Every robot opened in WebChat also receives the required, read-only list-workflows and launch-workflow skills. RoboTeam does not scan the workspace for skills. Manage repositories in RoboTeam and conversation skill selection on RoboTeam's Conversation skills page (WebChat menu). Later turns and continuations capture current configured source files. Use /list robots to discover workspace robots. See local skills and selection.

ALA introduces mounted skills in .agents/skills once at the start of the native conversation. Continued turns do not repeat that instruction. Conversation commands do not change skill selection.

Commands available in every robot

WebChat autocomplete passes the selected robot and conversation id to the command catalog. /model lists native models through ALA for that conversation's saved backend. Before the first turn, discovery previews the available backend without creating or selecting a saved conversation. The menu refreshes on conversation or backend changes and reports model-discovery failures instead of silently showing no options.

The bundled copilot repository contains bash, launch-gpt-researcher, list-workflows and launch-workflow, plus the internal workflow-creator and require-human-input skills. Its only skillset is copilot (bash and launch-gpt-researcher), which the default robot mounts. Every robot opened in WebChat receives list-workflows and launch-workflow as required, read-only skills. list-workflows lists the workspace workflow types, with their tasks and execution types; launch-workflow only starts one. Graph tasks mount only their selected skillsets or individual skills; branching instructions are supplied by the caller.

Every robot, including default, uses the same conversational wrapper. Commands select a conversation, inspect delegated tasks, choose skills, or configure subsequent executions. The robot's allowed skillsets and saved accounts determine which work it can execute; having the same command interface does not grant every robot the same skills.

How commands reach a robot

For graphical workflow tasks, RoboFlow starts the selected robot's runtime task and the task publishes liveSession: {mode, url} once its GUI session is ready. The wrapper verifies the remote task through the authenticated MCP client, persists this metadata with the task, and forwards it through structured WebChat events. WebChat renders the fixed English button Open live desktop or Open live browser in the task box; clicking it uses the existing right-hand panel. Snapshot reads retain the link after refresh. Only bounded same-router paths are accepted; external URLs and model-supplied labels are not used.

Open → Copilot on a robot card or Open Copilot here in Explorer selects the robot and cwd. A terminal can use ploinky cli roboTeamAgent --robot analyst --dir /workspace/project. Ploinky starts server/robot-cli.mjs inside RoboTeam; that process prepares the robot home and runs the shared wrapper. A robot is a persistent record, not one permanently running process. Independent CLI connections and conversations can execute concurrently.

In a terminal, type a command and press Enter. WebChat sends an authenticated HTTP input request to Ploinky, which writes the message to the wrapper's standard input. In WebChat mode, the message is a JSON envelope terminated by a newline; the slash command goes in its text field. Ploinky supplies the originating tab and page identity so the wrapper applies session selection to that connection. The browser does not write directly to ALA or to the graphical container.

{"__webchatMessage":1,"version":1,"text":"/session new","attachments":[],"references":[]}

This example shows the command payload, not a replacement for Ploinky authentication or routing metadata. Bare text is also accepted by the wrapper, but its WebChat compatibility parser groups nearby plain-text lines; integrations should preserve Ploinky's framed message protocol rather than pipe several unframed commands at once. Wrapper output includes structured session, task, and interaction events that Ploinky forwards to the browser.

Local commands such as /session new, /list robots, and /tasks are handled by the wrapper without asking the coding agent to interpret them. An ordinary prompt or /exec starts an ALA turn. The wrapper passes the saved session UUID and uses --resume-session on continuation. ALA's separate --control-stdin channel receives structured live-message and approval responses, not the wrapper's slash commands. MCP tools such as startBrowserTaskForRobot are a third interface for delegated execution; they are not slash commands written to chat.

/session new
/list robots
Inspect the files in this project.
/session
/session resume <saved-session-id>
Continue with the tests.

Submit each line as a separate interaction. Creating or selecting another conversation does not delete or cancel the previous one. Only one turn may execute in a conversation at a time; different CLI conversations can run concurrently. Desktop and Browser retain the single shared graphical container and queue per robot.

Dashboard controls

Each robot card has an Open menu with Browser, Desktop, Terminal and Copilot. Browser and Desktop start a session or reopen the active one. A separate Stop button stops the active GUI session. Terminal is visible only to administrators.

Administrators can select Open → Terminal on a robot card. This opens Ploinky's existing WebTTY in a new tab, inside the already-running RoboTeam agent, with the current directory set to $PLOINKY_WORKSPACE_ROOT/.data/roboTeamAgent/robots/<id>/. It does not create a Desktop or Browser container or start an ALA task. Ploinky authenticates the administrator and verifies the live target and its workspace mount. If RoboTeam is not an eligible writable terminal target, the action reports an error without falling back to another agent or the Box.

Manual Desktop and Browser openings also use the robot root as their working directory. The full workspace is read-only and the robot root is writable at its original path. Native accounts remain in home/. Selecting a folder creates its .roboteam/ (see Project storage): .ala/sessions/ holds ALA's conversation transcripts, sessions/ holds RoboTeam's turn metadata for each conversation, and tasks/<task-id>/ holds each task definition, its logs/ and its executions/. Saved conversations keep their original cwd. Native continuation is recorded in the folder's transcript, but it is bound to the robot home, so native resume depends on that robot still existing, while the folder's conversations and task records do not.

Open → Terminal prepares only the robot's selected coding-agent cache before requesting a WebTTY launch. The agent-installed /etc/ploinky/webtty-env.sh hook selects the validated robot home and loads its generated shell environment even though WebTTY disables normal Bash profile loading. Desktop and WebTTY use the same persistent authentication directories and selected shell entry points. This remains an administrator shell in the outer RoboTeam runtime, not an isolated robot sandbox. The shell sets CLAUDE_CONFIG_DIR="$HOME/.claude", so running claude there logs Claude Code in for this robot (see Claude Code). Terminal lifetime and closing controls belong to WebTTY. Failed launches keep their error visible in the new tab.

The robot card starts or stops the Browser and Desktop container. Once a graphical session is ready, the card prints its complete authenticated Selkies URL as a link. The link remains available while that session runs, so a user can reopen a window that was closed.

The Logs button occupies a separate row below the session actions. Its initial state hides the log panel. Activating it reads the latest 200 lines from podman logs for the active Desktop or Browser container, displays them beneath the button, and refreshes the snapshot once per second. RoboTeam starts both graphical containers with Podman's k8s-file log driver, which stores their standard output and error locally and keeps podman logs functional even though the outer RoboTeam container has no systemd journal. The panel never mixes ALA task output into these container logs. Activating Logs again hides the panel and stops the polling. New output stays visible while the reader is at the bottom; scrolling upward suspends automatic movement to the latest line. The dashboard does not display Take Control or Resume buttons.

Project storage in .roboteam

Every folder opened in a robot conversation, and every folder a robot task or workflow runs in, gets a .roboteam/ directory. RoboTeam creates it and owns everything in it except .ala/, which belongs to ALA. Nothing in it is migrated from the former .achilles-cli/ directory. The directory cannot be a symbolic link, and none of its entries may be one.

How RoboTeam runs ALA

In each robot card, Manage skills lists permitted repositories and named combinations from skillsets.md. An administrator adds a credential-free HTTPS Git URL with a generated repository ID; the API also accepts absolute workspace sources and optional explicit source names. Registration validates descriptors and records their shared Ploinky source without copying files or executing setup scripts. Skill folders must include their own scripts and resources; symlinks, nested skills, and dependencies outside a selected folder are unsupported. Removing a selected source makes future live executions fail visibly until reselected; historical pins require restoring a live selection before execution. Local imports read original working files. HTTPS sources use the current Ploinky checkout and workspace-first resolution.

Administrator-only Delete robot requires confirmation and a stopped container with no active or queued tasks or live chat processes. It permanently removes the robot's saved logins, files, imported skillsets and task catalogs. It does not delete the original repositories or shared executable cache.

Direct robot start tools accept skillSets, skillset and skills selectors. Workflow nodes use skillsets containing canonical repository-source/skillset identities. RoboFlow resolves them to the selected robot catalog and mounts only the declared combinations. Empty selections stay empty. Selected links are resolved after queue wait.

{"action":"start","workflowTypeId":"default","executionType":"terminal","objective":"Review the report","folder":"/workspace/project"}

Workflow member robots accept arrays or comma-separated skill selectors and RoboTeam normalizes them for MCP. robot_list includes the catalog metadata in its response. RoboTeam installs the selected union through the shared Ploinky client before starting ALA with canonical --cwd and --folder mounts. The initial skills instruction comes from RoboTeam once per native conversation.

ALA is the LLM execution process. RoboTeam starts it in the outer RoboTeam container, in parallel with the graphical container. ALA then starts the selected coding-agent CLI inside its Bubblewrap sandbox. The Desktop and Browser MCP servers stay inside their graphical containers and are reachable by ALA through random loopback ports.

The concrete paths and random port differ for each robot and task. A Desktop task produces an invocation equivalent to:

ala \
  --home /data/robots/<robot-id>/home \
  --cwd /workspace/<project> \
  --session-id <uuid> --control-stdin \
  --ca codex \
  --MCPServers desktop=http://127.0.0.1:<port>/mcp

A Browser task uses the same command shape with browser=http://127.0.0.1:<port>/mcp. A Simple task omits --MCPServers and does not start a graphical container.

ALA argumentMeaning in RoboTeam
--homeThe robot's persistent home. ALA uses it for coding-agent authentication and configuration. The same directory appears as /config in the graphical container.
--cwdThe caller-selected workspace directory. ALA uses it as the writable work tree. ALA, Desktop and Browser preserve its absolute path. The containing Ploinky workspace is mounted read-only and this working directory writable.
--control-stdinKeeps ALA's stdin open for control records. RoboTeam writes the turn prompt as the first record, {"type":"prompt","prompt":"...","displayText":"..."}, so long prompts stay out of the process argument list. RoboTeam writes no prompt file. Later records carry live messages and approval replies.

--MCPServersSupplies the task-local Desktop or Browser Streamable HTTP MCP address. --home supplies saved state; it does not contain a private copy of a coding-agent executable. RoboTeam resolves and caches the current Codex, OpenCode, Pi, and Claude Code npm packages. A concrete --ca selection places that CLI on ALA's PATH; auto prepares the robot's configured agents, omits --ca, and lets ALA use the codingAgent saved in --home. The Desktop mounts only those shared generations so a user can authenticate the selected CLI against the robot's persistent /config home. Use Codex, OpenCode or Claude Code for Desktop and Browser automation because ALA implements task-local MCP URL injection for those backends. Pi has no ALA-managed MCP injection and can run only Simple tasks, so RoboTeam rejects it for GUI work.

The shared server/robot-task.mjs wrapper prepares a conversation and starts the ALA command above. Chat uses the same engine through server/robot-cli.mjs. The engine also passes --session-id, --control-stdin, --permissions, and --folder <runtime-directory> as ploinky-runtime for direct SDK scripts. It passes no --config. It adds --ca only for an explicitly requested agent, such as a task's ca or a conversation bound to an agent before its first native turn, and --model only for an explicit per-execution model. Otherwise ALA reads the agent, model and effort from the config in --home, and it resumes a conversation on the agent it saved for it. Web search is always on for Codex and OpenCode, Claude Code keeps its built-in web tools, and Pi has none. It sets ALA_SESSIONS=<cwd>/.roboteam/.ala, passes --turn-id, and writes the turn prompt as the first stdin record, {"type":"prompt","prompt":"...","displayText":"..."}. prompt is what the coding agent receives and displayText is the user's own text, which ALA records in the transcript. On a native session's first turn, prompt holds the caller's system instructions, the human-report rule, the skills instruction and the user message. A resumed turn, such as a WebChat follow-up or a continued workflow phase, sends only the user message, plus the selected skill line when the user picked a skill, because the native session already holds the rest. A live message sent during a turn is wrapped once by the engine with the human-report rule. ALA appends the conversation text to <cwd>/.roboteam/.ala/sessions/<sessionId>.jsonl; RoboTeam keeps its turn metadata in <cwd>/.roboteam/sessions/<sessionId>.json. The robot home, mounted writable for execution, holds ALA's .ala/config.json and the coding agents' state. The same robot home is used by WebChat, Desktop, Browser and Terminal, so credentials never diverge.

Robot runtime and task delegation

RoboTeam prepares ploinky-runtime and passes --folder <path> as ploinky-runtime to ALA. The folder is mounted read-only at /workspace/ploinky-runtime; its tasks.sock carries task-start and live-session notifications with acknowledgements. MCP calls go through the Ploinky Router. Task logs and results are retrieved by the task observer, not sent through this socket. ALA runs outside the coding agent's Bubblewrap sandbox and only prepares its execution and mounts. A delegated robot can use the same notification channel when it has a launch skill selected.

Persistent task conversations

Each task receives an ALA session UUID. RoboTeam passes --session-id <uuid> --control-stdin and adds --resume-session on later executions. The runtime manager writes no prompt file. It sends {"type":"prompt","prompt":"<task>","systemPrompt":"<caller instructions>"} as the first stdin line of server/robot-task.mjs, which hands systemPrompt to the copilot runtime and runs the turn. Later stdin lines are live messages for the running turn. ALA records the selected backend and native continuation in the task folder's transcript, <cwd>/.roboteam/.ala/sessions/<uuid>.jsonl; RoboTeam resumes from its last continuation record. RoboTeam stores the project-owned task records under <cwd>/.roboteam/tasks/<task-id>/: task.json describes the request and its robot, logs/ holds the observed output and cursor, and executions/ holds one record per attempt or continuation. The shared project registry stores locations only. The backend is pinned for that conversation, including across process restarts. A missing native session causes an explicit failure instead of a fresh conversation.

Stop cancels execution while preserving the conversation and GUI container. Resume sends Continue. for Simple tasks, or a current-screen observation instruction for Desktop and Browser tasks. A custom continuation sends the user's new prompt and, for GUI tasks, the observation instruction. Every execution has its own native Ploinky task, while AchillesCLI retains one local task id and WebChat log bubble. That bubble and Open Task both accept messages after completion or while the task runs. Queued messages are waiting for delivery; a receipt marked delivered means the backend accepted the message, not that it has completed the requested action.

Task and container lifetime

The three start tools use Ploinky's native asynchronous task contract. Their initial MCP response contains the Ploinky task id. Standard error becomes the live task log, standard output becomes the final result, and the worker process remains alive until ALA exits. Desktop and Browser starts declare resumeTaskForRobot as their continuation tool. When a user stops one of those tasks, the worker returns an opaque continuation handle that identifies the exact interrupted RoboTeam task. Callers use the normal Ploinky /task status route for completion and getSessionUrlForRobotDesktop or getSessionUrlForRobotBrowser for the live GUI URL.

Each robot has one active graphical ALA slot and a FIFO queue for Desktop and Browser, with independent concurrent CLI conversations shared by Desktop, Browser, and Simple tasks. A new request waits instead of failing because another task is active. Pressing Stop on a live WebChat GUI task cancels its native task for human takeover: ALA stops, the visible container remains active, and later queued requests stay paused while the user works through Selkies. The explicit MCP stop tools do not enter manual-control mode. resumeTaskForRobot validates the continuation handle, places the resumed request ahead of the waiting queue, and releases manual-control mode. The resumed prompt contains only the new instruction and a request to inspect the current screen and preserve the user's changes; the original assignment remains in the saved native conversation.

A completed GUI task leaves at most one container running. RoboTeam reuses it when the next graphical task has the same mode and resolved cwd. A different mode or cwd replaces the idle container before the queued task starts. A Simple task leaves an existing GUI container untouched. Use the separate container-stop tool when the visible session is no longer needed.

RoboTeam starts ALA with ALA_EVENT_STREAM=1. It converts coding-agent-message events into readable progress text. In WebChat, the status line shows one complete line at a time: word deltas from OpenCode, Pi and Claude Code are joined per output stream, a whole Codex block shows its last line, and a line without a newline appears when its stream completes or switches. RoboTeam keeps the final ALA standard output separate, and lets Ploinky retain the complete forwarded task log. State changes such as queued, starting, and running also appear in that log. Successful completion updates the task status without adding a completion sentence to the log. The final response contains only ALA output, with no synthetic completion message when that output is empty.

Robot workflows

RoboFlow workflows are global directed graphs of tasks. Describe a workflow to generate a draft on the generation page, which starts the task and streams its live log tail while it runs, or through roboflow_generate_workflow; then refine named nodes, drag positions and connect edges on the drawing board. Each task declares name, prompt, skillsets and terminal, desktop or browser execution. Save persists the graph and layout. The server warns when no robot covers a task's skillsets; warnings do not block saving or starting. RoboFlow randomly selects an available matching robot for each visit. Desktop and browser tasks share each robot's GUI queue. Branching tasks return an outgoing edge; zero or one outgoing edge needs no routing prompt. The protected Standard development workflow (id default) has one node, uses the default robot and requires a caller-selected execution mode. SQLite stores global definitions and run snapshots; logs and final responses stay in the working folder. See DS007.

First-use preparation

The first operation that needs a coding agent or GUI automation server resolves the current release, installs it into /data/tool-cache, and validates it. Opening a Desktop or the Terminal prepares every coding agent for robot-specific login, so an agent can be logged in before it is selected for the robot. Later starts reuse the active generations. When release lookup fails, RoboTeam uses the last valid generation if one exists.

Nested sandbox diagnostics

The current RoboTeam container cannot mount ALA's private procfs inside an additional user namespace. ALA therefore uses its capability-assisted private-proc path, retains its other Bubblewrap boundaries, and drops all capabilities before Codex starts. An error stating that neither private-proc path is available indicates a runtime capability or seccomp regression. RoboTeam must not bypass ALA or start Codex unsandboxed.

The dashboard and Manage skills dialog use Explorer’s Inter typography, shared color tokens and light/dark theme preference. RoboTeam reads assistosExplorerTheme, then webchat_theme, and follows the browser theme when neither is saved. Theme changes in another tab are applied automatically. Robot actions wrap on narrow screens.

Stopping a graphical task from WebChat pauses its robot queue for manual control. Existing queued GUI tasks stay paused until Resume. If you stop all previous GUI tasks, launching a new GUI task returns control to automation. CLI tasks do not prevent this reset. Logs report when manual control blocks a queued task. The outer Ploinky operation may be running while its inner RoboTeam task is queued; a running desktop container also does not mean its task has started.

The robot chat /model <model-id> [effort|default] command validates effort against ALA native model metadata before saving. A native model ID may contain spaces; the command resolves the longest known ID and treats a single trailing token as the effort. /model lists models and their supported efforts; WebChat autocomplete first offers models as subcommands, then the selected model's supported efforts and default as argument completions, and the terminal picker asks for effort when supported. RoboTeam saves the selection atomically for the conversation's agent in the robot home .ala/config.json under models and efforts. The folder's .roboteam/settings.json holds no coding-agent models. /model default clears both overrides for the current backend. Selecting a model without effort clears its old effort. Every execution snapshots this configuration; a running turn keeps its captured selection.

WebChat displays the model and its configured effort together in the header badge, for example native-model · high. Clearing the effort override removes the effort from that badge. The legacy Skills popup is removed; use the Conversation skills menu link, which opens RoboTeam's Conversation skills page for the current conversation. The page reads and changes that conversation only, through GET and PATCH api/robots/<robotId>/conversations/<sessionId>/skills; a stale policy version returns 409 and invalid or mismatched context is an error, never robot defaults.

Background monitoring diagnostics

Task-monitoring diagnostics are suppressed in the browser and server consoles. Isolated robot task executions do not reattach saved tasks from the folder journal. They do not become chat messages or change a workflow to failed. Diagnostics include the error code and a redacted reason. Polling retries with increasing delays and resets its interval when the connection succeeds. New session keeps observing the opened folder’s saved workflow tasks.

Code Development

The Code Development preset is created at startup, in the background: if the Ploinky marketplace is not reachable yet, for example during a reinstall, RoboTeam starts anyway and retries every five seconds until the preset exists. Planning produces a detailed implementation and testing plan. Execution delegates implementation to child workflows, ordering implementation, testing and documentation by their dependencies. Validation checks the assembled result against the request, runs appropriate tests and fixes scoped integration defects. The route is Planning → Execution → Run workflows → Validation. All three phases use terminal execution. Like Default, this preset is read-only and cannot be edited or deleted, including through the API. Startup creates it only when absent. Existing presets receive the routing update that removes the direct Execution-to-Validation edge the phase skill requirements below, and the sequential delegation prompts; historical run graphs remain unchanged.

Each phase selects a robot covering all its required DocumentationSkills skills. These requirements do not change robot configurations or the requirements of delegated child workflows.

Use Continue on a failed phase to retry it. If preparation failed before the robot started, RoboFlow starts that phase with its original context and your continuation message. If execution already started, Continue resumes its saved task. Completed earlier phases are preserved.

A phase that has not produced output displays an empty log. Live logs refresh while a phase is active; after it ends, the viewer fetches its final log once. Workflow status continues refreshing so a continuation started elsewhere becomes visible. Temporary live-log failures retry with increasing delays.

Workflow and phase errors appear in red outlined boxes. Select the text to copy it manually; unchanged errors remain selectable while the page refreshes.

Terminate workflow permanently ends the workflow and all its sub-flows after confirmation in an on-page dialog. Select Cancel to leave it running or Terminate workflow to confirm; resume will not be possible. It stops active phases, cancels pending questions, and prevents pending children from starting. Terminated workflows cannot be resumed or continued; their logs and results remain available in History.

The workflow header shows the first two lines of its prompt. For longer prompts, use the arrow to expand or collapse the text.

RoboTeam supplies the Observability Explorer toolbar plugin from IDE-plugins/observability. It opens fullscreen beside RoboTeam, with Requires human input, Running, and History tabs. Explorer discovers the plugin automatically, just like the RoboTeam toolbar plugin; its implementation and tests live in this repository.

Observability, supplied by AchillesCLI/roboTeamAgent/IDE-plugins/observability, appears next to RoboTeam and opens fullscreen. Its default Requires human input tab lists paused and failed workflows. A workflow waiting for a business decision shows its question and three suggested answers. Choose one, or choose Other answer and write your response, then select Send answer. RoboTeam continues the same task and native session. Running lists active and queued workflows; History lists completed, failed, paused, and terminated workflows. Select a card on the left to see its prompt, local start date and time, execution duration, and number of finished node visits on the right. Repeated visits count separately. View workflow opens the full RoboTeam execution page in a new tab. The panel refreshes automatically every five seconds, without a manual Refresh button or update-status row; failed updates are shown explicitly and closing it stops polling. Terminated workflows appear only in History and cannot be resumed. Workflow data remains owned by RoboTeam.

In the workflow type editor, drag task cards in the left list to reorder them, then save. The six-dot grip on each editable card indicates that it can be dragged. A line marks the insertion position. You can also focus a card and use Alt + Arrow Up or Alt + Arrow Down. New executions show that order in their phase list; existing executions keep the order captured when they started. Reordering the list does not change graph routing or the first task.

Sequential child workflows

Select Allow sub-flows on a task in the editor. It gains a purple outline and the required view-only workflow-creator skill. Connect it to the shared Run workflows node and draw that node's continuation edges. The creator may choose an ordinary route or select workflows from their IDs and descriptions, supply each with a prompt, and choose the edge to follow after they finish.

RoboFlow runs selected sub-flows sequentially in array order in the same working folder. They must contain no creators. Each child receives its own prompt and the final response of the preceding child’s last task. A failed child blocks later children until Continue completes it successfully. A paused child waits for Resume. Later children remain pending. After all children complete successfully, execution follows the chosen edge. The parent remains running while any phase is active; otherwise paused takes precedence over failed.

Open the creator's Sub-flows tab to see child states, durations and links. Each child page links back to its parent. Pause workflow pauses active phases and children. Once paused, the same control becomes Resume workflow and continues only paused work with “Continue where you left off”. Completed and failed children remain unchanged, and timers exclude the pause. User input appears in logs as a separate Markdown block with a green background.

Repositories without declared skillsets expose individual skill names and descriptions in robot discovery. Select them using repository-id/skill-name. Delegated tasks receive only explicitly selected skills, including copilot. Direct default chats initially select only the copilot skillset; explicit exclusions and empty selections remain authoritative.

Required human reports

Every robot, including default and existing robots, always receives the required human-report skill from DocumentationSkills. Ploinky resolves the workspace checkout or prepares its internal repository copy. The required skill is shown as view-only in Manage skills and cannot be disabled through the skill selection API. An unavailable required source prevents execution.

Every user prompt, including a continuation, requires the entire final response between identical <<human-report>> markers on separate lines, following the human-report skill. WebChat has no View Summary button. Each workflow phase exposes a human-report tab that lists complete reports without their markers and refreshes during execution. A conversation's reports are read on demand from the agent messages and final answers that ALA recorded in its transcript. Workflow output uses byte ranges, which the endpoint reads instead of searching all output; historical workflow results are indexed lazily, and historical raw logs without output provenance are excluded. No separate summary text file is written. Continuing a workflow phase appends to its existing result file and retains references to earlier results, while normal result reads return the latest response.

Administrators can delete a custom workflow type using Delete on its dashboard card. Confirmation is required. Existing runs and their history are kept; the built-in Standard development workflow (id default) cannot be deleted.

New assistant replies show Thought for seconds or minutes beside their time in WebChat. This is the elapsed response duration, including preparation and tool execution, and remains visible when reopening the conversation. Old replies without timing data show only their time.

In the workflow type editor, task cards with no matching robot keep their yellow warning border when switching tasks. A selected task also has a separate selection outline. Warnings clear when coverage validation finds a matching robot.

At the start of a new conversation, RoboTeam instructs the robot to read the SKILL.md headers in .agents/skills and use those skills when needed. The prompt is built in copilot/src/lib/prompts.mjs without enumerating skills. This instruction is sent once, not repeated on conversation continuation.

Prompt definitions are centralized in copilot/src/lib/prompts.mjs. When RoboFlow dispatches a task it supplies the complete graph, objective, current task ID and previous final responses. A task with multiple outgoing edges also receives routing instructions.

Markdown output

ALA output in View thinking, workflow phase and generation logs, WebChat task logs, and human reports uses the same Markdown renderer as final WebChat messages. Consecutive output lines render as complete blocks so headings, lists, tables and fenced code survive live updates. Raw HTML is escaped and links allow only HTTP(S). File paths and words receive no custom token highlighting. Stored logs and report offsets remain unchanged. Final responses in workflow phase logs use heavier text only, without a colored background, border or extra label. Other log views retain their bordered background. View thinking includes the completed response when it was not recorded in the log. It also accepts plain-text log responses from older running servers.

Human input

Enable Allows human input in an ordinary task to let its robot request a business decision missing from the prompt and context. The internal require-human-input skill submits a question with three suggestions, then the robot ends execution and the workflow stays paused. In Explorer Observability → Requires human input, select the workflow and choose a suggestion or Other answer, then Send answer. RoboFlow continues the same task and native session with the answer before resuming graph traversal. The tab also includes other paused and failed flows. Pending questions survive a service restart.
