RoboTeam Documentation

RoboTeam exposes robot management and task execution as MCP tools. The Ploinky Router applies the tool policy before RoboTeam receives a call.

MCP tools

Robot conversations and the default copilot

Explorer's Open Copilot here opens roboTeamAgent with robot=default and the selected cwd. Every robot card has Open Chat. The former AchillesCLI wrapper now lives in copilot/ inside RoboTeam; there is no separate AchillesCLI agent or image. Existing AchillesCLI data is neither copied nor deleted.

A robot owns its home and configured accounts. A conversation owns its cwd, ALA session, transcript and selected skill catalog. Each message executes another turn in that conversation. Independent CLI conversations and Simple tasks run concurrently, including while a GUI task runs. Desktop and Browser still share one container and one graphical task queue.

Use /session, /session new, /session resume <id>, /tasks, /model and /permissions. Codex and OpenCode support native approvals; Pi rejects ask-for-approval. The bundled copilot skillset is available to all robots and initially selected together with local workspace skills only for default. /skills lists allowed sets and skill descriptions; /skills use copilot,<repository-id>/read-pdf selects a union and /skills use none clears it. Later turns and continuations capture current source files; /skills pin explicitly keeps the last executed catalog and /skills live resumes live capture. See local skills and selection.

Commands available in every robot

WebChat autocomplete passes the selected robot and conversation id to the command catalog. /model lists native models through ALA for that conversation's saved backend. Before the first turn, discovery previews the available backend without creating or selecting a saved conversation. The menu refreshes on conversation or backend changes and reports model-discovery failures instead of silently showing no options.

The bundled copilot skillset contains bash, launch-gpt-researcher, and launch-robot. Codex, OpenCode, and Pi are ALA execution backends, not separate Ploinky workers or launcher skills. Use launch-robot for delegated robot work.

Every robot, including default, uses the same conversational wrapper. Commands select a conversation, inspect delegated tasks, choose skills, or configure subsequent executions. The robot's allowed skillsets and saved accounts determine which work it can execute; having the same command interface does not grant every robot the same skills.

CommandBehavior

/raw, /exit, /quitThe wrapper recognizes a rendering toggle and terminal-exit commands. WebChat does not close the browser tab through these commands; close the tab to leave it.

Robot repositories are managed through Manage skills in the RoboTeam dashboard. Conversation commands select from that robot’s catalog; they do not update repositories.

How commands reach a robot

For graphical delegation, launch-robot publishes liveSession: {mode, url} through the existing one-way task receipts after the session becomes ready. The wrapper verifies the remote task through the authenticated MCP client, persists this metadata with the task, and forwards it through structured WebChat events. WebChat renders the fixed English button Open live desktop or Open live browser in the task box; clicking it uses the existing right-hand panel. The script's stdout also returns the startup confirmation, task id and exact live-session Markdown link to the coding agent. Snapshot reads retain the link after refresh. Only bounded same-router paths are accepted; external URLs and model-supplied labels are not used.

Open Chat on a robot card or Open Copilot here in Explorer selects the robot and cwd. A terminal can use ploinky cli roboTeamAgent --robot analyst --dir /workspace/project. Ploinky starts server/robot-cli.mjs inside RoboTeam; that process prepares the robot home and runs the shared wrapper. A robot is a persistent record, not one permanently running process. Independent CLI connections and conversations can execute concurrently.

In a terminal, type a command and press Enter. WebChat sends an authenticated HTTP input request to Ploinky, which writes the message to the wrapper's standard input. In WebChat mode, the message is a JSON envelope terminated by a newline; the slash command goes in its text field. Ploinky supplies the originating tab and page identity so the wrapper applies session selection to that connection. The browser does not write directly to ALA or to the graphical container.

{"__webchatMessage":1,"version":1,"text":"/session new","attachments":[],"references":[]}

This example shows the command payload, not a replacement for Ploinky authentication or routing metadata. Bare text is also accepted by the wrapper, but its WebChat compatibility parser groups nearby plain-text lines; integrations should preserve Ploinky's framed message protocol rather than pipe several unframed commands at once. Wrapper output includes structured session, task, and interaction events that Ploinky forwards to the browser.

Local commands such as /session new, /skills use, and /tasks are handled by the wrapper without asking the coding agent to interpret them. An ordinary prompt or /exec starts an ALA turn. The wrapper passes the saved session UUID and uses --resume-session on continuation. ALA's separate --control-stdin channel receives structured live-message and approval responses, not the wrapper's slash commands. MCP tools such as startBrowserTaskForRobot are a third interface for delegated execution; they are not slash commands written to chat.

/session new
/skills use copilot
Inspect the files in this project.
/session
/session resume <saved-session-id>
Continue with the tests.

Submit each line as a separate interaction. Creating or selecting another conversation does not delete or cancel the previous one. Only one turn may execute in a conversation at a time; different CLI conversations can run concurrently. Desktop and Browser retain the single shared graphical container and queue per robot.

Dashboard controls

Administrators can select Open Terminal on a robot card. This opens Ploinky's existing WebTTY in a new tab, inside the already-running RoboTeam agent, with the current directory set to that robot's persistent home. It does not create a Desktop or Browser container or start an ALA task. Ploinky authenticates the administrator and verifies the live target and its workspace mount. If RoboTeam is not an eligible writable terminal target, the action reports an error without falling back to another agent or the Box.

Open Terminal prepares the shared Codex, Pi and OpenCode cache before requesting a WebTTY launch. The agent-installed /etc/ploinky/webtty-env.sh hook selects the validated robot home and loads its generated shell environment even though WebTTY disables normal Bash profile loading. Desktop and WebTTY use the same persistent authentication directories and /data/tool-cache/shell/bin entry points. This remains an administrator shell in the outer RoboTeam runtime, not an isolated robot sandbox. Terminal lifetime and closing controls belong to WebTTY. Failed launches keep their error visible in the new tab.

The robot card starts or stops the Browser and Desktop container. Once a graphical session is ready, the card prints its complete authenticated Selkies URL as a link. The link remains available while that session runs, so a user can reopen a window that was closed.

The Logs button occupies a separate row below the session actions. Its initial state hides the log panel. Activating it reads the latest 200 lines from podman logs for the active Desktop or Browser container, displays them beneath the button, and refreshes the snapshot once per second. RoboTeam starts both graphical containers with Podman's k8s-file log driver, which stores their standard output and error locally and keeps podman logs functional even though the outer RoboTeam container has no systemd journal. The panel never mixes ALA task output into these container logs. Activating Logs again hides the panel and stops the polling. New output stays visible while the reader is at the bottom; scrolling upward suspends automatic movement to the latest line. The dashboard does not display Take Control or Resume buttons.

How RoboTeam runs ALA

In each robot card, Manage skills lists permitted repositories and named combinations from skillsets.md. An administrator adds a credential-free HTTPS Git URL with a generated repository ID; the API also accepts absolute workspace sources and optional explicit source names. Import captures a revision and validates the descriptors without executing setup scripts. Skill folders must include their own scripts and resources; symlinks, nested skills, and dependencies outside a selected folder are unsupported. Removing a selected source makes future live executions fail visibly until reselected; an explicit pin keeps its validated copy. Local imports read original working files. Re-add a HTTPS source to import a newer revision, then explicitly reselect it in existing policies.

Administrator-only Delete robot requires confirmation and a stopped container with no active or queued tasks or live chat processes. It permanently removes the robot's saved logins, files, imported skillsets and task catalogs. It does not delete the original repositories or shared executable cache.

The three start tools accept skillSets, its alias skillset, and skills as comma-separated strings. Named skillset IDs, explicit whole sources and qualified individual identities form a union. Direct chats use scoped defaults, initially copilot,workspace for default and empty for other robots. Delegated task omission and explicit empty arrays remain empty. The task stores a conversation policy reference before queueing and captures current bytes after queue wait. Resume uses the current policy without overwriting newer settings. Active execution and explicit pins keep their captured revision.

/exec launch-robot {"mode":"desktop","robotName":"analyst","task":"Review the report","skillSets":["<discovered-skillset-id>"],"skills":["<repository-id>/verify-sources"]}

AchillesCLI's launch-robot accepts arrays or comma-separated strings and normalizes them for MCP. Its discovery script includes the catalog metadata in its text response. RoboTeam converts the selected union into ALA's exclusive --skill-catalog option, preserving the configured home and model while replacing ALA repository discovery for that task.

ALA is the LLM execution process. RoboTeam starts it in the outer RoboTeam container, in parallel with the graphical container. ALA then starts the selected coding-agent CLI inside its Bubblewrap sandbox. The Desktop and Browser MCP servers stay inside their graphical containers and are reachable by ALA through random loopback ports.

The concrete paths and random port differ for each robot and task. A Desktop task produces an invocation equivalent to:

ala \
  --home /data/robots/<robot-id>/home \
  --cwd /workspace/<project> \
  --taskFile /data/robots/<robot-id>/runtime/<task-id>.prompt \
  --ca codex \
  --MCPServers desktop=http://127.0.0.1:<port>/mcp

A Browser task uses the same command shape with browser=http://127.0.0.1:<port>/mcp. A Simple task omits --MCPServers and does not start a graphical container.

ALA argumentMeaning in RoboTeam
--homeThe robot's persistent home. ALA uses it for coding-agent authentication and configuration. The same directory appears as /config in the graphical container.
--cwdThe caller-selected workspace directory. ALA uses it as the writable work tree. Desktop and Browser containers receive the same directory at /workspace.
--taskFileA private file written by RoboTeam with the task prompt. RoboTeam uses a file so long prompts do not need to be embedded in the process argument list.
--caSelects codex, opencode, pi, or auto. The selected CLI must exist and its account state must be available through --home.
--MCPServersSupplies the task-local Desktop or Browser Streamable HTTP MCP address. The current ALA adapter injects this URL into Codex configuration for the run.
--skill-catalogThe private JSON array of absolute skill directory paths; each directory is mounted read-only under /workspace/.agents/skills. RoboTeam resolves its MCP selectors before launching ALA. The standalone ALA --skillSets name filter is not the robot's allowed-repository registry.
--modelOptional native model override for the selected coding agent.

--home supplies saved state; it does not contain a private copy of a coding-agent executable. RoboTeam resolves and caches the current Codex, OpenCode, and Pi npm packages. A concrete --ca selection places that CLI on ALA's PATH; auto prepares all three and lets ALA apply its configured priority. The Desktop mounts all three shared generations so a user can authenticate each CLI against the robot's persistent /config home. Use Codex for Desktop and Browser automation because task-local MCP URL injection is currently implemented only by the Codex adapter. OpenCode and Pi can run Simple tasks.

The shared server/robot-task.mjs wrapper prepares a conversation and starts the ALA command above. Chat uses the same engine through server/robot-cli.mjs. The engine also passes --session-id, --control-stdin, --permissions, a private --config, and --folder <runtime-directory> as ploinky-runtime for direct SDK scripts. Conversation state is stored in /data/robots/<id>/copilot; ALA native metadata stays in the robot home.

Persistent task conversations

Each task receives an ALA session UUID. RoboTeam passes --session-id <uuid> --control-stdin and adds --resume-session on later executions. ALA stores the selected backend and native continuation under <robot-home>/.ala/sessions/; RoboTeam stores private task descriptors under the robot runtime directory. The backend is pinned for that conversation, including across process restarts. A missing native session causes an explicit failure instead of a fresh conversation.

Stop cancels execution while preserving the conversation and GUI container. Resume sends Continue. for Simple tasks, or a current-screen observation instruction for Desktop and Browser tasks. A custom continuation sends the user's new prompt and, for GUI tasks, the observation instruction. Every execution has its own native Ploinky task, while AchillesCLI retains one local task id and WebChat log bubble. That bubble and Open Task both accept messages after completion or while the task runs. Queued messages are waiting for delivery; a receipt marked delivered means the backend accepted the message, not that it has completed the requested action.

Task and container lifetime

The three start tools use Ploinky's native asynchronous task contract. Their initial MCP response contains the Ploinky task id. Standard error becomes the live task log, standard output becomes the final result, and the worker process remains alive until ALA exits. Desktop and Browser starts declare resumeTaskForRobot as their continuation tool. When a user stops one of those tasks, the worker returns an opaque continuation handle that identifies the exact interrupted RoboTeam task. Callers use the normal Ploinky /task status route for completion and getSessionUrlForRobotDesktop or getSessionUrlForRobotBrowser for the live GUI URL.

Each robot has one active graphical ALA slot and a FIFO queue for Desktop and Browser, with independent concurrent CLI conversations shared by Desktop, Browser, and Simple tasks. A new request waits instead of failing because another task is active. Pressing Stop on a live WebChat GUI task cancels its native task for human takeover: ALA stops, the visible container remains active, and later queued requests stay paused while the user works through Selkies. The explicit MCP stop tools do not enter manual-control mode. resumeTaskForRobot validates the continuation handle, places the resumed request ahead of the waiting queue, and releases manual-control mode. The resumed prompt contains only the new instruction and a request to inspect the current screen and preserve the user's changes; the original assignment remains in the saved native conversation.

A completed GUI task leaves at most one container running. RoboTeam reuses it when the next graphical task has the same mode and resolved cwd. A different mode or cwd replaces the idle container before the queued task starts. A Simple task leaves an existing GUI container untouched. Use the separate container-stop tool when the visible session is no longer needed.

RoboTeam starts ALA with ALA_EVENT_STREAM=1. It converts coding-agent-message events into readable progress text, keeps the final ALA standard output separate, and lets Ploinky retain the complete forwarded task log. State changes such as queued, starting, and running also appear in that log. Successful completion updates the task status without adding a completion sentence to the log. The final response contains only ALA output, with no synthetic completion message when that output is empty.

Robot delegation

AchillesCLI's Anthropic launch-robot skill calls internal RoboTeam tools through the real Ploinky MCP client and Router. Its scripts/list.mjs provides discovery through robot_list. Launch input accepts desktop <robot name>: <task>, browser <robot name>: <task>, or compact desktop: <task> and browser: <task> forms selecting default. JSON may omit robotName; explicit blank or unknown names remain errors. The parent fixes cwd and observes the asynchronous task while the script waits for the authenticated GUI link. Deleting default does not cause task-time recreation.

First-use preparation

The first operation that needs a coding agent or GUI automation server resolves the current release, installs it into /data/tool-cache, and validates it. Opening a Desktop prepares Codex, OpenCode, and Pi so all three commands are available for robot-specific login. Later starts reuse the active generations. When release lookup fails, RoboTeam uses the last valid generation if one exists.

Nested sandbox diagnostics

The current RoboTeam container cannot mount ALA's private procfs inside an additional user namespace. ALA therefore uses its capability-assisted private-proc path, retains its other Bubblewrap boundaries, and drops all capabilities before Codex starts. An error stating that neither private-proc path is available indicates a runtime capability or seccomp regression. RoboTeam must not bypass ALA or start Codex unsandboxed.

The dashboard and Manage skills dialog use Explorer’s Inter typography, shared color tokens and light/dark theme preference. RoboTeam reads assistosExplorerTheme, then webchat_theme, and follows the browser theme when neither is saved. Theme changes in another tab are applied automatically. Robot actions wrap on narrow screens.

Repositories without declared skillsets expose individual skill names and descriptions in robot discovery. Select them using repository-id/skill-name. Delegated tasks receive only explicitly selected skills, including copilot. Direct default chats initially select copilot and workspace; explicit exclusions and empty selections remain authoritative.
