Documentation / Architecture

Architecture

The rootless Ploinky Box starts RoboTeam with the bounded nested-Podman contract; Podman 5.8.7 inside it starts one Chromium or Webtop container per active robot.

Outer runtime

The custom roboteam-runtime-v5 image provides Podman 5.8.7, Node.js, npm, Bubblewrap, fuse-overlayfs, pasta, curl, and Git. Inner writable layers and transient metadata live at /var/lib/roboteam-podman/storage; images persist at /data/podman/images. Overlay storage uses fuse-overlayfs with force_mask=0700. The manifest follows the AssistOS-managed runtime channel and requests Ploinky's nestedPodman capability; the install hook requires the v5 marker and a successful command reporting exactly podman version 5.8.7 before preparing data or the terminal hook.

Robot runtime

RobotStore owns workspace-wide durable metadata and directories. RuntimeManager constructs exact Podman argument vectors, gives each robot one active graphical ALA slot and a FIFO queue for Desktop and Browser, with independent concurrent CLI conversations, tracks active runs in memory, and removes only labelled RoboTeam containers. It retains at most one GUI container per robot. It reuses that container when mode and resolved cwd match, or replaces it after the active task finishes when a queued graphical task requires another mode or cwd. Cancelling a native graphical task for human takeover creates a manual-control hold that blocks the queue without stopping the container. The explicit MCP stop tools stop ALA without creating that hold. A validated continuation resumes the exact interrupted request ahead of waiting work and releases the hold. Inner runs use --ipc=none so bounded nested Podman does not attempt a forbidden mqueue mount; GUI containers receive a private /dev/shm tmpfs. When the cached Codex runtime is added to a GUI container, the constructed PATH retains LinuxServer's /lsiopy/bin so the Selkies backend remains executable. The HTTP server enforces administrator-only creation and deletion and reverse-proxies authenticated Selkies HTTP and WebSocket traffic.

RobotStore startup ensures the ordinary name default through the same creation/layout logic as other robots. Its lookup and mutation are serialized across processes with normal create/delete operations. Repeated startup reuses existing metadata and home without adding a marker or special ID. Corrupt or ambiguous records fail closed; ordinary deletion remains available, with recreation only on the next startup. This registry initialization neither starts a GUI nor changes per-robot FIFO execution.

Networking and task execution

The outer container stays on Ploinky's managed network and is enabled globally for workspace access. Ploinky provisions ALA through RoboTeam's link-install declaration. It reuses the workspace Git checkout or clones it if absent, and exposes /Agent/linked/AdvancedLanguageAgent as a symlink to the writable workspace mount. RoboTeam resolves the checkout's real bin/ala.mjs for tasks, Copilot and skill discovery. Existing checkouts are never pulled automatically. Runtime settings are internal constants in server/constants.mjs, not manifest environment options. ALA uses the Ploinky-selected AgentLib source. The launcher generates a fresh internal token for the service and MCP callbacks on each start; task children do not inherit it. AgentServer/MCP uses port 7000 and the authenticated RoboTeam UI uses port 3001. Inner containers use pasta; Selkies port 3000 and MCP port 8100 are published only to random outer loopback ports. Desktop uses a Streamable HTTP bridge to computer-use-linux; browser uses Playwright MCP over CDP to the visible Chromium. ALA runs separately in the outer runtime with the robot home and caller cwd, and starts Codex inside its Bubblewrap sandbox. Each start MCP command remains alive until its queued RoboTeam task and ALA process finish. The command writes parsed ALA messages to standard error for Ploinky task logs and writes only the final result to standard output. A cancelled GUI command stops its exact inner task and returns an opaque native continuation handle. resumeTaskForRobot receives that handle through the Router and starts the replacement command on the same caller-owned task timeline. The real entrypoint prevents Ploinky's Node.js symlink-preservation flags from changing the base of ALA's relative ESM imports. Failed ALA tasks expose a bounded diagnostic tail through internal task status.

Nested Bubblewrap limitation

ALA normally creates a user namespace together with private PID, IPC, and UTS namespaces and a private procfs. In the current nestedPodman deployment, the kernel rejects the private procfs mount inside that additional user namespace. ALA detects this condition before execution and uses the outer container's admitted mount capability only to construct the private PID namespace and procfs, omitting the extra user namespace and dropping all capabilities before Codex starts. The Bubblewrap filesystem boundary, controlled writable mounts, filtered environment, isolated temporary directory, and private procfs remain in force. Codex does not create a second native sandbox inside this boundary. Failure of both private-proc construction paths stops the task rather than starting Codex without ALA isolation.

Runtime tool cache

ToolCache resolves current Codex, OpenCode, Pi, computer-use-linux, Supergateway, and Playwright MCP releases when needed. An operator can pin Codex, OpenCode, Pi or Claude Code to one exact version with ROBOTEAM_CODEX_VERSION, ROBOTEAM_OPENCODE_VERSION, ROBOTEAM_PI_VERSION or ROBOTEAM_CLAUDE_VERSION; a pinned agent skips the latest-version lookup, keeps the same generation identity, and never falls back to another version. It installs candidates into unique generations under /data/tool-cache, probes them, and switches current.json atomically. Desktop containers mount all three coding-agent generations read-only so a user can configure them. ALA receives the selected cached CLI on PATH. An unavailable upstream falls back only to the last validated generation.

Source folders

server/ owns robot lifecycle and HTTP operations, with workflow execution in server/roboflow/ and native integrations in server/plugins/. public/ contains the browser UI, tools/ exposes MCP operations, scripts/ handles startup and installation, shared/ contains server/copilot processing, and IDE-plugins/ integrates with Explorer.

copilot/ contains the CLI package. Within copilot/src/, repl/ handles terminal sessions, mcp/ command discovery, permissions/ approvals, ui/ rendering, and skills/ bundled task skills. lib/ groups supporting modules into execution/, cli/, config/, storage/, skills/, ploinky/, tasks/, webchat/, diagnostics/ and errors/. Prompt construction stays in lib/prompts.mjs. Consumers import modules at their actual locations.

Tests live in tests/ and copilot/tests/; documentation lives in docs/, with specifications in docs/specs/ and shared HTML fragments in docs/partials/. See DS001 for the folder responsibility map.

Workflow coordination

server/roboflow/subflows.mjs owns catalog filtering, plan validation, child creation and the join for Run workflows. The service serializes transitions per run. SQLite commits child graph snapshots and parent references together. Child status changes trigger parent reconciliation; the coordinator consumes no robot slot. The task that allows sub-flows supplies the plan and continuation edge through its final response.
