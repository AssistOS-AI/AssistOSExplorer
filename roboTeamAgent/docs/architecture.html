Documentation / Architecture

Architecture

One Ploinky agent contains the RoboTeam control service, AgentServer proxy, persistent profile store, desktop process manager, profile dashboard, and noVNC viewer.

Router and service boundary

The Explorer-compatible application plugin under IDE-plugins/roboteam-tool-button contributes a toolbar action after WebMeet. It contains no profile state or authorization logic; it opens the existing Router-authenticated dashboard, while RoboTeam continues to own every profile mutation and desktop operation.

The manifest declares one authenticated agent-port route for container port `7000`. Ploinky authenticates HTTP and WebSocket requests, strips untrusted internal headers, and injects `x-ploinky-auth-info` with the authorized user identity. The control service refuses profile APIs and desktop WebSockets without that identity.

The service proxies Ploinky MCP paths to the bundled AgentServer on loopback port `7001`. The MCP tools call back into the control service with `ROBOTEAM_INTERNAL_TOKEN`; external requests cannot derive this generated value.

Profile store

The `ProfileStore` writes one metadata file and dedicated directories for every profile. Creation uses an exclusive filesystem lock, allocates a unique UID, writes metadata through a temporary file and atomic rename, and applies restrictive ownership and modes. Reads filter by owner before returning profile data.

Desktop manager

The `DesktopManager` holds only active-process state in memory. A profile remains durable in the store while display numbers, RFB ports, and websockify ports are temporary slots. The manager exposes no direct listener to external clients. The HTTP service upgrades an authenticated profile WebSocket and tunnels it to the loopback websockify listener associated with that active session.

ALA boundary

The architecture gives every profile a durable workspace that an external ALA task runner can mount explicitly. This repository does not define the task request schema, ALA process invocation, task-repository selection, or interaction between a task and the active graphical desktop. Those interfaces require a separate specification before implementation.
