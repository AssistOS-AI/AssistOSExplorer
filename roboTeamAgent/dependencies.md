# Runtime dependency selection

RoboTeam uses the existing AdvancedLanguageAgent runtime for native execution, skill catalog isolation, and continued sessions. `package.json` pins that Git dependency to commit `af98d8e2a75139f2a64b175567767eeb5f7aecc7`, which supports both JSON skill manifests and live catalog directories and keeps native runtimes installed below `/workspace` visible inside the task sandbox. A moving branch reference could install an incompatible runtime during a fresh deployment.

ALA is maintained at https://github.com/AssistOS-AI/AdvancedLanguageAgent and uses the MIT license, included in its installed `LICENSE`. Preserve that license when redistributing the package. To update, validate the proposed ALA commit with the repository suites and Ploinky's cross-repository skill acceptance test, then change the exact Git revision in `package.json`. Ploinky installs this manifest into its owned runtime dependency cache; a repository package lock does not select that cache's dependency versions.

RoboTeam resolves the installed runtime through `resolveAlaInstallation` when it prepares an execution; a missing or incompatible ALA installation fails agent preparation. The runtime cannot be replaced with Node built-ins because ALA owns the native backend and sandbox protocol. This is an existing dependency; this change pins its revision and adds no package.

ALA declares the `ploinky-agent-lib` package for standalone use. Managed Ploinky deployments must bind that package name to the single admitted workspace AgentLib source, just as they bind `achillesAgentLib`. They must not execute a private transitive copy. Native executables, Bubblewrap, and their existing installation requirements remain owned by the ALA and RoboTeam runtime setup. The propagation tests themselves use Node built-ins and require Node 22 or newer on Linux; their optional native mode also needs the configured native runtime and a dedicated authenticated home.

Model effort support uses the existing ALA dependency and Node built-ins; no package is added. The coordinated ALA source update supplies detailed native model catalogs, config load/save APIs, `codingAgents.efforts`, and all three native effort adapters. The pinned deployment revision must be updated to a validated commit containing that change before release; this source work does not replace the deployment pin or install tools.

## Outer runtime prerequisites

The existing operator-managed `assistos/roboteam-agent:runtime` image supplies Podman 5.8.7, fuse-overlayfs, pasta, Node.js, npm and Bubblewrap. Its producer locks `quay.io/podman/stable@sha256:f94b291ea3ad28ca5c9362dd6ffb673778aefa157e73b8cea76da7e47a917b1e` in `container-image-builds/images/roboteam-agent/sources.lock.json`. Node.js also provides the embedded SQLite driver used by RoboFlow. These are inherited runtime dependencies; this compatibility repair adds none.

Before creating persistent data or the terminal hook, `scripts/install.sh` checks the `/opt/roboteam-runtime/contract-v6` marker for `roboteam-runtime-v6`, the required commands, successful exact `podman version 5.8.7` output, npm execution with cleared `NODE_OPTIONS`, the storage configuration file, and executable `/usr/local/bin/roboteam-podman-init`. Only after all checks pass does installation invoke the helper, before preparing data. Service initialization awaits the same absolute helper with a 30-second timeout before Podman checks and managed cleanup. Helper failure stops both paths. The image-owned helper uses the existing `mount` and `findmnt` utilities to establish absent `/var/lib/roboteam-podman` as tmpfs with `size=2g,mode=0700,nosuid,nodev`, reuses existing tmpfs without clearing it, and rejects symbolic links or other mounted filesystems. Graphroot and runroot use its `storage` and `run` subdirectories; images persist under `/data/podman/images`. Missing or incompatible prerequisites fail installation with the runtime-contract diagnostic. Rebuild or select a compatible runtime through the image-definition repository; startup never downloads these prerequisites. The Podman base and runtime marker must be updated together with this consumer check and verified before publication.
