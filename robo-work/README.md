# robo-work worker (state slice S1 and the r10 wiring)

Internal worker-state library for the RoboWork execution provider. It is a bounded P1 slice: authoritative state for robot lifecycle intents, operation receipts, admissions, origin bindings, public references, generation fencing and resource blockers. Since the r10 wiring it also runs as a Ploinky agent: `manifest.json`, `server/main.mjs` and `server/runtime/*` (see "Wiring (r10)" below). The S1 library itself still never runs a robot command; the runtime layer does, through the Node sandbox in `server/sandbox`.

## Robot utilities

The coordinator exposes `POST /v1/coordinator/robots/models` with `{robotId, agent}` and `POST /v1/coordinator/robots/agent-status` with `{robotId}`. Both authorize through the `robots/get` rule before reading the worker cache. Native catalogs use protocol-mode ALA with no project grant. Agent status uses a fixed helper in a workload sandbox with the worker robot HOME, no project grant and no provider endpoint. Only model IDs and effort metadata, or agent availability, login booleans and sanitized version tokens, leave those executions.

OpenCode listings merge native models with every model permitted to the worker by its own Soul Gateway catalog. The worker uses the same Router upstream and catalog validation as its inference channel. Gateway entries from native HOME plugins are replaced by this worker catalog; other coding backends receive no gateway entries. The listing shares the utility's deadline, admission caps and fifteen-second cache. A failed or invalid gateway refresh refuses the whole listing, and the final projection is capped at 512 KiB and 4096 entries. Gateway effort choices are empty because the catalog mapping advertises none. Each inference channel continues to expose and accept only its execution's selected model.

Utilities use an internal `utility` admission, the resource ledger and the normal recovery path. They have a 12-second deadline, a combined 512 KiB stdout/stderr limit, and atomic caps of one open utility per robot and four per worker. Sanitized successful projections have a 15-second cache, keyed by robot revision, limited to 128 entries. Schema 10 records the utility kind. Earlier stores, including schema 9, are refused unchanged; there is no migration or automatic deletion.

## Storage

`openWorkerState({dataDir, workspaceId, provider, limits, now, create, runtime, faults})` uses built-in `node:sqlite` (Node 24 or newer, no npm dependency). The store is `<dataDir>/execution-store/worker-state.sqlite`. First creation requires `create: true`; a missing store without it is `not_found`. Symbolic links and non-directory or non-regular state components are refused with `state_corrupt`, as are corrupt files and workspace, provider or schema-version mismatches. A corrupt or empty file is never replaced or initialized without `create`. The database uses foreign keys, WAL, `busy_timeout=5000`, `synchronous=FULL` and synchronous `BEGIN IMMEDIATE` transactions. These checks assume supervisor-exclusive storage and are not a confined-filesystem boundary.

`limits` must hold explicit positive safe integers for `requestBytes`, `robots`, `receipts`, `admissions` and `resultBytes`. Production G5 bounds remain unqualified. Receipts and tombstones are never pruned; exhaustion is `capacity_exceeded`.

## Trusted context

Methods take an internal verified context made by `createVerifiedContext` (workspace, scope, owner, authorized operations, origin namespace, origin key, administrator flag), kept separate from the request payload. It is a brand checked by identity, so a serialized or hand-built object is `forbidden`. It is an internal precondition and not token verification; a later routed adapter must build it only from verified Ploinky evidence. Tests label every context synthetic.

## Runtime adapter

An adapter provides synchronous `canPrepare()`, `attestRobot(info)` and `admissionReady(info)`, and optionally `requiredKinds(operation)` and `verifyAbsence(info)`. The default refuses all of them, so nothing can be provisioned, attested, admitted or cleared. Tests use synthetic adapters in `tests/helpers/synthetic.mjs`.

## Behavior summary

Provision, configure and delete record an intent, an immutable receipt, a separately queried completion and (provision, configure) a preparation blocker. Retries return the recorded receipt, including after reopen. Admission commits receipt, origin binding, public reference and admission (with its recorded logical kind, and for a first turn its session) in one transaction. `lookupOrigin` matches the verified namespace, key and scope, and unknown and foreign origins are the same `not_found`. Every mutation checks the handle's bound generation inside its transaction.

## Resource blockers

`server/stateBlockers.mjs` is the single module that touches the blocker tables. A blocker has a reservation ID (also its resource ID, never reused), a kind, an owning robot or none (worker-scoped), an owning execution and attempt or none, the owning generation, an immutable locator and, once, an identity tuple.

| Transition | Rule |
| --- | --- |
| Reserve (`reserveResource`) | Current-generation writer. The reservation ID is always generated by the library (a caller cannot supply one). An attempt that is `stopping` or terminal is refused (`operation_conflict`); robot and worker scoped reservations stay possible. A process-bearing reservation gets `marker` (its reservation ID) added to the locator. A (kind, caller locator) pair is never reserved twice, whatever the state of the earlier blocker, so quarantined and cleared locators stay retired (`operation_conflict`). The retirement is per (kind, locator): the same locator under another kind is a different resource, and the check is on the caller's locator before the generated marker is added. `retained: true` is refused together with an execution or attempt, and for a process-bearing or `process-tree` blocker (`invalid_request`). |
| Commit (`commitResource`) | Only from `reserved`, once; writes the identity. |
| Settle (`settleResource`, `releaseResource`, `quarantineResource`) | From `reserved` (by locator) or `committed`, with the exact resource ID and owning generation, under current-generation writer authority. Records `released` or `quarantined`. |
| Retain (`retainResource`) | An end-path decision. Moves an unsettled robot-owned blocker to the retained record so it no longer delays its attempt. Idempotent for a blocker that is already retained. Refused for a blocker of a prior generation (`stale_generation`), for a process-bearing or `process-tree` blocker (`invalid_request`) and for a terminal attempt (`operation_conflict`). A `stopping` attempt of the current generation may retain a non-process blocker: that is the intended transfer on a normal end path. |
| Clear (`clearQuarantine`) | Only from `quarantined`, to `released_by_operator`. |

The same table is enforced by a trigger. The library records the outcome the trusted runtime caller reached; it does not measure the release deadline and does not inspect `/proc`. A blocker settled absent (`released` or `released_by_operator`) lets deletion complete. A quarantined blocker keeps its robot nonready (`resource_quarantined` for admission, configure and attestation) and an accepted deletion `deleting`; a quarantined blocker with no owning robot marks the worker `degraded` (`getWorkerStatus`) and refuses only operations whose kind the adapter lists in `requiredKinds(operation)`. These effects are derived from the table, so they apply from the transaction that records the quarantine.

`clearQuarantine(context, {operationId, resourceId, attestation})` needs a verified direct administrator in the context (`administrator: true` plus the `administer` operation). `attestation` is the operator's evidence digest (64 hex characters). Order: administrator check, then one read snapshot that checks the writer generation first (`stale_generation`), then looks for a receipt to replay, then reads the blocker. Then the adapter's `verifyAbsence(info)` runs outside any transaction (`false` is `resource_present`; a throw, a malformed result or no answer is `runtime_unavailable`, which is what the default adapter yields). Last, one transaction re-checks the receipt and replays it when present, and otherwise compares-and-sets on still-quarantined and the current generation, writes `released_by_operator`, an immutable audit record (actor, time, evidence digest) and the receipt, and clears the owning robot's readiness attestation.

## Ending attempts

`beginAttemptEnd(context, {executionId, attemptId, expectedState, outcome})` records the classification (completed, failed, paused, human-input, cancelled or interrupted) and the bounded `outputText` and `data` payload, then moves the attempt to `stopping` (reference: `stopping`, `cleanup: pending`, no result). `settleAttempt` is an internal function without a public signature. It runs in the same transaction when the attempt has no unsettled blocker, and otherwise in the transaction that settles or retains its last blocker. It publishes the stored payload unchanged with `cleanup: released` or `quarantined`, once. A quarantined `process-tree` blocker makes the status `failed` with reason `termination_unverified` and keeps the recorded classification, `outputText` and `data` in the result. `transitionAttempt` only moves `queued` to `running`.

## Origins and operation IDs

An origin is keyed by workspace, verified `originNamespace`, verified `originKey` and `originRequestId`. The context rows are `mcp` with `user:<id>` or `agent:<principal>`, and `coordinator:<principal>` with `owner:user:<id>` or `binding:<id>`. For `admit`, `operationId` must equal the first 22 base64url characters of SHA-256 over the canonical JSON `{originNamespace, originKey, originRequestId}` of the context; any other value is `operation_conflict`. A re-invocation with the same origin returns the recorded admission without a new receipt, and a caller presenting the same `originRequestId` under another namespace or key derives another operation ID, admits independently and cannot observe the first origin (`lookupOrigin` returns `not_found`).

## Recovery

`beginGenerationRecovery(expectedGeneration)` rolls the generation once. Pending preparations are interrupted without replay and readiness attestations are invalidated. Every unfinished attempt of the prior generation that is not yet `stopping` moves to `stopping` with classification `interrupted`; one without an unsettled blocker publishes its interrupted result in the same transaction, and an attempt that was already `stopping` keeps its classification and payload. `completeGenerationRecovery` needs every prior-generation blocker settled (`released`, `quarantined` or `released_by_operator`) and every prior attempt settled; until then fresh admission, provisioning, configuration and attestation fail with `recovery_pending`.

## Adapter results and errors

Adapter calls fail closed. `canPrepare`, `attestRobot` and `admissionReady` must return exactly `true`; `requiredKinds` must return an array of strings and `verifyAbsence` must return a boolean. A throw or a malformed result is `runtime_unavailable` with no adapter text, inside or outside a transaction. SQLite errors are mapped by their primary code (the low byte of the extended code): busy and locked (5, 6, 261, 517, 773 and so on) are `runtime_unavailable`, only a UNIQUE or PRIMARY KEY violation (2067, 1555) is `operation_conflict`, because the library's own checks run before such an insert and it can only be a lost race. Every other failure, including a trigger rejection, CHECK, NOT NULL and FOREIGN KEY violations, is `state_corrupt`, so a logically inconsistent row or a library bug never looks like a benign race.

## Opening a store

A store with uncheckpointed WAL frames, the normal state after a killed writer, is validated first through a read-only connection, and a second read-only connection is held across the read-write close of a late refusal. A refused open therefore leaves the main file and the WAL byte-identical. SQLite may still rewrite the contents of the `-shm` recovery index on any open, even a read-only one, so the `-shm` bytes are not claimed stable; the library never deletes it. A read-only open of a store that has no `-wal` or `-shm` leaves empty ones behind, which is why such a store is validated by the read-write connection instead, and a stale `-shm` with a missing `-wal` is rebuilt by SQLite on the next read-write open. At open, `PRAGMA quick_check` must report `ok`, otherwise the open is refused with `state_corrupt`. This is `quick_check`, not the slower full `integrity_check`: it detects structural damage such as truncation and malformed pages but does not cross-check every index entry against its table. The schema version (now 7: the r10 wiring widened `reference_event.type` to `state`, `ala` and `truncated`, with no migration), the required blocker, admission, origin, reference, binding and control columns and the unique locator index are verified as well, so a store with an older layout is refused at open. A store without a WAL is validated by the read-write connection, whose close writes nothing. The statement that switches a new database to WAL is retried on busy or locked for up to 5 seconds, because SQLite does not always run the busy handler for it when several processes create the same store at once (observed: about 10 percent of 8-process starts failed within milliseconds with `runtime_unavailable` before the retry). A busy error that outlasts the retry is `runtime_unavailable` and is retryable.

## S1x extension (bindings, observation, control, token replay)

An additive extension for the S3b coordinator adapter. Schema version 4 adds the `binding`, `reference_event`, `reference_cursor`, `reference_control` and `token_replay` tables; no column of an existing table changes. Every write commits inside the same `BEGIN IMMEDIATE` transaction as the operation it belongs to.

| Piece | Rule |
| --- | --- |
| Limits | `limits` is exactly the five base keys, or the base keys plus all of `bindings`, `controls` and `tokenReplayEntries`. A method that needs an absent extension limit refuses with `capacity_exceeded`. |
| Contexts | `createVerifiedContext` takes an optional `robotOwnerId` (for example `workspace:<id>`): robot rows are recorded and compared against it, while the execution owner stays `ownerId`. `createVerifiedServiceContext` builds a context with no origin row for workspace robot lifecycle, readiness and reads (`provision`, `configure`, `delete`, `read`, `adapter_complete`, `attest`). Admission, origin lookup, binding, control and reference observation refuse service contexts. |
| Bindings | `registerBinding(context, {operationId, bindingId, kind, parentBindingId?}, replay?)`. Root form: a coordinator-API context (`coordinator:<p>` / `owner:user:<id>`) records `ownerId` with evidence `owner-grant`. Derived form: the parent's background context (`coordinator:<p>` / `binding:<parent>`) whose `ownerId` equals the parent's owner; the child is a `flow`, inherits the owner and the root, at depth at most 16. A retry returns the receipt; the same binding under another operation is `operation_conflict`; a missing, foreign or differently owned parent is `not_found`. `registerBinding` registers only `flow` and `schedule`; a `generation` kind, and any ID with the `gen_` prefix whatever kind is claimed, is `invalid_request`. Rows are never deleted; only `state` and `fence_revision` may change, through fences and continuation accepts (see the S6 section). `readBindingOwner({coordinator, bindingId})` is an internal read. |
| Background admission | `admit` under `coordinator:<p>` / `binding:<id>` requires that binding and its root to be active and owned by `ownerId`; otherwise `not_found`, with nothing recorded. The binding must be a `flow` or `generation` binding: a `schedule` binding is `invalid_request` with reason `binding_kind`. |
| Events | One state event per transition (queued, running, stopping with `cleanup: pending`, terminal with its `cleanup`), appended in the transaction that makes it. `listReferenceEvents(context, {referenceId, after, limit})` returns `{events, nextAfter}` with ISO-8601 `at`, refuses `after` beyond the last sequence, and returns `{gap: true, snapshotSequence}` before the retained window. |
| Observation | `observeReference(context, {referenceId})` returns the reference, `originRequestId`, logical and attempt identity, state, cleanup, result, `endedReason` (terminal only), `sequence` and `previousReference`. Visible to the execution owner, a verified administrator, or the background origin row the reference was admitted under; anything else is `not_found`, like an unknown reference. A background-binding context (`coordinator:<p>` / `binding:<id>`) gets the origin-row basis only, whatever `ownerId` or administrator flag it carries, so it can read its own binding's references and control none. |
| Control | `controlReference(context, {referenceId, operationId, op, attemptId?, payload?}, replay?)` with `op` `stop` or `message` (`payload {message, displayText?, id?}`); `pause` on an execution reference is `invalid_request`, decided after visibility (a caller who cannot see the reference gets `not_found`). On an observation reference the controls are the Part D fences (S6 section). Order: visibility (`not_found`), operation rule (stop: owner or administrator; message: owner; otherwise `forbidden`), recorded-control replay, attempt identity, capacity, effect. A queued stop cancels in the same transaction (`delivery: applied`); a running stop or message is recorded `delivery: pending` for the execution engine; a stop of a stopping or terminal attempt is `not_applicable`, computed and not recorded; while a stop is already pending for an attempt, a further stop returns that pending outcome without a new record, so repeated stops cannot exhaust the shared `controls` capacity; a message to a non-running attempt is `operation_conflict`. A message's canonical JSON payload `{message, displayText?, id?}` (bounded by `requestBytes` before persistence) is stored immutably with the record for the execution engine (NULL for `stop`), is part of the request digest, and is never returned by any read. |
| Token replay | Mutating methods (`admit`, `registerBinding`, `controlReference`, `beginProvision`, `configure`, `beginDelete`) take an optional `replay = {items: [{key, retainUntilMs}]}` (1 to 8 SHA-256 base64url keys) and consume it first in their own transaction: a live key is `forbidden` with reason `token_replayed`, a key whose `retainUntilMs` is not after the store clock is `invalid_request`, a full table is `capacity_exceeded` and nothing is evicted; at most 256 expired keys are pruned per consumption. `consumeTokenIds(replay)` burns the keys of a refused request in a separate transaction. |
| Robots | `listRobots(context)` returns every robot under the context's robot owner, tombstones included. |

## S6 source-only subset (schema versions 5 and 6): admission kinds, observation and obligations

Schema version 5 was one bump with no migration (R18), and version 6 (delta K-1, after the W2 review) keys the open-continuation index per coordinator and adds the obligation acceptance sequence, again with no migration: a store of an earlier version is refused at open with `state_corrupt`. It adds the recorded logical kind, the `session`, `obligation` and `outbox_revision` tables, observation references and the binding fence columns. It enables no deployed admission or execution path: the default runtime still refuses every admission and obligation admission and records nothing, and no caller is switched.

| Piece | Rule |
| --- | --- |
| Admission kinds | `admit` takes `kind` `task` (`logical: {}`), `continuation` (`logical: {logicalId}`) or `turn` (`logical: {sessionKey}`). |
| Recorded logical kind | `admission.logical_kind` is `task`, `session` or `flow`, recorded at admission, CHECK-constrained and immutable (a trigger). A `task` on the MCP or coordinator-API row records `task` with a new logical ID. A `task` on the background row records `flow` with the logical ID derived from the coordinator and the binding (the first 22 base64url characters of SHA-256 over canonical `{coordinator, bindingId}`), so every phase under one binding shares it and the same flow ID under another coordinator derives another. A `turn` records `session` (a turn is always session work, by CHECK). |
| Turns | Coordinator-API row only: on the MCP or background row a turn is `invalid_request` before any state access. `sessionKey` matches `^[A-Za-z0-9_.:-]{1,128}$`. Specification version 1 is exactly `{version: 1, prompt, model?, effort?, cwd?}`: `prompt` 1–32768 Unicode code points, `model` and `effort` 1–128, `cwd` relative (1–4096, no leading `/`, no `..` segment); no authority-named key at any depth; bounded by `requestBytes`. The first turn of a conversation creates the session `(scope, sessionKey)` in the admission transaction (after the readiness and capacity checks, so the `admissions` limit bounds sessions); later turns join it and share its logical ID. Joining with another robot is `operation_conflict`. A turn is admitted `queued` even while an earlier turn of its session is active. |
| First in, first out | `transitionAttempt` of a session turn is `robot_busy` while any earlier admission (lower rowid) of the same session is `queued`, `running` or `stopping`. Tasks and flow phases are not serialized. |
| Continuation | The named logical must be in the context's scope, with its owner and robot, otherwise `not_found`, so a foreign logical is never disclosed. It inherits the recorded kind. Only `task` work continues: an active attempt of the logical is `robot_busy`; a `session` logical (continue with `turn`) or a `flow` logical is `invalid_request`. |
| Observation facts | `observeReference` adds `logicalKind` and, for flow work, `bindingId` (from the reference's `binding:<id>` origin key), from which the S3b projection publishes `logical: {kind, id}` (the binding ID is the wire `logical.id` of flow work). An unrecorded kind is `state_corrupt`. |
| Recorded admission state | The admission receipt records `admissionState` (`queued` for an execution). `lookupOrigin` returns it as `admissionState` beside the live view, and both lookups project it, never live state. |
| Observation references | `reference.kind` is `execution` or `observation`. An execution reference carries its execution, attempt and logical IDs; an observation reference carries only its obligation (`reference.obligation_id`, equal to the reference ID), and an origin carries exactly one of an execution or an obligation (CHECKs). |
| Bindings and fences | `binding.kind` admits `generation` and `evidence` admits `obligation` (a root flow or generation binding created by an accepted obligation; a `generation` binding always has that evidence). `state` admits `paused` and `cancelled` on roots only; a trigger allows only active→paused, active→cancelled, paused→active and paused→cancelled, each with `fence_revision` + 1, and `cancelled` is final. |
| Obligation tables | `obligation` records the admitting coordinator, owner, request, deadline, decision state (`pending` to `accepted`, `rejected`, `expired` or `cancelled`; `accepted` to `paused` or `cancelled`, by trigger), continuation binding and expected fence revision, and a `bound` flag behind the one-open-continuation unique index, keyed on `(coordinator, continuation_of)` because bindings are per coordinator (version 6). `accepted_seq` is a strictly increasing acceptance sequence assigned in the accept transaction, unique and immutable, present exactly when a domain record is. `outbox_revision` rows are immutable and carry their fence revision. `reference_control.source` (`relay` or `fence`) keeps fence-written stops out of the `controls` count. |
| Limits | The S6 keys `obligations`, `outboxRevisions` and `obligationAcceptMs` are accepted only as a complete set on top of the base and S1x keys; a method that needs an absent one refuses with `capacity_exceeded`. |
| Obligation admission | `admitObligation(context, {operationId, originRequestId, obligationKind, request, continuationOf?}, replay?)` (operation `obligate`). Coordinator-API row, or MCP row with the verified hop coordinator on the context; the background row is `forbidden`. The operation ID derives from the origin, and the receipt replays it. Runtime readiness comes first (the default runtime: `runtime_unavailable`, nothing recorded), then `recovery_pending`. `request` is a plain object without authority keys, bounded by `requestBytes`. One transaction records the obligation, its observation reference (`obligationId` = `taskRef.id`), origin, a `pending-coordinator` state event and the receipt (`admissionState: 'pending-coordinator'`); `acceptBy` is the store clock plus `obligationAcceptMs`. A `flow-continuation` names `continuationOf.bindingId`, a root `obligation` flow binding of this coordinator and owner (otherwise `not_found`) that is `paused` (`active` or `cancelled` give `operation_conflict` with reason `binding_not_paused` or `binding_cancelled`) and has no other open continuation (`operation_conflict`); its fence revision is recorded. |
| Coordinator context | `createVerifiedCoordinatorContext({workspaceId, scope, coordinator, operations})` with `decide` (accept, reject) or `reconcile` (list, outbox): the verified coordinator alone. Another coordinator's obligation is `not_found`. |
| Accept | `acceptObligation(context, {operationId, obligationId, domainRecordId}, replay?)`, one transaction at the store clock. `obligationId` is the observation reference ID in the exact S1 form (22 canonical base64url characters). `domainRecordId` is `flow_<24 hex>` for a launch, `gen_<24 hex>` for a generation, the continued binding for a continuation (otherwise `invalid_request`). A pending obligation at or after `acceptBy` commits `expired`. A launch or generation creates its root binding (evidence `obligation`, the obligation's owner, fence revision 0), unless that ID is already a binding of this coordinator (`operation_conflict`, nothing changes, no receipt). A continuation moves its binding from `paused` to `active` (fence revision + 1) only while it is still paused at the recorded revision; otherwise it commits `rejected` with the stored reason `fence_changed`. The reply `{obligationId, decision, reason?, state, bindingId?, fenceRevision}` is recorded under the operation ID; a decided obligation replies `accepted` once accepted (whatever fence followed), otherwise `refused` with `expired`, `rejected`, `cancelled` or `fence_changed`. |
| Reject | `rejectObligation(context, {operationId, obligationId, reason}, replay?)`, `reason` matching `^[a-z][a-z0-9_]{0,63}$` (stored as `coordinator:<reason>`, so it cannot alias `fence_changed`). Pending at or after `acceptBy`: commits `expired`, refused `expired`. Pending: `rejected` (the reference publishes failed / `coordinator_rejected`). Decided: the recorded rejection, or refused with `accepted`, `expired`, `cancelled` or `fence_changed`. |
| Expiry | Reads compute `expired` without committing it. The next mutation of the obligation (accept, reject, a pending `stop`) or `sweepObligations()` (store clock) commits it. |
| List | `listObligations(context, {state: 'accepted', unbound: true, after, limit})`: this coordinator's accepted obligations whose outbox revision 1 is not applied, in acceptance order (`accepted_seq`, so equal or stepped-back clock values cannot reorder or skip an entry), at most `limit` (1–1000); `after` is `''` or a `nextAfter` (an obligation ID of this coordinator that was accepted); anything else is `invalid_request`. |
| Outbox | `applyOutbox(context, {obligationId, revision, fenceRevision, kind, data}, replay?)`. Revision 1 is exactly the `bound` kind; later revisions are last + 1. The same revision with the same canonical body returns the recorded reply; another body, a gap, a revision before acceptance or after a terminal one is `operation_conflict`. A fenced interval, or a `fenceRevision` older than a committed fence, applies nothing: `{applied: false, fenced, fenceRevision}`. A `terminal` revision publishes the reference's result once; `data` has no authority keys and is bounded. |
| Fences | `controlReference` on an observation reference, owner or administrator: pending `stop` before `acceptBy` cancels, at or after it commits `expired` (`not_applicable`); pending `pause` is `operation_conflict`; on an accepted interval `stop` and `pause` are cancellation and pause fences (`pause` of a generation is `operation_conflict`); `stop` on a paused interval whose binding is still paused, with no later interval accepted, cancels the binding and keeps the paused result; everything else is `not_applicable`. A fence moves the root binding with fence revision + 1, cancels queued executions admitted under the root or its derived bindings (this coordinator's background rows) and records one pending fence stop on each running one. Fence controls never hit the `controls` capacity; applied ones are recorded and replay their bytes. `message`, `attemptId` and `payload` are `invalid_request` after visibility. |
| Generation reads | Observe and events of a `generation` observation reference are also visible to a coordinator-API user context of the obligation's admitting coordinator; control still needs the owner or an administrator (`forbidden` for a visible caller who is neither). Every other context, `/task-refs` callers included, keeps the owner, administrator or origin rule. |
| Observation snapshot | `observeReference` on an observation reference returns `referenceKind: 'observation'`, the state (`pending-coordinator`, `accepted`, `completed`, `failed`, `cancelled` or `paused`), `obligation {obligationKind, state, acceptBy, fenceRevision}`, `logicalId` (the accepted domain record ID, or null) and the result; there is no attempt. `lookupOrigin` returns the recorded `admissionState` and `referenceKind`. |

## S6 source-only subset: terminal-target inventory (Part E)

`createTerminalTargetsAdapter({store, workspaceId, verifier, basePath})` serves `POST <basePath>/targets`, where `basePath` is the declared `terminals.path`; `createTerminalTargetsHttpHandler` (in `providerHttp.mjs`) dispatches only that method and path (anything else is 404 without an adapter call). It adds no schema.

| Piece | Rule |
| --- | --- |
| Authentication | `verifyProviderTerminalTargetsRequest` (`coordinatorAuth.mjs`): a Router Request in `x-ploinky-auth-info` with `typ: router-request`, `iss: ploinky-router`, `aud` = the provider, tool `__provider_terminal_targets__`, the received method, path and `rch` (method, path, query, raw body hash), a valid HS256 signature and lifetime. A fresh default-runtime store, or any store after the worker-start generation recovery under the default runtime, lists nothing |

## Known limitations

The same `originNamespace` and `originKey` arriving under two different scopes is not expected (a key identifies one verified caller). If it happens, `admit` with an origin ID that the first scope already used returns `operation_conflict`, while `lookupOrigin` from the second scope returns `not_found`, so the first scope's origin can be inferred. This is outside the specified origin rows and is not fixed here.

## Notes

A failed provision leaves the robot `failed` at revision 0; it is repaired with an explicit `configure` using `expectedRevision: 0`. `SCHEMA_VERSION` (now 6) is a single pre-release constant. `faults` on `openWorkerState` (`beforeCommit` and `afterCommit` taking a transaction label, `afterPragmas` taking the connection) is a test-only surface. After the pragmas are set, `journal_mode` (`wal`), `synchronous` (`2`) and `foreign_keys` (`1`) are read back for the connection, with BigInt values normalized, and any other value refuses the open with `state_corrupt` and a bounded `reason` (`pragma_journal_mode`, `pragma_synchronous` or `pragma_foreign_keys`).

### Protected-name masks: how they work and their known limits

Protected names (`.env`, `master-key`, `*.secrets`, `.ploinky`, `.data`, `.ploinky-box`, `.roboteam`, folded and Unicode-normalised) inside a project grant are hidden when a sandbox starts. `sandboxPrep` (root, inside a private mount namespace) opens the grant by an anchored `O_NOFOLLOW` walk, refuses a directory whose device and inode differ from the supervisor's record, scans it, binds an empty read-only file or directory over each protected entry (and over each provider `exclusions` path), scans the real tree again, and verifies every mask through a fresh descriptor of the staging view. Only then does bwrap start. A start that cannot be verified is refused `mask_unverified` and no robot code runs. A protected symlink is not masked (its target is governed by its own name).

Known limits, accepted and recorded (decision M-41, r10 AC9):

| Limit | What happens | Why it is not closed |
| --- | --- | --- |
| A name created later | A protected name that a writer creates, or attaches to another object by renaming it, AFTER verification is visible in a sandbox that is already running; the next start masks it | Masks are mounts of the start; the project stays live (Daniel, 2026-10-30) |
| A masked object renamed after verification | The mask is attached to the object, so it moves with the object: the object stays hidden under its new name, and the old name now belongs to whatever the writer put there | A mount follows the object, not the name |
| A rename and rename-back inside the mount calls | A writer that renames a protected object away and another object in, mounts run, and both are renamed back within the few milliseconds between the second scan and the mounts, can make a mask land on the other object; verification then confirms the NAME is masked while the scanned object is not | mount(8) resolves the target path at the moment of the call; the second scan of the real tree (prep) narrows the window but a rename and rename-back inside it cannot be told apart |
| A path renamed under bwrap's remount | Between prep and bwrap's own recursive bind, a writer can rename a masked path away; bwrap then fails ("Unable to apply mount flags ... No such file") and the command never runs. This is a refused start (observed 1 in 200 under a racing writer), not an exposure; its blocker is released | The refusal comes after prep from bwrap, so it is not the `mask_unverified` code |

The rename windows need a writer outside the sandbox (Explorer, a human, trusted code): a sandboxed robot cannot rename or delete a masked entry (`EBUSY`). A late protected name can also be made by another robot that shares the grant; a sandbox already running sees it until it ends. `tests/sandbox/live/race.mjs` measures them under a hostile racing writer (200 starts: each verified or refused; no object masked at verification ever shows its real content; the manifests of the worker store and other HOMEs are unchanged; at least 25 % of the starts must verify, so the run cannot pass by refusing everything) and `tests/sandbox/live/hostilepeer.mjs`, `crash.mjs`, `restart.mjs`, `backtoback.mjs`, `smoke.mjs`, `modelChannel.mjs` (the model channel's key hygiene and isolation) cover the other confinement and recovery claims. The live probes run as container root in the nested-podman profile (or as extra processes in the Box worker) and print one JSON document.


### Recovery and reused namespace inodes

The kernel reuses namespace inode numbers (a killed execution's network namespace became the replacement worker container's own). While a supervisor runs, it pins the namespaces it recorded, so a process that names a recorded inode is a real holder. After a crash there are no pins, and generation recovery (`recoverGeneration`, `runtime/recovery.mjs`, `walker.walk(blocker, { recovery: true })`) therefore never acts on an inode alone: a recorded inode equal to the supervisor's own namespace is treated as reused, and a holder counts only if it is attributable to the recorded execution (it carries one of the execution's reservation markers, is or descends from a process recorded for it by pid and start time, or sits in a pid namespace one of its trees still proves it owns; the prep and stage processes carry the marker on their argv at every exec stage, and their `mount` children descend from them). The netns blocker's by-name proofs (netns file, both veth ends, nft table) still decide whether the network is gone. A robot whose re-attestation keeps failing (`resource_quarantined`) is retried with a doubling delay (5 s up to 5 min) and the failure is logged once per state change.

Skills view (T2, decision M-22): a version-2 specification may carry `skills` (at most 64 `{name, path, required?}`, names unique and of the form `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`) with `skillsDigest`, the SHA-256 of their canonical JSON (the recorded selection digest; a mismatch is refused at admission). RoboTeam decides the selection (policy, required and admitted channel skills) and sends declared workspace paths; the worker alone resolves them (`executionFactory.mjs`): read-only through the anchored grant resolver (a source under `.ploinky/repos` as `skill-source`, depth at least 4; nothing else under `.ploinky`, no `.roboteam`, no link), and each must hold a regular `SKILL.md` (opened below the folder's descriptor, no link followed). Any refusal fails the attempt before anything starts: a required skill with `skill_required_unavailable`, another with its `grant_*` code or `skill_not_a_skill` (no skill is dropped silently). Skills are never ALA `--folder` entries or project grants. Every workload sees them at `/run/robo-work/skills/<name>`: prep stages each one exactly like a grant (anchored re-open with the recorded identity, scan, mask, rescan, verify) under a reserved stage name (`s<i>`, `bwrapArgs.mjs` `SKILL_STAGE_NAME`; a project grant can never carry one and a skill always does), then re-checks the regular `SKILL.md` through the staged view (`mask_unverified` otherwise), and bwrap binds it read-only over a read-only tmpfs (`--perms 0555 --tmpfs`, the binds, `--remount-ro`), so the view holds only the admitted skills and every write is EROFS. Masks and exclusions apply inside a skill as in a grant: protected names are masked by the same scan, and each specification `ignore` path below a skill folder becomes that skill's exclusion (masked in the view whether or not a grant also holds it); an `ignore` path equal to a skill folder or above it refuses that skill (`skill_folder_ignored`, or `skill_required_unavailable` when required). This relies on the launcher passing each grant entry's fields to `buildBwrapArgs` unchanged. A workload's `/run/robo-work` is its own read-only tmpfs (only the channels and skills binds), and its sandbox root is remounted read-only after every mount (decision M-69 Q2), so a workload can neither create nor rename anything outside its binds; HOME, the project grants, `/tmp` and `/dev/shm` are their own mounts and stay writable.

Active runtime sources (decision M-63, plan section 223): a folder that RoboTeam, the worker or Ploinky runs code from is never a writable robot grant or working project; an explicit read-only view of it (a skill folder, a read-only folder) stays permitted. The sources are the repository of every enabled agent's code (`agent-repository`), the Ploinky Agent library (`agent-library`), the AchillesAgentLib checkout selected in `local` mode (`agent-runtime-library`), every link-installed repository such as AdvancedLanguageAgent or DocumentationSkills (`linked-repository`), and the worker's own ALA checkout. Ploinky's Router reports them, workspace-relative and derived from the active routing lease, on its private listener (`GET /api/edge/runtime-sources`, callers limited to agents that declare an `executionProvider`); the worker reads them with `fetchRuntimeSources` from `${ROBO_WORK_PLOINKY_AGENT_DIR}/lib/runtimeSources.mjs`, signed with its own Ploinky identity. `server/runtime/executionGrants.mjs` is the only module that imports the grant resolver: `resolveExecutionGrants` asks for the list once per launch that has a writable grant, never caches it, and resolves every grant with the worker store as a protected location (refused in every mode) and, for a writable grant only, the sources as `sourceLocations`; the anchored resolver refuses a writable grant that lies inside a source or aliases it by identity (`grant_inside_active_source`) or contains it (`grant_contains_active_source`), before the supervisor exists. The rule fails closed for writable work only: when the list cannot be read (Router unavailable, a malformed or partial answer, a timeout, no reader), a launch with a writable grant is refused `runtime_sources_unavailable` before any grant is opened, while a launch with no grant or only read-only grants (skills included) never asks for the list and runs. Each launch fetch is logged as `runtime_sources_fetched` with the authorization generation, the counts by kind, `outsideWorkspace` and the number of local roots, never a path. While at least one attempt with a writable grant runs, one shared 60 s recheck per worker fetches the list again (decision M-67 Q2); an attempt whose writable grant now lies inside, contains or aliases a source (compared by its resolved path, its identity and the spelling it was reported under) is ended through the normal stop path as `failed` with end reason `source_activated` (final: a pending human-input question or a recorded task failure does not relabel it), and a recheck that cannot read the list does nothing (logged once per state change). RoboTeam shows each of these reasons as a plain message. Residuals: the full section 225 lifecycle interlock is deferred until after r10 (decision M-66), so a source that becomes active while a robot holds a write grant on it stays writable until the next successful recheck (a recheck that cannot read the list does nothing), and anything a robot wrote there earlier persists and becomes trusted executed code once the folder is activated. Operator note: before enabling, updating or link-installing an agent from a folder, close the robot tasks and terminals on it, and review it if robots ever had write access to it. Two human-made aliases are not detected (decision M-66 Q3): a bind mount of a source placed inside a granted directory, and a pre-existing file hard link into a source; robots cannot create either (only grants are mounted, and link(2) across mounts fails with `EXDEV`).

Approval relay (T2, decision M-30): a specification with `permissions: 'ask-for-approval'` is planned (flow work, which has no owner to answer, is refused `approval_unsupported`). ALA's `coding-agent-request` records are not relayed as `ala` events: the store records a bounded, plain-text `approval-request` event (title 200, message 2,000, detail 8,000 code points, at most 8 options; control characters and bidirectional overrides removed) and one `approval` row per request. The first of the owner's answer, the deadline (`ROBO_WORK_APPROVAL_TIMEOUT_MS`, default 15 minutes, `expired`), the attempt's end (`ended`) and ALA's own resolution (`cancelled`, `expired`; `backend-resolved` is recorded `cancelled`) resolves it once, with one `approval-resolved` event. At most 8 requests are open; a further one, or one that cannot be relayed, is resolved `limit` and cancelled in ALA. Each open request holds a place of the per-reference event total for its resolution, and an approval-capable attempt keeps one more place free of `ala` events for a `limit` record. The owner answers with the `answer` control `{requestId, optionId}` or `{requestId, cancelled: true}`: owner-only with that request's own fresh grant (an administrator who is not the owner and the coordinator's background row are refused), recorded `pending` in the same transaction that resolves the request, then written once to ALA's stdin as exactly `{type: 'interaction-response', id, optionId}` or `{..., cancelled: true}` and acknowledged; ALA's `interaction-response-rejected` makes it final `rejected`, an answer whose request ALA resolved before it could be written is final `ended` (never `applied`), and the attempt's end makes an undelivered one final `ended`. RoboTeam keeps refusing ask-for-approval turns until the Router signs interaction responses (decision M-69 Q1), so in practice this relay is dormant for now. While a request is open the inactivity bound is held (the 4-hour maximum keeps counting).

Tests: `node --test 'robo-work/tests/*.test.mjs'` and `node --test 'robo-work/tests/runtime/*.test.mjs'`.

## Robot terminals (M-8)

A robot terminal is a worker execution of kind `terminal` (store schema 9: an internal reference row, never listed to a coordinator; terminal admissions are created only by this path, a coordinator admit of kind `terminal` is `invalid_request`). Ploinky's WebTTY owns browser authentication and transport; its provider adapter opens one WebSocket at exactly `terminals.path` (`/v1/terminal-control`) on the provider port.

| Topic | Contract |
|---|---|
| Channel authentication | The upgrade carries a Router-service token (purpose `execution-provider-terminal`) as the only key of `x-ploinky-auth-info` (`{"routerServiceToken": "<jws>"}`), verified with Ploinky's own `${ROBO_WORK_PLOINKY_AGENT_DIR}/lib/routerServiceToken.mjs` before the 101 (401/403/503 otherwise; 503 when that module cannot be loaded). The worker then sends `challenge{nonce}`; `hello`/`reattach` carry a hello-purpose token bound to that nonce. A refused hello or reattach closes the connection and changes nothing |
| Ownership | One session per worker process: `hello-ok{ownershipSessionId, workerGeneration, leaseExpiresAt, secret}`. The 32-byte secret lives in worker memory only (the possession proof is an HMAC keyed by it), is never persisted or logged, and is zeroed when the session ends. A new hello supersedes the session (its terminals end `supersession`); a reattach with a valid proof moves it to the new connection (`superseded-connection` to the old one) and answers the PTY inventory. Lease 15 s, renewed by hello, reattach and heartbeat; at expiry every terminal ends `lease-expiry`. A launched terminal that is neither attached nor closed within 15 s ends `unclaimed`. An operation is forgotten once its PTY ended or its refusal was sent, so the per-session bound (1024) counts open work only |
| Launch | `launch{operationId, targetId, project, cols, rows, launchEvidence}`. The evidence is a Router Request (`typ: router-request`, tool `__provider_terminal_launch__`, method `LAUNCH`, path = `terminals.path`, `rch` = computeRch of the exact launch fields) whose actor is a direct non-guest administrator user; its jti is consumed durably before anything is admitted. Idempotent per (session, operationId); another request hash is `operation_conflict`. Refusals are `launch-failed{code}` with nothing spawned: `forbidden`, `not_found`, `robot_not_ready`, `terminal_limit`, `grant_refused`, `sandbox_unavailable`. `targetId` is the worker robot ID; `project` is null (HOME) or `{selection, relativePath: ''}` (a non-empty `relativePath` is refused in version 1); the selection is resolved only through `resolveExecutionGrants` (role `project`, write: the active-source rule M-63 applies) and registered with the source watch |
| Sandbox | The fixed shell `/usr/bin/setsid --ctty --wait /bin/bash -l` (environment `HOME=/home/robot`, `TERM=xterm-256color`, `PATH=/usr/local/sbin:/usr/local/bin:/usr/bin:/bin`, `LANG=C.UTF-8`) starts through the sandbox launcher chain, role `terminal` (setpriv, unshare, stage.sh prep, bwrap, stage.sh final; fd allowlist 0-2) with the PTY slave as stdio 0-2, the robot's HOME, the project grant, the masks and the execution network with the workload firewall. The sandbox root is bwrap's per-sandbox tmpfs and stays writable (the root ruling); it never writes to the host. The publication order is anchor, runtime directory, network, terminal process tree; no endpoint and no ALA |
| PTY | Opened with the image's node-pty (`ROBO_WORK_NODE_PTY_DIR`, default `/usr/local/lib/ploinky/webtty/node_modules/node-pty`) through `open()`: node-pty never forks. The slave is paused at once and closed in the worker after the launch; the master (not close-on-exec, which every spawn chain closes) stays in the worker and is closed first at every end |
| Data | Output is numbered from 1 per PTY and kept in a 1 MiB replay buffer; `attach` replays after its cursor or sends `gap{firstAvailable}`. The master is paused while the socket holds more than 256 KiB or while no connection is attached and the buffer is full. Input is accepted only from the attached connection and in sequence (a duplicate is acknowledged again, a jump closes the connection); `ack` follows the master write. Terminal bytes are never logged, persisted or recorded: an end records `outputText: ''` and `data: {cause, exitCode?}`; logs carry sizes and counts |
| Ends | `exit` (with the exit code when the shell exited normally), `shutdown` (user or Router close, Close terminals, a revoked source grant), `supersession`, `lease-expiry`, `unclaimed`, `generation-end` (worker shutdown). Each runs the section 5.5 end path (beginAttemptEnd, then the ledger); `ended` is sent only after the result is published, and not at all when termination cannot be verified (the robot is then not ready with `resource_quarantined`). A worker restart ends the prior generation's terminals through generation recovery (`interrupted`) |
| Caps and lifecycle | 4 terminals per robot and `ROBO_WORK_MAX_TERMINALS` (default 16) per worker, counted over queued, running and stopping terminals in the admission transaction; terminals never count against `ROBO_WORK_MAX_CONCURRENT` or `limits.admissions`. Configure and delete refuse `terminals_open` (HTTP 409, body `{error, terminals: <count>}`) while any terminal of the robot is open; `POST /v1/coordinator/robots/terminals/close {robotId}` (administrator grant) ends them through the normal end path and answers `{robotId, closed, unverified}` |
| Connection bounds | At most 8 connections and 4 awaiting their hello; the hello is due within 10 s. The codec refuses fragmentation, unmasked frames, RSV bits, unknown opcodes and any frame above 26 B + 64 KiB from its header alone |
