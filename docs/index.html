AchillesIDE

A secure, extensible workspace where files, editors, AI-assisted workflows, and specialized agents work together without giving up clear ownership or authorization boundaries.

People and AI agents need a shared workspace where they can work on the same project, use the same context, and collaborate without exposing credentials or protected data. Files, conversations, decisions, and domain tools should remain connected, while every action still respects the identity, permissions, and responsibilities of its owner.

AchillesIDE brings files, previews, editing, AI-assisted workflows, and specialized tools into one authenticated browser workspace. Explorer provides a consistent surface for working with the project, so users and agents can act on the current context without repeatedly moving information between separate applications.

Explorer owns the shared workspace experience, while each specialized agent owns its domain operations and protected state. The Ploinky router authenticates requests, and verified plugins connect Explorer to enabled agents. Before performing a protected action, the owning agent validates the caller and applicable policy, then returns only the result needed by the workspace.

Agents and Plugins

Explorer provides the shared workspace shell. The integrations below are declared by explorer/manifest.json or discovered from verified IDE-plugins manifests. Each owning agent remains responsible for its domain behavior, authorization, and protected state. Runtime-owned workspace data volumes live below .data/; .ploinky/repos is the single named source-state volume exception.

Fresh deployments require an AdvancedLanguageAgent checkout at the workspace root with its selected achillesAgentLib dependency available. Explorer enables RoboTeam globally before Achilles CLI so both agents can use that workspace checkout during startup.

The QA workflow installs ALA from its default branch, verifies its exact clean revision, and binds it to the same Ploinky-selected AgentLib used by the agents. Its preflight exercises the ALA loader and required CLI options before starting the fifteen-agent runtime graph.

OnlyOffice, WebMeet Scribe (Meeting Secretary), and WebMeet STT are disabled by default. An administrator can enable each from Marketplace. Office editing requires OnlyOffice; automatic meeting notes require Scribe. The current Secretary uses browser SpeechRecognition and does not require the separate STT service.

Live Media Runtime

LiveKit Server runs as AchillesIDE/liveKitServerAgent from this repository. Explorer and WebMeet enable the same runtime, which owns Redis, LiveKit Server, Egress, and private health. Its pinned image, readiness checks, .data/liveKitServerAgent/ storage, Router routes, and fixed UDP 7882 media mux are unchanged. The default stack requires no separate media-runtime repository or basic installation. Skills Explorer deployment retires existing media registrations through Ploinky before source update, verifies old runtime absence inside the owning Box, and preserves agent data. Failed migration evidence remains available for recovery and retry.

Explorer-Owned and External Entries

The help plugin is owned by Explorer and is covered by the runtime plugins guide. The manifest also enables Achilles CLI, Soul Gateway, and Umami as supporting dependencies. Ploinky core supplies the administrator-only WebTTY surface through the selected Explorer host. Explorer owns its folder target chooser, while Ploinky supplies safe Box and live-agent choices and remains authoritative for runtime identity, mount access, translated working directory, and launch authorization. This checkout does not provide local documentation entry pages for those dependencies or that core surface, so the overview does not create unsupported links for them.
