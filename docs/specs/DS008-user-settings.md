# DS008 User Settings

## Introduction

[Explorer](wiki.html#definition-explorer) exposes settings surfaces for preferences and enabled integrations without allowing browser state to become the source of authority.

## Core Content

The Settings modal must expose the confirmed My Account, Agents, Plugins, Keymap, Editor, Theme, Avatar, and administrator-only Administration and [Hardware limits](wiki.html#definition-hardware-limits) surfaces. Settings controls must use shared [WebSkel](wiki.html#definition-webskel) and [Explorer](wiki.html#definition-explorer) [UI](wiki.html#definition-ui) components and must present loading, error, empty, and disabled states consistently.

Settings must mount its existing component inside the shared `expanded-modal` in component mode, fullscreen by default. The shell exclusively owns the header, fullscreen/restore, dragging, resizing, Refresh, Open in new tab and Close controls. The Settings component must contain no independent header or dialog sizing rules. Its content scrolls inside the shell while tabs and applicable Save/Cancel controls remain available.

Open in new tab must open the same authenticated [Explorer](wiki.html#definition-explorer) application with `?settings=<tab>` and the existing `#file-exp/...` workspace route. This address opens the same Settings component, tracks the active tab on refresh, and removes the settings parameter after closing. The initiating tab and its unsaved draft remain unchanged; unsaved drafts are not transferred to another tab. A URL selects a tab but grants no administrative authority. Refresh remounts Settings with its active tab and saved preferences, not the original launch snapshot. Close, Cancel, Escape and Refresh require confirmation before discarding changed Keymap, Theme or Editor preferences or dirty hardware-policy drafts. Save persists the preferences and returns the settings result through the shared shell to the originating [Explorer](wiki.html#definition-explorer) presenter.

[UserPersisto](wiki.html#definition-userpersisto) controls live in agent-owned pages opened in separate browser tabs. Settings → My Account contains links to the account dashboard and its personal sign-in security section, plus Authentication policy for accounts with settings-management capability. Settings → Administration contains links to Users and Applications, visible only to accounts with the corresponding management capability. These Settings surfaces contain no embedded account forms, user lists, application editors, or policy controls. Billing is hidden for now. The [UserPersisto](wiki.html#definition-userpersisto) entry under Agents uses its declared `settingsUrl` for Configure, following the same external-page navigation contract as other agent dashboards.

All account pages are relative to `/base-agent-additional-server/userPersistoAgent/7000/service/dashboard/`. The root page is My Account and remains available to every active authenticated account, including accounts without [Explorer](wiki.html#definition-explorer) access. `users.html` requires `admin.users.manage`; `applications.html` and `authentication.html` require `admin.agentSettings.manage`. The agent checks current persisted capabilities for document requests and every administrative API call. Shared scripts and styles require authentication. Navigation visibility improves usability but never grants authority. [UserPersisto](wiki.html#definition-userpersisto) owns page scrolling, loading and error states, and transient enrollment and application-secret cleanup when leaving its pages.

Agent settings must be discovered from enabled agent manifests and loaded only when available to the current account. Plugin settings must use the [Explorer](wiki.html#definition-explorer) settings contract, persist workspace plugin state only at `.data/explorer/plugin-settings.json`, and honor the application plugin whitelist. Agent-avatar overrides must persist only at `.data/explorer/avatar-overrides.json`.

The optional manifest editor remains a distribution/export feature. It must never remove `.agents/skills` wholesale or adopt an existing output from its name. [Ploinky](wiki.html#definition-ploinky) and [Explorer](wiki.html#definition-explorer) share `.agents/.ploinky-skill-exports.json` version 1, whose entries record owner, SHA-256 content/membership/mode digest and source. Only outputs matching their last-exported digest may be replaced or removed. Unrecorded legacy files, edited managed outputs, independently authored `.claude` content and unrelated local skills remain intact with diagnostics. Conflicting same-name export sources are rejected. Publication stages and validates bytes, rechecks moved output before replacement, and retains retired trees in `.agents/.ploinky-export-backups` to preserve writes through old file handles; cleanup of retained backups is a separate user decision. A read of manifest state reports verified output state separately from selections and does not manufacture an installed list from the manifest.

[Explorer](wiki.html#definition-explorer) Settings must not expose a Copilot tab, request a Copilot skill catalog, or mutate robot or conversation skill selection. Conversation-settings links must not open a settings page. Robot skills and skillsets remain owned and managed by RoboTeam; removing these [Explorer](wiki.html#definition-explorer) controls must not change their discovery, persistence, or execution.

Keymap settings must support the declared file search, content search, replace, save, autocomplete, and Settings actions, including clearing individual shortcuts and restoring defaults. Theme settings must apply the supported global light or dark theme. Editor settings must keep auto-save disabled by default, apply a configurable idle interval when enabled, and preserve the external-change conflict check before saving.

Avatar settings must require authenticated access and must use the configured AxiFace integration contract. The profile avatar is browser-owned preference state. Its `expressionMode` is either `audio` or `manual` and defaults to `audio`; the shared avatar form exposes this as the automatic voice-adaptation control and disables the manual emotion selector while it is active. Choosing a WebMeet quick emotion switches the browser-scoped override to `manual`. [Explorer](wiki.html#definition-explorer) stores and validates this preference but does not analyze microphone media; the active WebMeet browser owns local analysis and transient room projection. Agent-avatar overrides must remain unavailable unless the authenticated user has management authority. [Explorer](wiki.html#definition-explorer) must validate returned agent configuration before rendering it and must keep a failed external avatar integration from blocking normal workspace navigation.

[Explorer](wiki.html#definition-explorer) preinstall generates the public AxiFace pack catalog at `explorer/shared/generated/axi-face-packs.json`, an explicitly ignored [Explorer](wiki.html#definition-explorer) asset. [Explorer](wiki.html#definition-explorer) and WebMeet load it through `/explorer/shared/generated/axi-face-packs.json`. Pack manifests and rendering assets retain their `/explorer/shared/vendor/axi-face/` URLs. Catalog generation must leave the selected AxiFace source checkout unchanged, including when `AXIFACE_REPO_PATH` selects an external checkout; it must not generate `packs/index.json` or change ignore rules inside AxiFace.

Administrative settings must remain hidden from non-administrators. Administrative operations, including [DPU](wiki.html#definition-dpu) data sources, must request data through the owning agent's authorized tools; the client must not reproduce administrative authorization rules or embed secrets in browser-visible configuration.

[Explorer](wiki.html#definition-explorer) Administration is a navigation surface; [UserPersisto](wiki.html#definition-userpersisto)'s standalone pages load their own fixed HTTP APIs. Registration, browser credentials, and account policy belong to [UserPersisto](wiki.html#definition-userpersisto); there is no [Ploinky](wiki.html#definition-ploinky) local login-branding component or request to the retired `/api/agents/<agent>/settings` route. Administrative reads and mutations use scoped `POST api/admin/...` routes with same-origin credentials and bounded JSON bodies. [UserPersisto](wiki.html#definition-userpersisto) verifies the Router's signed invocation and derives the actor from its user subject, ignoring payload identities and forwarded role claims. Exact-Origin checks and persisted capability checks apply to every operation; there is no arbitrary tool dispatch. See [DS012 UserPersisto](specsLoader.html?spec=DS012-user-persisto.md) for the complete route contract. The separate provider-neutral Router administration API remains a compatibility surface, not the transport for these pages.

The [UserPersisto](wiki.html#definition-userpersisto) Users page requires email in user forms but allows an empty username and display name. Rows preserve these optional stored values instead of filling them with an email-derived label. Saving a role change for an email-only account must leave its username and display name empty unless the administrator explicitly edits them.

The default Users list excludes accounts whose only role is `selfRegistered` and shows their global count. Accounts with an additional role remain visible. Search matches email, username, display name, or user ID by case-insensitive substring across every account, including self-registered users, before pagination. Typing or submitting a search resets to the first page; clearing restores the default list. Search results keep the existing role editor. Saving a role refreshes the results and count, and accounts promoted to `user` appear in the default list. The `POST api/admin/users/list` API accepts optional `search`, `excludeOnlyRole`, and `includeRoleCounts` filters and returns `singleRoleCounts` when requested; counts cover all accounts independently of search. The same persisted administrator capability and signed-request checks apply to filtered requests too.

Administration loading, success, and error messages must remain visible in the owning [UserPersisto](wiki.html#definition-userpersisto) page and retain their live-region semantics. Browser errors or lost authority must not reveal stale administrator data or leave management controls enabled.

[Hardware limits is a separate editable administrator tab](wiki.html#definition-hardware-limits); Administration remains a navigation surface containing links. The tab uses GET and POST `/api/marketplace/hardware-limits`, the Router's administrator session, exact-origin mutation proof and current policy token. It shows one policy editor per repository/agent and exact-instance subrows for aliases, desired/applied limits, usage, pending changes and refused/blocked causal fixes. Requested limits use `cpus` at least 0.05 with at most two decimal places, integer `memoryPercent` from 1 to 100, and `gpu={smPercent,vramPercent}` with both integer percentages from 1 to 100. Existing GPU fields are preserved when editing CPU or RAM. Rendered GPU MiB and applied bytes are display values, not the requested policy schema. Apply sends exact registry keys. Conflicts preserve unsaved edits while refreshing authoritative state. CPU/RAM assurance is kernel enforcement, NVIDIA MPS GPU shares are best-effort, and the unified-memory RAM disclosure is advisory (kernel-enforced, MPS best-effort and advisory are the three assurance labels). On unified-memory NVIDIA GPUs (GB10 / DGX Spark) the panel adds a per-Box line, "RAM limits on this Box do not cover GPU device memory", labelled with the assurance Ploinky reports in `gpu.unifiedMemory` (advisory when absent), and the help states that a RAM limit does not cap the GPU device memory (`cudaMalloc`) an agent allocates, that only the agent's own admission check keeps that memory within the budget, that an overrun takes memory from the whole host, and that managed, pinned-host and ATS allocations are charged to the RAM limit (measured on GB10, driver 580.178.04). On a unified host whose GPU is not eligible, shares stay refused and the SM and VRAM inputs stay disabled. On the qualified GB10 (PCI `0x2E1210DE`, driver 580.178.04) `gpu.eligible` is true and the panel enables the inputs, labels the second field "GPU memory % (unified pool)", and describes the policy as "{sm}% GPU SM / {vram}% of the unified memory pool". The basis rule is that the GPU memory percentage resolves against the Box memory envelope (`gpu.shareBasis`, kind `unified-pool`), not against physical VRAM, and applied rows show the resolved bytes per CUDA process. For that qualified host the panel replaces the advisory line with "GPU memory share: best-effort, per CUDA process (MPS); cooperative: a process that drops the MPS environment is not limited" and renders one row per `gpu.unifiedMemory.allocationKinds` entry: `device` (`cudaMalloc`) "GPU share only", `managed` "RAM limit and GPU share (counted against both)", `pinned-host` "RAM limit only", and `pageable` "ATS (pageable) memory used by the GPU: RAM limit only". The help appends that the share is a best-effort, per-CUDA-process MPS limit on `cudaMalloc` and managed memory, measured at a 1 GiB limit, that managed memory also counts against the RAM limit, and that pinned-host and ATS memory count only against the RAM limit; the sentence is byte-identical with Ploinky's `HARDWARE_HELP.gpu`. Dedicated GPUs keep "GPU VRAM %" and "% of physical VRAM". Help discloses the accepted workspace-master-key authority exposure.

Save compares a fresh policy token with the token observed when the draft began. A changed token prevents the mutation and marks the draft for review. Review and save sends the refreshed token only after an explicit subsequent action. Every mutation obtains a fresh session/origin proof, with one fresh-proof retry for the Router's CSRF rejection. The panel hides access after 401, 403 or not_in_box, while an authorized store failure remains visible. Background reads pause while a draft is dirty; Refresh preserves its values. Closing Settings aborts pending reads and mutations and ignores late replies. Mutation and authority-loss generations invalidate older reads. Partial HTTP 207 results and partial conflict errors retain individual applied/refused/blocked/pending outcomes, coordinated exact keys and remaining pending keys before the authoritative state reload.

Each exact-instance row shows its profile-specific desired limits beside applied values. A successful polling reply received during unsaved edits is deferred so it cannot replace the focused input. Background read failures update the error notice without replacing edited inputs. Authorization failures still remove editor access immediately.

Settings improve the workspace experience while configuration authority remains with the configured service or owning agent.
