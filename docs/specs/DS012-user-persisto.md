# DS012 UserPersisto

## Introduction

UserPersisto is the durable identity and account authority for Explorer deployments. It owns users, roles, capabilities, authentication state, SSO sessions, OAuth applications, OIDC grants and tokens, credit balances, subscriptions, Stripe event state, payment projections, and audit events. Persisto is its primary database. EmailAgent owns transactional delivery and Stripe remains the external monetary source of truth. [DS013 OAuth/OIDC](DS013-oauth-oidc.md) defines its standards-facing provider contract.

Ploinky remains provider-neutral. Explorer selects UserPersisto through `sso.providerAgent` in its manifest and requires `explorer.access` through `routerAccess.requiredCapability`. Ploinky owns the browser session cookie, callback orchestration, route enforcement, exact-generation checks, and CSRF boundary. UserPersisto owns credential verification, current identity projection, role and capability decisions, and provider-side user administration.

All Explorer registration and login flows use UserPersisto. Ordinary accounts are passwordless: they sign in with a verified email code, an enrolled passkey or authenticator app (TOTP), or Google. The only password is a single deployment-configured administrator password for the designated administrator. Ploinky no longer provides a browser password store or local authentication mode. The manifest's SSO requirement is authoritative; retired local authentication declarations are rejected. A missing or unavailable provider must fail closed. This release does not preserve existing workspace authentication modes or migrate local accounts into UserPersisto.

## Core Content

### Installation setup and the initial administrator

A new durable store contains roles and capabilities but no user account. Setup state is an explicit persisted record, `systemSetting` key `installation.setup` with value `{ complete: true, initialAdministratorId, method, completedAt }`, where `method` is `google`, `emailCode` or `adminPassword`. An absent record means unclaimed. Authority derives only from this committed record, never from the current user count: restarting, deleting, blocking or demoting accounts, or an empty users table, never reopens public ownership. The application never deletes the record, and a malformed record fails closed as claimed.

The first completed Google authentication, verified email signup, or correct administrator-password authentication claims the installation. Starting a redirect, opening a page, typing an email or requesting a code does not. Every eligible first-account path uses one serialized decision in `lib/setup.mjs`: after server-verified authentication and live-parent checks, and while holding the parent lock, then the `users` lock, then the persistence scope, the completion reads the committed setup record. Unclaimed gives the account role `admin` and stages the setup record in the same fail-closed commit as the account, its role links, any Google binding and the SSO handoff. Claimed takes the ordinary path: returning users sign in, and a new account requires `selfRegistrationEnabled` and receives exactly `selfRegistered`. Concurrent Google and email completions therefore produce exactly one administrator; an administrator-password completion racing a signup resolves whichever administrator committed first. Invalid, expired, cancelled or interrupted work before the commit creates no owner, and a failure while staging the setup record leaves neither the owner nor the record after restart.

`selfregistered.dashboard.access` is the only capability of `selfRegistered`; public signup never grants `explorer.access`, and the registration role fails closed with `registration_role_must_be_restricted` if it was ever changed to grant administration or Explorer access. An administrator grants Explorer by assigning the `user` role. There is no configurable registration role, no administrator invitation and no arbitrary account creation: the retired `users/create`, `sso-admin-user-create` and `userpersisto_user_create` operations return `user_creation_unsupported` or no longer exist.

Browser sign-in and signup are part of an already initiated parent: a live Router SSO login request or an OIDC interaction. Every operation validates the live parent first; a dead or expired SSO request is a client error (`400 login_request_invalid` or `login_request_expired`) and an expired OIDC interaction reports `attempt_expired`. Replayed, mismatched, or expired handoff codes are rejected the same way (`auth_code_invalid`, `auth_code_consumed`, `auth_code_expired`), and the provider projection of a missing or blocked account reports `user_not_found` or `user_not_active`. Public JSON authentication endpoints require object bodies; malformed JSON, null, arrays and scalars return `400 invalid_json`. OIDC interaction and Google resume forms retain the form-encoded contracts in DS013.

Username and display name remain optional throughout provider projections and administration. An omitted username is returned as an empty string, never synthesized from the email address. Saving a role-only change for an email-only account must not create or validate a fabricated username.

No account is seeded at startup. The retired development bootstrap no longer creates an account; `USERPERSISTO_DEV_BOOTSTRAP=true` only enables the labelled development log fallback for email codes described below.

User deletion through the provider administration contract is a reversible deactivation: the account becomes `blocked`. Provider administration continues to address a blocked account: role, profile and status updates succeed and leave it blocked until an authorized status change reactivates it. Blocking an administrator or removing its administrator role is rejected when it would leave no other active administrator. Administration never changes a sign-in email (`email_change_unsupported`) and never accepts a password (`password_unsupported`).

### Administrator password

The administrator password is one deployment secret, `USERPERSISTO_ADMIN_PASSWORD`, declared in the agent manifest as optional with an empty default and set through Ploinky's protected variable store, for example `ploinky var USERPERSISTO_ADMIN_PASSWORD '<value>'` followed by restarting UserPersisto. There is no default, no second source and no public form that invents it. A value of 12–1024 characters enables the path; an absent or out-of-range value makes the action unavailable (`404 admin_password_unavailable`) and hides its UI, and an out-of-range value logs a one-time warning without the value.

Before setup, a correct password creates the dedicated local administrator: email `''`, username `administrator`, display name `Administrator`, source `initial-admin-password`, and an optional contact email that stays unverified. This is the only account without a sign-in email. After setup, the same path resolves only the designated initial administrator, which must still exist, be `active` and hold `admin`; otherwise it returns the neutral `authentication_failed`. It never promotes the caller's session, grants a role to a supplied email or creates another administrator, so a blocked, deleted or demoted designated administrator does not regain authority through it. The password also works for a designated administrator created through Google or email.

The durable verifier is `systemSetting` `auth.adminPassword.state` = `{ passwordHash (scrypt), version, updatedAt }`, synchronized at startup and on first use. A changed or removed value replaces or deletes the state, rotates `version`, and advances the designated administrator's account generation, which invalidates proofs bound to the old version and revokes that administrator's sessions (see *Credential changes and sessions*). Removing the variable from a password-created administrator that has no other usable method strands that account until the variable is configured again; startup logs a warning in that case.

Guessing protection works before any user exists and across fresh requests and tabs: all attempts share one lock; a durable global budget allows 30 failures per 15 minutes (`auth.adminPassword.throttle`); a per-source budget of 5 failures per 15 minutes uses the Router's trusted `x-ploinky-rate-source` partition (guest routes only; other requests share one bucket); budgets are checked before hashing; candidates longer than 1024 characters are rejected without hashing and candidates shorter than 12 characters without hashing or counting. A distributed attacker can temporarily exhaust the global budget and so block this one path; Google and email administrators keep their other methods.

### Verified email sign-in and registration

Email attempts are bound to the parent, the browser and a generation. The browser proof is an `up_browser` cookie (32 random bytes, HttpOnly, SameSite=Strict, `Secure` on HTTPS) whose path is the browser-visible service prefix plus `/service/`; the server stores only its digest. An encrypted `authAttempt` record keyed by `sha256(flow, parentId, sha256(browserProof))` holds the normalized email, the purpose (`login` or `register`), the current generation, the challenge hash, counters and an optional completion. A code is six digits, expires after `min(5 minutes, parent deadline)`, allows five failures per attempt across generations and a resend after 60 seconds, and each resend, email change or purpose change starts a new generation that invalidates earlier codes. Cancel clears the challenge server-side but keeps the counters.

Limits cannot be reset by restarting or resending: at most five sends per attempt; in memory five sends per address and 20 per rate source (200 shared) per 15 minutes, and 20 discoveries per parent and 60 per source (600 shared); and a durable budget of ten verification failures per address per hour, shared with Google mailbox and link codes and My Account codes. Budgets fail closed when saturated and report `rate_limited` with `retryAfter`.

A login code goes only to an active account's verified mailbox; a registration code only to an unused address while unclaimed setup or `selfRegistrationEnabled` allows it. No account exists before the correct code. Completion rechecks the live parent, policy, setup state and uniqueness under the `users` lock: a registration code never authenticates an existing account; a late same-email collision returns `account_exists` so the wizard can switch to sign-in, and a policy change returns `registration_disabled`. The Router SSO handoff code is staged in the same commit as the account and the attempt's completion tombstone, so a lost response replays the same unconsumed handoff to the same browser and parent only; OIDC completions resume through the engine's committed interaction result.

Delivery reporting is honest: `accepted` when the provider accepted the message, `failed` (`502 delivery_failed`, no success message, immediate retry allowed) on a known failure, and `unknown` when the transport errored. When `USERPERSISTO_DEV_BOOTSTRAP=true` and the send was not accepted, the code is written to the agent log labelled `DEVELOPMENT email code` and reported as `development-log`; this is never a production method. Email logs keep only an address digest.

Public account discovery (`discover`) returns only `{ exists, methods: { emailCode, passkey, totp } }` for usable local methods. It never exposes credential names, identifiers, counts, timestamps, roles or Google linkage. The existence disclosure is an accepted consequence of the selected sign-in design.

Production email availability requires configured delivery in addition to enabled policy and a verified sign-in mailbox. UserPersisto queries EmailAgent’s agent-only `email_auth_code_status`, which returns only `{ available }` after validating sender credentials, address and any selected authentication template. The bounded two-second probe sends no email, exposes no configuration values, and treats missing, denied, malformed or timed-out responses as unavailable. Wizard discovery, account confirmation controls and the administrator policy guard use that result. Policy updates probe once before entering persistence and refuse to count an unconfigured email method as the administrator’s remaining way to sign in. Only the exact `USERPERSISTO_DEV_BOOTSTRAP=true` flag makes the documented development log delivery available without a configured provider; it does not change EmailAgent’s readiness result or seed an account. Already delivered proofs can still complete when delivery subsequently becomes unavailable. Controlled test transports and readiness functions are construction-time dependencies, never request bypasses. MCP error responses and malformed delivery acknowledgments are known send failures.

### Authentication policy

The durable authentication policy contains enabled methods (`emailCode`, `passkey`, `totp`, `google`), whether later self-registration is allowed, and allowed browser redirect origins. With no stored policy or override, all four methods are enabled and self-registration is on. The retired `password` method and `defaultRegistrationRole` are not accepted (`invalid_auth_method`, `invalid_policy_field`); an environment `USERPERSISTO_AUTH_METHODS` naming a retired method ignores it with a one-time warning. Google is available whenever it is enabled and completely configured, including during unclaimed setup. Environment overrides remain authoritative, every save is checked against the effective policy, and administrator settings identify the override names.

Deliberate policy changes must leave every active administrator a usable sign-in method: the administrator password (designated administrator only, when configured), email code with a verified mailbox, an enabled passkey or TOTP allowed by policy, or Google when enabled, configured and bound. Otherwise the save fails with `administrator_auth_method_required`. Passkey and TOTP are never mandatory.

### The sign-in wizard

One wizard (`public/auth/wizard.js`) serves both surfaces through protocol adapters: the Router SSO page (`sso-adapter.js`, JSON calls under `/service/auth/`) and the OIDC interaction (`oidc-adapter.js`, CSRF form posts to `/service/oidc/interaction/<uid>/<action>`). The opening screen offers **Continue with Google** when usable, an email field with **Next**, a Login/Register switch when registration is available, the requesting application name for OIDC, and a secondary **Administrator sign-in** entry only when the administrator password is configured. While setup is unclaimed it explains that the first completed sign-in becomes the administrator and starts in Register mode, as does an OIDC `screen_hint=signup`.

Next discovers the address and applies four transitions: Login with an existing email shows a chooser of usable methods (email code first); Login with an unknown email asks whether to register and switches only on confirmation; Register with an existing email asks whether to sign in and switches only on confirmation; Register with an unknown email sends the registration code directly. The code screen offers Resend after the cooldown, Change email and Cancel, and every exit cancels the server attempt. Administrator sign-in is a separate screen; it never reuses the entered email and never turns the chooser into a password form. Errors are recoverable and explicit; expiry (the authoritative parent deadline is displayed) offers Start again for SSO (`/auth/login?returnTo=…`) or tells OIDC users to restart from the application. Late results from an abandoned screen are ignored, a pending passkey prompt is aborted on navigation, and only `{ mode, email }` is kept in `sessionStorage` for reload; a reload resumes an active code challenge from server state. Google denial or cancellation returns to the live wizard with a notice.

SSO completion returns JSON `{ code, redirectUri, state }` for the stored Router callback and keeps the Router's own state and browser binding. OIDC completions are native form POSTs that end in the engine's `interactionFinished` redirect; a failure re-renders the wizard with a readable error. Administrator sign-in and Google linking never approve application scopes; OIDC consent remains a separate step.

Passkey login requires nonempty, canonical base64url client data that decodes to a JSON object. Malformed assertions and invalid client data are audited authentication denials and return the same neutral authentication failure as other invalid credentials, rather than a server error. Invalid client-data encoding, shape, type, or missing challenge is rejected before consuming a challenge. Valid assertions still require the expected browser origin, relying-party identifier, challenge, user presence, user verification (the UV flag; browser options request `userVerification: 'required'` for registration and sign-in), signature, and authenticator counter; challenges and counters cannot be replayed. Wizard passkey challenges are bound to their parent (`sso-login:<requestId>` or `oidc-login:<uid>`).

Ploinky binds each pending login transaction to an independent browser proof in an HttpOnly, SameSite=Lax cookie. HTTPS deployments use Secure host-prefixed cookies. Callback validation requires that proof before consuming pending state or setting a session; a copied callback in another browser fails, and concurrent tabs retain separate proofs. Successful callbacks clear their proof and cannot be replayed. SSO authorization codes and login state are short-lived. Provider authorization codes are single-use. If the provider rejects a callback exchange with HTTP 400, 401, or 403, the Router returns HTTP 400 `invalid_authorization_code`, without issuing a session cookie or exposing provider rejection details. Unexpected server failures remain server failures. Redirect URIs must be absolute HTTP(S) URLs whose origin is loopback or explicitly allowed by policy. Provider session validation reloads the user, roles, capabilities, and active status from Persisto so blocking an account or changing its roles is enforced on the next remote validation.

The browser login URL uses the validated callback's public origin, preserving its hostname and port. The configured login path must remain on that origin. Runtime bridge calls continue to use the private `routerBaseUrl`; a loopback bridge address must never replace a remote browser's public login address or change the host of its callback proof cookie.

### Roles and capabilities

Google authenticates an external identity with the pinned canonical issuer `https://accounts.google.com` and its verified case-sensitive subject. UserPersisto resolves that tuple to an immutable local owner; email is never the binding key. Returning linked users retain their local ID, profile, credentials and current roles, even if Google changes the email claim. Missing or blocked local owners deny authentication without email fallback or replacement. A new Google account goes through the setup decision: on an unclaimed installation it becomes the initial administrator (setup `method: 'google'`), afterwards it requires current self-registration and receives exactly `selfRegistered`. No password is synthesized. Registration policy never demotes an existing linked account or prevents its normal sign-in.

#### Google registration and collision linking

An unbound Google identity that matches a local account's normalized sign-in email requires fresh proof of that exact account and an explicit **Link Google and continue** confirmation, all in the same live parent and browser-bound transaction. Eligible proofs are: a link-specific six-digit code sent to the account's verified, enabled sign-in mailbox (`send-link-code`/`verify-link-code`, bound to the transaction and the mailbox version); an enrolled, enabled, policy-allowed passkey or TOTP; or the administrator password, for the designated administrator only. Existing sessions, the Google claims themselves and codes of other purposes are ineligible. **Don't link; go back** returns to the wizard without linking.

The authoritative-Google shortcut is narrow: when the Google identity is authoritative for its email (a Gmail address, or a Workspace `hd` equal to the email domain, with `email_verified`) and that email exactly matches the account's current verified sign-in mailbox with email code enabled, explicit consent alone may link. The proof is created at consent time with the mailbox version. A non-authoritative address never offers the shortcut. The password administrator's unverified contact address is not a sign-in mailbox and is never a link target.

The server selects and retains the collision account ID and email. Confirmation rechecks that ID, the unchanged sign-in email and mailbox version (`sha256(email, emailVerifiedAt, authGeneration)`), active status, current Google policy, the proof method's current availability and credential version, the administrator-password version, parent validity, identity ownership and the account's existing Google grouping. A changed local email invalidates the attempt; a changed Google email is never copied to the account. Initially a local user may have only one Google identity; replacement, transfer, unlinking and linking a different address are unsupported. A newly discovered collision after a registration mailbox challenge follows the same rule. Passkey challenges bind purpose, transaction and target before consumption. Pending proofs retain only a digest of the credential material actually verified, plus its enrolled key when applicable; TOTP replacement, passkey replacement or removal, an administrator-password rotation and a generation change invalidate them. Ordinary usage counters do not.

New registration requires a usable Google-verified email. Authoritative Google email authority may verify the mailbox directly; a third-party address without that authority additionally requires fresh EmailAgent proof before reserving any user or email. This `google-registration-email` proof lives inside the encrypted Google transaction, has bounded attempts, expiry and resend cooldown, reports delivery honestly, and cannot authenticate through wizard endpoints. Delivery failure creates no account.

This linking rule does not claim global prevention of account pre-hijacking. An actor who controls an account's verified mailbox can prove it. Historical credential provenance, general recovery and Google unlinking remain deferred.

#### Google identity durability

`externalIdentity` stores only the canonical issuer, subject, immutable local `userId`, identity key and timestamps. Its unique key is SHA-256 over the encoded issuer/subject tuple and lookup compares the original tuple. Grouping by user provides only a safe `{ type: 'google', name: 'Google' }` profile method. Profile, user lists, SSO and UserInfo never expose provider subjects, transaction payloads, proofs, tokens or keys. No duplicate Google `authMethod` row is created and no email-based backfill occurs when reopening old snapshots.

Trusted external registration/linking validates policy, role and uniqueness before staging the user, roles, binding and audit without intermediate flushes, then commits one snapshot. Lock order is parent flow, users/domain, persistence scope; non-reentrant locks must not be reacquired from their locked helper. Network requests never run inside the persistence scope. An unexpected error after staging poisons the store so no unrelated later flush can publish partial state. Failure after rename but before directory fsync can leave a complete unacknowledged identity after restart: a fresh attempt resolves its existing binding without duplicate creation or replayed success. A failed downstream handoff may leave a complete identity; it never authorizes reissuing a consumed result.

The initial role policy is:

| Role | Capabilities |
| --- | --- |
| `admin` | `explorer.access`, `admin.users.manage`, `admin.agentSettings.manage`, `admin.billing.manage` |
| `user` | `explorer.access` |
| `selfRegistered` | `selfregistered.dashboard.access` |

Public registration after setup always uses `selfRegistered`, which must exist and must not grant administrative or Explorer capabilities. SSO router access is capability-based. Explorer does not declare a local-role compatibility mapping; neither local role names nor caller-supplied roles or capabilities grant Explorer access. Explorer's protected surface requires `explorer.access`; therefore both `admin` and `user` can enter Explorer, while `selfRegistered` cannot unless an administrator changes policy.

Administrative MCP and provider operations re-read the persisted actor and its capabilities. They must not trust caller-supplied role arrays. Profile updates are limited to the authenticated user's username and display name; role and status changes use the administrative path.

Agent tools authorize only the runtime-verified invocation grant. User-supplied top-level context, role, actor, or capability fields are data and never authority. EmailAgent similarly restricts settings to a verified administrator and delivery operations to a verified agent caller.

### Account dashboard and credential enrollment

The account dashboard is served at `/base-agent-additional-server/userPersistoAgent/7000/service/dashboard/`. Its manifest route requires an authenticated Ploinky session. Any active UserPersisto account may read and update its own profile and enroll permitted sign-in methods there, including accounts without `explorer.access`. Explorer declares this path as its `routerAccess.capabilityDeniedRedirect`: a denied HTML document GET is redirected to the dashboard, while API calls, mutations, MCP, SSE, and WebSocket traffic keep their denial responses. The redirect is a local same-origin path and must not redirect back to the denied resource.

This route uses the companion Ploinky authenticated-service routing behavior: an explicitly owned and matching `access: authenticated` service declaration retains the inherited identity provider while applying the service's own capability requirement. Undeclared and guest/public service routes retain the owner's capability checks. Installing the agent UI without the matching Router changes does not establish restricted-account dashboard access. Later public registration defaults to the `selfRegistered` role and therefore reaches this dashboard without opening Explorer.

Every dashboard request verifies the Router's HTTP invocation token with the mounted `/Agent/lib/invocationAuth.mjs` helper, binding audience, method, internal path, query, raw body hash, expiry, and replay protection. The acting user comes from the signed user subject/actor, followed by an active-account lookup in Persisto. Unsigned carrier fields and request body identities never select an account. Authentication requires a UserPersisto identity; a local Ploinky account cannot become a UserPersisto user implicitly.

UserPersisto owns four standalone pages beneath this authenticated service path. Explorer Settings contains only links that open these pages in separate browser tabs; the Agents Configure action follows the UserPersisto plugin's `settingsUrl` to the root dashboard. My Account contains personal profile and sign-in security, while workspace-wide authentication policy has its own page.

| Page relative to `dashboard/` | Purpose | Required persisted authority |
| --- | --- | --- |
| `./` | My Account, profile, sign-in email verification and permitted credential enrollment | Any active authenticated account |
| `users.html` | User search, counts, details, roles and deactivation | `admin.users.manage` |
| `applications.html` | OAuth/OIDC application registration and management | `admin.agentSettings.manage` |
| `authentication.html` | Workspace authentication policy and Google readiness | `admin.agentSettings.manage` |

Protected documents require the listed capability before their HTML is served. Shared dashboard assets require an active authenticated account. Page navigation reflects current capabilities, but server authorization is independent of link visibility. Pages own their scrolling and status messages rather than embedding their forms in the Settings modal.

The dashboard exposes a fixed self-service API, relative to its public path:

The normal Router session/CSRF gate also applies. There is no arbitrary tool-dispatch API. Passkey requests use the verified browser origin and its hostname, ignoring supplied origin or relying-party overrides. Re-authentication and contact verification are dashboard operations only: no MCP tool issues a grant or accepts a confirmation code or the administrator password.

Administrative pages use the following fixed `POST api/admin/...` endpoints, including POSTs for reads that accept query arguments. Successful responses are `{ok: true, result}` with the existing tool's result; errors retain `{ok: false, error}` and their HTTP status. Each endpoint forwards only its listed fields to a fixed tool. Caller-supplied actor, context, role claims and unknown fields cannot select administrative authority. `roles` is editable target data only on role updates. Every operation re-reads the persisted actor's required capability.

There is no account creation, password or sign-in email endpoint. User deletion remains reversible deactivation; the last active administrator cannot be blocked or lose its administrator role. Application operations preserve the validation, one-time secret and grant-revocation rules in [DS013](DS013-oauth-oidc.md). Operator Google credentials are not accepted by any dashboard endpoint.

Profile responses retain user, roles, capabilities, credits, and subscription data and add safe `authMethods`, `allowedAuthMethods`, `reauthenticationMethods`, `emailVerified`, `contact` (`{ email, verified, pending }`) and `enrollments` summaries. Passkeys expose configured state and enabled count; TOTP exposes configured state and whether an unexpired setup is pending. Credential payloads, TOTP secrets, challenge values, grants and password hashes are excluded. Policy changes immediately affect enrollment acceptance and the reported allowed methods.

#### Fresh confirmation, enrollment and contact verification

Enrollment is optional and happens after sign-in. Each sensitive operation (`passkey.register`, `totp.enroll`, `contact.verify`) first needs explicit re-authentication with a currently available method: an email code to the verified sign-in mailbox (six digits, five minutes, five failures, 60-second resend, the durable per-address budget), an enrolled passkey (challenge scoped to the account and operation), an enrolled TOTP (sharing the account's login lockout and replay protection), the administrator password for the designated administrator, or the already linked Google account. Success issues a single-use grant, stored only as a hash in an `authChallenge` with purpose `operation-grant`, bound to the account, that one operation and the account generation, and valid for five minutes. Starting the operation consumes it; a grant for another account or operation, an expired or reused grant, and a grant issued before a generation change are refused with `403 operation_grant_required`. An arbitrary old session or a reused registration challenge cannot enroll, and a recent sign-in does not substitute for this confirmation.

Google confirmation opens a separate popup and never creates or links an account. It binds the operation, local actor, current account generation and initiating browser, and requires the returned issuer and subject to match that actor’s existing binding. It requests the account chooser and the signed `auth_time` claim; a missing authentication time, a time over five minutes old, or a future time beyond the allowed clock tolerance is refused. Google’s documented parameters do not guarantee a new credential prompt, so a stale Google session requires signing in again at Google and retrying. The popup carries no operation grant back in its URL or browser storage: the original authenticated dashboard polls for the one-use grant. Cancellation, wrong-account responses, expiry and generation changes cannot authorize enrollment. See the [Google OIDC reference](https://developers.google.com/identity/openid-connect/reference).

Passkey and TOTP sign-in are reached through the account's sign-in email, so they can be enrolled only once the account has a verified sign-in mailbox (`verified_email_required`). TOTP setup is staged: the current authenticator keeps working until the new secret is proven; a newer start supersedes older setups (`setup_superseded`), five wrong codes or a generation change end the setup, and replacing an enabled authenticator advances the account generation. Passkey registration binds its challenge to the grant's generation and reports verification failures as `400 registration_failed`. Its final generation and uniqueness checks share the users lock and persistence scope with credential creation. Passkey counters and TOTP login/re-authentication updates use that same exclusion so concurrent authenticator replacement cannot restore a retired credential.

The password-created administrator starts without a sign-in email; its contact address is unverified and grants no sign-in, linking or recovery authority. After a `contact.verify` grant, **Verify this email** sends a code to the chosen address; the correct code makes that address the account's verified sign-in email (rechecking eligibility and uniqueness under the users lock). This never replaces an existing verified mailbox (`sign_in_email_exists`) and never takes an address another account uses (`email_taken`). Adding a mailbox replaces nothing, so it does not advance the generation.

The standalone My Account page owns these controls; Settings → My Account links to it. The confirmation step lists the profile's `reauthenticationMethods`, and codes, passwords, setup secrets and grants are cleared on success, cancellation, navigation and component removal and are never stored in browser storage. These are alternative sign-in methods; this revision does not introduce step-up or a mandatory second factor.

#### Credential changes and sessions

Each account carries an integer `authGeneration`. TOTP replacement and an administrator-password rotation or removal (for the designated administrator) advance it and, in the same staged commit, remove the account's stored OIDC sessions, grants, access and refresh tokens, authorization codes, and completed login or account-bound consent interactions. Pending email login challenges and completed email retries are bound to the original account ID, verified mailbox and generation; a new generation cannot turn an old proof into a fresh login. SSO handoffs carry the generation verified by authentication and reject issuance or consumption after it changes. Generation checks and handoff consumption share the persistence scope with credential changes. The Router's provider session stores the generation from the SSO handoff; `sso-user` refuses an older one with `401 session_revoked`, so Router sessions end at their next revalidation, within 30 seconds by default. Self-contained OIDC ID tokens are not stored and stay valid until they expire (at most 300 seconds). Mailbox versions, grants and staged setups include the generation, so they become invalid too.

### Explorer administration and settings

The standalone Users page exposes Previous/Next controls and total counts in pages of 100 users through its signed dashboard API. Mutations reload the current page, and deletion or role changes that empty the last page move to the preceding valid page. The default list requests `excludeOnlyRole=selfRegistered` and `includeRoleCounts=true`, presenting only a count of accounts whose sole role is `selfRegistered`. Nonempty search clears the exclusion and searches email, username, display name and local ID across all users before pagination. Role promotion updates both the default list and global counts. `userpersisto_user_list` forwards the same bounded `search`, `excludeOnlyRole` and `includeRoleCounts` inputs; browser filtering must not hide matching users on another page. Accounts are created by signing in, so there is no create form. The sign-in email is shown read-only; update forms preserve optional username/display name values and never send email or a password. Details and role changes are separate actions so a failed action cannot be mistaken for a completed combined save. Explorer's own Administration users view follows the same rules and the Router maps `user_creation_unsupported`, `password_unsupported` and `email_change_unsupported` to provider-neutral `400` responses.

The existing provider-neutral Router user-administration surface remains available independently of the standalone pages. It applies exact-origin and session-bound CSRF protection, current provider-session validation and administrator checks before delegating provider methods. UserPersisto re-authorizes the persisted actor. The standalone pages use their own fixed agent HTTP endpoints and do not depend on this compatibility API or its local-control proof exchange.

Ploinky's retired `/auth/account` and login-branding settings routes are unavailable. Explorer Administration contains links to the authorized UserPersisto pages and does not offer local login branding. Old local browser credentials cannot authorize Marketplace, policy, or other protected controls. The verified local CLI operator channel remains a separate runtime control channel; it does not provide browser password login or establish an Explorer user session.

The UserPersisto settings entry links authenticated users to their standalone account dashboard. Authentication policy and applications require `admin.agentSettings.manage`; users require `admin.users.manage`. Billing configuration and provider credentials retain their existing administrator restrictions and are not added to Settings as embedded forms. Provider configuration secrets remain in the runtime secret store and are never embedded as manifest values. Google readiness exposes secret presence only, never the credential or a masked fragment.

The standalone Applications page registers OAuth/OIDC clients and provides create, edit, enable/disable, delete, secret rotation, and pagination in pages of 100. It displays the configured issuer and discovery URL, or an explicit disabled state. **Settings → Administration → Applications** opens this page in a separate browser tab. Client secrets are generated by the server and returned only on creation or rotation; the UI displays that value once in a transient field, never in client lists or browser storage, and clears it on refresh, navigation, dismissal, or loss of administrator status. The server re-reads `admin.agentSettings.manage` for every application operation; UI visibility is not authorization. The adjacent Authentication policy page manages workspace-wide sign-in/registration policy and Google readiness separately from personal account security.

### Credit and payment journal

Credits use an append-only `creditTx` journal and a reconciled `creditAccount` projection. Each stable business reference produces a deterministic transaction identifier. Repeating an identical operation is a no-op that returns the reconciled balance; reusing a reference with different financial data is rejected. Amounts are positive safe integers and a balance or reserved balance may never become negative.

Reservations have a durable lifecycle: `reserved`, then exactly one full `committed` or `released` transition. Commit and release must match the original user, amount, and reference. Reservation identity is scoped to the user and business reference, so different users may safely reuse a reference. Reservation projections are reconstructed from reserve/spend/release journal entries, preserving terminal status. Legacy raw-reference projections are accepted only for their owning user; an old cross-user collision with a stranded reserve journal can be repaired on retry or settlement. Partial settlement is not supported by this revision.

Stripe webhook signatures are verified over the raw request body with a five-minute timestamp tolerance. A Stripe event identifier is bound to its payload hash. Paid credit checkouts create one deterministic purchase journal entry only after the event identity matches a checkout previously initiated and journaled by UserPersisto. The checkout snapshots the number of credits before redirecting to Stripe, so later configuration changes cannot alter an in-flight purchase. Identity, amount, and currency conflicts fail before credits are applied; unpaid completion events create no credits. Processed events are idempotent, failed events remain retryable, and reusing an event identifier with a different payload is rejected. `paymentTransaction` is an operational projection of Stripe checkout/payment state; it is not a replacement for Stripe's monetary records.

Checkout creation accepts an explicit client idempotency key or generates one, scoped by user and checkout kind. Before contacting Stripe it durably records a `checkoutIntent` containing the normalized request, exact provider form, price, URLs, quantity, and credits. Identical retries reuse that snapshot and the recorded session; changed quantity with the same key is rejected. Checkout retries and webhook processing share a serialization boundary, and checkout creation never resets an existing paid payment. Stripe requests have a 15-second deadline covering response headers and body; a stalled request returns `504 stripe_timeout`, releases the billing queue, and leaves its durable intent available for an exact retry. An uncertain response retries the exact provider form/key only while the unresolved intent is younger than 23 hours; older intents return `checkout_reconciliation_required` to avoid provider key expiry creating another purchase. Signed webhook metadata can connect a lost response to its durable intent. Pre-upgrade checkouts retain their existing payment snapshots, but historical client-key mappings cannot be reconstructed automatically. Only an active authenticated account may start checkout.

Subscription events retrieve the current Stripe subscription resource instead of trusting delivery order or second-resolution event timestamps. A canceled subscription is a durable terminal tombstone for its provider identifier. Stripe retrieval or identity-validation failures leave the event retryable; they do not restore a stale active state.

### Durability and deployment constraints

UserPersisto and EmailAgent use the same immutable Ploinky Node image as Explorer. Their workspace data roots are `.data/userPersistoAgent` and `.data/emailAgent`, each mounted at `/data`; Persisto retains its `/data/persisto` directory and EmailAgent retains `/data/settings.enc.json`. Before upgrading an existing deployment that used `.ploinky/data/userPersistoAgent` or `.ploinky/data/emailAgent`, stop the affected agents and migrate their data into the corresponding `.data` roots. The runtime does not read those retired paths automatically.

EmailAgent uses Ploinky's default AgentServer to serve its declared MCP tools. UserPersisto owns its HTTP service on `USERPERSISTO_SERVICE_PORT` (default `7000`) and starts the bundled AgentServer on `PORT` (default `7001`) only after persistence initialization and HTTP listener readiness. Its public service routes retain port `7000`; MCP tools forward to the service port independently of the MCP port. An unexpected MCP server exit fails the agent. Graceful shutdown drains MCP while HTTP and the store remain available, then drains HTTP and closes Persisto; a failed or timed-out drain cannot acknowledge clean shutdown. These private listeners add no physical-host publication.

Both agents retain their declared JSON Schema argument constraints through MCP validation and discovery. Tool subprocesses read arguments from the AgentServer `input` envelope and verify the signed invocation in `metadata.invocation`; EmailAgent also accepts its legacy `arguments` envelope.

Persisto remains the model and index engine. UserPersisto replaces the upstream error-swallowing autosaver with a tracked durable adapter: each flush gathers objects, indexes, and groupings into one versioned, checksummed snapshot, writes a private temporary file, fsyncs it, atomically renames it, and fsyncs the containing directory. CRUD cannot race snapshot gathering. Registration, role mutation, and credit workflows additionally hold a shared persistence scope so an unrelated flush cannot publish a partially linked initial owner or credit workflow. Role changes add requested links before removing obsolete ones, and account/reservation projections are rebuilt from the append-only credit journal when they disagree. This is not a general multi-record ACID transaction API.

Save failures propagate as `503 persistence_unavailable` and poison the cached store until restart; subsequent reads and retries cannot acknowledge uncommitted cached changes. A corrupt snapshot or legacy file fails startup rather than becoming an empty installation. Existing per-object Persisto files are imported on first open; after a successful save, `.userpersisto.snapshot.json` is authoritative and legacy files remain untouched. Backups and restores must include the current snapshot. Each dirty flush rewrites the complete snapshot, so storage cost grows with the retained dataset.

These guarantees require one active UserPersisto writer for a persistence volume. An exclusive `.userpersisto.writer.json` lock refuses a live or ambiguous second writer and records the owning Ploinky instance and enable generation when available. Normal shutdown releases its own lock. After an abrupt Box or agent-process stop, a replacement may remove the unchanged predecessor lock only when local process liveness proves that its owner is gone, or when a complete current Ploinky identity proves that a foreign-container lock belongs to a legacy or different generation. A malformed lock, a live local owner, or a foreign lock from the current generation remains fail-closed. The filesystem must provide exclusive creation, atomic same-directory rename, and fsync semantics. Multiple active writers and high-availability failover remain unsupported. Operators must back up the Persisto volume, retain Stripe event history, and reconcile the local payment projection against Stripe after storage recovery. This credit journal is application accounting; financial custody, regulated bookkeeping, tax, chargeback, and revenue-recognition requirements remain outside this component.

### Compatibility scope and deliberate deferrals

This revision provides the existing Ploinky identity-provider interface alongside the OAuth 2.0 / OpenID Connect endpoints specified in DS013: discovery, JWKS, authorization code with mandatory S256 PKCE, token exchange, UserInfo, refresh-token rotation, confidential client credentials, introspection, revocation, and RP-initiated logout. Operators enable these endpoints with an explicit public issuer; existing Ploinky SSO behavior remains available independently. OIDC interactions use the existing enabled authentication methods and registration policy, with browser-bound login and explicit scope consent. OAuth tokens do not authenticate requests to protected Explorer routes.

This scope does not imply full Keycloak feature parity or OpenID certification. SAML, general identity federation/social login beyond the pinned Google client, account recovery or recovery codes, administrator invitations, arbitrary account creation, general email replacement, Google unlinking or linking a different email, step-up authentication, mandatory multi-factor policy, dynamic client registration, implicit/hybrid/password grants, device authorization, and high availability remain deferred. Email code, passkey, TOTP and Google are enabled by default and can be restricted by policy; passkey and TOTP credentials are optional and enrolled from the standalone My Account dashboard. A Google-only account can confirm an enrollment using its already linked Google identity even when email delivery is unavailable.

The seeded `admin`, `user`, and `selfRegistered` roles and their capability links are durable. User role assignment is implemented, while arbitrary role/capability definition administration is deferred. Ploinky revalidates provider sessions on its configured cadence (30 seconds by default), except user-administration requests, which force a remote validation. Deployments needing immediate route revocation must lower that interval or add provider-driven revocation.

The unclaimed installation is operationally sensitive: the first completed sign-in of any kind becomes the administrator. Configure `USERPERSISTO_ADMIN_PASSWORD` and complete **Administrator sign-in** immediately after the first deployment, or keep the deployment on a trusted network until an administrator exists. High availability requires a future transactional or single-leader storage design; starting two writers against the same Persisto volume is not a supported scaling strategy.

## Conclusion

UserPersisto preserves durable local identity, current authorization and financial consistency across Explorer and registered applications. Optional Google verification changes the sign-in credential, never the local account authority.
