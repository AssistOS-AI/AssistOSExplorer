# DS012 UserPersisto

## Introduction

UserPersisto is the durable identity and account authority for Explorer deployments. It owns users, roles, capabilities, authentication state, SSO sessions, OAuth applications, OIDC grants and tokens, credit balances, subscriptions, Stripe event state, payment projections, and audit events. Persisto is its primary database. EmailAgent owns transactional delivery and Stripe remains the external monetary source of truth. [DS013 OAuth/OIDC](DS013-oauth-oidc.md) defines its standards-facing provider contract.

Ploinky remains provider-neutral. Explorer selects UserPersisto through `sso.providerAgent` in its manifest and requires `explorer.access` through `routerAccess.requiredCapability`. Ploinky owns the browser session cookie, callback orchestration, route enforcement, exact-generation checks, and CSRF boundary. UserPersisto owns credential verification, current identity projection, role and capability decisions, and provider-side user administration.

All Explorer registration and login flows use UserPersisto. An account signs in with its own password, a verified email code, an enrolled passkey or authenticator app (TOTP), or Google, as policy allows. A password is chosen when signing up with an email or set later from My Account. An unclaimed installation accepts the literal password `admin` once to create its initial administrator; it then becomes that account’s own hashed password. There is no shared login fallback, administrator-set password or unauthenticated password reset. Ploinky no longer provides a browser password store or local authentication mode, and account passwords never pass through Ploinky. The manifest's SSO requirement is authoritative; retired local authentication declarations are rejected. A missing or unavailable provider must fail closed. This release does not preserve existing workspace authentication modes or migrate local accounts into UserPersisto.

## Core Content

### Installation setup and the initial administrator

A new durable store contains roles and capabilities but no user account. Setup state is an explicit persisted record, `systemSetting` key `installation.setup` with value `{ complete: true, initialAdministratorId, method, completedAt }`, where `method` is `google`, `passwordSignup` or `initialPassword`. An absent record means unclaimed. Authority derives only from this committed record, never from the current user count: restarting, deleting, blocking or demoting accounts, or an empty users table, never reopens public ownership. The application never deletes the record, and a malformed record fails closed as claimed.

The first completed Google authentication, verified password signup or initial-password setup claims the installation. Starting a redirect, opening a page, typing an email, choosing a password or requesting a code does not. Every eligible first-account path uses one serialized decision in `lib/setup.mjs`: after server-verified authentication and live-parent checks, and while holding the parent lock, then the `users` lock, then the persistence scope, the completion reads the committed setup record. Unclaimed gives the account role `admin` and stages the setup record in the same fail-closed commit as the account, its role links, its password credential and any Google binding. Claimed takes the ordinary path: returning users sign in, and a new account requires `selfRegistrationEnabled` and receives exactly `selfRegistered`. Concurrent Google, signup and initial-password completions therefore produce exactly one administrator; every other completion re-reads the committed record and takes the ordinary path or fails with `account_exists` or `registration_disabled`. Invalid, expired, cancelled or interrupted work before the commit creates no owner, and a failure while staging the setup record leaves neither the owner nor the record after restart.

The initial-password exception uses the ordinary password screen after **Email** and **Next**. While setup is unclaimed and `password` is enabled, an unknown address may submit raw password exactly `admin`; case changes, whitespace and Unicode lookalikes do not claim setup. No email delivery, verification code or password confirmation is required. `loginWithInitialPassword` rechecks parent validity, setup, policy and email uniqueness before hashing, when admitted from the bounded KDF queue, and under the users lock before committing. Its per-source budget allows 10 hashes per 15 minutes (100 for the shared source). The account, its own encrypted scrypt credential, admin role, permanent setup record, browser-bound completion and SSO handoff are committed together. A concurrent loser is refused and never creates an unverified ordinary account. Same-browser retries recover only that completion; later sign-ins use the account’s normal verifier. Ordinary password creation still requires 15 to 128 characters.

The initial administrator’s email remains unverified. Email-code sign-in and Google’s authoritative-mailbox shortcut cannot use it; the normal My Account contact-verification operation can verify it after email delivery is configured. Existing enrollment and password-change rules still require a verified mailbox. First setup works identically with `PROD` absent or present. Normal verified signup remains available through **Sign up** when delivery is configured, and Google remains available as before.

`selfregistered.dashboard.access` is the only capability of `selfRegistered`; public signup never grants `explorer.access`, and the registration role fails closed with `registration_role_must_be_restricted` if it was ever changed to grant administration or Explorer access. An administrator grants Explorer by assigning the `user` role. There is no configurable registration role, no administrator invitation and no arbitrary account creation: the retired `users/create`, `sso-admin-user-create` and `userpersisto_user_create` operations return `user_creation_unsupported` or no longer exist.

Browser sign-in and signup are part of an already initiated parent: a live Router SSO login request or an OIDC interaction. Every operation validates the live parent first; a dead or expired SSO request is a client error (`400 login_request_invalid` or `login_request_expired`) and an expired OIDC interaction reports `attempt_expired`. Replayed, mismatched, or expired handoff codes are rejected the same way (`auth_code_invalid`, `auth_code_consumed`, `auth_code_expired`), and the provider projection of a missing or blocked account reports `user_not_found` or `user_not_active`. Public JSON authentication endpoints require object bodies; malformed JSON, null, arrays and scalars return `400 invalid_json`. OIDC interaction and Google resume forms retain the form-encoded contracts in DS013.

Username and display name remain optional throughout provider projections and administration. An omitted username is returned as an empty string, never synthesized from the email address. Saving a role-only change for an email-only account must not create or validate a fabricated username.

No account or stored credential is seeded at startup; the initial-password exception creates its credential only when the first claim succeeds. The retired development bootstrap no longer creates an account; `USERPERSISTO_DEV_BOOTSTRAP=true` only enables the labelled development log fallback for email codes described below.

User deletion through the provider administration contract is a reversible deactivation: the account becomes `blocked`. Provider administration continues to address a blocked account: role, profile and status updates succeed and leave it blocked until an authorized status change reactivates it. Blocking an administrator or removing its administrator role is rejected when it would leave no other active administrator. Administration never changes a sign-in email (`email_change_unsupported`) and never sets, reads or resets an account password (`password_unsupported`).

### Account passwords

#### Credential

An account has at most one password, stored as an `authMethod` owned by `lib/auth/userPassword.mjs`: `key` `<userId>:password`, `type` `password`, `enabled` `true`, and `credential` `{ hashEncrypted, version, setAt }`. `hashEncrypted` is `encryptOidcPayload({ hash }, 'userpersisto:password:v1:<userId>')` (AES-256-GCM under the retained settings key), so the authenticated context binds the verifier to its owner. `version` is 16 random bytes in hex and rotates only when the password changes; `setAt` records the change. A credential that fails to decrypt is unusable, never a match. Profiles report only `authMethods` `{ type: 'password', name: 'Password' }` and `enrollments.password` `{ configured }`; no hash, version or timestamp is exposed, and the pre-release `user.passwordHash` field is never read or written.

Hashing uses native `node:crypto` scrypt with one supported profile, `N = 32768`, `r = 8`, `p = 3`, a 16-byte random salt, a 64-byte key and an explicit `maxmem` of 64 MiB (Node's 32 MiB default refuses this profile). This is one of the equivalent scrypt configurations in the OWASP password-storage guidance. The stored string is `scrypt$N$r$p$<salt>$<hash>` in base64url. A stored string that does not parse to exactly this profile and these lengths fails closed as an unsupported verifier; there is no legacy profile, rehash path or compatibility reader. Verification always evaluates the KDF once, against a process-wide dummy verifier when no usable credential exists, and compares with `timingSafeEqual`. The KDF runs through the asynchronous `crypto.scrypt`, never inside the `users` lock or the persistence scope, and through a gate of at most two operations in flight and 16 queued with a five-second wait; a saturated gate returns `rate_limited` with `retryAfter: 5` and never counts as a failed guess. Measured on a 12th Gen Intel Core i7-12700H, one hash takes 136 to 144 ms with the Ploinky Node image's Node v24.19.0 binary and with Node v24.21.0. This is a measurement, not a gate: the work factor is never lowered to meet a latency target. Tests use `setKdfProfileForTests`, `setKdfObserverForTests` and `resetKdfForTests`; no request or environment variable selects a profile.

#### Input policy

`normalizeSecret` serves creation and presentation: it requires a string of 1 to 1024 UTF-16 code units, requires well-formed UTF-16 (`isWellFormed()`), and applies NFKC. Longer input is refused, never truncated.

| Rule | Creating a password (signup, My Account) | Presenting a password (login, re-authentication, Google link proof) |
| --- | --- | --- |
| Raw bound and encoding | Otherwise `invalid_password` (`too_long` or `invalid_characters`) | Otherwise the neutral `authentication_failed`, without a KDF and without spending a failure budget |
| Control characters | None (`\p{Cc}`), otherwise `invalid_characters` | Not applied |
| Length | 15 to 128 Unicode code points after NFKC (`too_short`, `too_long`) | No minimum and no creation maximum; only 4096 UTF-8 bytes after NFKC, otherwise `authentication_failed` without a KDF |
| Confirmation | `NFKC(password) === NFKC(confirmation)`, otherwise `password_mismatch` | Not applicable |
| Content | Not the email (case-insensitive), not one repeated code point, not in the frozen `lib/auth/commonPasswords.mjs` list (`equals_email` or `too_common`) | Not applicable |

Characters of every class are allowed, there are no composition rules and no expiry, and paste and credential managers work. A later tightening of the creation policy never rejects a previously valid password at login. The case-insensitive "not the email" rule is rechecked during **Change email** without retaining plaintext. Email-shaped passwords retain an encrypted comparison verifier alongside the primary verifier: a lowercase password reuses its primary scrypt verifier, while a mixed-case password requires one additional scrypt evaluation of its lowercase form. A proposed address is compared through the same bounded KDF gate and signup source budget; a match refuses the change and preserves the pending signup for a corrected address.

#### Verification order and guessing limits

`loginWithUserPassword` and `verifyAccountPassword` share one implementation. The order is: transport and presentation checks (neutral failure, no KDF); the per-source attempt budget; the per-address and global waiter bounds; the per-email login lock; inside it a recheck of the live parent, the `password` policy and the per-email failure budget; a short read of the account and credential; the KDF outside every store lock (the stored verifier only for an active account with an enabled, supported credential, otherwise the dummy); and under `serializePersisted('users')` a re-read requiring a live parent, password still enabled, the same credential version, an active account and an unchanged `authGeneration`. When work waits for a global KDF slot, admission repeats the live-parent, policy and failure-budget checks before the evaluation begins. Signup and My Account password writes likewise revalidate their attempt or grant and current eligibility when admitted. A failure stages its durable count and a denied audit in one commit and returns `authentication_failed`; a success clears the count and stages an ok audit. Because the budget is rechecked and the failure recorded inside one serialization boundary, a burst cannot obtain more evaluations than the limit. Ordinary password login stages no attempt tombstone and offers no lost-response replay; initial-password setup uses its browser-bound completion record to recover a lost creation response.

| Control | Scope | Limit | Refusal |
| --- | --- | --- | --- |
| Failure budget, existing account | Durable `authThrottle` keyed by the address; cleared on success | 10 failures per 15 minutes | `rate_limited` with `retryAfter`, no KDF |
| Failure budget, unknown address | In memory, same numbers, no durable writes for invented addresses | 10 per 15 minutes | Same |
| Attempts per rate source | In memory, keyed by the Router's trusted `x-ploinky-rate-source`; requests without it share one bucket | 20 per source, 300 shared, per 15 minutes | `rate_limited` |
| Waiters | Process | 4 per address, 64 total | `rate_limited`, no KDF, no failure recorded |
| Signup hashing and email comparison | In memory, per source, charged for each KDF evaluation | 10 per source, 100 shared, per 15 minutes | `rate_limited` |
| My Account hashing | In memory, per account, before hashing | 5 per 15 minutes | `rate_limited` |

Password failures never touch the TOTP lockout counters. A distributed attacker can keep one address's password login throttled; its other methods and Google remain usable.

A password exists in memory only for the request carrying it. It is never logged (including under `ACHILLES_DEBUG`), returned, stored in the browser, sent through MCP tools or accepted by administrative endpoints. Its durable forms are the encrypted credential and, for at most the parent lifetime, the scrypt string inside an encrypted pending signup. Audit events `auth.password.register`, `auth.password.login` (ok, or denied with `invalid_credentials`), `auth.password.reauthenticate`, `auth.password.set` and `auth.password.change` are staged in their owning commits and never contain a password, verifier, code or the plain address of an unknown account.

### Verified email codes and password signup

Email attempts are bound to the parent, the browser and a generation. The browser proof is an `up_browser` cookie (32 random bytes, HttpOnly, SameSite=Strict, `Secure` on HTTPS) whose path is the browser-visible service prefix plus `/service/`; the server stores only its digest. An encrypted `authAttempt` record, format version 2, is keyed by `sha256(JSON.stringify(['userpersisto:auth-attempt:v2', flow, parentId, sha256(browserProof)]))` and encrypted under the context `userpersisto:auth-attempt:2:<key>`. It holds the normalized email, the purpose (`login` or `register`), the current generation, the challenge hash, counters, an optional staged signup `{ verifier, emailComparisonVerifier?, verifierId, stagedAt }` and an optional completion. A record of any other format is never found, decrypted or converted; the bounded sweep removes it by expiry. A code is six digits, expires after `min(5 minutes, parent deadline)`, allows five failures per attempt across generations and a resend after 60 seconds. Each resend, email change or purpose change starts a new generation that invalidates earlier codes. A code hash is bound to the attempt key, its generation and either the staged `verifierId` (signup) or the literal `login`, so a code from another person's pending signup can neither complete the mailbox owner's attempt nor activate another password. Cancel clears the challenge and any staged signup server-side but keeps the counters.

Limits cannot be reset by restarting or resending: at most five sends per attempt (the cap reports `rate_limited` with `reason: send_limit`); in memory five sends per address and 20 per rate source (200 shared) per 15 minutes, and 20 discoveries per parent and 60 per source (600 shared); and a durable budget of ten verification failures per address per hour, shared with Google mailbox and link codes and My Account codes. A refused start spends the same send budgets as a send. Every issued challenge counts, whatever its delivery outcome. Budgets fail closed when saturated and report `rate_limited` with `retryAfter`.

A login code goes only to an active account's verified mailbox while `emailCode` is enabled and delivery is available; the login operations refuse `purpose: 'register'` with `invalid_request`. Completion rechecks the live parent, policy, status, mailbox and generation under the `users` lock. The Router SSO handoff code is staged in the same commit as the attempt's completion tombstone, so a lost response replays the same unconsumed handoff to the same browser and parent only; OIDC completions resume through the engine's committed interaction result.

#### Pending signup lifecycle

Password signup is the public way to create an account with an email; Google is the other. Entering an email, choosing a password or requesting a code creates no user, role link, setup record, email reservation, credential, session, handoff or OIDC result, and blocks no other browser or Google registration for the same address. `startSignup` runs in this order: email, confirmation and creation-policy validation; the live parent; a read-only precheck that `password` is enabled, registration is open (unclaimed setup or `selfRegistrationEnabled`), delivery is available, the address is unowned and the attempt is neither locked nor completed (a refusal spends the send budgets); the per-source signup hashing budget; the primary KDF outside every store lock, with an optional second comparison verifier only for an email-shaped mixed-case password; `issueChallenge`, which repeats the checks and stages the verifier with a new `verifierId` and delivery `pending` under the persistence scope; delivery outside the store locks with `purpose: 'signup-verification'`; and the recorded outcome. Refusals before staging (`invalid_email`, `password_mismatch`, `invalid_password`, `account_exists`, `registration_disabled`, `auth_method_disabled`, budgets, a saturated gate, `persistence_unavailable`) leave nothing durable, so the password is chosen again. Once a verifier is staged, the signup operations answer `200` with the public challenge whatever the delivery outcome:

| `challenge.delivery` | Meaning | Code accepted | Next send |
| --- | --- | --- | --- |
| `accepted` | The provider accepted the message | Yes | After the 60-second cooldown |
| `unknown` | The transport errored; the message may have been sent | Yes | After the cooldown |
| `development-log` | Written to the agent log under `USERPERSISTO_DEV_BOOTSTRAP=true` | Yes | After the cooldown |
| `failed` | Known provider failure after staging | No | Immediately |
| `pending` | Observed later: the delivering request ended without recording an outcome | No | Immediately |

**Resend code** and **Send again** (`resendSignup`) and **Change email** (`changeSignupEmail`) issue a new generation and code while keeping the staged verifier, so they carry no password. Resends run no KDF; an email change uses the optional comparison verifier to refuse a password equal to the proposed address before changing the attempt; the cooldown is skipped only after `failed` or `pending`. A purpose change to `login`, Cancel or leaving the verification screen, five wrong codes, a verified completion and a refused completion erase the staged verifier. A registration without a staged verifier (or with an unsupported one) returns `409 signup_restart_required`, and the wizard asks for the password again with the email kept. Everything shares `expiresAt = parent.expiresAt`, so nothing survives the parent. Two tabs on one parent share one attempt; the newest generation wins and a reload resumes the current server state. Different parents or browsers are independent, and the first verified completion wins.

`completeSignup` runs under `serializePersisted('users')` inside the parent lock. It validates the parent and the verifier-bound code (a completed attempt takes the replay branch), rechecks that `password` is enabled (`auth_method_disabled`), that registration is open (`registration_disabled`) and that the address is unowned (`account_exists`); each refusal consumes the proof and erases the verifier, and a registration proof never authenticates or modifies an existing account. It then prepares the account with `emailVerified: true` and setup method `passwordSignup`, and commits once: the user, role links, the setup record when first, the password credential (the staged scrypt string wrapped for its owner), the completion tombstone without the verifier, the `auth.password.register` audit and, for SSO, the handoff with the consumed login request. The user is then signed in without another prompt. SSO has one persistence boundary and replays a lost response to the same browser and parent. OIDC has two: the local commit, then `interactionFinished`, where the engine persists its interaction result. A stop between them leaves an active account and a completed attempt without an interaction result; the same browser recovers by repeating `signup-verify`, which rechecks status and generation and finishes the interaction again, or the user simply logs in with the chosen password. A failure while staging poisons the store, so no partial owner, credential or setup record is published.

#### Delivery, discovery and availability

Login code delivery reports `accepted` when the provider accepted the message, `failed` (`502 delivery_failed`, no success message, immediate retry allowed) on a known failure, and `unknown` when the transport errored. When `USERPERSISTO_DEV_BOOTSTRAP=true` and a send was not accepted, the code is written to the agent log labelled `DEVELOPMENT email code` and reported as `development-log`; this is never a production method. Email logs keep only an address digest. Signup codes carry `purpose: 'signup-verification'` to EmailAgent's `email_send_auth_code`, which then uses the subject "Verify your email to finish creating your account" and states that the account is created only after the code is entered on the sign-up page; with a configured template the variables become `{ code, purpose }`. Every other code keeps the generic message.

Public account discovery (`discover`) returns only `{ exists, methods: { password, emailCode, passkey, totp } }`. `methods.password` is true only for an active account with an enabled credential while policy allows `password`. A blocked account reports every method false, so no field distinguishes a missing enrollment from blocked status; pending signups are invisible. Discovery never exposes credential names, identifiers, counts, timestamps, roles or Google linkage, and it is advisory, never authority. The existence disclosure is an accepted consequence of the selected sign-in design.

Email availability requires configured delivery in addition to enabled policy: email signup also needs `password` enabled and open registration, and login codes need a verified sign-in mailbox. UserPersisto queries EmailAgent’s agent-only `email_auth_code_status`, which returns only `{ available }` after validating sender credentials, address and any selected authentication template. The bounded two-second probe sends no email, exposes no configuration values, and treats missing, denied, malformed or timed-out responses as unavailable; signup routes that would send mail refuse with `403 registration_disabled` while delivery is unavailable. Wizard discovery, account confirmation controls and the administrator policy guard use that result. Policy updates probe once before entering persistence and refuse to count an unconfigured email method as the administrator’s remaining way to sign in. Only the exact `USERPERSISTO_DEV_BOOTSTRAP=true` flag makes the documented development log delivery available without a configured provider; it does not change EmailAgent’s readiness result or seed an account. Already delivered proofs can still complete when delivery subsequently becomes unavailable, provided their method remains enabled. Controlled test transports and readiness functions are construction-time dependencies, never request bypasses. MCP error responses and malformed delivery acknowledgments are known send failures.

### Authentication policy

The durable authentication policy contains enabled methods (`password`, `emailCode`, `passkey`, `totp`, `google`), whether later self-registration is allowed, and explicitly configured redirect origins. With no stored policy or override, all five methods are enabled and self-registration is on. Unsupported method names, including the retired `adminPassword`, and `defaultRegistrationRole` are refused (`invalid_auth_method`, `invalid_policy_field`); an environment `USERPERSISTO_AUTH_METHODS` naming an unsupported method ignores that name with a one-time warning, and an override naming no supported method is ignored. A stored policy or override without `password` deliberately disables password signup and login; there is no stored-policy migration. Disabling a method affects new authentication only: `password` login and signup are refused at start and again at completion, including a signup started earlier, and existing sessions are untouched. Google is available whenever it is enabled and completely configured, including during unclaimed setup. Environment overrides remain authoritative, every save is checked against the effective policy, and administrator settings identify the override names.

`PROD` has no authentication, email-delivery or logging meaning. The manifest does not declare it, and its presence, absence or value changes no screen, method or outcome; production and other deployments follow the same policy.

Deliberate policy changes must leave every active administrator a usable sign-in method: an enabled password while `password` is enabled, email code with a verified mailbox and available delivery, an enabled passkey or TOTP allowed by policy, or Google when enabled, configured and bound. Otherwise the save fails with `administrator_auth_method_required`. Passkey, TOTP and a password are never mandatory.

### Authentication origins

Callback (redirect URI) and browser-origin checks share one membership rule: an implicitly allowed loopback origin (`localhost`, `127.0.0.1` or `[::1]` on any port), an explicitly configured origin, or, while automatic trust is enabled, an origin in freshly verified workspace Router metadata. A nonempty `USERPERSISTO_ALLOWED_REDIRECT_ORIGINS` replaces the stored explicit list; otherwise the stored list applies. Managed Router origins are never written into either source, so rebinding, port changes, removal and rollback need no cleanup.

`USERPERSISTO_TRUST_ROUTER_ORIGINS` controls automatic trust, and the manifest declares `true`. Unset or empty also means enabled; only `true` or `false` (case-insensitive, surrounding whitespace ignored) are valid. Any other value is a configuration error that denies managed-only origins with `auth_origin_topology_invalid`.

A process runs under a managed Ploinky runtime when any part of the generated Router descriptor contract is present: `PLOINKY_ROUTER_DESCRIPTOR_FILE`, `PLOINKY_EDGE_TOPOLOGY_FILE`, `PLOINKY_INTERNAL_ROUTER_URL`, `PLOINKY_AGENT_PRIVATE_SECRET` or a `PLOINKY_ENV_SOURCE_PLOINKY_*` provenance marker. A broken remainder of that contract is an error, never standalone mode. Standalone execution uses loopback and explicit origins only and loads nothing from a Ploinky runtime. When a managed decision needs automatic trust, UserPersisto first reads the edge topology through the runtime's `edgeTopology.mjs` reader. A valid topology without `routerOrigins` identifies a runtime without this capability: automatic trust is unsupported and only loopback and explicit origins apply. A present array advertises the capability but grants nothing by itself, because Ploinky writes the topology before its routing selector commits. UserPersisto then reads `GET /api/edge/runtime-origins` through `/Agent/lib/runtimeRouterOrigins.mjs`, which verifies the signed generated Router descriptor, signs a fresh private assertion and validates the bounded response from the active routing lease.

Every decision reads again; one SSO login start shares a single read between its canonical-origin and login-request checks, and no permission is cached across decisions. Startup and readiness never call the operation, which avoids a dependency cycle with graph activation. A missing or unreadable topology or a transient Router state (`503` from the operation, timeout or refused connection) denies managed-only origins with `503 auth_origin_topology_unavailable`. A malformed topology, missing helper, `404`, rejected identity, redirect or invalid response denies them with `503 auth_origin_topology_invalid` and is never treated as an older runtime. Loopback and explicit matches never need the read. Diagnostics log one safe line per distinct failure category, without origins, paths, tokens or payloads.

Pending SSO requests revalidate their stored callback whenever the wizard loads them and again before a handoff code is issued. After a rebind, port change or removal, a pending request for a removed origin therefore fails with `redirect_origin_not_allowed` before any code exists, while requests for loopback, explicit or still-bound origins continue. Passkey registration and login options and verification use the same membership. Relying-party ID, challenge, signature, user presence and verification, counter and replay checks are unchanged, and browsers still require a secure context for WebAuthn. This does not change Google callback registration or OIDC client `redirect_uris`.

Origin failures are typed: `400 invalid_redirect_uri` for a malformed callback or one carrying credentials, `403 redirect_origin_not_allowed`, `403 browser_origin_not_allowed`, and the two `503` topology errors above; `invalid_browser_origin` keeps `400`. Normal origin denials happen before login requests, browser proofs, email or codes are created. The provider runtime preserves the code and status for the Router, which presents only these exact pairs with fixed wording as an accessible login error page or JSON body; any other provider failure remains a neutral `500 auth_failure`, and callback code rejections remain `invalid_authorization_code`. The wizard shows the same fixed wording.

Administrators receive read-only origin provenance from `policy/get` and `userpersisto_auth_policy_get`: `allowedRedirectOriginsSource` (`policy` or `environment`), `loopbackOriginsAllowed`, `managedOriginTrustEnabled`, `managedOriginStatus` (`verified`, `disabled`, `standalone`, `unsupported`, `unavailable`, `invalid` or `invalid-setting`), `managedOriginGeneration`, `managedRedirectOrigins` and `effectiveRedirectOrigins`. `allowedRedirectOrigins` remains the writable explicit list. The Authentication policy page shows managed origins in a separate read-only section, and its editable field and saves contain only explicit origins. Setters refuse these metadata fields, including `registrationRole` and `environmentOverrides`, with `400 read_only_policy_field` instead of dropping or saving them.

### The sign-in wizard

One email-first wizard (`public/auth/wizard.js`) serves both surfaces through protocol adapters: the Router SSO page (`sso-adapter.js`, JSON calls under `/service/auth/`) and the OIDC interaction (`oidc-adapter.js`, CSRF form posts to `/service/oidc/interaction/<uid>/<action>`). The flow and every server rule are the same on both. The opening screen shows the heading **Sign in** (OIDC with `screen_hint=signup`: **Create your account**, which changes nothing else), the first-run notice while setup is unclaimed ("The first completed sign-in becomes its administrator"), the OIDC application name, any Google notice, **Sign in with Google** when Google is usable, **Email** and **Next**. It has no password field, administrator control or Login/Register switch; OIDC adds **Cancel**, which submits the `abort` form.

**Next** runs discovery. A registered address always opens **Enter your password**: a read-only email field (`autocomplete="username"`), **Password** (`autocomplete="current-password"`), **Log in**, **Try another way** and **Back**. When password sign-in is unavailable, the input and **Log in** are disabled with one neutral line, "Password sign-in is not available in this workspace." when policy disables the method and otherwise "Password sign-in is not available for this account here. Choose Try another way.", and focus moves to **Try another way**; nothing mentions blocking or Google. A wrong password shows "That password is not correct. Try again or choose another way to sign in." and never reveals remaining guesses. **Try another way** always lists **Email me a code**, **Use a passkey** and **Use an authenticator app** in that order. Unusable entries are disabled with one reason ("Not available in this workspace.", "Not available in this browser or at this address." or "Not available for this account."), a static line says that sign-in methods are managed from My Account, and **Use your password** returns to the password screen. When nothing is usable the screen suggests Google or the workspace administrator.

While `initialPasswordSetup` is true, an unknown address first opens the ordinary password screen with an explanation to enter `admin`; **Sign up** remains available there when verified signup is usable. Discovery refreshes this availability, and the server always rechecks it. Otherwise an unknown address opens **Create an account?** with **Sign up** when email signup is available (open registration, `password` enabled and delivery available), a Google registration screen when only Google signup is available, and otherwise a no-account screen. **Sign up** opens **Create your password** with the read-only email, **Password** and **Confirm password** (`autocomplete="new-password"`) and the hint "Use at least 15 characters."; the wizard checks the published `passwordPolicy` numbers (a mismatch empties and focuses the confirmation) and the server repeats every rule. **Create account** stages the signup and opens **Enter the 6-digit code sent to *email*** with an honest delivery line, the statement that the account is created only after the code is entered, **Verify**, **Resend code** with its cooldown counter, **Change email** and **Cancel**. The `failed` and `pending` delivery states show **We could not send the code**, disable the code input and **Verify**, say that the chosen password is kept, and enable **Send again** at once. **Change email** opens **Change your email** and sends a code for the new address without asking for the password. While a signup start or email change is running, Back is disabled to keep the displayed state consistent with the server. Verification, resend and opening Change email cannot overlap; Cancel remains available. Five wrong codes lock the screen with **Start over**. A correct code creates the account and completes sign-in automatically. `account_exists` at signup start, email change or verification opens **Log in instead?**, whose **Log in** rediscovers the address and opens the password screen; `registration_disabled` leaves the signup with its message; `signup_restart_required` returns to **Create your password** with the email kept.

Password inputs carry no `maxlength`, because HTML measures it in UTF-16 code units and browsers silently truncate pasted text. Every transition empties password and code inputs, and a submitted password leaves the page only inside its request. Leaving a login-code flow cancels its server attempt. Cancelling a pending signup erases its staged verifier; opening Change email preserves that staging until the new address is accepted or the signup is cancelled. Errors use fixed copy: rate limits say "Too many attempts. Wait *n* s and try again.", and the send cap says "Too many codes were requested. Start again." (SSO offers **Start again**; OIDC says to restart from the application). Expiry (the authoritative parent deadline is displayed) offers **Start again** for SSO (`/auth/login?returnTo=…&prompt=login`) or **Close window** for OIDC. Late results from an abandoned screen are ignored, a pending passkey prompt is aborted on navigation, and only `{ email }` is kept in `sessionStorage`; a reload resumes a pending signup without asking for the password again, or an active login code, from server state. An ambiguous signup-start, resend or email-change failure also re-reads the bound attempt and resumes its actual address and challenge; if this read fails, a secret-free **Try again** / **Cancel** screen retries only the read, without another password or KDF. Google denial or cancellation returns to the opening screen with a notice.

SSO completion returns JSON `{ code, redirectUri, state }` for the stored Router callback and keeps the Router's own state and browser binding. OIDC credential completions (`password-login`, `signup-verify`, `email-verify`, `totp`, `passkey-verify`) are native form POSTs that end in the engine's `interactionFinished` redirect; a failure re-renders the wizard with status 400, a readable error and the attempted email, and the wizard resumes the screen the user left with empty secret inputs. Password login, signup and Google linking never approve application scopes; OIDC consent remains a separate step.

Passkey login requires nonempty, canonical base64url client data that decodes to a JSON object. Malformed assertions and invalid client data are audited authentication denials and return the same neutral authentication failure as other invalid credentials, rather than a server error. Invalid client-data encoding, shape, type, or missing challenge is rejected before consuming a challenge. Valid assertions still require the expected browser origin, relying-party identifier, challenge, user presence, user verification (the UV flag; browser options request `userVerification: 'required'` for registration and sign-in), signature, and authenticator counter; challenges and counters cannot be replayed. Wizard passkey challenges are bound to their parent (`sso-login:<requestId>` or `oidc-login:<uid>`).

Ploinky binds each pending login transaction to an independent browser proof in an HttpOnly, SameSite=Lax cookie. HTTPS deployments use Secure host-prefixed cookies. Callback validation requires that proof before consuming pending state or setting a session; a copied callback in another browser fails, and concurrent tabs retain separate proofs. Successful callbacks clear their proof and cannot be replayed. SSO authorization codes and login state are short-lived. Provider authorization codes are single-use. If the provider rejects a callback exchange with HTTP 400, 401, or 403, the Router returns HTTP 400 `invalid_authorization_code`, without issuing a session cookie or exposing provider rejection details. Unexpected server failures remain server failures. Redirect URIs must be absolute HTTP(S) URLs whose origin is loopback, explicitly allowed, or a freshly verified workspace Router origin (see Authentication origins). Provider session validation reloads the user, roles, capabilities, and active status from Persisto so blocking an account or changing its roles is enforced on the next remote validation.

The browser login URL uses the validated callback's public origin, preserving its hostname and port. The configured login path must remain on that origin. Runtime bridge calls continue to use the private `routerBaseUrl`; a loopback bridge address must never replace a remote browser's public login address or change the host of its callback proof cookie.

Before creating a local SSO login request, a Router that supplies `supportsCanonicalLoginOrigin: true` may receive only `canonicalLoginOrigin` instead of a provider request. UserPersisto derives that hint from enabled, complete Google callback configuration, and only when the validated Router callback and configured callback use different exact loopback hosts (`localhost`, `127.0.0.1`, or `[::1]`) with the same HTTP(S) scheme and port. The Router validates the hint independently and restarts `/auth/login` with a 303 on that origin before minting pending state or a browser proof. The relative return target, login prompt and explicit agent selection survive; no prior state, code or proof crosses origins. The fresh canonical request follows the ordinary SSO path. This negotiation requires the runtime secret, never redirects a public origin or changes port/scheme, and is omitted for older Routers, disabled Google or incomplete configuration. Google Origin, callback, cookie and replay checks remain exact.

### Roles and capabilities

Google Identity Services authenticates an external identity using a public client ID and a Google-signed ID token; no Google client secret is configured or distributed. Fresh local installations use the shared public client at exactly `http://localhost:8080` and retain their own Ploinky-generated settings encryption key. A dedicated same-origin page renders Google's button and submits the token with the server-issued nonce and browser-bound transaction to UserPersisto for verification (DS013). Google issuer spellings are normalized to `https://accounts.google.com` after verification. UserPersisto resolves that issuer and the verified case-sensitive subject to an immutable local owner; email is never the binding key. Returning linked users retain their local ID, profile, credentials and current roles, even if Google changes the email claim. Missing or blocked local owners deny authentication without email fallback or replacement. A new Google account goes through the setup decision: on an unclaimed installation it becomes the initial administrator (setup `method: 'google'`), afterwards it requires current self-registration and receives exactly `selfRegistered`. No password is synthesized: a Google-created account has none until one is set in My Account, and its password screen shows the neutral unavailable state. Google never sets, reveals or changes a local password, and setting a password never alters the binding. Registration policy never demotes an existing linked account or prevents its normal sign-in.

An operator may explicitly configure that same public client together with a canonical HTTPS service URL after its owner registers the deployment's exact JavaScript origin with Google. Both configuration fields are required; absent fields still select only the localhost default, partial configuration fails closed, and the shared client's HTTP alternatives remain limited to the two documented port-8080 loopback origins. This changes configuration admission only: Google audience/nonce verification, exact request and parent origins, per-browser proof, configuration fingerprint, Secure cookies, and local account/role decisions remain unchanged.

#### Google registration and collision linking

An unbound Google identity that matches a local account's normalized sign-in email requires fresh proof of that exact account and an explicit **Link Google and continue** confirmation, all in the same live parent and browser-bound transaction. Eligible proofs are: a link-specific six-digit code sent to the account's verified sign-in mailbox while `emailCode` is enabled (`send-link-code`/`verify-link-code`, bound to the transaction and the mailbox version); the account password, verified by `verifyAccountPassword` under the same lock, budgets and KDF gate as login, while `password` is enabled; or an enrolled, enabled, policy-allowed passkey or TOTP. Existing sessions, the Google claims themselves and codes of other purposes are ineligible. **Don't link; go back** returns to the wizard without linking.

The authoritative-Google shortcut is narrow: when the Google identity is authoritative for its email (a Gmail address, or a Workspace `hd` equal to the email domain, with `email_verified`), that email exactly matches the account's current verified sign-in mailbox, and `emailCode` is enabled, explicit consent alone may link. The shortcut is a mailbox-control proof, appropriate exactly where mailbox control already signs the account in; it is created at consent time with the mailbox version. A non-authoritative address never offers the shortcut. An unverified contact address is not a sign-in mailbox and is never a link target.

The server selects and retains the collision account ID and email. Confirmation rechecks that ID, the unchanged sign-in email and mailbox version (`sha256(email, emailVerifiedAt, authGeneration)`), active status, current Google policy, the proof method's current availability and credential version, parent validity, identity ownership and the account's existing Google grouping. Every local credential proof retains the account generation as well as its credential key and version; password proofs use `credentialVersion('password', [version, setAt])`. A password change therefore invalidates pending password, TOTP and passkey link proofs even when the other credential is unchanged. A changed local email invalidates the attempt; a changed Google email is never copied to the account. Initially a local user may have only one Google identity; replacement, transfer, unlinking and linking a different address are unsupported. A newly discovered collision after a registration mailbox challenge follows the same rule. Passkey challenges bind purpose, transaction and target before consumption. Pending proofs retain only a digest of the credential material actually verified, plus its enrolled key when applicable; a password change, TOTP replacement, passkey replacement or removal and a generation change invalidate them. Ordinary usage counters do not.

New registration requires a usable Google-verified email. Authoritative Google email authority may verify the mailbox directly; a third-party address without that authority additionally requires fresh EmailAgent proof before reserving any user or email. This is an additional proof within an already verified Google transaction, not standalone email sign-in. This `google-registration-email` proof lives inside the encrypted Google transaction, has bounded attempts, expiry and resend cooldown, reports delivery honestly, and cannot authenticate through wizard endpoints. Delivery failure creates no account.

This linking rule does not claim global prevention of account pre-hijacking. An actor who controls an account's verified mailbox can prove it. Historical credential provenance, general recovery and Google unlinking remain deferred.

#### Google identity durability

`externalIdentity` stores only the canonical issuer, subject, immutable local `userId`, identity key and timestamps. Its unique key is SHA-256 over the encoded issuer/subject tuple and lookup compares the original tuple. Grouping by user provides only a safe `{ type: 'google', name: 'Google' }` profile method. Profile, user lists, SSO and UserInfo never expose provider subjects, transaction payloads, proofs, tokens or keys. No duplicate Google `authMethod` row is created and no email-based backfill occurs when reopening old snapshots.

Trusted external registration/linking validates policy, role and uniqueness before staging the user, roles, binding and audit without intermediate flushes, then commits one snapshot. Lock order is parent flow, users/domain, persistence scope; non-reentrant locks must not be reacquired from their locked helper. Network requests never run inside the persistence scope. An unexpected error after staging poisons the store so no unrelated later flush can publish partial state. Failure after rename but before directory fsync can leave a complete unacknowledged identity after restart: a fresh attempt resolves its existing binding without duplicate creation or replayed success. A failed downstream handoff may leave a complete identity; it never authorizes reissuing a consumed result.

| Role | Capabilities |
| --- | --- |

Explorer's protected surface requires `explorer.access`; therefore both `admin` and `user` can enter Explorer, while `selfRegistered` cannot unless an administrator changes policy.

### Account dashboard and credential enrollment

The account dashboard is served at `/base-agent-additional-server/userPersistoAgent/7000/service/dashboard/`. Its manifest route requires an authenticated Ploinky session. Any active UserPersisto account may read and update its own profile and enroll permitted sign-in methods there, including accounts without `explorer.access`. Explorer declares this path as its `routerAccess.capabilityDeniedRedirect`: a denied HTML document GET is redirected to the dashboard, while API calls, mutations, MCP, SSE, and WebSocket traffic keep their denial responses. The redirect is a local same-origin path and must not redirect back to the denied resource.

This route uses the companion Ploinky authenticated-service routing behavior: an explicitly owned and matching `access: authenticated` service declaration retains the inherited identity provider while applying the service's own capability requirement. Undeclared and guest/public service routes retain the owner's capability checks. Installing the agent UI without the matching Router changes does not establish restricted-account dashboard access. Later public registration defaults to the `selfRegistered` role and therefore reaches this dashboard without opening Explorer.

Every dashboard request verifies the Router's HTTP invocation token with the mounted `/Agent/lib/invocationAuth.mjs` helper, binding audience, method, internal path, query, raw body hash, expiry, and replay protection. The acting user comes from the signed user subject/actor, followed by an active-account lookup in Persisto. Unsigned carrier fields and request body identities never select an account. Authentication requires a UserPersisto identity; a local Ploinky account cannot become a UserPersisto user implicitly.

UserPersisto owns five standalone pages beneath this authenticated service path. Explorer Settings contains only navigation links; the Agents Configure action follows the UserPersisto plugin's `settingsUrl` to the root dashboard. My Account contains personal profile and sign-in security, while workspace-wide authentication policy has its own page. Account navigation and the UserPersisto settings plugin link to Roles for users with role-management access.

The Users page assigns roles with a searchable multi-select dropdown. The administrator-only `users/list` result includes `availableRoles`, the complete persisted role-name catalog independent of user filtering and pagination. The Roles page searches and pages the complete role catalog and allows creating a custom role, editing its description and permission bindings, and deleting an unused custom role. Permission changes affect all assigned users when authorization is evaluated again, subject to existing Router session revalidation and token lifetimes.

This preserves administrator recovery, default Explorer access and the restricted public-signup role. Deleting an assigned custom role fails with `409 role_in_use`; callers must first change its user assignments. Duplicate names fail with `409 role_name_taken`, and unknown role IDs return `404 role_not_found`. Names and descriptions are escaped in the page, mutations are serialized in the UI, and confirmed authentication or management-access loss clears the cached catalog and editor.

The role domain revalidates the active actor's `admin.users.manage` capability while holding the shared `users` lock and persistence scope, then performs all validation before staged persistence. Creates, updates, permission-link changes, deletes and their audit event commit through one fail-closed snapshot boundary. Role deletion and assignment share the same lock so they cannot create orphan assignments. Catalog reads enumerate every storage page for roles, permissions and assignments. The list result is `{roles, permissions, totalCount}`, with roles projected as `{id, name, description, priority, builtin, capabilities, userCount}` and permissions as `{capability, description, scope}`. #### Fresh confirmation, enrollment and contact verification

Enrollment is optional and happens after sign-in. Each sensitive operation (`password.set`, `passkey.register`, `totp.enroll`, `contact.verify`) first needs explicit re-authentication with a currently available method, offered in the order password, email code, passkey, TOTP and Google: the account password (verified under the login rules and bound to its credential version when the grant is issued), an email code to the verified sign-in mailbox (six digits, five minutes, five failures, 60-second resend, the durable per-address budget), an enrolled passkey (challenge scoped to the account and operation), an enrolled TOTP (sharing the account's login lockout and replay protection), or the already linked Google account. Success issues a single-use grant, stored only as a hash in an `authChallenge` with purpose `operation-grant`, bound to the account, that one operation and the account generation, and valid for five minutes. Starting the operation consumes it; a grant for another account or operation, an expired or reused grant, and a grant issued before a generation change are refused with `403 operation_grant_required`. An arbitrary old session or a reused registration challenge cannot enroll, and a recent sign-in does not substitute for this confirmation.

Google confirmation opens the dedicated GIS page in a separate popup and never creates or links an account. It binds the operation, local actor, current account generation and initiating browser, and requires the returned issuer and subject to match that actor’s existing binding. The verifier requires a signed `auth_time`; an absent value, a time over five minutes old, or a future value beyond clock tolerance is refused. GIS does not guarantee this claim or a new credential prompt, and fresh token issuance alone never counts as recent authentication. When Google cannot provide the required proof, another enrolled confirmation method may be used when policy permits it. The popup carries no operation grant back in its URL or browser storage: the original authenticated dashboard polls for the one-use grant. Cancellation, wrong-account responses, expiry and generation changes cannot authorize enrollment. Google transactions accept exactly the grant operations above, so a Google-only account can confirm setting its first password without email delivery. See the [Google ID-token verification guide](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).

Password, passkey and TOTP sign-in are reached through the account's sign-in email, so they can be set up only once the account has a verified sign-in mailbox (`verified_email_required`). TOTP setup is staged: the current authenticator keeps working until the new secret is proven; a newer start supersedes older setups (`setup_superseded`), five wrong codes or a generation change end the setup, and replacing an enabled authenticator advances the account generation. Passkey registration binds its challenge to the grant's generation and reports verification failures as `400 registration_failed`. Its final generation and uniqueness checks share the users lock and persistence scope with credential creation. Passkey counters and TOTP login/re-authentication updates use that same exclusion so concurrent authenticator replacement cannot restore a retired credential.

`POST api/auth/password/set` sets a first password or changes the current one (`lib/auth/passwordManagement.mjs`). Its order keeps a valid grant usable after predictable mistakes and consumes it exactly once: (1) validate the confirmation and the creation policy, which never touches the grant; (2) with read-only checks and no KDF, require an active actor, a verified mailbox, `password` enabled and the grant, which is only looked up and validated: a missing or foreign grant is refused with `operation_grant_required` untouched, and an already invalid grant of this account (expired, another operation, an older generation) is deleted and refused; (3) consume the per-account hashing budget and hash outside every store lock, revalidating the actor, policy and grant when a queued KDF slot becomes available; (4) under the `users` lock, re-read and revalidate the grant together with the actor's status, the mailbox, the policy, the grant generation and the current credential version, then commit once: delete the grant, write the credential, advance the generation when a password was replaced, and stage `auth.password.set` or `auth.password.change`. Two requests presenting the same valid grant may both hash, but they serialize at step 4: the first commit deletes the grant and the second finds none and writes nothing, even though a first set leaves `authGeneration` unchanged. A refusal at step 4 for any other reason writes no credential and deletes the grant. Administrators cannot set another account's password.

Contact verification applies only to an account without a verified sign-in mailbox, including the initial-password administrator; its contact address is unverified and grants no sign-in, linking or recovery authority. After a `contact.verify` grant, **Verify this email** sends a code to the chosen address; the correct code makes that address the account's verified sign-in email (rechecking eligibility and uniqueness under the users lock). This never replaces an existing verified mailbox (`sign_in_email_exists`) and never takes an address another account uses (`email_taken`). Adding a mailbox replaces nothing, so it does not advance the generation.

The standalone My Account page owns these controls; Settings → My Account links to it. Its **Password** row offers **Set a password** or **Change password** after fresh confirmation, with **New password** and **Confirm new password** inputs (`autocomplete="new-password"`, no `maxlength`) that apply the creation rules. The grant stays only in memory while the form is open, so a refused password (`invalid_password`, `password_mismatch`, `rate_limited`) can be corrected without confirming again; any other refusal forgets it. After a change the page reports that every session, including the current one, is signed out. The confirmation step lists the profile's `reauthenticationMethods` (the password option is labelled **Password**), and codes, passwords, setup secrets and grants are cleared on success, cancellation, navigation and component removal and are never stored in browser storage. These are alternative sign-in methods; this revision does not introduce step-up or a mandatory second factor.

#### Credential changes and sessions

Each account carries an integer `authGeneration`. A password change and TOTP replacement advance it and, in the same staged commit, remove the account's stored OIDC sessions, grants, access and refresh tokens, authorization codes, and completed login or account-bound consent interactions. A first password set, like adding a mailbox or a first authenticator, replaces nothing and keeps the generation. Pending email login challenges and completed email retries are bound to the original account ID, verified mailbox and generation; a new generation cannot turn an old proof into a fresh login, and operation grants, staged TOTP setups, passkey challenges, Google link proofs and SSO handoffs bound to the old generation are refused. SSO handoffs carry the generation verified by authentication and reject issuance or consumption after it changes. Generation checks and handoff consumption share the persistence scope with credential changes. The Router's provider session stores the generation from the SSO handoff; `sso-user` refuses an older one with `401 session_revoked`, so Router sessions end at their next revalidation, within 30 seconds by default. Self-contained OIDC ID tokens are not stored and stay valid until they expire (at most 300 seconds). Mailbox versions, grants and staged setups include the generation, so they become invalid too.

Blocking an account advances no generation: authentication is refused for every method at start and at completion with the neutral failure, the next Router revalidation refuses the session (`user_not_active`), OIDC activity checks fail and no new tokens are issued. Role or permission changes revoke nothing: the identity still authenticates normally and the next revalidation returns the current roles and capabilities, so capability routing changes (losing `explorer.access` redirects HTML navigation to My Account and denies protected calls; gaining it opens Explorer). A disabled method, closed registration or unavailable delivery also keeps the generation; it is refused at start and rechecked in every locked completion, and a pending signup then ends with `registration_disabled` or `auth_method_disabled` and its verifier is erased.

### Explorer administration and settings

The standalone Users page exposes Previous/Next controls and total counts in pages of 100 users through its signed dashboard API. Mutations reload the current page, and deletion or role changes that empty the last page move to the preceding valid page. The default list requests `excludeOnlyRole=selfRegistered` and `includeRoleCounts=true`, presenting only a count of accounts whose sole role is `selfRegistered`. Nonempty search clears the exclusion and searches email, username, display name and local ID across all users before pagination. Role promotion updates both the default list and global counts. `userpersisto_user_list` forwards the same bounded `search`, `excludeOnlyRole` and `includeRoleCounts` inputs; browser filtering must not hide matching users on another page. Accounts are created by signing in, so there is no create form. The sign-in email is shown read-only; update forms preserve optional username/display name values and never send email or a password. Details and role changes are separate actions so a failed action cannot be mistaken for a completed combined save. Explorer's own Administration users view follows the same rules and the Router maps `user_creation_unsupported`, `password_unsupported` and `email_change_unsupported` to provider-neutral `400` responses.

The existing provider-neutral Router user-administration surface remains available independently of the standalone pages. It applies exact-origin and session-bound CSRF protection, current provider-session validation and administrator checks before delegating provider methods. UserPersisto re-authorizes the persisted actor. The standalone pages use their own fixed agent HTTP endpoints and do not depend on this compatibility API or its local-control proof exchange.

Ploinky's retired `/auth/account` and login-branding settings routes are unavailable. Explorer Administration contains links to the authorized UserPersisto pages and does not offer local login branding. Old local browser credentials cannot authorize Marketplace, policy, or other protected controls. The verified local CLI operator channel remains a separate runtime control channel; it does not provide browser password login or establish an Explorer user session.

The UserPersisto settings entry links authenticated users to their standalone account dashboard. Authentication policy and applications require `admin.agentSettings.manage`; users require `admin.users.manage`. Billing configuration and provider credentials retain their existing administrator restrictions and are not added to Settings as embedded forms. Runtime encryption and provider signing keys remain in the runtime secret store and are never embedded as manifest values. Google readiness exposes its public client ID, canonical sign-in origin, configuration source and missing setting names; this integration has no Google client secret.

The standalone Applications page registers OAuth/OIDC clients and provides create, edit, enable/disable, delete, secret rotation, and pagination in pages of 100. It displays the configured issuer and discovery URL, or an explicit disabled state. **Settings → Administration → Applications** opens this page in a separate browser tab. Client secrets are generated by the server and returned only on creation or rotation; the UI displays that value once in a transient field, never in client lists or browser storage, and clears it on refresh, navigation, dismissal, or loss of administrator status. The server re-reads `admin.agentSettings.manage` for every application operation; UI visibility is not authorization. The adjacent Authentication policy page manages workspace-wide sign-in/registration policy and Google readiness separately from personal account security.

### Credit and payment journal

Credits use an append-only `creditTx` journal and a reconciled `creditAccount` projection. Each stable business reference produces a deterministic transaction identifier. Repeating an identical operation is a no-op that returns the reconciled balance; reusing a reference with different financial data is rejected. Amounts are positive safe integers and a balance or reserved balance may never become negative.

Reservations have a durable lifecycle: `reserved`, then exactly one full `committed` or `released` transition. Commit and release must match the original user, amount, and reference. Reservation identity is scoped to the user and business reference, so different users may safely reuse a reference. Reservation projections are reconstructed from reserve/spend/release journal entries, preserving terminal status. Legacy raw-reference projections are accepted only for their owning user; an old cross-user collision with a stranded reserve journal can be repaired on retry or settlement. Partial settlement is not supported by this revision.

Stripe webhook signatures are verified over the raw request body with a five-minute timestamp tolerance. A Stripe event identifier is bound to its payload hash. Paid credit checkouts create one deterministic purchase journal entry only after the event identity matches a checkout previously initiated and journaled by UserPersisto. The checkout snapshots the number of credits before redirecting to Stripe, so later configuration changes cannot alter an in-flight purchase. Identity, amount, and currency conflicts fail before credits are applied; unpaid completion events create no credits. Processed events are idempotent, failed events remain retryable, and reusing an event identifier with a different payload is rejected. `paymentTransaction` is an operational projection of Stripe checkout/payment state; it is not a replacement for Stripe's monetary records.

Checkout creation accepts an explicit client idempotency key or generates one, scoped by user and checkout kind. Before contacting Stripe it durably records a `checkoutIntent` containing the normalized request, exact provider form, price, URLs, quantity, and credits. Identical retries reuse that snapshot and the recorded session; changed quantity with the same key is rejected. Checkout retries and webhook processing share a serialization boundary, and checkout creation never resets an existing paid payment. Stripe requests have a 15-second deadline covering response headers and body; a stalled request returns `504 stripe_timeout`, releases the billing queue, and leaves its durable intent available for an exact retry. An uncertain response retries the exact provider form/key only while the unresolved intent is younger than 23 hours; older intents return `checkout_reconciliation_required` to avoid provider key expiry creating another purchase. Signed webhook metadata can connect a lost response to its durable intent. Pre-upgrade checkouts retain their existing payment snapshots, but historical client-key mappings cannot be reconstructed automatically. Only an active authenticated account may start checkout.

Subscription events retrieve the current Stripe subscription resource instead of trusting delivery order or second-resolution event timestamps. A canceled subscription is a durable terminal tombstone for its provider identifier. Stripe retrieval or identity-validation failures leave the event retryable; they do not restore a stale active state.

### Durability and deployment constraints

UserPersisto and EmailAgent use the same immutable Ploinky Node image as Explorer. Their workspace data roots are `.data/userPersistoAgent` and `.data/emailAgent`, each mounted at `/data`; Persisto retains its `/data/persisto` directory and EmailAgent retains `/data/settings.enc.json`. Before upgrading an existing deployment that used `.ploinky/data/userPersistoAgent` or `.ploinky/data/emailAgent`, stop the affected agents and migrate their data into the corresponding `.data` roots. The runtime does not read those retired paths automatically.

The exact required Persisto runtime from commit `a711a67f6bdfdec15af91f9f79aa8a0d69397149` is bundled, unchanged and with its MIT license/digest inventory, under `userPersistoAgent/external/Persisto`. Both the model engine and legacy-import storage strategy load from that read-only source tree. Agent startup does not clone, fetch, install or modify files under `/code`; Ploinky's read-only source mounts remain enforced. Only installation-owned data is written under `PERSISTENCE_FOLDER`. A missing runtime fails before store creation and before listeners are opened.

EmailAgent uses Ploinky's default AgentServer to serve its declared MCP tools. UserPersisto owns its HTTP service on `USERPERSISTO_SERVICE_PORT` (default `7000`) and starts the bundled AgentServer on `PORT` (default `7001`) only after persistence initialization and HTTP listener readiness. Its public service routes retain port `7000`; MCP tools forward to the service port independently of the MCP port. An unexpected MCP server exit fails the agent. Graceful shutdown drains MCP while HTTP and the store remain available, then drains HTTP and closes Persisto; a failed or timed-out drain cannot acknowledge clean shutdown. These private listeners add no physical-host publication.

Both agents retain their declared JSON Schema argument constraints through MCP validation and discovery. Tool subprocesses read arguments from the AgentServer `input` envelope and verify the signed invocation in `metadata.invocation`; EmailAgent also accepts its legacy `arguments` envelope.

Persisto remains the model and index engine. UserPersisto replaces the upstream error-swallowing autosaver with a tracked durable adapter: each flush gathers objects, indexes, and groupings into one versioned, checksummed snapshot, writes a private temporary file, fsyncs it, atomically renames it, and fsyncs the containing directory. CRUD cannot race snapshot gathering. Registration, role mutation, and credit workflows additionally hold a shared persistence scope so an unrelated flush cannot publish a partially linked initial owner or credit workflow. Role changes add requested links before removing obsolete ones, and account/reservation projections are rebuilt from the append-only credit journal when they disagree. This is not a general multi-record ACID transaction API.

Save failures propagate as `503 persistence_unavailable` and poison the cached store until restart; subsequent reads and retries cannot acknowledge uncommitted cached changes. A corrupt snapshot or legacy file fails startup rather than becoming an empty installation. Existing per-object Persisto files are imported on first open; after a successful save, `.userpersisto.snapshot.json` is authoritative and legacy files remain untouched. Backups and restores must include the current snapshot. Each dirty flush rewrites the complete snapshot, so storage cost grows with the retained dataset.

These guarantees require one active UserPersisto writer for a persistence volume. An exclusive `.userpersisto.writer.json` lock refuses a live or ambiguous second writer and records the owning Ploinky instance and enable generation when available. Normal shutdown releases its own lock. After an abrupt Box or agent-process stop, a replacement may remove the unchanged predecessor lock only when local process liveness proves that its owner is gone, or when a complete current Ploinky identity proves that a foreign-container lock belongs to a legacy or different generation. A malformed lock, a live local owner, or a foreign lock from the current generation remains fail-closed. The filesystem must provide exclusive creation, atomic same-directory rename, and fsync semantics. Multiple active writers and high-availability failover remain unsupported. Operators must back up the Persisto volume, retain Stripe event history, and reconcile the local payment projection against Stripe after storage recovery. This credit journal is application accounting; financial custody, regulated bookkeeping, tax, chargeback, and revenue-recognition requirements remain outside this component.

### Compatibility scope and deliberate deferrals

This revision provides the existing Ploinky identity-provider interface alongside the OAuth 2.0 / OpenID Connect endpoints specified in DS013: discovery, JWKS, authorization code with mandatory S256 PKCE, token exchange, UserInfo, refresh-token rotation, confidential client credentials, introspection, revocation, and RP-initiated logout. Operators enable these endpoints with an explicit public issuer; existing Ploinky SSO behavior remains available independently. OIDC interactions use the existing enabled authentication methods and registration policy, with browser-bound login and explicit scope consent. OAuth tokens do not authenticate requests to protected Explorer routes.

This scope does not imply full Keycloak feature parity or OpenID certification. SAML, general identity federation/social login beyond the pinned Google client, account recovery or recovery codes, unauthenticated password reset, administrator-set passwords, administrator invitations, arbitrary account creation, general email replacement, Google unlinking or linking a different email, step-up authentication, mandatory multi-factor policy, dynamic client registration, implicit/hybrid/password grants, device authorization, and high availability remain deferred. Password, email code, passkey, TOTP and Google are enabled by default and can be restricted by policy; a password is chosen at signup or set later, and passkey and TOTP credentials are optional, all from the standalone My Account dashboard. A user who forgot a password signs in with another method through **Try another way** or Google and then changes it; recovery for a user with no other usable method remains deferred. A Google-only account can confirm an operation, including setting its first password, using its already linked Google identity even when email delivery is unavailable, subject to the effective operation policy.

The seeded `admin`, `user`, and `selfRegistered` roles and their capability links are durable and protected. Custom role administration and assignment of registered capabilities are implemented; defining new capability types through administration, application-specific roles, composite roles, groups and realms remain deferred. Custom roles may carry OIDC role claims without any capability; the `roles` OAuth scope requests those claims and does not define a role. Ploinky revalidates provider sessions on its configured cadence (30 seconds by default), except user-administration requests, which force a remote validation. Deployments needing immediate route revocation must lower that interval or add provider-driven revocation.

The unclaimed installation is operationally sensitive: the first completed initial-password setup, verified signup or Google sign-in becomes the administrator. Email plus the literal password `admin` allows this first claim without an email provider. Normal signup requires EmailAgent delivery or the labelled development log delivery (`USERPERSISTO_DEV_BOOTSTRAP=true`); the shared Google client works at `http://localhost:8080` without configuration. Claim the installation immediately after the first deployment and keep the deployment on a trusted network until an administrator exists. High availability requires a future transactional or single-leader storage design; starting two writers against the same Persisto volume is not a supported scaling strategy.

## Conclusion

UserPersisto preserves durable local identity, current authorization and financial consistency across Explorer and registered applications. Optional Google verification changes the sign-in credential, never the local account authority.
