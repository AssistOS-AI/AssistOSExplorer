# DS010 Workspace Operations

## Introduction

[Explorer](wiki.html#definition-explorer) provides one workspace surface for navigating, creating, changing, locating, and removing supported resources while preserving filesystem confinement and agent-owned authorization.

## Core Content

In tree mode, page reload and deep links retain the workspace root and expand every ancestor of the directory or selected file from the URL. The selected path must not replace the tree root with its parent; workspace siblings remain visible. A tree-mode deep link requests the listing of the target's parent together with the workspace root listing, and the listings of all ancestors that are not loaded yet are requested together before they are revealed in order; a tree with a specs filter keeps the one-by-one reveal. Opening a text file requests its version information before its content, without waiting in between, so a change that lands meanwhile is more likely to be detected by the later external-change check than missed, and the deep-link path refreshes the view once, through the open itself. The editor's external-change check does not run while the browser tab is hidden.

[Explorer](wiki.html#definition-explorer) must browse configured workspace roots, restore supported file and directory routes, and select the registered preview or editor for the chosen resource. Ordinary paths must use [Explorer](wiki.html#definition-explorer)'s filesystem contract. Virtual paths under `/Confidential` must use [DPU](wiki.html#definition-dpu) operations and must not be translated into ordinary filesystem mutations.

Page changes must stay independent of each other. A history navigation (an address-bar hash change, Back, or Forward) to the page that [Explorer](wiki.html#definition-explorer) is still mounting, without page data, joins that pending mount instead of mounting a second copy, and the mounting page applies the location that is current when its presenter initializes. Any other page change replaces the mounted page as before. A page render waits only for descendant components that are connected to the document, so the render of a page that was replaced while it was mounting finishes and releases its loading indicator. [Explorer](wiki.html#definition-explorer) must never queue, serialize, or delay a page change behind another page change. A `file-exp` page that is already detached from the document must stay inert: it must not load a route, write browser history, or bind document or window listeners in `afterRender`. Initial bootstrap must mount its route only into an empty page root and must accept a newer page that is mounted before or after its own mount, so it never joins a pending mount and never overrides a newer navigation or its address. Bootstrap must mount the route of the address that is current when the page root is set, so a hash change made while [Explorer](wiki.html#definition-explorer) is still loading is applied wherever [WebSkel](wiki.html#definition-webskel) would honour it, that is, for a page that is a configured component; an address that names no configured component keeps the startup route, and `agent-runtime-wait` keeps the startup capture.

The New menu must create files and folders only when the current location permits them. Supported context actions must include rename, copy, cut, paste, upload, open in a new tab, and delete where the selected resource and owning provider allow that action. An administrator also receives Open Terminal Here for directories; ordinary users must not receive that menu item. The launcher opens an Explorer-owned target chooser with only the canonical workspace-relative directory. After choosing a RoboWork robot, the chooser directly displays eligible running Ploinky agents, or an empty state, without an Environment selector. The chosen agent uses the clicked directory and original robot home. Ordinary processes in that agent can access the selected home. Temporary image-based environments are not offered here. Eligibility depends on an actual container mount covering the clicked folder, not merely global enablement; no fallback working directory is used. Explorer passes an opaque launch ID to the terminal and does not let the browser choose a container, shell, arguments, environment, user, or runtime flags. Closing the terminal tab detaches the viewer and keeps the shell running. Administrators manage existing shells through [Live Sessions](wiki.html#definition-live-sessions) in the toolbar: Attach embeds a view, Open in new tab opens a fresh isolated tab, closing an embedded view keeps the shell running without asking, and confirmed Kill ends the shell. Only the owner can type; another administrator can watch and Kill. Logout detaches viewers, and the same owner can reattach after signing in again. A shell expires after 24 hours without input, output, resize or attach, or after seven days in total. Delete must require confirmation. Successful mutations must invalidate affected caches, refresh the relevant directory, and clear selection or clipboard state that references a removed or moved path.

The New, Tools, and Account dropdowns close as soon as an enabled action is selected, including plugin actions that load on demand. Clicking empty space inside a menu leaves it open.

Find File must search workspace paths by name and support excluded glob patterns. Private `.data` trees must be excluded from default browser autocomplete discovery. Find/Replace in Files must support a base path, excluded patterns, case-sensitive matching, regular expressions, whole-word matching, selectable results, Replace Selected, and Replace All. Background search-job state must persist only under `.data/explorer/search-jobs`. Replace All must warn when results are truncated, large replacement sets must require confirmation, and the result must report changed files, missing matches, failures, or timeout state without claiming an unconfirmed success.

Ordinary file and directory context menus provide Download through the authenticated same-origin `/workspace-files/<encoded-workspace-relative-path>?download=1` Router surface. Files are attachments with their original bytes and UTF-8 filename; directories are streamed ZIP64 attachments with the selected directory as their root, including nested regular files and empty directories. The request addresses the literal selected workspace path, not the legacy agent-asset source remapping used by preview URLs. Plain preview URLs retain their existing inline and folder-index behavior. GET transfers data; HEAD validates the selected root and attachment headers without reading or compressing its contents. Other methods are rejected. No additional public route, port, archive dependency or temporary workspace file is introduced.

Download confinement validates both lexical paths and their canonical targets against the workspace. Direct requests and ancestor archives exclude `.data` trees, `.secrets` and names ending in `.secrets`, and `.ploinky` runtime metadata; `.ploinky/repos` source entries are the exception. Directly selected symlinks must resolve inside this same eligible boundary; recursive archives skip all symlinks and non-regular/non-directory entries. Files are opened with no-follow and identity revalidation, and traversal revalidates directory identity. ZIP payloads are compressed with backpressure, with at most 100,000 central records and 32 MiB of central-directory metadata retained. Archives are live reads, not snapshots. Errors after transfer starts interrupt the response without publishing a successful partial archive; client cancellation closes readers. Content-Disposition uses a sanitized ASCII fallback plus an encoded UTF-8 filename, and responses use no-store and nosniff headers.

Explorer performs one HEAD preflight before handing a same-origin attachment URL to the native browser download manager, never buffering file contents into a Blob. It closes the context menu but preserves navigation, selection, editor contents and clipboard state. Duplicate in-flight preparation for an entry is suppressed. Presenter disposal cancels preparation and prevents late browser actions. Failed access, missing entries and older Routers without attachment support produce a visible message. DPU virtual paths receive no ordinary download action and must never bypass their provider through this route. Downloads require both updated Explorer assets and a download-capable Ploinky core; changing Explorer alone does not activate server behavior.

`search_files` returns `{ results: string[], truncated: boolean }` by default. The optional boolean `includeKind: true` returns `{ results: [{ path, kind }], truncated }`, with workspace-relative slash-prefixed paths and `kind` equal to `file` or `folder`. The kind comes from the existing directory index or traversal entry, without another per-result metadata request. Valid symlinks retain their resolved file/directory classification and existing traversal behavior; broken links and other unsupported entry types are omitted only in typed mode. Both modes preserve exclusions, protected-path filtering, allowed-root validation, and result-limit/truncation behavior. Cached results and in-flight searches must include the response mode in their key so typed results cannot be reused for string callers or vice versa.

`directory_tree` returns a nested JSON tree of `{ name, type, children? }` entries for the requested path. `maxDepth` bounds directory depth and `maxNodes` bounds the total number of emitted entries: every entry, files and directories alike, counts once toward `maxNodes`, and the requested root itself is not an entry. Traversal stops once the limit is reached, so a directory holding many files cannot exceed the limit. Directory listings reuse each entry's `lstat` metadata for ordinary files and directories and call `stat` only to follow symbolic links, and `directory_tree` describes no more entries per directory than its remaining `maxNodes` budget; metadata is gathered per call, with output unchanged.

Every ordinary filesystem search and mutation must remain confined to configured allowed roots. DPU-backed actions must use effective resource capabilities for creation, rename, deletion, upload, child creation, and permissions. A disabled action must not be bypassed by sending the equivalent ordinary [Explorer](wiki.html#definition-explorer) filesystem tool.

[Explorer](wiki.html#definition-explorer)'s user-facing filesystem tools refuse controller state, agent private data and key material with the rules of the [Ploinky](wiki.html#definition-ploinky) Router's `/workspace-files` guard: any `.ploinky` segment except a leading `.ploinky/repos`, any `.data` segment, and any `master-key`, `.env`, or name ending in `.secrets`. Names are compared after NFKC normalization, lowercasing, and removal of trailing dots and spaces, so case, Unicode compatibility, and trailing-character variants match; `explorer/utils/server/protected-workspace-paths.mjs` holds the predicate, and a unit test compares it with the Ploinky module. Every path argument of every tool, including the source and destination of move and copy, folder arguments, document paths, and scoped search paths, is classified in its lexical form before any filesystem access and again at its canonical symlink-resolved target, where a top-level entry that the filesystem resolves to `.data` or `.ploinky` also counts as that directory. A refused path returns an explicit `Access denied: protected path` error whether or not it exists. A path through a dangling or looping symbolic link is refused as unresolved, so a write cannot create the link's target. Listings, `directory_tree`, `search_files`, `search_text`, and `replace_text` omit protected entries, and they omit symbolic links whose canonical target is protected, unresolved, outside the allowed roots, or the `.ploinky` root. Only the listing tools project the workspace-root `.ploinky`, named as such, as a folder that contains only `repos`, so managed sources stay browsable; every other operation on it is refused. Recursive delete, move, and copy are refused for a workspace root and for any tree that holds a protected entry, and an overwriting copy also checks the tree it would replace. Content reads (`read_file` and `read_text_file` including head and tail, `read_media_file`, `read_multiple_files`, the file reads and binary probe of `search_text` and `replace_text`, and WebMeet asset reads) open the classified canonical file with a descriptor-bound open: macOS refuses a symbolic link in any component, Linux requires the descriptor's own path to equal the classified path, and other platforms refuse the read. Writes, directory mutations, copies, edits, and [CRDT](wiki.html#definition-crdt) document reads stay path-based after classification, so a concurrent writer that swaps a classified directory for a symbolic link can still race them. [Explorer](wiki.html#definition-explorer)'s own `.data/explorer` state, including search jobs, plugin settings, avatar overrides, [CRDT](wiki.html#definition-crdt) state, and Router-staged WebMeet blobs under `.data/<agent>/blobs`, is reached only through the private-data boundary and is never user-browsable. Managed agent sources below a leading `.ploinky/repos`, including that directory itself, are readable but read-only for these tools, because [Ploinky](wiki.html#definition-ploinky) runs agents from them and keeps that tree writable inside global agents: a write there would run code inside the agents whose data these rules protect. Tools are classified as reading or writing by name, every tool that is not explicitly a reading tool runs in write mode, and the mode reaches every path check the handler makes; copying from a managed source is a read of the source. `replace_text` skips managed sources, and the shared content writer also refuses a managed or protected target, which covers [CRDT](wiki.html#definition-crdt) saves addressed by document id after a read-only open; opening a managed document that has no [CRDT](wiki.html#definition-crdt) state yet is refused with the same denial, because initializing it would rewrite the file. [CRDT](wiki.html#definition-crdt) deletion staging, restore, and crash recovery always check the document path for writing. Uploads use the [Ploinky](wiki.html#definition-ploinky) Router's `/upload` surface rather than an [Explorer](wiki.html#definition-explorer) tool, so this guard does not cover them.

The directory Manage skills action uses an 80% viewport modal styled with [Explorer](wiki.html#definition-explorer) tokens and the RoboTeam repository layout. It provides repository navigation, a selected-source detail panel, Add repo and Remove controls, and an addition popup containing recommended registered [Ploinky](wiki.html#definition-ploinky) skill repositories and valid workspace skill repositories. Recommendations already registered in the target folder have a disabled Added button. [Ploinky](wiki.html#definition-ploinky) recommendations must include Git repositories directly under the workspace with a nonempty skills/ directory and valid names and descriptions in existing SKILL.md descriptors. A skill subdirectory without SKILL.md must produce a visible recommendation warning without excluding the repository; that subdirectory is not a selectable skill. Local repositories need no remote URL. Hidden directories, dependency directories, symbolic repository entries and invalid skill trees must not be discovered. Sources prefer the workspace checkout, then the managed repository cache. Local checkout reads must not pull or change branches. Add registers the source in `ploinky-skills-manifest.json` and publishes selected skills as relative symlinks in the target folder's `.agents/skills`. Remove and disable retire only exports whose ownership and link identity are still proven. Unrecorded files, user replacements and edited legacy copies remain untouched with diagnostics. Legacy copies remain preserved until explicitly migrated. Editing through a skill symlink edits the repository source when that source is an ordinary workspace checkout; a managed checkout under `.ploinky/repos` stays read-only for [Explorer](wiki.html#definition-explorer)'s file tools. Relative targets must resolve both on the host and under the container workspace mount. Disable invalidates the changed skill paths, the skills listing and structure subtree. Closing a changed skills dialog clears cached browser directory listings and refreshes the tree. Tree refresh also clears childrenCache, invalidates pending child loads through directory generations, and reloads previously expanded branches while retaining their expansion state.

The manager uses a repository navigation at left and one selected-source panel at right, rather than expandable repository rows. The folder context must come from the projected structured state. A discreet + Add repo action beside Repositories opens a child native modal with URL/name entry, recommendations and local feedback without replacing the parent view. The sole Close button, Escape and the popup backdrop preserve the parent selection, scroll and typed draft and restore focus; Escape must not be intercepted by the parent WebSkel modal. Pending submissions cannot be repeated or dismissed; success closes the popup and selects the new source, while errors remain local. The selected source's More actions menu provides removal. Removing the selected source chooses another remaining source or shows an empty state. On narrow screens navigation moves above content; header and footer remain outside scrolling panes. Presenter unloading closes the child, removes its event listeners and prevents late rendering. Use existing Explorer/RoboTeam color tokens only, without copying RoboTeam's robot-only required-skills or catalog policy.

A repository may define root `skillsets.md`, using H1 names and H2 Description and Skills sections with a bullet list of member names. Validate definitions before export. When definitions exist, show each skillset's description, Enabled/Disabled checkbox and compact inline member names inside its card without duplicating grouped names in another list. Ungrouped names remain visible without individual controls. The server must reject individual toggles for those repositories. Add selects the union of declared members. Enable adds every member to the saved selection; Disable removes every member. Overlapping combinations derive their state from the resulting selected skills and may be partially enabled, represented by a mixed checkbox and explicit label. Repositories without declared skillsets retain individual Enabled/Disabled checkboxes. The existing skill mutation tool accepts either a skillset name or an individual skill name according to this rule. Its published [MCP](wiki.html#definition-mcp) schema and runtime schema must both declare skill and skillset as optional strings, with enabled required as a boolean; the handler validates which selector applies. The dialog renders the mutation response immediately, preserving the source selection and scroll and restoring confirmed state after errors. Popup HTML structure and scoped CSS rules mirror RoboTeam's compact grouping and button variants. Popup header rules must neutralize global header backgrounds, shadows and padding. Skillset toggles occupy the top-right corner of each card in both interfaces. All members of one toggle are saved and synchronized in one operation, with export conflicts reported to the user.

[Explorer](wiki.html#definition-explorer) must use the shared authenticated [Ploinky](wiki.html#definition-ploinky) repository client for listing, repository preparation, install and remove. Install uses skillRepos entries with an absolute project destination and explicit skill folder names. It is additive and must preserve conflicting files and links. Deselection must explicitly remove only matching previously selected symlinks. [Ploinky](wiki.html#definition-ploinky) validates workspace containment, creates missing `.agents/skills` and `.claude -> .agents`, and returns per-path outcomes. [Explorer](wiki.html#definition-explorer) retains manifest and selection ownership.

The four skills-manifest tools (`read_skills_manifest_state`, `add_skills_manifest_repo`, `set_skills_manifest_skill_enabled`, `remove_skills_manifest_repo`) project their responses by the privilege of the original verified invocation, decided before any asynchronous work from `metadata.invocation` through the shared `authInfoFromInvocation` (delegated `usr`/`user` claims take precedence over the actor). Only a non-guest administrator role receives physical repository paths, configured repository URLs and raw error text. Usernames, tool arguments, plain headers, agent callers and the machine identity used by the repository client grant nothing; a missing or malformed context is restricted. Restricted responses keep repository names, branches, cache and status flags, selected and available skills, skillsets and skill output states. They omit repository paths and physical sources, give manifest and folder references as contained workspace-relative paths (`/folder/ploinky-skills-manifest.json`) or omit them, reduce diagnostics to name, reason and status, replace cache errors with a fixed status message, and return thrown errors only when the message names validated repository, skill or skillset names. Repository URLs in restricted responses, including recommendation aliases and skill output provenance, are credential-free display values: userinfo, query and fragment are removed, and local paths, `file:` URLs and ambiguous forms become empty, matching the [Ploinky](wiki.html#definition-ploinky) Marketplace rule. Internal repository records, configured URLs, manifest bytes and repository-client arguments are unchanged. The Manage skills dialog reads state only through the structured tool, never falls back to reading the raw manifest file, keeps recommendations whose display URL is empty, and adds a recommendation by its repository name, which the server resolves. This covers these structured tool and dialog responses; authorized file tools can still read the manifest itself.

Workspace operations are complete only when users can manage and locate supported resources while [Explorer](wiki.html#definition-explorer) and each owning agent preserve their authorization and storage boundaries.

### Folder coding sessions

Directory context menus group Open Terminal Here, the available Open Copilot here plugin contribution, and Open Coding Sessions Here. Terminal and coding-session entries and actions require an administrator; Copilot keeps its existing visibility. Router authorization is authoritative, including direct requests. The coding-session popup uses WebSkel lifecycle and shared modal controls. Its mode tabs expose selected state and keyboard navigation with arrow keys, Home and End. Back precedes the tabs at the top and is disabled at the navigation root; Refresh sits beside the current step heading. Session rows use the shared theme tokens and retain individual action menus. The coding list reads RoboWork’s persistent folder index and live terminals in one request, without enumerating robot homes. The first visit imports existing histories in the background. Later updates inspect only catalogs with known sessions or recorded launches. Failed catalog updates preserve previously indexed rows and show a warning. Refresh reads the index. RoboWork automatically reconciles previously visited folders every fifteen minutes, including catalogs that were empty, to discover conversations created outside the launch flow. There is no manual index-maintenance action. The popup reads one snapshot on opening and never polls or displays background-update loading. Existing index reads never trigger scans based on age. Refresh explicitly reads the latest saved snapshot; first-time imports and scheduled maintenance continue independently in the service. Supervised lists read the existing pair registry without resolving native conversations until a role is opened. The wider popup uses a single New page with robot and coding-agent fields directly below the page heading for ordinary sessions, without an inner card or repeated title. Robots use a searchable combobox with keyboard selection and a bounded scrolling dropdown; coding agents use a native select without search. Supervised creation presents independent Supervisor and Worker sections side by side, stacking on narrow screens. The provider returns the common coding-agent catalog with the robots. Either field can be selected first; changing the robot preserves the coding agent and does not fetch another agent list. Start remains disabled until all required fields are selected. Only the bounded list scrolls, keeping the header, navigation and search visible. Both tabs initially show the folder session history. Coding sessions combines running and saved native conversations across robots and coding agents, labeling each row with its robot and coding agent. + New opens the configuration form; Start opens the configured conversation. Supervised sessions labels both roles with their robot and coding agent, lists the same folder pairs as the CLI, and uses + New to configure both roles on the same page. Creation starts both processes and opens separate Supervisor and Worker tabs using independent single-use attachment tokens. Both tabs are reserved during the Start click; if either popup is blocked, no pair is created and the unused reservation closes. Kill stops only the process. It synchronizes the selected robot and coding-agent history before and after stopping, so saved conversations remain listed and reopen using their original native ID. An unavailable catalog produces a warning and preserves previously indexed rows. Running coding-session rows display running in green regardless of whether a terminal viewer is attached. Each running terminal or role has a three-dot Kill action with confirmation; stopping one role does not stop its counterpart. One live pair per folder remains enforced.

The browser uses the administrator-only, mutation-proof-protected `/webtty/coding-sessions` endpoint. Requests contain only a workspace-relative directory and validated selection identifiers. The Router selects exactly one active manifest-declared provider, forwards allowed operations through verified routing and identity, and reuses CLI supervised launch, instruction, history and resume logic. Both clients share the existing workspace pair store. Pair listings exclude control channel identifiers. Terminal handoff uses the Live Sessions WebTTY attach-token contract, in a new tab isolated from its opener; tokens occur only in URL fragments. Closing the chooser or tab does not stop the terminal. Failures are visible in the chooser, and an unavailable or ambiguous native conversation never silently becomes a new role conversation.

Live Sessions accepts the WebTTY row field `lastOutputAt` as optional output activity metadata: either null before any output or a positive integer timestamp. Older rows without this field remain valid. Malformed timestamps and unknown fields still fail validation. Coding-session terminals use the same row contract as other WebTTY terminals.

The folder coding-session action stays disabled with a loading indicator until an administrator-only readiness probe confirms both WebTTY availability and a successful signed robots request to the configured provider. Explorer checks only while the folder action menu is open, every two seconds while waiting and every fifteen seconds when ready. Closing the menu, opening the coding-session popup, or disposing the page cancels the timer and aborts the pending request. Reopening the folder menu starts a fresh check; the popup does not own a readiness poll. Readiness never scans conversation histories or starts providers; startup failures return a normal not-ready response.

Session rows display the current robot name and coding agent as separate pills, with explicit robot and coding-agent labels for assistive technology. Rows with process actions show a vertical three-dot menu instead of a navigation chevron. Running rows retain the conversation title alongside the pills, preferring the indexed native title over the terminal label. Only live processes show the green “running” status; stopped sessions have no status label. Runtime provider names are omitted. Coding and supervised rows show relative age in minutes, hours or days, with the exact date on hover. Running rows use the latest terminal activity; saved conversations and pairs use their update time. Ages refresh with the list, without background timers.

The terminal chooser preselects the robot named default when present and uses one editable robot combobox. Clicking opens all robots, typing filters the dropdown immediately, and a mouse click or arrow keys plus Enter selects a robot. Escape or leaving the field closes the dropdown and restores the selected name. Changing between robots in live-agent mode preserves the container list and selection without discovery requests; Open obtains a fresh profile-bound launch for the chosen robot and revalidates the same container before handoff. The selected directory is emphasized in the header and is not repeated on container rows. Repetitive HOME disclosures and the Cancel, Retry and Refresh buttons are omitted; the close icon remains available.
