# DS010 Workspace Operations

## Introduction

Explorer provides one workspace surface for navigating, creating, changing, locating, and removing supported resources while preserving filesystem confinement and agent-owned authorization.

## Core Content

In tree mode, page reload and deep links retain the workspace root and expand every ancestor of the directory or selected file from the URL. The selected path must not replace the tree root with its parent; workspace siblings remain visible.

Explorer must browse configured workspace roots, restore supported file and directory routes, and select the registered preview or editor for the chosen resource. Ordinary paths must use Explorer's filesystem contract. Virtual paths under `/Confidential` must use DPU operations and must not be translated into ordinary filesystem mutations.

Page changes must stay independent of each other. A history navigation (an address-bar hash change, Back, or Forward) to the page that Explorer is still mounting, without page data, joins that pending mount instead of mounting a second copy, and the mounting page applies the location that is current when its presenter initializes. Any other page change replaces the mounted page as before. A page render waits only for descendant components that are connected to the document, so the render of a page that was replaced while it was mounting finishes and releases its loading indicator. Explorer must never queue, serialize, or delay a page change behind another page change. A `file-exp` page that is already detached from the document must stay inert: it must not load a route, write browser history, or bind document or window listeners in `afterRender`. Initial bootstrap must mount its route only into an empty page root and must accept a newer page that is mounted before or after its own mount, so it never joins a pending mount and never overrides a newer navigation or its address. Bootstrap must mount the route of the address that is current when the page root is set, so a hash change made while Explorer is still loading is applied wherever WebSkel would honour it, that is, for a page that is a configured component; an address that names no configured component keeps the startup route, and `agent-runtime-wait` keeps the startup capture.

The New menu must create files and folders only when the current location permits them. Supported context actions must include rename, copy, cut, paste, upload, open in a new tab, and delete where the selected resource and owning provider allow that action. An administrator also receives Open Terminal Here for directories; ordinary users must not receive that menu item. The launcher opens an Explorer-owned target chooser with only the canonical workspace-relative directory. The chooser requests safe, short-lived choices from the same-origin Ploinky core, lists Ploinky Box first, and shows only live agents Ploinky has proven can access that folder. It displays the effective working directory and selected-folder read-only or read/write access returned by Ploinky. A target click directly opens `/webtty/#launch=<opaque-id>` in a new tab without an opener or referrer; a blocked popup keeps the chooser open. Explorer does not infer mounts, translate working directories, retain raw runtime identity, or let the browser choose a container, shell, arguments, environment, user, or runtime flags. Presentation does not replace Router authorization, and Explorer must never expose a physical host working directory. Delete must require confirmation. Successful mutations must invalidate affected caches, refresh the relevant directory, and clear selection or clipboard state that references a removed or moved path.

Find File must search workspace paths by name and support excluded glob patterns. Private `.data` trees must be excluded from default browser autocomplete discovery. Find/Replace in Files must support a base path, excluded patterns, case-sensitive matching, regular expressions, whole-word matching, selectable results, Replace Selected, and Replace All. Background search-job state must persist only under `.data/explorer/search-jobs`. Replace All must warn when results are truncated, large replacement sets must require confirmation, and the result must report changed files, missing matches, failures, or timeout state without claiming an unconfirmed success.

`search_files` returns `{ results: string[], truncated: boolean }` by default. The optional boolean `includeKind: true` returns `{ results: [{ path, kind }], truncated }`, with workspace-relative slash-prefixed paths and `kind` equal to `file` or `folder`. The kind comes from the existing directory index or traversal entry, without another per-result metadata request. Valid symlinks retain their resolved file/directory classification and existing traversal behavior; broken links and other unsupported entry types are omitted only in typed mode. Both modes preserve exclusions, protected secret-name filtering, allowed-root validation, and result-limit/truncation behavior. Cached results and in-flight searches must include the response mode in their key so typed results cannot be reused for string callers or vice versa.

Every ordinary filesystem search and mutation must remain confined to configured allowed roots. DPU-backed actions must use effective resource capabilities for creation, rename, deletion, upload, child creation, and permissions. A disabled action must not be bypassed by sending the equivalent ordinary Explorer filesystem tool.

The directory Manage skills action uses an 80% viewport modal styled with Explorer tokens and the RoboTeam repository layout. It lists expandable repositories, recommended registered Ploinky skill repositories and valid workspace skill repositories, Add repo and Remove controls. Recommendations already registered in the target folder have a disabled Added button. Ploinky recommendations must include Git repositories directly under the workspace with a nonempty skills/ directory and valid names and descriptions in existing SKILL.md descriptors. A skill subdirectory without SKILL.md must produce a visible recommendation warning without excluding the repository; that subdirectory is not a selectable skill. Local repositories need no remote URL. Hidden directories, dependency directories, symbolic repository entries and invalid skill trees must not be discovered. Sources prefer the workspace checkout, then the managed repository cache. Local checkout reads must not pull or change branches. Add registers the source in `ploinky-skills-manifest.json` and publishes selected skills as relative symlinks in the target folder's `.agents/skills`. Remove and disable retire only exports whose ownership and link identity are still proven. Unrecorded files, user replacements and edited legacy copies remain untouched with diagnostics. Legacy copies remain preserved until explicitly migrated. Editing through a skill symlink edits the repository source. Relative targets must resolve both on the host and under the container workspace mount. Disable invalidates the changed skill paths, the skills listing and structure subtree. Closing a changed skills dialog clears cached browser directory listings and refreshes the tree. Tree refresh also clears childrenCache, invalidates pending child loads through directory generations, and reloads previously expanded branches while retaining their expansion state.

A repository may define root `skillsets.md`, using H1 names and H2 Description and Skills sections with a bullet list of member names. Validate definitions before export. When definitions exist, show individual skill names without individual controls, and show each skillset's description, members and Enable/Disable button. The server must reject individual toggles for those repositories. Add selects the union of declared members. Enable adds every member to the saved selection; Disable removes every member. Overlapping combinations derive their state from the resulting selected skills and may be partially enabled. Repositories without declared skillsets retain individual Enable/Disable controls. The existing skill mutation tool accepts either a skillset name or an individual skill name according to this rule. Its published MCP schema and runtime schema must both declare skill and skillset as optional strings, with enabled required as a boolean; the handler validates which selector applies. The dialog renders the mutation response immediately. Popup HTML structure and scoped CSS rules mirror RoboTeam, including skill-member chips and button variants. Popup header rules must neutralize global header backgrounds, shadows and padding. Skillset toggles occupy the top-right corner of each card in both interfaces. All members of one toggle are saved and synchronized in one operation, with export conflicts reported to the user.

Explorer must use the shared authenticated Ploinky repository client for listing, repository preparation, install and remove. Install uses skillRepos entries with an absolute project destination and explicit skill folder names. It is additive and must preserve conflicting files and links. Deselection must explicitly remove only matching previously selected symlinks. Ploinky validates workspace containment, creates missing `.agents/skills` and `.claude -> .agents`, and returns per-path outcomes. Explorer retains manifest and selection ownership.

## Conclusion

Workspace operations are complete only when users can manage and locate supported resources while Explorer and each owning agent preserve their authorization and storage boundaries.
