# DS010 Workspace Operations

## Introduction

[Explorer](wiki.html#definition-explorer) provides one workspace surface for navigating, creating, changing, locating, and removing supported resources while preserving filesystem confinement and agent-owned authorization.

## Core Content

In tree mode, page reload and deep links retain the workspace root and expand every ancestor of the directory or selected file from the URL. The selected path must not replace the tree root with its parent; workspace siblings remain visible. A tree-mode deep link requests the listing of the target's parent together with the workspace root listing, and the listings of all ancestors that are not loaded yet are requested together before they are revealed in order; a tree with a specs filter keeps the one-by-one reveal. Opening a text file requests its version information before its content, without waiting in between, so a change that lands meanwhile is more likely to be detected by the later external-change check than missed, and the deep-link path refreshes the view once, through the open itself. The editor's external-change check does not run while the browser tab is hidden.

[Explorer](wiki.html#definition-explorer) must browse configured workspace roots, restore supported file and directory routes, and select the registered preview or editor for the chosen resource. Ordinary paths must use [Explorer](wiki.html#definition-explorer)'s filesystem contract. Virtual paths under `/Confidential` must use [DPU](wiki.html#definition-dpu) operations and must not be translated into ordinary filesystem mutations.

Page changes must stay independent of each other. A history navigation (an address-bar hash change, Back, or Forward) to the page that [Explorer](wiki.html#definition-explorer) is still mounting, without page data, joins that pending mount instead of mounting a second copy, and the mounting page applies the location that is current when its presenter initializes. Any other page change replaces the mounted page as before. A page render waits only for descendant components that are connected to the document, so the render of a page that was replaced while it was mounting finishes and releases its loading indicator. [Explorer](wiki.html#definition-explorer) must never queue, serialize, or delay a page change behind another page change. A `file-exp` page that is already detached from the document must stay inert: it must not load a route, write browser history, or bind document or window listeners in `afterRender`. Initial bootstrap must mount its route only into an empty page root and must accept a newer page that is mounted before or after its own mount, so it never joins a pending mount and never overrides a newer navigation or its address. Bootstrap must mount the route of the address that is current when the page root is set, so a hash change made while [Explorer](wiki.html#definition-explorer) is still loading is applied wherever [WebSkel](wiki.html#definition-webskel) would honour it, that is, for a page that is a configured component; an address that names no configured component keeps the startup route, and `agent-runtime-wait` keeps the startup capture.

The New menu must create files and folders only when the current location permits them. Supported context actions must include rename, copy, cut, paste, upload, open in a new tab, and delete where the selected resource and owning provider allow that action. An administrator also receives Open Terminal Here for directories; ordinary users must not receive that menu item. The launcher opens an Explorer-owned target chooser with only the canonical workspace-relative directory. The chooser requests safe, short-lived choices from the same-origin [Ploinky](wiki.html#definition-ploinky) core, lists [Ploinky](wiki.html#definition-ploinky) Box first, and shows only live agents [Ploinky](wiki.html#definition-ploinky) has proven can access that folder. It displays the effective working directory and selected-folder read-only or read/write access returned by [Ploinky](wiki.html#definition-ploinky). A target click directly opens `/webtty/#launch=<opaque-id>` in a new tab without an opener or referrer; a blocked popup keeps the chooser open. [Explorer](wiki.html#definition-explorer) does not infer mounts, translate working directories, retain raw runtime identity, or let the browser choose a container, shell, arguments, environment, user, or runtime flags. Presentation does not replace Router authorization, and [Explorer](wiki.html#definition-explorer) must never expose a physical host working directory. Closing the terminal tab detaches the viewer and keeps the shell running. Administrators manage existing shells through [Live Sessions](wiki.html#definition-live-sessions) in the toolbar: Attach embeds a view, Pop out opens a fresh isolated tab, and confirmed Kill ends the shell. Only the owner can type; another administrator can watch and Kill. Logout detaches viewers, and the same owner can reattach after signing in again. A shell expires after 24 hours without input, output, resize or attach, or after seven days in total. Delete must require confirmation. Successful mutations must invalidate affected caches, refresh the relevant directory, and clear selection or clipboard state that references a removed or moved path.

Find File must search workspace paths by name and support excluded glob patterns. Private `.data` trees must be excluded from default browser autocomplete discovery. Find/Replace in Files must support a base path, excluded patterns, case-sensitive matching, regular expressions, whole-word matching, selectable results, Replace Selected, and Replace All. Background search-job state must persist only under `.data/explorer/search-jobs`. Replace All must warn when results are truncated, large replacement sets must require confirmation, and the result must report changed files, missing matches, failures, or timeout state without claiming an unconfirmed success.

Ordinary file and directory context menus provide Download through the authenticated same-origin `/workspace-files/<encoded-workspace-relative-path>?download=1` Router surface. Files are attachments with their original bytes and UTF-8 filename; directories are streamed ZIP64 attachments with the selected directory as their root, including nested regular files and empty directories. The request addresses the literal selected workspace path, not the legacy agent-asset source remapping used by preview URLs. Plain preview URLs retain their existing inline and folder-index behavior. GET transfers data; HEAD validates the selected root and attachment headers without reading or compressing its contents. Other methods are rejected. No additional public route, port, archive dependency or temporary workspace file is introduced.

Download confinement validates both lexical paths and their canonical targets against the workspace. Direct requests and ancestor archives exclude `.data` trees, `.secrets` and names ending in `.secrets`, and `.ploinky` runtime metadata; `.ploinky/repos` source entries are the exception. Directly selected symlinks must resolve inside this same eligible boundary; recursive archives skip all symlinks and non-regular/non-directory entries. Files are opened with no-follow and identity revalidation, and traversal revalidates directory identity. ZIP payloads are compressed with backpressure, with at most 100,000 central records and 32 MiB of central-directory metadata retained. Archives are live reads, not snapshots. Errors after transfer starts interrupt the response without publishing a successful partial archive; client cancellation closes readers. Content-Disposition uses a sanitized ASCII fallback plus an encoded UTF-8 filename, and responses use no-store and nosniff headers.

Explorer performs one HEAD preflight before handing a same-origin attachment URL to the native browser download manager, never buffering file contents into a Blob. It closes the context menu but preserves navigation, selection, editor contents and clipboard state. Duplicate in-flight preparation for an entry is suppressed. Presenter disposal cancels preparation and prevents late browser actions. Failed access, missing entries and older Routers without attachment support produce a visible message. DPU virtual paths receive no ordinary download action and must never bypass their provider through this route. Downloads require both updated Explorer assets and a download-capable Ploinky core; changing Explorer alone does not activate server behavior.

`search_files` returns `{ results: string[], truncated: boolean }` by default. The optional boolean `includeKind: true` returns `{ results: [{ path, kind }], truncated }`, with workspace-relative slash-prefixed paths and `kind` equal to `file` or `folder`. The kind comes from the existing directory index or traversal entry, without another per-result metadata request. Valid symlinks retain their resolved file/directory classification and existing traversal behavior; broken links and other unsupported entry types are omitted only in typed mode. Both modes preserve exclusions, protected secret-name filtering, allowed-root validation, and result-limit/truncation behavior. Cached results and in-flight searches must include the response mode in their key so typed results cannot be reused for string callers or vice versa.

`directory_tree` returns a nested JSON tree of `{ name, type, children? }` entries for the requested path. `maxDepth` bounds directory depth and `maxNodes` bounds the total number of emitted entries: every entry, files and directories alike, counts once toward `maxNodes`, and the requested root itself is not an entry. Traversal stops once the limit is reached, so a directory holding many files cannot exceed the limit. Directory listings reuse each entry's `lstat` metadata for ordinary files and directories and call `stat` only to follow symbolic links, and `directory_tree` describes no more entries per directory than its remaining `maxNodes` budget; metadata is gathered per call, with output unchanged.

Every ordinary filesystem search and mutation must remain confined to configured allowed roots. DPU-backed actions must use effective resource capabilities for creation, rename, deletion, upload, child creation, and permissions. A disabled action must not be bypassed by sending the equivalent ordinary [Explorer](wiki.html#definition-explorer) filesystem tool.

The directory Manage skills action uses an 80% viewport modal styled with [Explorer](wiki.html#definition-explorer) tokens and the RoboTeam repository layout. It lists expandable repositories, recommended registered [Ploinky](wiki.html#definition-ploinky) skill repositories and valid workspace skill repositories, Add repo and Remove controls. Recommendations already registered in the target folder have a disabled Added button. [Ploinky](wiki.html#definition-ploinky) recommendations must include Git repositories directly under the workspace with a nonempty skills/ directory and valid names and descriptions in existing SKILL.md descriptors. A skill subdirectory without SKILL.md must produce a visible recommendation warning without excluding the repository; that subdirectory is not a selectable skill. Local repositories need no remote URL. Hidden directories, dependency directories, symbolic repository entries and invalid skill trees must not be discovered. Sources prefer the workspace checkout, then the managed repository cache. Local checkout reads must not pull or change branches. Add registers the source in `ploinky-skills-manifest.json` and publishes selected skills as relative symlinks in the target folder's `.agents/skills`. Remove and disable retire only exports whose ownership and link identity are still proven. Unrecorded files, user replacements and edited legacy copies remain untouched with diagnostics. Legacy copies remain preserved until explicitly migrated. Editing through a skill symlink edits the repository source. Relative targets must resolve both on the host and under the container workspace mount. Disable invalidates the changed skill paths, the skills listing and structure subtree. Closing a changed skills dialog clears cached browser directory listings and refreshes the tree. Tree refresh also clears childrenCache, invalidates pending child loads through directory generations, and reloads previously expanded branches while retaining their expansion state.

A repository may define root `skillsets.md`, using H1 names and H2 Description and Skills sections with a bullet list of member names. Validate definitions before export. When definitions exist, show individual skill names without individual controls, and show each skillset's description, members and Enable/Disable button. The server must reject individual toggles for those repositories. Add selects the union of declared members. Enable adds every member to the saved selection; Disable removes every member. Overlapping combinations derive their state from the resulting selected skills and may be partially enabled. Repositories without declared skillsets retain individual Enable/Disable controls. The existing skill mutation tool accepts either a skillset name or an individual skill name according to this rule. Its published [MCP](wiki.html#definition-mcp) schema and runtime schema must both declare skill and skillset as optional strings, with enabled required as a boolean; the handler validates which selector applies. The dialog renders the mutation response immediately. Popup HTML structure and scoped CSS rules mirror RoboTeam, including skill-member chips and button variants. Popup header rules must neutralize global header backgrounds, shadows and padding. Skillset toggles occupy the top-right corner of each card in both interfaces. All members of one toggle are saved and synchronized in one operation, with export conflicts reported to the user.

[Explorer](wiki.html#definition-explorer) must use the shared authenticated [Ploinky](wiki.html#definition-ploinky) repository client for listing, repository preparation, install and remove. Install uses skillRepos entries with an absolute project destination and explicit skill folder names. It is additive and must preserve conflicting files and links. Deselection must explicitly remove only matching previously selected symlinks. [Ploinky](wiki.html#definition-ploinky) validates workspace containment, creates missing `.agents/skills` and `.claude -> .agents`, and returns per-path outcomes. [Explorer](wiki.html#definition-explorer) retains manifest and selection ownership.

The four skills-manifest tools (`read_skills_manifest_state`, `add_skills_manifest_repo`, `set_skills_manifest_skill_enabled`, `remove_skills_manifest_repo`) project their responses by the privilege of the original verified invocation, decided before any asynchronous work from `metadata.invocation` through the shared `authInfoFromInvocation` (delegated `usr`/`user` claims take precedence over the actor). Only a non-guest administrator role receives physical repository paths, configured repository URLs and raw error text. Usernames, tool arguments, plain headers, agent callers and the machine identity used by the repository client grant nothing; a missing or malformed context is restricted. Restricted responses keep repository names, branches, cache and status flags, selected and available skills, skillsets and skill output states. They omit repository paths and physical sources, give manifest and folder references as contained workspace-relative paths (`/folder/ploinky-skills-manifest.json`) or omit them, reduce diagnostics to name, reason and status, replace cache errors with a fixed status message, and return thrown errors only when the message names validated repository, skill or skillset names. Repository URLs in restricted responses, including recommendation aliases and skill output provenance, are credential-free display values: userinfo, query and fragment are removed, and local paths, `file:` URLs and ambiguous forms become empty, matching the [Ploinky](wiki.html#definition-ploinky) Marketplace rule. Internal repository records, configured URLs, manifest bytes and repository-client arguments are unchanged. The Manage skills dialog reads state only through the structured tool, never falls back to reading the raw manifest file, keeps recommendations whose display URL is empty, and adds a recommendation by its repository name, which the server resolves. This covers these structured tool and dialog responses; authorized file tools can still read the manifest itself.

Workspace operations are complete only when users can manage and locate supported resources while [Explorer](wiki.html#definition-explorer) and each owning agent preserve their authorization and storage boundaries.
