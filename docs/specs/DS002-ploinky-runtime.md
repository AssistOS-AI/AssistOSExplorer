# DS002 Ploinky Runtime

## Introduction

Explorer runs as the static Ploinky agent and depends on Ploinky for startup orchestration, router access control, and workspace configuration.

## Core Content

Explorer declares a same-origin `routerAccess.capabilityDeniedRedirect` to UserPersisto's authenticated account dashboard. Only denied HTML document GET navigation follows it; API, MCP, SSE, WebSocket, and mutation denials remain errors. The account service's explicitly owned and matching authenticated route retains the inherited identity provider but applies its own capability policy, allowing active restricted accounts to manage their profile without granting Explorer access. Undeclared and guest/public routes retain owner capability checks. The dashboard verifies the Router's signed HTTP invocation against the actual method, internal path, query, and raw body before resolving its current persisted actor. See [DS012](DS012-user-persisto.md) for the account API and enrollment contract.

UserPersisto constructs browser login URLs on the validated callback origin while keeping runtime bridge requests on the private Router address. This preserves the exact public host and port and the initiating browser's host-bound callback proof.

Optional Google sign-in uses a separate UserPersisto transaction and cookie, while preserving Ploinky's provider-neutral SSO handoff and original core state. `/service/auth/*` remains guest transport admission, including the explicit Google callback. Do not add an overlapping `publicProtocol` exception: restrictive policy combination keeps it guest. Guest admission grants no local user authority. Google callback cookies are distinct from Router proofs; the Router removes its own cookies and overwrites forwarding headers before proxying. Public callback/issuer configuration, not raw Host or caller forwarding headers, determines URLs. Local completion uses fixed relative Location headers with the Router-visible additional-server prefix so guest sanitization retains them; the verified Google HTTPS authorization destination may remain absolute. OIDC completion returns to the original interaction path without widening its existing cookies. DS012 and DS013 define account ownership, proof validation and exact downstream completion.

#### Configuration can change the Box lifecycle

The public `ploinky var` wrapper may prepare and reconcile the selected Box before writing a variable. A successful setter does not establish initialized application readiness, and a failed setter can follow a completed recreation. Before the first generic command, identify the selected physical workspace and exact mounted public CLI checkout, owned immutable Box/container/image IDs, exact image-reference label, Router/media ports, mounts and AgentLib source mode/path/commit/content fingerprint/physical-source identity. Stop on missing or ambiguous ownership. An equal Git revision in another checkout is not equal mounted source identity. Preserve the exact `PLOINKY_BOX_IMAGE` reference and verify its immutable image ID; switching an equivalent tag to a digest is still a planned lifecycle change. Explicit `PLOINKY_WORKSPACE_ROOT` must exist and match the physical selected directory, since an absent path can fall back to workspace discovery.

Before authorized lifecycle work, protect the paired encrypted secret file/master key, workspace `.data`, persistent Box binds and selected source/routing state through the secure backup procedure. Do not print backups or secret values. Public `help`, `status --verbose` and `--dry-run` avoid owned-Box reconciliation but status/dry-run still use temporary image capability probes. Dry-run does not forecast prospective AgentLib replacement; verbose status omits immutable image identity and truncates fingerprints. Generic `list`, `network status`, `vars` and `echo` prepare the Box, and the last two also disclose values; none is a safe readiness substitute.

After every Google setter, reinspect exact owned container/image/source identities before continuing. Reuse the same explicit workspace, mounted CLI and exact host image selector for each command. With the same initialized Box, `restart userPersistoAgent` is the supported targeted configuration activation path and validates/reuses existing sources without reconciliation. A recreated or uninitialized Box requires planned managed graph recovery with `start explorer`. Retained workspace metadata and an initialized status flag alone do not establish an active graph. The selected Ploinky runtime must check the exact owned Box's public Router health before entering a targeted restart and refuse an inactive graph without changing routing; it must also retire each successfully published targeted runtime's completed candidate receipt so a subsequent restart can preserve the same logical identity. Unexpected generation, decryption failure or readiness failure stops the sequence for selected-environment recovery without replacing keys, emptying stores or deleting unrelated resources. Verify retained users/roles/keys, graph initialization, redacted Google readiness and an existing administrator sign-in in the browser after activation. Keep Google disabled until ready. The operator procedure and exact independent callback registrations are documented in [workspace operations](../workspace-operations.html#google-sign-in).

The shared Node agents in the Explorer graph must select the same immutable Ploinky Node image through their manifests. The image supplies Node 24 on Debian Trixie and a maintained Git/libcurl stack that negotiates GitHub HTTP/2 without a forced HTTP version. Image publication must prove native amd64 and arm64 Git clone, fetch, and npm Git dependency installation before the manifest digest changes.

The `explorer/manifest.json` enable list must declare the agents that Explorer requires for its integrated workspace experience. `ploinky start explorer` is the supported local startup command. The Explorer route is served by the Ploinky router and browser access must use the router session rather than direct agent ports.

The LiveKit media runtime is owned by this repository as `AchillesIDE/liveKitServerAgent`. Explorer and WebMeet must enable that exact identity with `no-wait`; an explicitly enabled Scribe must wait for the same runtime. LiveKit retains its pinned image, managed readiness probe, shared generated API credentials, and `.data/liveKitServerAgent/` volumes. Router signaling and private Twirp keep their existing unqualified convention paths; the Box retains its fixed outer Router TCP boundary and single UDP `7882` media publication. This ownership change does not add a runtime or another media listener. Explorer stack manifests and deployment workflows must not install or register a separate media-runtime repository or depend on `basic`. The runtime contract is documented in `liveKitServerAgent/docs/specs/`.

The Skills Explorer deployment must retire existing media-repository registrations before application source update. Its bounded migration must capture every exact retiring runtime key durably before Ploinky lifecycle mutations, disable only currently verified retiring registry records, and disable and uninstall the repository through Ploinky. Pending-only keys must never become alias-resolved disable requests. Before source retirement, the migration must prove captured runtimes absent in the supervisor-validated owning Box's nested engine using an explicit command and exact acknowledgement, then revalidate that Box identity. Host-engine absence, a stopped registry entry, or an unexecuted shell cannot establish this proof. Failure must preserve the migration record and prevent update and startup until supported lifecycle recovery succeeds. Successful completion must remove old runtime records, repository enablement, and the checkout while retaining agent data. Retired source names may appear only inside the workflow's explicit migration block.

`onlyOffice`, `webmeetScribeAgent`, and `webmeetStt` must be disabled by default and omitted from the default Explorer dependency graph, including transitive enable lists. An administrator may enable each independently through Marketplace using the existing router-authorized agent lifecycle controls. OnlyOffice plugin admission must remain available when its agent is enabled. Existing workspace enablement choices are not reset by these defaults. Meeting Secretary uses browser SpeechRecognition and does not require `webmeetStt`.

Explorer must declare `AchillesCLI/roboTeamAgent global no-wait`. RoboTeam owns Copilot through the ordinary `default` robot, launched with `agent=roboTeamAgent&robot=default`; the retired `AchillesCLI/achilles-cli` agent must not be required. RoboTeam requires the workspace's `AdvancedLanguageAgent` checkout and its selected `achillesAgentLib` dependency. Copilot settings query the same robot's public skill catalog.

The tracked QA workflow must provision `AdvancedLanguageAgent` at the workspace root from its remote default branch, record the exact commit before cloning, and reject a checkout that moves or becomes dirty. Before starting Explorer, it must bind ALA's package dependency to the one Ploinky-selected AgentLib at `/opt/ploinky-agentlib`, reject a private copy or shadowing checkout, exercise ALA's real loader, and verify the `--home`, `--cwd`, and `--MCPServers` CLI contract. It must not install a second AgentLib through ALA's mutable package dependency. ALA is a workspace prerequisite, not an additional runtime; readiness remains fourteen agents and ten no-wait completions.

Explorer must obtain its filesystem roots from the configured runtime environment and enforce those roots for filesystem MCP operations. The browser may bootstrap a display context from `list_allowed_directories`, but it must not treat that result as authorization for paths outside the server-enforced roots.

Every active top-level agent manifest must declare workspace-backed writable data volumes below `.data/`. The sole source-state exception is `.ploinky/repos` mounted at `/workspace/.ploinky/repos`. Managed `persistentStorage` declarations must use a safe one-segment key and an absolute container path. Repository validation must positively classify every writable volume and persistent-storage declaration; merely rejecting one retired prefix is insufficient. Explorer private writers must resolve their paths through the shared `.data/explorer` boundary, reject symbolic-link components or files, and canonically revalidate that boundary before reading or writing avatar overrides, plugin settings, search jobs, or CRDT state.

Ploinky router authentication and secure invocation data are authoritative for protected browser and agent calls. Every Explorer deployment uses SSO mode and the UserPersisto provider declared in its manifest; Ploinky binds that provider without hard-coding its identity in router code. Canonical workspace startup resolves one provider from the admitted graph under the workspace lock, rejects missing or conflicting providers before runtime mutations, and persists the binding after generation inactivation and before Router launch. Router and provider resolve the same declared shared generated secrets through the persisted profile; private provider keys are not exported.

Explorer registration and credential verification go through UserPersisto, whose ordinary accounts are passwordless (DS012). Ploinky no longer offers local browser password authentication, credential seeding, or local-role capability mappings; `pwd` declarations and `routerAccess.localAuthRoles` are rejected. The manifest's SSO requirement is authoritative, and missing or unavailable UserPersisto authentication fails closed. Preserving existing workspace authentication modes and migrating local accounts are outside this release's scope.

Ploinky's retired `/auth/account` and local login-branding settings routes are unavailable. Old local browser credentials cannot authorize Marketplace, policy, or other protected controls. The verified local CLI operator channel remains available for runtime control and does not establish a browser password login or Explorer user session.

Login initiation binds each callback transaction to an HttpOnly browser proof cookie; validation requires that proof before consuming state or establishing a session. The router must remotely revalidate SSO sessions and require the manifest-declared `explorer.access` capability before forwarding protected Explorer traffic. An agent must derive the acting principal from verified invocation context and must not trust a client-declared actor identity.

UserPersisto also exposes OAuth/OIDC under its declared additional-server public protocol route, as specified in [DS013](DS013-oauth-oidc.md). A manifest's generic `publicProtocol` opt-in admits only the declared paths and methods, with explicit CORS and loopback-redirect behavior required by external OAuth clients; it does not disable protection on adjacent service or Explorer routes. Public protocol requests use the provider's standard authorization, PKCE, token, and browser-interaction protections rather than requiring a pre-existing Ploinky session. The public issuer is explicit configuration and must include the Router-visible additional-server prefix; host or forwarded headers must not select the issuer. Discovery, endpoints, cookie paths, and redirects remain consistent with that issuer behind the Router. OAuth access and ID tokens are not substitutes for Ploinky's verified invocation context or protected-route session.

Release evidence for a managed Ploinky Box must accept exactly the runtime's semantic label schema. That schema binds the selected achillesAgentLib mode, source-identity hash, content fingerprint, workspace-relative source path, and optional Git commit alongside the Box identity, immutable image, cache fingerprints, and two-publication network boundary. A release-manifest gate must reject a running Box whose AgentLib commit does not equal the verified manifest commit, and its post-browser check must prove that the full semantic-label set and outer generation did not change. The ordinary Copilot release gate requires the manifest's exact immutable image digest and reference plus a fresh outer generation; it must not reinterpret the fixed OCI creation time of that pinned release image as deployment age. Gates whose purpose includes fresh-image validation retain their bounded image-age requirement.

The tracked Explorer QA deployment must derive the canonical achillesAgentLib URL and immutable commit from the selected Ploinky runtime's dependency lock. It must reject a noncanonical source, a malformed commit, or a locked commit that differs from the selected remote default-branch head; leave AgentLib selection on that immutable lock rather than applying one mutable global branch to both AgentLib and application repositories; retain explicit per-repository graph branches; and never set a retired AgentLib selection environment variable. Process admission is necessary but does not establish readiness: the deployment must bind all ten expected no-wait markers to the current deployment start, reject mixed, stale, malformed, or terminal-failed evidence, and require every corresponding run-scoped status to reach terminal `running` before its stable-ready streak can advance. After all fourteen expected runtimes are admitted and semantically ready, deployment evidence must prove every managed repository's exact revision and require the outer Box AgentLib labels to identify the locked managed commit with valid content-fingerprint and physical-source-identity hashes.

WebTTY is a Ploinky core Router surface rather than an Explorer agent dependency or agent-port service. A selected Explorer host must include the `webtty` surface explicitly. Explorer may present its terminal launcher only to an administrator. Selecting **Open Terminal Here** opens an Explorer-owned target chooser and sends only the canonical workspace-relative directory to Ploinky's mutation-protected discovery endpoint. Ploinky is the authority for target eligibility, immutable runtime identity, live-mount access, translated working directory, and launch authorization. Explorer renders the safe rows returned by Ploinky with Ploinky Box first, then opens the same-origin `/webtty/#launch=<opaque-id>` route from the selected row's direct click. It must not put the opaque launch ID in a query parameter or browser storage, and it must never send a container selector, shell, runtime flags, translated or physical path, or environment value. Router authorization remains authoritative even when the launcher is omitted.

The WebTTY recovery gate must observe Explorer requests from initial navigation and wait for deferred plugin rendering and finite response bodies before navigating Explorer away for Router fault injection. Only successful responses with the exact `text/event-stream` media type may be excluded from the bounded wait. Failed requests must remain failures in the unchanged diagnostic ledger, with strict checks before and after navigation.

Marketplace reads use the authenticated router session. Before an administrator installs or uninstalls a repository or enables or disables an agent, Explorer must obtain a fresh session-bound proof from the router, verify that its origin exactly matches the current browser origin, and send it with the Marketplace mutation. Local control requests use the administrative control proof; configured public application hosts use the browser mutation proof bound to the selected host and active routing generation. Ploinky must validate a local administrator session against the selected application's user store before admitting a public Marketplace mutation. Public-host selection alone is never administrator authorization. Explorer must not persist this proof in component state or weaken the router check when the proof is absent or invalid. Only one agent mutation may be pending at a time; runtime-mode selection remains a stable native control, and mutation failures stay visible until explicitly dismissed. Marketplace normalizes runtime evidence to Disabled, Starting up, Running, Stopped, Failed, Paused, or Unknown; it refreshes agent state while Marketplace is mounted and exposes Configure only for a verified Running runtime.

Marketplace initial rendering and refreshes must use the authenticated, same-origin `/api/marketplace` JSON catalog on both local and public origins; the browser must not request the private `/status/data` control surface. Refreshes run serially every three seconds after the preceding request settles, continue after agents reach Running, abort when the component unloads, and stop on permanent authorization or HTTP failures. A confirmed 401 or 403 response invalidates cached management permission and removes management controls. A mutation invalidates an older in-flight read so its late response cannot overwrite the mutation result. Unchanged inventory must update normalized labels, accessible status, current lifecycle detail, enabled-agent registry/counts, and the operational Configure gate in place while retaining native row controls, selected runtime modes, focus, expansion, and pending mutation text. Leaving Running disables Configure on the next accepted catalog refresh. Details from an earlier lifecycle must not remain attached to a new state. Structural inventory or permission changes may rebuild the affected content.

Both Marketplace tabs must exclude skill entries, repositories classified as `skills` or `mixed`, and the repositories `basic`, `cloud`, `container-image-builds`, `copilot-agents`, `demo`, `extra`, `security`, and `vibe`. The known skill sources `AchillesCopilotBasicSkills`, `DocumentationSkills`, and `PloinkySkills` remain excluded when installed under another local name. Match repository names and decoded Git source basenames case-insensitively, including `.git` suffixes and SSH URLs, and propagate exclusion to aliases and every associated agent. Apply this presentation policy before repository grouping, search, type filtering, enabled-agent counts, and lifecycle refreshes. Normalized identities apply only to visibility exclusion. Grouping, enabled-agent counts, and lifecycle references must preserve exact local repository and agent names, including distinct repositories such as `tools`, `tools.git`, and `Tools`. Repos exposes only Agent Repos and Others. Visible agents retain the existing lifecycle controls and router-authorized mutations. Hiding an entry must not uninstall a repository, disable an agent, modify the router catalog, or disable the skills subsystem.

Repository documentation preview must remain reachable through the repository-scoped route `/.ploinky/repos/AchillesIDE/docs/development.html` when the workspace exposes the repository mount.

Explorer startup loaders must wait for a reported runtime to become running before invoking its application operations. Before the first MCP handshake, the initial agent waiting route observes the authenticated same-route startup protocol (`GET /<agent>/` with `X-Ploinky-Agent-Startup-Probe: 1`) across a stable generation window. A 202 starting response does not authorize MCP initialization; ordinary inactive-route and CSRF rejection remain unchanged.

Explicit local development verification uses `SMOKE_SOURCE_VERIFICATION=local-snapshot` and a separately supplied `SMOKE_LOCAL_SNAPSHOT_MANIFEST`. This mode requires the same loopback application and inspected Box origin, exact base commits, complete tracked/nonignored source-tree SHA-256 digests, the immutable Box image, and verified live source mounts and generated source links. It verifies the same identities again after the browser gate. Release remains the default and retains clean-repository checks; QA acceptance rejects local snapshot mode. See [local snapshot E2E](../regression/local-snapshot-e2e.md).

Explorer must enable RoboTeam globally and route Open Copilot here through the RoboTeam copilot plugin with `agent=roboTeamAgent`, `robot=default` and the selected directory. Robot selection must remain in the WebChat launch query and declared MCP command-catalog arguments. Explorer must not enable a separate AchillesCLI agent or copy its persisted data. RoboTeam owns robot account configuration, conversational state and graphical task limits.

## Conclusion

Ploinky provides the deployment and trust boundary; Explorer provides the workspace interface inside that boundary.
