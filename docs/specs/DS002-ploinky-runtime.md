# DS002 Ploinky Runtime

## Introduction

Explorer runs as the static Ploinky agent and depends on Ploinky for startup orchestration, router access control, and workspace configuration.

## Core Content

Explorer CLI and its worker adapter must recognize direct execution by
the canonical real filesystem path of `process.argv[1]`, including absolute and
relative symlink entrypoints. Importing either module must not read stdin, serve
requests or produce CLI output. Direct CLI execution preserves its stdin JSON,
argv fallback, tool envelope and exit-status behavior. This import-safety repair
does not itself change `toolWorkers` or any tool's `worker` descriptor; the active declaration is described below.

Box smoke acceptance must independently compare the selected container, immutable
image ID/reference, application/Box origins, same-path workspace and verified source
manifest before and after a cohort. The common explicit-Box profile retains the
hard 30-minute generation cap, records image creation time and its disabled image-age
policy, and preserves additional screen/network and DPU fallback age checks.
Required account inputs/roles and opt-in flags must be verified before lengthy
execution without exposing private values. Complete spec filenames and title grep
are the selector contract; file/line suffixes are forbidden. Discovery and terminal
outcomes must exactly match the selected acceptance-ledger identities, each with one
expected pass and zero retries, skips, flakes, cancellations or blocked outcomes.
Exit zero and discovery alone are insufficient. GPT Researcher stays excluded,
browser errors stay strict.

WebTTY readiness evidence must retain bounded last-cause and sampled identity
information on failure, preserve the primary assertion when artifact writing fails,
and reject a proved stale generation immediately. Copilot diagnostics must retain
the first visible terminal error/time with submission/reply outcome and must not
accept an error bubble as an assistant reply. The official release cohort uses
OnlyOffice-only authenticated Marketplace activation, while the unchanged
three-agent activation profile remains a separately required cohort. All three
official gates must fit one fresh generation with measured setup/execution/cleanup
durations and a stated margin; infeasible scheduling remains blocked.

Explorer declares a same-origin `routerAccess.capabilityDeniedRedirect` to UserPersisto's authenticated account dashboard. Only denied HTML document GET navigation follows it; API, MCP, SSE, WebSocket, and mutation denials remain errors. The account service's explicitly owned and matching authenticated route retains the inherited identity provider but applies its own capability policy, allowing active restricted accounts to manage their profile without granting Explorer access. Undeclared and guest/public routes retain owner capability checks. The dashboard verifies the Router's signed HTTP invocation against the actual method, internal path, query, and raw body before resolving its current persisted actor. See [DS012](DS012-user-persisto.md) for the account API and enrollment contract.

UserPersisto constructs browser login URLs on the validated callback origin while keeping runtime bridge requests on the private Router address. This preserves the exact public host and port and the initiating browser's host-bound callback proof.

Explorer tool calls must distinguish an MCP transport session from the browser's authenticated Router session. A missing or invalid MCP session remains a tool connection failure after the MCP client's bounded recovery; it must not trigger an expired-login alert or login navigation. Only an explicit Router HTTP 401 `not_authenticated` response triggers that tool-call login flow, preserving the current Explorer path and hash. Transport failures and permission denials do not change the authenticated account or its roles.

Browser MCP handles belong to the verified user and authentication session that initialized them. Another login, including a later login by the same user, must initialize its own transport. Explicitly public anonymous routes retain handles scoped to their exact public target; private Router-to-Agent pooled sessions retain per-request signed authority. A foreign browser handle cannot acknowledge notifications, replace a session or delete it.

Each SSO authorization or identity/proof admission obtains a fresh provider description, including `/auth/token` and HTTP, MCP, SSE and WebSocket handshakes. The Router has no positive authorization TTL. Callers captured before a provider dispatch may share that result; later callers wait for the next serialized validation. UserPersisto reads account status, generation, roles and capabilities within one persistence scope. Completed demotion or capability removal affects the next admission while the account's remaining permissions stay usable. Logout, revocation and provider configuration reload prevent delayed validation or refresh from restoring authority. Requests admitted before a concurrent mutation may finish under their accepted snapshot; existing streams gain no new push-cancellation mechanism.

Optional Google sign-in uses a separate UserPersisto transaction and cookie, while preserving Ploinky's provider-neutral SSO handoff and original core state. `/service/auth/*` remains guest transport admission, including the explicit Google callback. Do not add an overlapping `publicProtocol` exception: restrictive policy combination keeps it guest. Guest admission grants no local user authority. Google callback cookies are distinct from Router proofs; the Router removes its own cookies and overwrites forwarding headers before proxying. Public callback/issuer configuration, not raw Host or caller forwarding headers, determines URLs. Local completion uses fixed relative Location headers with the Router-visible additional-server prefix so guest sanitization retains them; the verified Google HTTPS authorization destination may remain absolute. OIDC completion returns to the original interaction path without widening its existing cookies. DS012 and DS013 define account ownership, proof validation and exact downstream completion.

#### Configuration can change the Box lifecycle

The public `ploinky var` wrapper may prepare and reconcile the selected Box before writing a variable. A successful setter does not establish initialized application readiness, and a failed setter can follow a completed recreation. Before the first generic command, identify the selected physical workspace and exact mounted public CLI checkout, owned immutable Box/container/image IDs, exact image-reference label, Router/media ports, mounts and AgentLib source mode/path/commit/content fingerprint/physical-source identity. Stop on missing or ambiguous ownership. An equal Git revision in another checkout is not equal mounted source identity. Preserve the exact `PLOINKY_BOX_IMAGE` reference and verify its immutable image ID; switching an equivalent tag to a digest is still a planned lifecycle change. Explicit `PLOINKY_WORKSPACE_ROOT` must exist and match the physical selected directory, since an absent path can fall back to workspace discovery.

Before authorized lifecycle work, protect the paired encrypted secret file/master key, workspace `.data`, persistent Box binds and selected source/routing state through the secure backup procedure. Do not print backups or secret values. Public `help`, `status --verbose` and `--dry-run` avoid owned-Box reconciliation but status/dry-run still use temporary image capability probes. Dry-run does not forecast prospective AgentLib replacement; verbose status omits immutable image identity and truncates fingerprints. Generic `list`, `network status`, `vars` and `echo` prepare the Box, and the last two also disclose values; none is a safe readiness substitute.

After every Google setter, reinspect exact owned container/image/source identities before continuing. Reuse the same explicit workspace, mounted CLI and exact host image selector for each command. With the same initialized Box, `restart userPersistoAgent` is the supported targeted configuration activation path and validates/reuses existing sources without reconciliation. A recreated or uninitialized Box requires planned managed graph recovery with `start explorer`. Retained workspace metadata and an initialized status flag alone do not establish an active graph. The selected Ploinky runtime must check the exact owned Box's public Router health before entering a targeted restart and refuse an inactive graph without changing routing; it must also retire each successfully published targeted runtime's completed candidate receipt so a subsequent restart can preserve the same logical identity. Unexpected generation, decryption failure or readiness failure stops the sequence for selected-environment recovery without replacing keys, emptying stores or deleting unrelated resources. Verify retained users/roles/keys, graph initialization, redacted Google readiness and an existing administrator sign-in in the browser after activation. The operator procedure and exact independent callback registrations are documented in [workspace operations](../workspace-operations.html#google-sign-in).

Explorer must obtain its filesystem roots from the configured runtime environment and enforce those roots for filesystem MCP operations. The browser may bootstrap a display context from `list_allowed_directories`, but it must not treat that result as authorization for paths outside the server-enforced roots.

The Explorer CLI and prepared tool-worker adapter share `handleExplorerToolCall`. An explicit envelope `tool` precedes the current `toolEnv.TOOL_NAME`. The worker must never use ambient `process.env.TOOL_NAME` to choose a tool. CLI imports must not consume stdin, and direct execution must retain input, arguments, metadata, output bytes, failure newline, and exit-code behavior, including execution through staged source symlinks.

Every call creates a fresh Explorer runtime and owns its invocation context. The handler must dispose that runtime in `finally` after output completes or fails. Disposal is idempotent, clears the registered search cleanup interval, retires invocation context and cleanup references, and is not a callable MCP tool. The filesystem dependency has module-level allowed roots, so each fresh runtime must reset them and one worker must execute only one call at a time. Command-mode search continues to await completion; existing operation-owned CRDT heartbeat cleanup remains unchanged.

The adapter uses the Ploinky-supplied `serveToolWorker` callback and bootstrap/socket protocol. It must not implement a second transport. `explorer/mcp-config.json` declares `toolWorkers.explorer` (`command` `tools/explorer_tool_worker.sh`, `cwd` the literal `workspace`, `size` 3, default limits) and `"worker": "explorer"` on 43 tools. Every tool keeps its spawn `command`. The pool falls back to spawn only when it is degraded (repeated workers dying before completing a call) or the code identity cannot be read; saturation, a call timeout or a worker crash return failures to the caller instead of retrying in spawn mode. These eight tools stay in spawn mode:

| Tool | Reason |
| --- | --- |
| `search_text` | Runs for up to 30 s and would hold a pool lane |
| `replace_text` | Runs for up to 45 s |
| `update_avatar_settings_agent` | Imports code from `AXIFACE_REPO_PATH`, which is outside the code-identity roots |
| `llm_autocomplete` | Uses its own command, `tools/llm_autocomplete_tool.sh` |
| `add_skills_manifest_repo`, `set_skills_manifest_skill_enabled`, `remove_skills_manifest_repo`, `read_skills_manifest_state` | Call the Router repository client (`listRepositories`, `prepareRepository`, `install`, `remove`) with timeouts of up to 30 s |

`collect_ide_plugins` stays in the pool: its only external process is a local `git config` read with a 2 s timeout, and it makes no network or Router call.

Module-state and environment audit: the runtime is created and disposed per call, the invocation context is set and cleared in `finally`, the tokens exist only in the call frame and are never logged by the pool, caches are scoped to the per-call runtime, the Markdown CRDT document lock is owned by a per-acquisition token that is tracked in-process while held (a lock file naming the live worker pid with a token that is no longer held, for example after a failed release, is treated as stale and recovered at once, while locks held by concurrent operations still exclude others and cross-process semantics are unchanged; a release that cannot be confirmed because the lock file could not be read or removed raises a process-wide flag, and the worker adapter then changes `process.env` during the call, which makes the Ploinky worker recycle (exit) after delivering the result, so other live workers recover the lock through the dead-pid path instead of waiting for the lock timeout; spawn mode is unaffected because the process exits after every call), filesystem roots are reset per runtime and one call runs at a time, children are awaited, a `process.env` write recycles the worker, and `process.env` reads are limited to container-fixed values (`FS_CACHE_TTL_MS`, `PLOINKY_AGENT_NAME`/`AGENT_NAME`). The only external-source reader, `AXIFACE_REPO_PATH`, is excluded. Accepted differences from spawn mode: a 300 s per-call limit (spawn has none when unset), a 256 MiB frame cap, and code-identity recycling when tool sources change. Tests pin the declaration, the worker and spawn-only sets, token and identity isolation, error isolation, cache freshness after external writes, and bursts and latency against spawn mode (`explorer/tests/unit/explorerToolWorker.test.js`). Rollback: set `PLOINKY_TOOL_WORKERS=0` to force spawn mode, or revert the `toolWorkers` declaration and the `worker` fields. The shipped `explorer/manifest.json` currently sets `PLOINKY_TOOL_WORKERS` to `0` in `profiles.default.env`, so Explorer runs every tool in spawn mode by default: on Linux a single call is faster in a worker (about 22 ms against 98 ms), but a 12-call burst is about 1.5 times slower because each dispatch runs a synchronous code-identity check. The declaration stays in place for controlled testing; a workspace value takes precedence over the manifest literal, so `ploinky var PLOINKY_TOOL_WORKERS 1` followed by `ploinky restart explorer` re-enables the pool. Turn it back on by default only after the identity check no longer slows bursts. The Box smoke preflight no longer requires the opt-in to be absent.

Every active top-level agent manifest must declare workspace-backed writable data volumes below `.data/`. Explorer's preinstall hook selects global mode and the exact `PLOINKY_WORKSPACE_ROOT` as its project path. Ploinky mounts that root at the same absolute path in the Box and global Explorer runtime, including `.ploinky/repos`; Explorer declares no additional fixed workspace alias. Managed `persistentStorage` declarations must use a safe one-segment key and an absolute container path. Repository validation must positively classify every writable volume and persistent-storage declaration; merely rejecting one retired prefix is insufficient. Explorer private writers must resolve their paths through the shared `.data/explorer` boundary, reject symbolic-link components or files, and canonically revalidate that boundary before reading or writing avatar overrides, plugin settings, search jobs, or CRDT state.

Ploinky router authentication and secure invocation data are authoritative for protected browser and agent calls. Every Explorer deployment uses SSO mode and the UserPersisto provider declared in its manifest; Ploinky binds that provider without hard-coding its identity in router code. Canonical workspace startup resolves one provider from the admitted graph under the workspace lock, rejects missing or conflicting providers before runtime mutations, and persists the binding after generation inactivation and before Router launch. Router and provider resolve the same declared shared generated secrets through the persisted profile; private provider keys are not exported.

Explorer registration and credential verification go through UserPersisto (DS012); account passwords are UserPersisto credentials, never Ploinky ones. Ploinky no longer offers local browser password authentication, credential seeding, or local-role capability mappings; `pwd` declarations and `routerAccess.localAuthRoles` are rejected. The manifest's SSO requirement is authoritative, and missing or unavailable UserPersisto authentication fails closed. Preserving existing workspace authentication modes and migrating local accounts are outside this release's scope.

Ploinky's retired `/auth/account` and local login-branding settings routes are unavailable. Old local browser credentials cannot authorize Marketplace, policy, or other protected controls. The verified local CLI operator channel remains available for runtime control and does not establish a browser password login or Explorer user session.

Login initiation binds each callback transaction to an HttpOnly browser proof cookie; validation requires that proof before consuming state or establishing a session. The router must remotely revalidate SSO sessions and require the manifest-declared `explorer.access` capability before forwarding protected Explorer traffic. An agent must derive the acting principal from verified invocation context and must not trust a client-declared actor identity.

UserPersisto also exposes OAuth/OIDC under its declared additional-server public protocol route, as specified in [DS013](DS013-oauth-oidc.md). A manifest's generic `publicProtocol` opt-in admits only the declared paths and methods, with explicit CORS and loopback-redirect behavior required by external OAuth clients; it does not disable protection on adjacent service or Explorer routes. Public protocol requests use the provider's standard authorization, PKCE, token, and browser-interaction protections rather than requiring a pre-existing Ploinky session. The public issuer is explicit configuration and must include the Router-visible additional-server prefix; host or forwarded headers must not select the issuer. Discovery, endpoints, cookie paths, and redirects remain consistent with that issuer behind the Router. OAuth access and ID tokens are not substitutes for Ploinky's verified invocation context or protected-route session.

Its post-browser check must prove that the full semantic-label set and outer generation did not change. Explorer startup loaders must wait for a reported runtime to become running before invoking its application operations. Before the first MCP handshake, the initial agent waiting route observes the authenticated same-route startup protocol (`GET /<agent>/` with `X-Ploinky-Agent-Startup-Probe: 1`) with a two-mode route stability check: it reads the startup probe twice and compares the Router generation and, when present, the activation token. A newer Router adds `activation`, `activeForMs` and `mutation` to the ready body. The settle wait (2.5 s) is skipped only when the first read carries a valid activation token (`/^[A-Za-z0-9_-]{1,64}\.[1-9][0-9]{0,15}$/`), `mutation` is `idle` and `activeForMs` (a safe integer >= 0) is at least the settle; the second read must then show the same generation and activation and still `idle`. Every other case, including malformed fields, any `mutation` other than `idle` and an older Router that sends none of the fields, waits the full settle between the reads and requires an unchanged generation and activation (forward check). A routing mutation that starts after the second read of a skipped check is not observed (accepted residual). A 202 starting response does not authorize MCP initialization; ordinary inactive-route and CSRF rejection remain unchanged.

The shared expanded modal waiting sequence reads the Marketplace agent catalog once per open. The entry returned by the ensure-running step is the first runtime read of the wait (only when it reports the agent running); a not-running entry, later poll iterations and failures re-read `/api/marketplace/agents`. After the stability probe, the target route probe and the MCP `listTools` probe run concurrently; the first rejection is mapped to the modal error state and an abort is checked before and after the probes. The route stability probe keeps its signature and return value and uses the two-mode contract above (`activeForMs`-based skip with a fallback to the full forward check).

A toolbar plugin whose `toolbarModal.mode` is `iframe` (for example WebMeet) renders inside the modal iframe, which loads its own components. Its lazy first-click path therefore registers only the presenter component in the Explorer parent and skips `plugin.dependencies` (`ensureComponentRegistered(name, { includeDependencies: false })`). Component-mode modals (Git, Marketplace, Help, Observability) mount their component in the parent and keep full dependency registration. A later registration without the option still registers the dependencies of a presenter that was registered without them. Every other path, including component-mode and non-modal plugins and the room-entry route that mounts `webmeet-dashboard` in the parent, registers dependencies as before.

Explicit local development verification uses `SMOKE_SOURCE_VERIFICATION=local-snapshot` and a separately supplied `SMOKE_LOCAL_SNAPSHOT_MANIFEST`. This mode requires the same loopback application and inspected Box origin, exact base commits, complete tracked/nonignored source-tree SHA-256 digests, the immutable Box image, and verified live source mounts and generated source links. It verifies the same identities again after the browser gate. Every runtime path is derived from the verified same-path workspace root (the Box mounts the workspace at its own host path; there is no `/workspace` alias), and snapshot evidence is a separate generation that never substitutes for image-mode release evidence. Release remains the default and retains clean-repository checks; QA acceptance rejects local snapshot mode. See [local snapshot E2E](../regression/local-snapshot-e2e.md).

Explorer must enable RoboTeam globally and route Open Copilot here through the RoboTeam copilot plugin with `agent=roboTeamAgent`, `robot=default` and the selected workspace-relative directory. The action appears only on directory context menus, not in Tools. Invalid directory context must fail rather than omit the launch directory or fall back to the workspace root. Robot selection must remain in the WebChat launch query and declared MCP command-catalog arguments. Explorer must not enable a separate AchillesCLI agent or copy its persisted data. RoboTeam owns robot account configuration, conversational state and graphical task limits.

Hardware refusal propagates only across blocking dependency edges and consumers explicitly waiting on a no-wait result. A refused optional no-wait child retains an inactive route and visible reason without blocking Explorer. A genuinely required refused dependency blocks its transitive consumers; those consumers are never ready. Hardware policy and administration follow DS008.

### Marketplace activation recovery

A Marketplace activation timeout or abnormal worker exit does not prove that child processes or installer runtimes stopped. Ploinky retains mutation ownership and reports recovery required; subsequent conflicting mutations must fail rather than reclaim that lease from age or worker death alone. From the selected workspace on the physical host, the operator stops the exact owned Box with `ploinky stop`, verifies it is stopped, then runs `ploinky start explorer`. The inner stop may report an error even after the outer Box stops, so verify the actual state before continuing. The next start retires the retained lease only after the runtime proves the previous Box stopped or absent. A timed-out worker must not be described as having automatically terminated every descendant.

## Conclusion

Ploinky provides the deployment and trust boundary; Explorer provides the workspace interface inside that boundary.
