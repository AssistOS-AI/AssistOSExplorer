Explorer MCP Tools

This page documents the MCP contract owned directly by Explorer. It is the filesystem-facing tool surface defined in explorer/utils/server/tool-definitions.mjs, dispatched by explorer/utils/server/tool-runtime.mjs, and invoked through explorer/tools/explorer_tool.mjs. It does not document gitAgent tools or soplangAgent tools, because those remain agent-owned contracts with their own documentation.

Explorer uses MCP to expose safe workspace operations to the browser and to other agents. The contract covers file reads and writes, directory traversal, search, metadata inspection, plugin catalog aggregation, plugin settings persistence at .data/explorer/plugin-settings.json, and exposure of the active allowed roots. WebMeet media commits accept staged blobs only at .data/<short-agent-name>/blobs/<blob-id>.

Path Safety

All Explorer MCP tools enforce the configured allowed roots. Relative paths are resolved inside the workspace context, absolute paths are accepted only if they stay inside allowed roots, and traversal outside those roots is rejected. That path model is the reason Explorer can expose reads, edits, copies, moves, and directory searches without giving callers unrestricted host filesystem access.

For the broader backend boundary, see Backend → Filesystem MCP. For domain operations owned by other agents, continue to the Git Agent or SOPLang Agent documentation instead of treating Explorer as a shared tool dump.

Collaboration Boundaries

The internal-only SCRIPTA surface consists of scripta_crdt_ensure_folder, scripta_crdt_workspace_list, scripta_crdt_create, scripta_crdt_open, scripta_crdt_mutate, scripta_crdt_delete, scripta_collaboration_open, scripta_collaboration_pull, scripta_collaboration_apply, scripta_collaboration_merge_markdown, webmeet_media_commit, and webmeet_media_get. Explorer owns path validation, the authoritative Automerge state, validation of browser-originated changes, Markdown materialization, and room-scoped WebMeet attachment storage. The collaboration tools expose only a public SCRIPTA replica; workspace paths and Explorer persistence metadata remain server-side. Complete Meeting Notes revisions use scripta_collaboration_merge_markdown to apply returned Markdown to the supplied public snapshot, merge it with the current replica, preserve private SCRIPTA state, and commit the canonical document in one serialized transaction. scripta_crdt_delete accepts the explicit prepare, commit, and rollback phases so the room attachment and Explorer document cannot diverge after an ordinary operation failure. Media commit verifies a staged blob and its sidecar, recognizes supported image bytes, records safe file metadata, and moves the asset into document-multimedia/webmeet/<roomId>/assets/; media get resolves only a room and asset id. Generic filesystem tools are not exposed to the WebMeet collaboration path.

WebMeet exposes webmeet_scripta_workspace_list only as an authenticated read path for the document picker, plus webmeet_scripta_sync_open, webmeet_scripta_sync_pull, webmeet_scripta_sync_apply, and webmeet_scripta_sync_close for authorized browser replicas. Semantic create, attach, delete, navigation, vote, structural, and AI operations still pass through webmeet_event_command; binary CRDT synchronization is not persisted as chat.

WebMeet exposes webmeet_event_command as its sole blackboard mutation tool. Canonical JSON events execute directly; multilingual /event and /robo text is interpreted by the local blackboard-event code skill before the same versioned event contract is applied.

The skills-manifest editor installs Anthropic-style skill folders identified by skills/*/SKILL.md. If a repository contains no such folders, Explorer may retain the cloned repository in its cache, but it does not add the repository to ploinky-skills-manifest.json and returns a normal informational message describing that outcome.

These tools are specific to Explorer's host role: they aggregate plugin manifests from the workspace, persist enabled or disabled plugin state for the UI, and reveal the currently active filesystem roots. Git mutations and SOPLang execution are intentionally absent here because they belong to their own agents.
