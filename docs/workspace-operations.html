Workspace Operations

Explorer is the primary workspace surface for browsing directories, opening files, selecting compatible previews or editors, and invoking contextual actions without leaving AchillesIDE. The current path is reflected in the application route, so a supported file or directory location can be restored after navigation.

File selection opens the appropriate text editor, Markdown editor, media preview, Office integration, or agent-backed view. Ordinary workspace paths use Explorer's filesystem tools. Paths under /Confidential are virtual resources and use the permissions and storage contract owned by DPU. Research acquisition and access-request controls preserve the selected DPU resource, display an immediate busy state, and refresh the resource preview when the authorized operation or confirmation flow completes. After acquisition, use Verify read beside any entry in Verified Files to perform a real bounded read through DPU and see the byte count and continuation state directly in Explorer.

File and Folder Management

The New menu creates a folder or file in the current directory. In /Confidential/Secrets, the file action is presented as New Secret. Creation controls are disabled when the current DPU-backed location does not grant the required capability.

Context menus provide Rename, Copy, Cut, and Delete for supported entries. Directories also provide Paste into and Upload here; files can be opened in a new browser tab. Administrators additionally receive Open Terminal Here, which opens the Explorer-owned terminal target chooser described below. Ordinary users do not receive the item, and Router authorization remains authoritative for direct requests. Delete requires user confirmation, and Explorer refreshes the affected directory and clears invalid selection or clipboard state after the operation.

In tree mode, reloading the page keeps the workspace tree and opens the ancestor folders of the path in the URL. Other workspace folders remain visible.

Manage skills

Open Manage skills from a directory's context menu. The dialog uses RoboTeam's popup structure and CSS: expand a repository, add a recommended repository or enter a Git URL, and use Remove to unregister it. Recommendations already added to this folder show a disabled Added button. Explorer prefers a repository checkout directly in the workspace before the managed cache. The repository row shows the resolved local path, such as /workspace/DocumentationSkills.

Selected skills are relative symlinks under the target folder's .agents/skills, with the selection saved in ploinky-skills-manifest.json. Changes to the source repository are visible through those links. Editing through a link edits the source. Remove and Disable remove managed exports while preserving unrelated files, user replacements and modified legacy copies.

For repositories with skillsets.md, controls apply only to skillsets. Each item shows its description and member names, with Enable/Disable at the top right. Enable adds all members; Disable removes all members. Overlapping skillsets can become partially enabled. Repositories without declared skillsets keep individual skill controls. Closing the dialog after changes refreshes the contents of expanded tree branches while keeping them open. Adding a repository enables all declared skillset members, or all skills when there are no skillsets.

Copy, cut, and paste use Explorer's ordinary filesystem contract and are unavailable for DPU-managed entries. DPU-backed rename, delete, upload, folder creation, file creation, and permissions controls appear only when the effective resource capabilities allow them. This keeps the same Explorer interaction model while preserving the owning service's authorization rules.

Uploads target the selected directory, or the current directory when no directory is selected. Ordinary uploads use Explorer's authenticated upload route; Confidential uploads are delegated to DPU and rejected when the destination does not allow new content.

Terminal Targets

Open Terminal Here sends only the canonical workspace-relative directory to Ploinky's same-origin, mutation-protected discovery route. The chooser lists Ploinky Box first. It then lists only running agents whose current runtime identity and live mounts Ploinky has independently proven can access the selected folder. Explorer does not inspect containers, infer mounts, or translate a path.

Each choice shows its server-provided label, detail, effective working directory, and read-only or read/write access for the selected folder. Agent choices also explain that the terminal uses the container's normal user, tools, environment, permissions, and credential context. A read-only badge describes this folder mapping, not the entire container.

Selecting a row directly opens /webtty/#launch=<opaque-id> in a new tab with no opener or referrer. The short-lived launch ID is not a container selector and is not placed in a query parameter or browser storage. A blocked popup leaves the chooser open. Refresh replaces the complete discovery batch, and cancel asks Ploinky to invalidate the unused choices. Explorer never sends a raw container identity, translated or physical path, shell, arguments, environment, user, or runtime flags.

Find and Replace

Find file searches workspace paths by name after at least two characters and can exclude comma-separated glob patterns. Selecting a result navigates directly to that path. The default shortcut is Cmd/Ctrl+P.

Find/Replace in files searches file content within a selected base path. Users can enable case-sensitive, regular-expression, or whole-word matching and can exclude files with glob patterns. Results retain file, line, column, and preview context so individual matches can be selected.

Replace Selected changes only selected matches. Replace All applies the active query to the selected scope and warns when the visible search result is truncated. Large replacements require confirmation, changed files are refreshed, and partial failures or timeouts remain visible in the result summary. The default shortcuts are Cmd/Ctrl+Shift+F for search and Cmd/Ctrl+Shift+R for find/replace.

The browser invokes the root-confined Explorer search and replace tools; it does not receive unrestricted host filesystem access. Private .data trees are excluded from default autocomplete discovery, and background search jobs are stored under .data/explorer/search-jobs. Explorer resolves private writers through one canonical .data/explorer boundary and rejects symbolic-link components before persistence.

Workspace Settings

The Settings modal combines user preferences with workspace-scoped integration controls:

  • Agents loads settings components declared by enabled agents and available to the current account.
  • Plugins enables or disables discovered workspace plugins within the host manifest whitelist.
  • Copilot shows RoboTeam instruction-skill inventory, effective selection and the selected conversation's active execution revision. In a robot chat, open the WebChat menu and choose Conversation skills to edit that conversation in Explorer. The conversation keeps its saved working directory even if Explorer is browsing another folder. Ordinary Settings edits the default robot's defaults for future conversations. Enable and disable controls save a versioned policy through RoboTeam; Refresh reads current state. Changes affect the next execution and preserve work already running. Invalid conversation links show an error instead of opening defaults.
  • Administration contains links to the Users and Applications pages permitted by your account. Each opens in a separate browser tab owned by UserPersisto. Users shows the count of accounts whose only role is selfRegistered and leaves them out of the default list. Search by email, username, display name, or user ID to find any account and change its role. Search covers all accounts before pagination; clearing the search restores the default list. Accounts promoted to user appear in that list. Accounts are created when people sign in, so there is no create form, the sign-in email is read-only and no page sets passwords. Details and roles have separate actions; deactivation blocks an account reversibly. Applications provides the complete OAuth/OIDC form, client list, and pagination in its own scrollable page.
  • My Account contains links to your standalone profile and personal sign-in security page. Accounts with settings-management access also have an Authentication policy link for workspace-wide sign-in methods and registration rules. The UserPersisto entry under Agents → Configure opens the same page, following the agent's declared settings URL. Settings contains navigation links for these account surfaces; their forms and lists live in UserPersisto.
  • Keymap changes or clears shortcuts for file search, content search, replace, save, autocomplete, and Settings, and can reset them to defaults.
  • Editor controls code-editor auto-save. Auto-save is disabled by default and uses a configurable idle interval when enabled; an external file change still blocks the save and produces a warning.
  • Theme selects the global light or dark application theme.
  • Avatar stores the user's profile avatar in the browser, controls whether WebMeet adapts AxiFace automatically to the user's voice or uses a manually selected emotion, and exposes agent-avatar overrides only when the authenticated user can manage them.

On the Users page, open the Roles dropdown to select one or more roles from the stored catalog. Use Search roles to filter a long list; hidden selections are retained. Press Escape to close the dropdown, then use Save roles to apply the selection. Custom roles created on the Roles page appear after refreshing the user list.

Open Roles in UserPersisto navigation to create a custom role, edit its description and permissions, or delete an unused role. Select permissions from the registered capability catalog; leaving the selection empty creates a role that applications can recognize without granting workspace access. Creating a role does not assign it to anyone: open Users and save the desired assignments separately. Changing a role's permissions affects everyone assigned that role when access is checked again.

Role names are permanent, case-sensitive identifiers of 1–128 characters using letters, digits, dots, underscores, colons or hyphens, beginning with a letter or digit. Descriptions may contain up to 1000 characters. The built-in admin, user and selfRegistered roles are protected. Remove a custom role from its users before deleting it. Role administration does not define new capability types or provide application-specific or composite roles. The OAuth scope roles requests assigned role claims; individual role names are not OAuth scopes.

The Marketplace lists available agents and repository sources. Administrators can install or remove repositories and enable or disable agents. Marketplace management works on the local control origin and configured public application origin. Explorer obtains a fresh router proof bound to the session and exact origin; public requests also bind to the selected application host and active routing generation. The router verifies administrator access for that application before any mutation; a missing, stale, or mismatched proof is reported as an error and does not change the workspace. The UI permits one agent mutation at a time, keeps the native runtime-mode selector stable during rerenders, and retains failures until the operator explicitly dismisses them. Each agent shows a normalized Disabled, Starting up, Running, Stopped, Failed, Paused, or Unknown state. Marketplace refreshes the authenticated JSON catalog every three seconds after the preceding read completes on both local and public origins, including after agents reach Running. Configure is disabled until the runtime is verified as running. Updates retain row controls, runtime-mode choices, focus, and expanded groups while refreshing labels, accessible status, current lifecycle details, and enabled-agent counts. A refreshed stopped or disabled state disables Configure without rebuilding the row. Closing Marketplace aborts the active read; authorization failures stop refreshes and remove management controls, and stale reads cannot overwrite a completed mutation.

Both Marketplace tabs hide skills repositories (including mixed agent-and-skill sources), skill entries, and the repositories basic, cloud, container-image-builds, copilot-agents, demo, extra, security, and vibe, along with their agents. Repository aliases follow the same policy by source URL. Search, repository filters, enabled-agent counts, and refreshes include only visible entries. Repos offers Agent Repos and Others. These visibility rules leave installed repositories, enabled agents, and the skills subsystem intact.

Plugin state and agent-avatar overrides use Explorer tools or the owning integration. Browser-only preferences such as keymap, theme, profile avatar, and editor auto-save do not replace server-side authorization or agent configuration.

Explorer prepares the AxiFace pack catalog at /explorer/shared/generated/axi-face-packs.json for both Explorer and WebMeet. This generated file belongs to Explorer and is excluded from its source checkout. Pack manifests and rendering assets keep their existing /explorer/shared/vendor/axi-face/ URLs, and catalog preparation leaves the AxiFace checkout unchanged.

First administrator

A fresh installation has no account. The first completed sign-in becomes the administrator: a Google sign-in or a verified email signup. Opening the page, typing an email or requesting a code does not claim it, and only one administrator is created when completions race. The claim is recorded permanently; removing or blocking accounts never reopens it. Later public sign-ups receive selfRegistered and open My Account until an administrator assigns the user role.

Complete Google or verified-email sign-in to claim a fresh deployment before letting other users connect. Administrators use the same sign-in page and methods as other users.

All accounts have no password. They sign in with an email code, an enrolled passkey or authenticator app, or Google. Passkeys and authenticator apps are optional; add them from My Account after confirming it is you.

Google sign-in

UserPersisto includes its pinned Persisto runtime in the repository. It starts with Ploinky's read-only source mounts and writes account data only to the installation's data directory; no startup Git checkout or Google secret import is required.

When enabled and configured, Continue with Google is available on the sign-in wizard, including before setup, where a Google sign-in can become the first administrator. Google verifies identity; UserPersisto keeps the local account ID, profile and roles. After setup, new Google accounts receive selfRegistered and open My Account until an administrator grants Explorer access. Returning linked users retain their roles even when registration is disabled. My Account lists Google without exposing provider subjects or tokens.

If the email already belongs to a local account, prove that account and then confirm Link Google and continue: request a link code sent to its verified sign-in email, use its enrolled passkey or authenticator code. When Google is authoritative for exactly that verified email (a Gmail address or a matching Workspace domain), consent alone is enough. Don't link; go back returns to the sign-in page. Google never changes the local email, and an unverified contact address is not a link target.

Passkey linking keeps the credential's existing relying-party domain and origin checks. The IP-address preview is not a valid WebAuthn relying-party domain; use a link code or authenticator code there. Passkeys require a configured hostname and a credential enrolled for that domain. Local browser tests can use localhost with matching issuer and callback registrations. See the WebAuthn relying-party identifier requirements.

A new non-Gmail address without verified Workspace authority also needs a fresh email code before an account is reserved. This registration proof cannot log into or link an existing account. Mail delivery failure creates no account. Expired proof or an ambiguous interruption during verification requires a fresh attempt.

Administrators open Settings → My Account → Authentication policy in its separate UserPersisto tab to enable Google and inspect effective environment overrides, public client ID, sign-in origin and missing setting names. Google sign-in uses no client secret. Keep an existing usable administrator sign-in method enabled.

Clone and sign in locally

Start Explorer through the normal Ploinky workspace flow and open http://localhost:8080. A fresh installation supplies the public Google client ID and generates its own local encryption key; no Google secret file or credential import is needed. Continue with Google opens a dedicated page with Google's sign-in button. Google returns a signed identity token, UserPersisto verifies it, and the existing local sign-in completes. The shared client also supports an explicitly configured http://127.0.0.1:8080 origin. An HTTPS deployment may explicitly use the shared client once its owner registers that exact origin with Google; other HTTP loopback ports need a custom client.

Custom origins and operator configuration

For a different HTTPS origin, use an operator-selected Google OAuth Web application client and have its owner register that bare origin under Authorized JavaScript origins. This may be the existing shared client or a separate deployment client. Configure its actual branding, audience, contacts and required homepage/privacy/terms/domain ownership. This integration uses the official Google Identity Services browser SDK and its JavaScript credential callback; a Google Authorized redirect URI is unnecessary. Only identity information is requested. Audience/test-user settings and Workspace restrictions still apply. See Google's setup guidance.

Set the public USERPERSISTO_GOOGLE_CLIENT_ID and USERPERSISTO_GOOGLE_REDIRECT_URI together. The latter keeps a callback-shaped value, such as https://id.example/base-agent-additional-server/userPersistoAgent/7000/service/auth/google/callback, to identify the canonical origin and service prefix. To use the shared client at 127.0.0.1, set its public ID and http://127.0.0.1:8080/base-agent-additional-server/userPersistoAgent/7000/service/auth/google/callback together. The callback path itself no longer accepts Google responses. Partial configuration fails closed; both absent fields still select localhost. A canonical HTTPS URL with an explicitly supplied shared client ID is accepted, while the shared client's HTTP alternatives stay restricted to localhost or 127.0.0.1 on port 8080. Google must separately authorize the configured origin. Retain the Ploinky-generated USERPERSISTO_SETTINGS_KEY with the installation's data. There is no Google secret or flow-mode setting.

Box preflight for configuration changes

Before any ploinky var, select an authorized workspace and record its physical path, exact public CLI checkout mounted at /opt/ploinky, owned Box ID, immutable image ID, exact image-reference label, mounts, ports and AgentLib physical source identity/content fingerprint. Use the existing exact PLOINKY_BOX_IMAGE selector for reuse and verify its immutable image ID. A matching commit in another physical checkout or an equivalent tag-to-digest change can still recreate the Box. Set PLOINKY_WORKSPACE_ROOT only after its directory exists and physical path matches. Securely back up the paired encrypted secrets/master key, workspace data, durable Box binds and routing/source state outside test artifacts.

The public wrapper may prepare/reconcile the Box before a setter runs. A failed setter does not undo a prior recreation. Public help, status --verbose and --dry-run avoid owned-Box reconciliation, although status/dry-run still use temporary image probes. Dry-run does not forecast prospective AgentLib replacement; verbose status truncates fingerprints and omits immutable image identity, and a zero exit code does not prove readiness. Do not substitute list, network status, vars or echo: all prepare the Box, and vars/echo can disclose values.

With the verified workspace, mounted public CLI and exact host image selector on every command, set the two public Google configuration values using ploinky var NAME VALUE. The default localhost setup needs neither setter. Do not append plaintext to .ploinky/.secrets or replace the installation's master/encryption keys. Inspect the safe readiness response.

After each setter, compare exact owned container/image/source identities and stop on unexpected change. The same initialized Box uses restart userPersistoAgent for refreshed configuration through the targeted path. A recreated or uninitialized Box needs managed graph recovery with start explorer. Retained workspace metadata can still report initialized after recreation, so require an active public Router and verified graph readiness. Use a Ploinky candidate that checks public Router health before targeted restart changes routing and retires the completed runtime candidate receipt after successful publication; both protections are required for safe refusal and repeated targeted restarts. Unexpected ownership, decryption failure or failed readiness requires selected-environment diagnosis against the recorded candidate and secure backup, never unrelated cleanup. Verify initialized graph, retained users/roles/keys, an existing administrator sign-in and both browser routes before enabling Google. See DS002 for the lifecycle contract.

The Google option appears when the sign-in wizard has loaded. Its dedicated page loads Google's maintained SDK; an unavailable SDK shows a recoverable error, and Cancel returns to the live sign-in page. Only that page permits Google resources and the popup/referrer policies they need. The signed ID token is sent to UserPersisto in a same-origin POST and never stored in a URL, browser storage or logs.

Local Explorer sign-in automatically uses the configured loopback hostname. With the default setup, opening http://127.0.0.1:8080 restarts sign-in at http://localhost:8080. This requires the updated Router and UserPersisto provider together. The redirect happens before login cookies are created, preserves your destination, and applies only between loopback hostnames on the same protocol and port while Google is enabled and fully configured. Public hosts and existing OAuth/OIDC interactions are not redirected.

ScriptaHub actions and cancellation

ScriptaHub retains the selected PDF edition/language or feedback draft in its original tab. The popup returns through UserPersisto's ordinary consent/token flow even if navigation detaches the opener; a same-origin channel supplements strict opener messages. Original-tab Cancel remains available through network validation and delayed Continue. Cancellation or the whole-attempt deadline discards the candidate local session and prevents the action, including stale Continue activation. It cannot undo a remote account/link already committed. Reloading or closing the original tab loses the pending action. Anonymous reading and direct PDF URLs remain public.

Controlled signed-token and HTTP tests are separate from real Google browser verification. The 14 September 2026 integration checks verified real Google sign-in in Chrome on both supported loopback origins using the shared public client ID and no Google secret. Full Box deployments, other browsers and Workspace account policies need their own acceptance checks. GIS uses the standard identity scopes: OpenID, email and basic profile. Disabling Google is the first rollback action; retain identity rows, replay tombstones, snapshot and encryption key.

Safety and Ownership Boundaries

Explorer validates ordinary filesystem operations against configured allowed roots on every call. It does not translate a browser-visible path into authority outside those roots. Destructive actions require an explicit user action, and server errors remain visible instead of being interpreted as successful mutations.

Virtual resources and plugin actions keep their own ownership boundaries. DPU decides permissions for Confidential resources, while Git, SOPLang, WebMeet, Tasks, and other domain agents own their mutations and diagnostics.
