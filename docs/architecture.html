Architecture

Explorer is the static host shell of the workspace, not just another agent with a narrow tool surface. A Ploinky workspace needs one application that can own navigation, preview, editing, and runtime plugin mounting without absorbing the domain logic of Git, DPU, SOPLang, tasks, assistant flows, or media tooling. Architecture matters here because the product boundary is easy to get wrong: if Explorer becomes too thin, users end up stitching together unrelated agent surfaces; if it becomes too broad, domain rules drift into the host and become harder to maintain.

The implemented architecture answers that tension by keeping Explorer responsible for the shared IDE shell while dependent agents keep responsibility for permissions, state, and mutations in their own domains. Explorer therefore sits at the center of the workspace experience, but it is intentionally not the owner of every operation the workspace can perform.

Runtime Structure

The shared Node agents use the immutable Ploinky Node image recorded in their manifests. It supplies Node 24 on Debian Trixie and a maintained Git/libcurl stack. Publication verifies Git clone, fetch, and npm Git dependency installation on native amd64 and arm64 before a new image digest is adopted.

Explorer runs inside Ploinky, which provides the router, workspace routing table, agent lifecycle, and startup orchestration. Explorer is configured as the static agent, so the router redirects the workspace entry point to /explorer/index.html and then proxies Explorer-prefixed requests to the Explorer agent. The Explorer container itself is defined by explorer/manifest.json, which declares the runtime image, custom server command, environment, and the dependency agents that must be enabled alongside it.

At startup, ploinky start explorer prepares the recursive manifest graph and captures an early inactive generation with exact identities and every retained route targetless. Static preinstall and startup config providers run against that topology. Ploinky then aborts the early lease, reloads and re-evaluates retained predecessor runtimes, rotates newly stale tuples, and captures the final inactive targetless generation. Only its exact lease may authorize targets when blocking dependency waves start. Each wave applies its private targets and passes readiness before dependents start. Explorer starts only after its blocking prerequisites are ready; detached no-wait helpers launch afterward. A live no-wait process remains semantically starting until its current-run readiness probe and route activation publish terminal success; Workspace Monitor and the tracked QA gate preserve that distinction. Router activation uses coordinated generation apply and cannot add a physical-host mapping. That readiness model matters because Explorer is only useful as an IDE shell when the domain agents it surfaces are also available.

The Ploinky Box keeps edge ownership outside Explorer. Ploinky mounts an immutable, non-secret topology generation before consumer hooks start. Long-lived integrations resolve their active locator for each join, editor session, or settings launch, while browser plugins use only the authenticated one-locator no-store projection. Product manifests declare private HTTP service targets; they cannot add physical-host publications.

The private Router listener gate has three exact states. required-loopback always requires 127.0.0.1:8081 while RoutingServer is ready. required-assigned-managed-gateway applies only when current Podman inspection and kernel inventory prove that the bridge gateway is assigned to the exact reported network_interface, in which case exactly one listener is required. inactive-unassigned-managed-gateway requires no listener when that assignment is absent; the inactive state remains fail-closed and does not prove managed-bridge activation or reachability. Missing or stale evidence, cross-interface assignment, missing or extra listeners, wildcard listeners, and unrelated binds fail closed.

Current rootless limitation: the observed Podman host.containers.internal:host-gateway mapping terminates on the box outer-facing interface, so managed-bridge access to private Router 8081 cannot satisfy the approved bind boundary. That lane remains inactive and fail-closed pending Ploinky DS004 Question #8; Explorer does not substitute the public listener, a direct target, a widened bind, a forwarding sidecar, or alternate authorization.

Agent launch pages observe runtime readiness and a stable authenticated Router startup generation before sending the first MCP request. Local development E2E can explicitly verify packaged source-tree hashes and live runtime mounts; release and QA acceptance retain their clean-source requirements.

UserPersisto keeps identity and account state in its workspace-backed Persisto volume under .data/userPersistoAgent. Its single-writer lock is bound to the owning Ploinky runtime identity. A normal stop releases that lock; after an abrupt Box or agent stop, a replacement generation can recover only an unchanged lock proven to belong to its dead predecessor. Live, malformed, and current-generation foreign locks remain fail-closed, so restart continuity does not weaken the one-writer storage boundary.

This runtime relationship is asymmetric. Explorer owns the host UI and filesystem-facing shell, but agents such as gitAgent, dpuAgent, soplangAgent, tasksAgent, and multimedia remain separate runtime units. For example, soplangAgent receives its own MCP calls for document synchronization and build execution and reads the mounted workspace directly; it is not a hidden module inside the Explorer backend.

For research data, Explorer projects /Confidential/Research Data and /Confidential/Jobs as virtual records and hosts the administrator Data Sources component. Authorization, source credentials, confirmation proposals, job transitions, and provenance remain owned by dpuAgent; Explorer does not reproduce those rules.

Host Implementation

The Explorer implementation is split between the browser application built with WebSkel and the CLI-based MCP tool runtime. Explorer defines tools in utils/server/tool-definitions.mjs, dispatches them through utils/server/tool-runtime.mjs, and exposes the process entry point through tools/explorer_tool.mjs and tools/explorer_tool.sh. The runtime enforces filesystem-safe operations and allowed-directory constraints; static assets and browser routing are provided by the configured Ploinky agent runtime. Application-category plugins are filtered through Explorer's applicationPlugins manifest policy before they are mounted into the browser experience.

On the frontend side, the single-page application (SPA) under explorer/ owns navigation, selection state, preview routing, editors, and runtime component loading. Bootstrap captures an initial hash route before asynchronous startup, mounts the selected WebSkel page, and applies that route exactly once after the page presenter has registered its listener; encoded file paths are therefore decoded only after the Explorer page is ready, without a second navigation or synthetic history event. Ordinary Markdown source editing flows through the embedded markdown-editor component and its TinyMDE editor, while SOPLang-aware structured editing is opened explicitly through document-view-page. Other text and code files use the general-purpose editor components. HTML preview, media preview, and other content-aware experiences are orchestrated from the same host shell, which is why the frontend structure lives as a unified application rather than as a collection of unrelated agent UIs.

Three libraries and services define architectural boundaries rather than incidental implementation detail. WebSkel owns component registration and presenter lifecycle in the browser shell. TinyMDE provides ordinary Markdown source editing and emits incremental text changes. Automerge provides the shared conflict-free authority for workspace Markdown: source editing emits text-range operations, structured and SCRIPTA editing emits semantic operations, and Explorer materializes the converged state back to Markdown.

The boundary between these two layers is operational rather than theoretical. The MCP runtime provides the constrained file and plugin catalog surface the browser needs. The frontend decides how those resources become a coherent IDE experience. Where the browser needs a domain action, it invokes the owning agent instead of reimplementing the domain logic locally. Blob handling follows a separate router convention and is not part of Explorer's filesystem tool runtime.

The application structure is declared in webskel.json, which lists the pages, components, and modals that make up the host shell. Representative components include:

Component Description
file-exp The main page orchestrating the file explorer view.
file-exp-entries Dedicated presenter for rendering and updating the entries table/list.
file-exp-preview Dedicated presenter for preview area orchestration (code/media/markdown/html).
html-web-view Sandboxed iframe presenter used by HTML preview (Code/Web/Split modes).
document-view-page Renders a structured SOPLang-aware document with its chapters and paragraphs.
markdown-editor Embeds TinyMDE for normal Markdown source editing and sends incremental text-range changes through Explorer's Markdown CRDT flow.
chapter-item / paragraph-item Represents a single chapter or paragraph within a document.
file-editor A general-purpose text editor for any file type.
files-menu Component responsible for displaying a browsable list of files and directories.
insert-image-modal A modal for uploading and inserting images into a document.

Each component is driven by a JavaScript presenter class that manages its state and lifecycle. Presenters use an invalidate() method to trigger re-renders, making the UI reactive to data changes.

Document Collaboration

All workspace Markdown editing uses the Explorer-owned Automerge CRDT service, which keeps canonical working state in private workspace data, validates document paths, merges concurrent changes, and materializes the resulting Markdown representation back to the workspace. The plain TinyMDE interface emits incremental text-range operations, while the structured and SCRIPTA interfaces emit semantic document operations. Its MCP contract includes open, change, merge, save, synchronization, and SCRIPTA collaboration operations.

SCRIPTA Markdown proposals use a fresh Automerge actor for every writable fork, so concurrent proposals from one base remain independent. Explorer records accepted proposal identities in private canonical state and returns the current document for retries without duplicating changes, even after a restart, later edits, or undo.

Office documents use OnlyOffice instead. OnlyOffice provides the co-editing WebSocket transport and sends signed save callbacks through OnlyOfficeAgent, which persists the document to the workspace or delegates Confidential persistence to dpuAgent. Each Office mount captures its configuration before awaiting script loading, so concurrent presenter changes cannot replace its document identity or preload URL. Explorer retains an Office session only while its editor remains mounted and active. Native disconnect, backup-copy, and expiry warnings retire that render; reopening obtains a fresh session and supports further durable edits. OnlyOffice records authenticated final-save or no-change closure and, separately, successful save-and-disconnect drain completion, avoiding later saves against retired document keys. Explorer does not apply the Markdown CRDT to Office files, non-Markdown source files, or Confidential DPU virtual Markdown, whose owning DPU retains its own write contract.

Identity, Administration, and Billing

UserPersisto and EmailAgent use Explorer's immutable Ploinky Node image and store workspace data under .data/userPersistoAgent and .data/emailAgent, mounted at /data. Existing deployments using the retired .ploinky/data roots must stop these agents and migrate their data before upgrading; the in-container paths remain unchanged.

EmailAgent serves its tools through Ploinky's default MCP AgentServer. UserPersisto keeps its HTTP service on private port 7000 and starts the bundled MCP AgentServer on private port 7001 after its store and HTTP listener are ready. Tool calls continue to use the HTTP service port. UserPersisto supervises MCP and drains it before closing HTTP and Persisto, so clean shutdown releases the sole writer's lock. These listeners add no physical-host ports.

Both agents preserve their declared JSON Schema constraints when listing and validating MCP tools. Tool subprocesses read the AgentServer input envelope and verify signed invocation metadata; EmailAgent also accepts its legacy arguments envelope.

Every Explorer workspace uses UserPersisto for registration and login, including password verification. Locked startup selects the provider from the admitted manifest graph. Router and provider use the same declared shared secrets. Ploinky no longer offers local browser password authentication or credential seeding; retired local-auth declarations are rejected, and an unavailable provider fails closed. Existing local accounts are not migrated. UserPersisto sessions require explorer.access to open Explorer, and each login callback must carry the initiating browser’s private proof cookie. Provider client errors during a callback exchange, including an expired authorization code or an account blocked after code issuance, produce a neutral HTTP 400 response without a session cookie; unexpected server failures remain failures.

Explorer user administration delegates to UserPersisto after current session and administrator checks. The retired /auth/account and login-branding settings routes are unavailable, and Explorer Administration loads only the provider-backed users API. Old local browser credentials cannot authorize Marketplace, policy, or other protected controls. The verified local CLI operator channel remains available for runtime control, without providing browser password login or an Explorer user session.

Initial registration requires an email and an 8–1024-character password before an administrator can be created. Both user administration interfaces provide Previous/Next navigation and total counts, with 100 users per page. The UserPersisto search box filters the displayed page. Provider user forms require email while username and display name remain optional. Provider projections and editable rows keep absent optional fields empty; changing the role of an email-only account does not synthesize a username. Password sign-in always uses email. Saving a change preserves the current page.

The Ploinky SSO authentication page shows one form at a time. A fresh installation displays owner registration only. Once an owner exists, the page starts with sign-in; multiple enabled methods appear in a labeled Sign-in method select that honors the enabled default and never includes a disabled method. When self-registration and password authentication are enabled, a Create account link-style button switches to registration, with a Sign in link back. Registration explains that the account starts with dashboard access by default and that an administrator grants Explorer access. Switching views clears passwords, codes, and pending challenges while retaining the URL's SSO transaction state; late responses from the abandoned form do not change the current view or redirect it.

Accounts without Explorer access land on My account, where they can update their profile and enroll permitted passkeys or an authenticator app. The same enrollment controls are available in the Settings My Account → Profile panel. The dashboard is an authenticated service at /base-agent-additional-server/userPersistoAgent/7000/service/dashboard/; it verifies each signed Router request and checks the current active account. Setup keys are transient and cleared when setup finishes or the user leaves. The first registration creates the administrator. Authentication endpoints reject malformed JSON and non-object request bodies with a client error before processing credentials or creating accounts. Later public registration, including OAuth/OIDC signup, defaults to selfRegistered with dashboard-only access; an administrator can grant user access or explicitly change the permitted registration role. Browser logins retain the public workspace address while provider bridge calls use the private Router address.

Passkey sign-in validates canonical base64url client data and rejects malformed assertions as ordinary authentication failures. Invalid client data does not consume the challenge. Successful sign-in still verifies the browser origin, relying-party identifier, challenge, user presence, signature, and authenticator counter, with replay protection.

UserPersisto also provides OAuth 2.0 and OpenID Connect for registered external applications. Configure USERPERSISTO_OIDC_ISSUER with the stable public HTTPS URL ending in /base-agent-additional-server/userPersistoAgent/7000/service/oidc, then restart the agent. Discovery advertises authorization, token, UserInfo, public signing keys, introspection, revocation, and logout endpoints. Authorization code requires S256 PKCE; refresh tokens rotate on use. Existing Ploinky SSO remains available, and OAuth tokens do not grant access to protected Explorer routes.

Administrators use Settings → My Account → Profile → Manage OAuth applications or the Applications tab to register exact callback URLs, choose public or confidential clients, and manage grants, scopes, status, and secrets. Client lists have 100-row pages. A confidential secret is shown only on creation or rotation; save it immediately in the application's secret store. User sign-in follows the enabled authentication policy and requires scope consent. Back up the stable USERPERSISTO_SETTINGS_KEY with the Persisto snapshot because durable signing keys, cookies, protocol records, and client credentials depend on it.

This interoperability scope includes opaque API access tokens, RS256-signed ID tokens, and confidential client credentials. API consumers must use authenticated introspection under the issuing client; shared resource-server credentials and JWT API audiences are not provided. Full Keycloak feature parity, identity federation, dynamic client registration, and high availability remain outside this revision. See DS013 OAuth/OIDC for setup examples and the exact security and verification contract.

UserPersisto stores Persisto objects and indexes in an atomic, checksummed snapshot. Failed writes return an error and block cached operations until storage is repaired and the service restarts. Critical user and credit workflows exclude unrelated saves. Legacy per-object stores import without deleting their files; after the first successful save, .userpersisto.snapshot.json is authoritative. Back up that snapshot. Only one writer may open a volume: normal shutdown releases its lock; after an abrupt kill, stop all writers and verify the owner is gone before removing the stale .userpersisto.writer.json lock. Dirty saves rewrite the full snapshot, and multi-writer operation is unsupported.

Reservations are scoped by user and reference and can be repaired from the credit journal. Checkout records an immutable purchase intent before contacting Stripe, so retries keep the original price, quantity, credits, and payment state. Unresolved requests older than 23 hours require reconciliation. Subscription events read current Stripe state; a canceled subscription cannot be restored by an older delivery. See DS012 UserPersisto for the recovery and compatibility contract.

Development Context

Explorer development happens inside a Ploinky workspace, not as a standalone web app detached from the rest of the runtime. That means local changes need to be understood in the same environment where the router, dependency agents, and workspace mounts are present. Install Node.js 20+ and npm, then start the workspace through the Explorer entrypoint.

From a Ploinky workspace that contains the AchillesIDE repository, the normal startup path is:

ploinky start explorer
# Dashboard: http://127.0.0.1:8080/dashboard
# Main Explorer UI: http://127.0.0.1:8080/#file-exp/

The Explorer entrypoint applies the required global workspace mode, default workspace-root configuration, dependency startup, and router launch. Runtime plugins are discovered from enabled agent-owned IDE-plugins/ directories in the workspace, and application plugins are filtered by Explorer's applicationPlugins policy from explorer/manifest.json. If you change a plugin config.json or add a new plugin, restart Explorer so discovery runs again. Most ordinary UI, JS, and CSS changes are then visible through a normal browser refresh.

The Box release harness uses a separate fixed Router and authentication baseline after the full Ploinky graph and listener gate succeed. That release-only smoke gate is owned by its harness and is not part of the workspace-local Explorer startup procedure.

This baseline proves the dashboard, Explorer shell, and routed WebChat shell through Router. It is not the separate WebMeet two-account ScreenShare gate or the WebMeet external-network direct/relay matrix, and none of those gates substitutes for another.
