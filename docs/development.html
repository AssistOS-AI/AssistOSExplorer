Development

Explorer development happens inside the running workspace rather than in a detached frontend sandbox. That is important because the behaviors developers usually touch, such as filesystem routing, runtime plugin discovery, HTML preview, and dependent-agent availability, all depend on the surrounding Ploinky environment. This page is therefore not a full architecture guide; it is the short operational reference for getting a local Explorer workspace into a useful development state and checking that the current runtime assumptions still hold.

The practical implication is simple: changes should be evaluated in the same setup where Explorer is the static agent, the workspace root is mounted, and repo-scoped static paths are reachable through the router. If that context is missing, many issues that look like UI bugs are actually environment mismatches.

Bootstrap Flow

From a Ploinky workspace that contains the AchillesIDE repository, the usual startup path is:

ploinky start explorer

Ploinky owns repository and agent enablement, default workspace-root configuration, dependency startup, and router launch for this entrypoint. Open the dashboard at http://127.0.0.1:8080/dashboard, then open Explorer at http://127.0.0.1:8080/#file-exp/.

The main Explorer UI is served at http://127.0.0.1:8080/#file-exp/. HTML preview is expected to use repo-scoped file URLs rather than a flattened docs namespace. A representative preview URL looks like:

/.ploinky/repos/AchillesIDE/docs/development.html?__previewReload=1

Within that running workspace, the Explorer UI is organized around the host page file-exp and its dedicated presenters such as file-exp-entries, file-exp-preview, and html-web-view. The component registry source of truth remains explorer/webskel.json, so UI refactors should be checked against that file rather than inferred from screenshots or browser state.

Verification

Explorer's CLI and worker adapter recognize direct execution through the canonical filesystem path, including absolute and relative symlinks. Imports produce no CLI output, read no stdin and start no worker. The CLI retains its JSON input and exit-status contract. The explorer warm pool is active for 43 tools; explorerToolWorker.test.js pins the declaration, token and error isolation, cache freshness, and worker-versus-spawn latency (it needs the sibling Ploinky checkout, or PLOINKY_ROOT).

Box smoke profiles use the canonical npm test -- --project=chromium --workers=1 --retries=0 runner with complete spec filenames and title greps. Common preflight independently compares the selected container, immutable image ID/reference, origins, same-path workspace and exact source manifest before and after execution. It retains the 30-minute generation cap and records the applicable image-age policy. Required flags, private sign-in inputs and authenticated roles are checked before lengthy execution. Both discovery and terminal outcomes must exactly match the selected acceptance ledger, with one expected pass per identity and no skips, retries, flakes, cancellations or missing results. See the regression runbook and smoke README for inputs and cohort scheduling.

WebTTY attaches bounded last-failure and runtime stability evidence, rejects proved stale generations immediately and preserves the primary failure if artifact writing fails. Copilot records the first terminal error and observation time with submission/reply outcome. An error bubble cannot establish a reply. The official release cohort activates OnlyOffice alone through authenticated Marketplace controls; the three-agent activation workflow remains a separate required check. The official WebMeet coverage is the two-account media gate and the public-room gate, in which a cookie-less guest joins a public room from its UI-published URL and chats with the owner while the team-room URL is refused. All four official gates require one candidate and fresh generation with measured durations and margin.

Browser identifiers must work on both loopback and direct HTTP LAN origins. Explorer uses WebSkel's createSecureUuid export for loader, document, variant, image, and browser idempotency IDs. It uses cryptographic browser randomness and fails explicitly when none is available. Maintain this helper and loader behavior in the WebSkel source repository, run its source and build tests, then copy the generated ESM/UMD files and MIT license into explorer/shared/libs/webskel. Do not patch the generated bundles or install a global browser API shim. Explorer carries four groups of instance-level overrides, and the vendored bundle stays unmodified in each case: explorer/services/runtime/explorerResourceLoader.js overrides ResourceManager.loadComponent, explorer/shared/ui/expanded-modal-loading.js overrides showLoading and hideLoading, and explorer/services/runtime/pageChangeGuards.js overrides ResourceManager.waitForDescendantRenders and changeToDynamicPage, and explorer/main.js replaces showModal and createReactiveModal on the instance. The upstream follow-up is a WebSkel change that makes its descendant wait skip components that are not connected to the document; once a refreshed bundle contains that rule, remove the render guard and update the T1 characterization in explorer/tests/unit/pageNavigationRace.test.js in the same change. Run the browser UUID compatibility tests and a real HTTP LAN browser check after refreshing the dependency.

The fastest useful checks confirm Explorer's runtime contracts. Repo-scoped static documentation paths must resolve through the router, and frontend edits must continue to use the documented component registry and preview routes. Typical checks are:

# Unit tests
cd explorer
npm test

# Spot-check repo-scoped static docs path
curl -I "http://127.0.0.1:8080/.ploinky/repos/AchillesIDE/docs/development.html"

# Spot-check shared static asset path
curl -I "http://127.0.0.1:8080/.ploinky/repos/AchillesIDE/docs/styles.css"

Release smoke checks inspect the live outer Box rather than trusting a fixture description. The exact Box labels must bind the selected achillesAgentLib mode, source identity, content fingerprint, workspace-relative source path, and Git commit. The ordinary Copilot gate additionally requires that commit to match the verified release manifest before and after Chromium, while the outer container generation and complete semantic-label set remain unchanged. It pins the manifest's immutable image digest and reference but measures freshness from the new outer-container generation; screen and native-network gates separately retain their bounded fresh-image checks.

The WebTTY recovery gate waits for Explorer plugin rendering and outstanding finite response bodies before navigating Explorer away for Router fault injection. Authorization and icon requests are observed from initial navigation even when plugin rendering does not await them. Only successful responses with the exact text/event-stream media type are excluded from this bounded wait. Failed requests remain visible to strict diagnostics before and after navigation.

The WebTTY gate logs the primary page out to the public /auth/logged-out page, never to the protected Explorer root. It requires that exact same-origin landing, the signed-out content and one bounded, non-retrying read of /auth/token that must answer exactly HTTP 401 {"ok":false,"error":"not_authenticated"}, then requires clean diagnostics and zero /auth/login navigations, UserPersisto wizard documents, same-origin wizard google/start POSTs and accounts.google.com/gsi requests on that page until the intentional re-login. A logout to the root starts an idle wizard that the later sign-in abandons, which aborts the old document's requests; this is old-document abandonment and not a failure of the sign-in finish barrier. Only counts are recorded.

Smoke sign-in diagnostics distinguish one transport event from failures. When a password sign-in leaves the UserPersisto wizard while Google's sign-in script is still loading, the browser aborts that script request. The sign-in helper acknowledges that single abort only with document-specific CDP proof after the authenticated principal is verified; the original event stays in the evidence. Console errors, page errors, cleanup POST failures and every other request failure stay strict, the OnlyOffice recovered-CSRF rule remains the only browser-error acknowledgement, and release gates still require zero unacknowledged browser errors. The wizard itself retires its Google transaction before navigating, so a clean sign-in has no failed cleanup request. See tests/smoke/README.md.
