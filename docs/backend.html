Explorer Backend

The Explorer backend gives the workspace UI controlled filesystem access and plugin discovery through Model Context Protocol (MCP) tools. It validates every filesystem request against configured roots and exposes only the operations owned by Explorer.

Domain behavior remains in dedicated agents. Explorer may route a user action to Git, DPU, SOPLang, WebMeet, or another enabled service, but it does not absorb those agents' execution models into its backend. This page documents Explorer-owned backend behavior and identifies integration boundaries without duplicating agent documentation.

Filesystem MCP

MCP, the Model Context Protocol, is the contract Explorer uses to expose filesystem-safe operations to the browser and to other agents. In Explorer, tool definitions live in utils/server/tool-definitions.mjs, dispatch lives in utils/server/tool-runtime.mjs, and the process entry point is tools/explorer_tool.mjs, invoked by tools/explorer_tool.sh. Every filesystem call is mediated by an allowed-roots model before it touches the workspace.

Allowed roots are derived from ASSISTOS_FS_ROOT or MCP_FS_ROOT. Relative paths are resolved inside the first allowed root, then normalized and validated before execution. That means the browser can request reads, writes, moves, copies, searches, and directory traversal without gaining unconstrained access to the host filesystem. Violations are surfaced as MCP errors rather than being silently coerced into risky behavior.

The Explorer backend runs through the shared Ploinky AgentServer and the command-backed tools declared in explorer/mcp-config.json. Those tools serve workspace-confined filesystem operations and aggregate plugin manifests from enabled agent or repo-local plugin folders. The browser reaches them only through the authenticated router MCP proxy, which mints the secure-wire invocation required by AgentServer. MCP execution failures remain errors at this boundary and are not parsed as plugin catalogs or directory listings.

handleExplorerToolCall is shared by the CLI and the prepared tools/explorer_tool_worker.mjs adapter. Each call creates its own filesystem runtime and invocation context, then disposes its cleanup interval in finally, including tool and output failures. The adapter uses Ploinky's supplied serveToolWorker API and runs one call at a time. Its tool name comes from the current envelope or tool environment, without using an ambient TOOL_NAME.

The worker adapter is inactive in the shipped MCP configuration. Every tool retains its existing spawn command. Enabling workers requires the actual Box compatibility gate, measured worker acceptance, and a complete per-agent module-state and external-source identity audit. The prepared adapter does not establish those results.

Operationally, the filesystem MCP surface covers several capability groups rather than one giant undifferentiated tool list. It supports text and media reads, atomic writes and edits, directory listing and traversal, move/copy/delete operations within the allowed roots, metadata and content searches, and plugin-catalog introspection through collect_ide_plugins. Calls remain stateless from the client point of view: the client sends a path and arguments, and the backend validates the request against the configured roots on every call.

For the current Explorer-owned tool list, use the dedicated Explorer MCP tools reference.

Blob handling follows a related but separate router convention. In the Ploinky model, the router can proxy /blobs/<agent> to an agent that implements blob handlers and returns JSON describing the stored payload. The Explorer filesystem tool runtime does not itself implement the blob endpoint. Filesystem MCP tools and blob-capable agent behavior are therefore separate contracts.

A representative MCP request looks like this:

// Request (read a file head)
{
  "method": "read_text_file",
  "params": { "path": "README.md", "head": 20 }
}

// Response (success)
{
  "content": "# Explorer Agent...",
  "truncated": true
}

// Response (error outside roots)
{
  "error": "Path is outside allowed directories"
}

Tip: prefer relative paths rooted in the first allowed directory to avoid ambiguity when multiple roots are configured.

Agent Integration Boundaries

Explorer can expose UI actions that delegate structured document synchronization, execution, and build requests to soplangAgent. The SOPLang agent owns those operations, their runtime state, their MCP contract, and their diagnostics. Explorer owns only the host interaction and the explicit handoff.

Use the SOPLang Agent overview for its product role, the SOPLang architecture for runtime ownership, the execution workflow for synchronization and build behavior, and the SOPLang MCP tools reference for callable interfaces.

Operational Notes

If MCP reports “Path outside allowed roots”, verify ASSISTOS_FS_ROOT or MCP_FS_ROOT and make sure the requested path is inside an allowed root. Filesystem path validation, Explorer tool dispatch, and plugin-catalog failures belong to the Explorer backend.

Failures returned by a delegated domain action belong to the agent that owns that action. Use the linked agent documentation for its runtime configuration, logs, and troubleshooting contract rather than treating Explorer as a shared backend for every workspace service.
