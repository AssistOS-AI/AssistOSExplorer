# Google sign-in for UserPersisto: implementation plan

Status: proposed implementation, planning only. Reviewed on 11 September 2026 against `user-persisto-v2`. Task tags: planning, authentication, routing, bootstrap, browser-e2e.

## Intended outcome and scope

Add **Continue with Google** to UserPersisto's existing sign-in and registration screens. Google authenticates an external identity; UserPersisto remains the identity and authorization authority, creates and stores local users, owns their roles, and remains ScriptaHub's OpenID Connect provider. Explorer continues to obtain its session through Ploinky's existing SSO callback. ScriptaHub continues to obtain UserPersisto tokens and resumes the original Download PDF or Suggest An Edit action.

Use server-side authorization code with S256 PKCE, state, nonce, and an independent browser proof. Promote the already pinned `openid-client` package to a production dependency. Retain the existing Node.js ESM architecture, four-space JavaScript formatting, native HTTP service, Persisto storage, and WebSkel settings presenter. This does not need Passport, Express, Firebase, Google browser scripts, One Tap, refresh tokens from Google, or a new identity service.

New Google registrations must receive exactly `selfRegistered`, only after initial owner setup and while self-registration is enabled. This deliberately follows this request rather than the configurable default role used by existing password registration. Returning linked users keep their local user ID, roles, capabilities and profile. Blocked accounts cannot authenticate. An existing email is a collision requiring fresh authentication with an already enrolled local password, passkey or TOTP credential and explicit linking consent; email-only proof never authorizes a merge or first Google link in this release.

Anonymous reading and direct PDF URLs remain public. The ScriptaHub buttons are an interaction gate, not PDF access control. No Google credentials, tokens, or subject identifiers become ScriptaHub credentials. General federation, automatic email merging, Google API access, unlinking/recovery, mandatory MFA, and browser-tab reload recovery are outside this implementation.

This document is the only intended worktree change. No integration has been implemented, runtime configuration changed, deployment restarted, commit created, or branch pushed.

## Architecture and security decisions

### Two separate OIDC relationships

| Relationship | Client and issuer | Completion |
| --- | --- | --- |
| Google → UserPersisto | UserPersisto is a confidential Google **Web application** client; issuer pinned to `https://accounts.google.com` | Google code is exchanged and ID token verified only in UserPersisto. A validated external identity is resolved to a local user. |
| UserPersisto → ScriptaHub | ScriptaHub remains public client `scriptahub-preview` of the configured UserPersisto issuer | Existing UserPersisto interaction, local claims, application consent, authorization code, PKCE exchange and current UserInfo checks complete normally. |
| UserPersisto → Explorer | Existing provider-neutral Ploinky SSO bridge | Issue the existing UserPersisto handoff code; Ploinky validates its own pending state and original browser proof before creating its session. |

The inner Google state/nonce/verifier must be independent of ScriptaHub's outer values and Ploinky's core state. Google success alone must not skip local status checks, original-flow validation, or ScriptaHub application consent.

### Protocol and dependency

Move `openid-client: 6.8.7` from `devDependencies` to `dependencies` and regenerate the lockfile so its runtime transitive dependencies are present with production-only installation. Keep `oidc-provider: 9.12.0`. The agent already declares Node `>=22`, which satisfies the existing ESM/Web Crypto runtime requirements. Do not change the base image or upgrade unrelated packages as part of federation. Existing OIDC tests already exercise this client package.

Use `discovery(new URL('https://accounts.google.com'), ...)`, `ClientSecretPost`, `randomPKCECodeVerifier`, `calculatePKCECodeChallenge`, `randomState`, `randomNonce`, `buildAuthorizationUrl`, and `authorizationCodeGrant` with `pkceCodeVerifier`, `expectedState` and `expectedNonce`. Explicitly enable `enableNonRepudiationChecks`: this library does not otherwise promise signature verification of tokens received over direct TLS. Require an ID token and RS256 signature verification using the issuer's JWKS. Keep production upstream requests HTTPS-only; insecure-provider support is confined to injected test fixtures. [Client discovery](https://raw.githubusercontent.com/panva/openid-client/v6.8.7/docs/functions/discovery.md), [code exchange](https://raw.githubusercontent.com/panva/openid-client/v6.8.7/docs/functions/authorizationCodeGrant.md), [signature-check option](https://raw.githubusercontent.com/panva/openid-client/v6.8.7/docs/functions/enableNonRepudiationChecks.md).

Request only `openid email`, `response_type=code`, query response mode, and S256. Do not request Google offline access, force consent on every login, or fetch a picture/profile. Optional local names can remain empty. Google's current discovery advertises S256, RS256, query response mode and secret-post/basic token authentication. Cache public discovery/JWKS normally, with bounded network timeouts and library key refresh behavior. Do not hold a persistence lock while fetching them or exchanging a code. [Google discovery](https://accounts.google.com/.well-known/openid-configuration).

Validate signature/algorithm, issuer, exact Google client audience, authorized-party `azp` where present or required, expiration, issuance-time sanity, and the retained nonce. Validate the authorization response's issuer when supplied/required by discovered metadata. Reject missing/malformed claims, duplicate critical callback parameters, simultaneous code/error responses, and an absent ID token. Use a bounded clock tolerance, initially the library's 30 seconds. Never accept browser-posted identity claims or use Google's `tokeninfo` debugging endpoint as the production verifier. These checks follow the OIDC token-validation rules. [OIDC Core §3.1.3.7](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation).

Bind a case-sensitive, nonempty, bounded `sub` to a canonical Google issuer. Google documents the stable subject and warns that email can change. Its documentation also mentions the legacy issuer spelling `accounts.google.com`; the default discovery-based client validates the canonical HTTPS issuer strictly. Keep that strict behavior for this flow and cover it in real Google verification; do not disable issuer checks or rewrite a JWT to accommodate an unexpected legacy response. Any future compatibility support must verify the original signed token and explicitly normalize only an allowed Google issuer to the same binding key. [Google OIDC identity claims](https://developers.google.com/identity/openid-connect/openid-connect).

### Persistent identity and transaction model

Prefer two small domain-specific types over overloading `oidcRecord` or duplicating identity ownership in `authMethod`.

| Record | Proposed shape and invariants |
| --- | --- |
| `externalIdentity` | `identityKey`, `issuer`, `subject`, `userId`, `createdAt`, `lastUsedAt`. Unique indexed `identityKey = SHA-256(JSON.stringify([canonicalIssuer, sub]))`; grouping by `userId`. Store the original tuple and compare it on lookup. A binding's owner is immutable. Initially permit one Google identity per local user; reject replacement or transfer. No tokens or passwords in this record. |
| `googleAuthTransaction` | Unique indexed `stateHash`; `status`, integer `expiresAt`, encrypted `payload`, version. The 256-bit state hash also serves as the opaque resume handle, strictly as a record selector and never an authentication proof. Payload contains independent browser-proof hash, PKCE verifier, nonce, configured callback/client identity and configuration fingerprint, originating flow, original parent identifiers, and timestamps. After verification retain only minimal validated identity facts and any bound local reauthentication evidence. |
| Parent-specific transaction data | Explorer: durable provider request ID, distinct Router core state, stored callback and initiating public origin. OIDC: exact interaction UID, client ID and validated parent callback/context. Linking: target local ID and normalized email resolved on the server, eligible non-email credential method, fresh local authentication result/time, and explicit confirmation state. Email lookup can identify a collision candidate; only fresh authentication with its existing password/passkey/TOTP credential authorizes linking that account. Parent context and authorization never come from a caller-provided role/user ID. |
| Terminal transaction | Keep a consumed/failed/cancelled tombstone through original expiry for replay handling; erase verifier/nonce/claims when no longer needed. Expired/missing records reject identically. Bounded expiry cleanup on reads/writes; no persistent idle timer requirement. |

All of these are **proposed** types/fields, not existing schema. Add indexes/groupings in `lib/schema.mjs` and application validation in their owning modules. Existing users, passwords, local IDs, roles and OIDC keys require no conversion and no email-based backfill. New records appear only after explicit interaction. Reopening an old snapshot must initialize the new types without altering existing identity data.

Reuse the established AES-256-GCM encryption primitive and retained `USERPERSISTO_SETTINGS_KEY`, with Google-specific authenticated context including the transaction key and version. Either import the existing payload helpers from `lib/oidc/secrets.mjs` or extract them without changing existing key derivation or ciphertext compatibility. Do not store Google transactions in `oidcRecord`: the current signing-material initializer treats existing OIDC records without signing material as corruption. Separate storage lets Google work for Explorer even when UserPersisto's downstream OIDC issuer is disabled.

Do not create a second Google `authMethod` row. `lib/authorization.mjs` can add `{ type: 'google', name: 'Google' }` from the external-identity grouping to its safe profile summary. Public user responses, SSO projections, UserInfo and administrative lists must not gain transaction payloads, provider subjects, proofs, keys or tokens.

### Atomic account creation and lock order

Add a trusted domain operation for external registration/linking; never pass a dummy password to `registerUser`, expose `allowInitialAdmin` to a request body, or call the administrative create-user API from the Google handler.

Existing persistence scopes only exclude concurrent work. Implement explicit no-flush staging for user, role links, external identity and audit, followed by one successful snapshot flush. Add internal staging options/helpers for `createUserInternal`, `setUserRolesInternal` and `recordAudit`, retaining normal defaults for existing callers. Validate every input, uniqueness, role and policy before the first mutation. If an unexpected error occurs after staging starts, poison/invalidate the active store so an unrelated later flush cannot publish partial staged state. Recovery reopens a valid snapshot; a failure after rename but before directory fsync may leave the complete, unacknowledged identity commit present. Resolve a fresh attempt idempotently by identity key and email ownership rather than assuming rollback. The invariant is no partial user/role/binding set and no replayed login success.

This needs a small explicit store-failure seam in `lib/store.mjs`/`lib/durable-storage.mjs`, not a claim that Persisto now supports general database transactions. Test crash/failure injection after each staged write and at snapshot rename/fsync. Storage failure must produce no authenticated response, and cached retries must fail closed.

Use one documented lock order for completion: parent flow lock → users/domain lock → persistence scope. Acquire named locks before entering the persistence scope; do not hold that scope while waiting for a users lock already held by an operation waiting for the scope. Existing `serialize` is not reentrant. Factor locked internal helpers so the new completion path does not recursively call `createUser`, `issueAuthCode`, or an interaction helper already holding the same lock. Review races with ordinary registration, role changes and blocking, not only two Google callbacks.

Persist the complete local user/binding before acknowledging it or issuing downstream success. If downstream completion fails after that identity commit, the account remains a valid linked account and a fresh sign-in recovers it. This is acceptable; reissuing an already-consumed handoff is not. Recheck the live parent immediately before account creation and completion, under the same local exclusion boundary.

### Account resolution and linking

| State after Google verification | Required result |
| --- | --- |
| Binding exists; local user active | Sign in to that local ID, with current roles/capabilities. Registration policy is irrelevant to returning users. Do not overwrite email/name/username or reset roles from current Google claims. |
| Binding exists; user blocked or missing | Deny. Do not fall back to email lookup or create a replacement account. |
| No binding; matching normalized local email exists | Offer fresh authentication with an already enrolled, enabled local password/passkey/TOTP credential and explicit **Link Google and continue** within the same browser-bound transaction. Do not merge, reveal account details, or issue success on email match alone. |
| Collision authentication succeeds | The authenticated user ID must equal the server-selected collision target and the verified method must be an eligible non-email credential. Under the users lock, recheck active status, retained local email, Google policy, global identity ownership, the target's existing Google grouping and parent validity; then create the binding once. A changed local email invalidates this pending collision context and requires a fresh attempt, without selecting a different user. If a different Google subject is already linked to that user, reject even after successful local authentication. Preserve all existing roles, credentials and profile. |
| Collision has only mailbox/email-code proof | No link and no Google-flow session or action, whether the local email was unverified or historically verified. Neither current Google claims nor a mailbox challenge makes email-only authentication eligible for first linking in this release. |
| Collision user has no usable enabled non-email credential, or authentication fails | No link and no new account. End this attempt with existing sign-in/admin recovery guidance. An existing session alone, including one created by email-code login, is insufficient for this first link; never use the pending, unlinked Google identity as its own reauthentication proof. |
| No binding/email collision; setup complete, registration enabled | Create a passwordless local user with `source: 'google-self-registration'`, role exactly `selfRegistered`, optional fields empty, and the binding in one durable operation. Validate `selfRegistered` still exists and has no administrative capabilities. |
| No binding/email collision; registration disabled or installation empty | Deny account creation. Google must be hidden in the owner-setup view and rejected server-side even if a form predates the policy change. First-owner setup remains the existing password flow. |
| Same subject arrives concurrently | Exactly one binding and, at most, one new local user. A completed/replayed transaction cannot issue another login result. |
| Two different subjects present the same email | Serialize against the local email index. The later attempt follows authenticated linking or rejects; it cannot steal the first binding or create duplicate email users. |

Password registration currently leaves `emailVerifiedAt` empty (`lib/users.mjs:129–150`), while email-code login sends to an existing account without requiring prior email verification (`lib/auth/email-code.mjs:29–65`). An attacker can therefore pre-register someone else's email with an attacker-known password. Letting the mailbox owner attach Google using only an emailed code would preserve that attacker credential. To close this scenario without adding account recovery or credential revocation, the first release accepts only an already enrolled password, passkey or TOTP credential for collision authentication. It has **no historically verified email-code exception**: `emailVerifiedAt` alone is not treated as a credential-ownership history. Ordinary email-code login remains a separate existing flow; its proof/session cannot satisfy Google linking, and the link UI cannot enroll or reset a credential from mailbox proof as a shortcut.

This closes the **direct collision-linking path under review**, not account pre-hijacking globally. Existing ordinary account tools allow an active email-login actor to set/change a password or enroll passkey/TOTP outside the linking UI (`tools/registry.mjs:101–109`, `:125–165`), then start a new Google attempt with that credential. That inherited enrollment/recovery behavior can preserve other attacker-controlled credentials. This plan does not establish historical credential provenance or redesign those tools; broader recovery, provenance and credential-revocation policy remains deferred. The R1 acceptance claims below are deliberately limited to the direct Google/email-proof link attempt.

Reuse the enabled password, passkey and TOTP verifiers, bound to the Google transaction's exact target and purpose. Validate passkey challenge purpose/transaction/target before consumption. Do not call `verifyEmailCode` from a Google linking endpoint: it currently does not validate `purpose` or `correlationId`. Ordinary email-code login endpoints must explicitly reject non-login-purpose challenges before consuming them; the new registration mailbox proof lives only in the Google transaction and is never an ordinary login challenge. Request bodies cannot choose the expected context or method eligibility. Track a short-lived authenticated target in durable transaction state, then require a separate same-origin confirmation POST. Recheck policy and eligibility at start, verification, and final consumption. Hiding a button is not enforcement.

Require a usable email and Google's verified-email assertion for new registration. Google warns that a verified third-party email on a Google account may no longer be controlled by that Google account; Gmail and verified Workspace email have different authority. As a conservative product security decision derived from that caveat, for a new non-Gmail account without an authoritative Workspace `hd` assertion, require a fresh EmailAgent code to that address before reserving the local email and binding Google. Use a dedicated transaction-bound `google-registration-email` challenge, with attempt/expiry limits and no account creation in the email sender. This is a narrow prerequisite for safe new registration, not a universal OIDC requirement, email-based linking, or a general recovery flow. Existing bindings still resolve by issuer/subject even if email changes. Record `emailVerifiedAt` only from an accepted current proof; clear it if an administrator changes the local email. [Google server-side verification and email authority](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).

The new mailbox-proof path should keep its proof state in the encrypted Google transaction and reuse existing EmailAgent delivery and challenge hashing primitives without enabling ordinary emailCode login against policy. It is eligible only for a prospective new account with no email collision and cannot call the existing login verifier to create a user. Recheck email uniqueness after proof: a newly discovered collision requires the non-email linking policy above; mailbox proof cannot override it. If EmailAgent is unavailable, these registrations fail safely with retry guidance and no reserved user. Do not silently treat the third-party Google email assertion as fresh mailbox control.

## Browser transaction lifecycle and APIs

Use an independent, cryptographically random browser proof per attempt, retained in an HttpOnly host-only cookie. Set SameSite=Lax so it returns on Google's top-level GET callback. Use Secure on public HTTPS; permit non-Secure only for the exact configured loopback HTTP environment. Scope the cookie to the external UserPersisto `/service/` prefix so both the Google callback and OIDC resume can receive it. A `__Secure-` name can be used on HTTPS; a `__Host-` name would require `Path=/`, so do not combine it with a narrower path. Do not use `Domain`, localStorage, or a readable proof cookie. Give attempts distinct cookie names and bounded per-parent issuance to support concurrent tabs without overwriting proofs.

The initial lifetime is at most five minutes and never exceeds the parent's remaining lifetime. Do not extend expiry on resume, challenge retry, or process restart. ScriptaHub currently limits only callback waiting to five minutes and removes that timer when the callback arrives. Replace this with a whole-attempt deadline starting at the original user action and lasting through configuration/discovery, current-account validation, authorization, token exchange, UserInfo, session publication and the final action, including delayed Continue activation. Use an absolute monotonic browser deadline and check it explicitly after asynchronous work; a suspended/throttled timer is not proof that time remains. A later UX change to the five-minute budget must coordinate all layers explicitly.

| Proposed transition | Validation and durable behavior |
| --- | --- |
| Start → `pending` | Validate live parent, configured callback origin, enabled Google method and completed setup. Explorer initiation requires exact Origin plus `application/json`, rejecting missing/null/foreign origins and simple form content types; OIDC initiation also requires its existing interaction CSRF token. Generate state/nonce/verifier/proof, persist the transaction, then set proof cookie and navigate to Google. No user is created here. |
| Callback → `exchanging` | Accept GET only. Look up the hashed state, verify independent cookie proof, expiry, configuration fingerprint and `pending` status. Reject duplicates/malformed responses. Durably claim once before contacting Google. Wrong/missing browser proof must not consume another browser's valid attempt. |
| Google denial → `cancelled` | Only after valid state/proof. Clear the proof as appropriate and show a neutral error at the retained local flow. No token exchange, identity or user mutation. Ignore provider error prose in rendered HTML/logs. |
| Code exchange → `verified` | Outside persistence locks, exchange once and validate token. Persist minimal verified identity facts encrypted, then discard Google code/token material. A Google callback replay cannot exchange again. |
| `verified` → local resume | Redirect to a fixed, server-generated local resume route tied to the original parent. An opaque transaction handle is only a selector; the cookie and parent proof remain mandatory. No arbitrary `returnTo` or user-selected destination. |
| Resume → linking/mailbox proof or completion | Recheck original interaction/login request, client, policy, configuration and active user. Retain only bounded proof state until final confirmation or successful completion. |
| Completion → `consumed` | Create/link identity safely if required; complete exactly the original downstream login once, preserve consent, erase transient secrets and retain tombstone. Clear this attempt's cookie without deleting another tab's proof. |
| Restart before exchange | Durable `pending` can continue while parent, proof and expiry remain valid. |
| Crash during/after token exchange but before durable verification | `exchanging` is non-retryable. Require a fresh attempt; do not guess whether Google already redeemed the code. |
| Restart after durable verification | A still-valid resume can continue without a second Google exchange, after rechecking both browser and parent context. |
| Restart after downstream issuance/consumption | Never replay or mint another result for that transaction. A fresh login may use the already committed identity. Router restart invalidates Explorer's in-memory parent state and requires a fresh Explorer login. |

The state/proof, redirect binding and replay rules implement the relevant OAuth security principles without confusing durable storage with exactly-once network delivery. [OAuth Security BCP, RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html).

### Proposed route contract

All paths below are internal agent paths; browser links include `/base-agent-additional-server/userPersistoAgent/7000` before `/service`. None of the Google routes exists today.

| Method/path | Purpose and response |
| --- | --- |
| `POST /service/auth/google/start` | Explorer origin-checked JSON initiation with `requestId` and distinct core `state`. Validate the stored request and callback; return an allowlisted Google authorization URL for `location.assign`, after saving state/cookie. Reject caller-supplied issuer, callback, role and user identity overrides. |
| `POST /service/oidc/interaction/:uid/google` | OIDC initiation using existing interaction cookie, CSRF and Origin checks. Return JSON authorization URL through a dedicated local script handler, then navigate the existing popup itself. Do not open a nested popup. |
| `GET /service/auth/google/callback` | Shared Google code/error callback. Validate the independent transaction proof; exchange/verify; redirect to the originating local resume route. Handle before generic static fallback. |

### ScriptaHub completion must tolerate a missing opener

The existing callback forwards only the outer UserPersisto callback URL. The original ScriptaHub tab performs the code exchange and token verification. Preserve that split. Today the callback has no delivery path without `window.opener`; the original tab also treats `popup.closed` as cancellation. A COOP navigation can sever the opener or make the window reference appear closed. This is a risk to verify, not a claim that Google always does so. [Browser COOP behavior](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cross-Origin-Opener-Policy).

Add a native, same-origin `BroadcastChannel` keyed by the unpredictable outer state alongside the existing strict `postMessage` path in `ScriptaHub/src/auth-client.js` and `src/auth-callback.js`. Open the channel before navigating. Validate exact callback origin/path, bounded URL, one matching state, and payload type; retain the source-window check for `postMessage`. Accept only the first valid response across both transports. The original tab still requires its own PKCE verifier, expected nonce/state, signature verification and current UserInfo role checks before authorizing an action. No channel message can assert user identity or roles. Close channels/listeners on completion/cancel/expiry, and discard late responses. Do not use persistent localStorage as a code/token relay.

Feature-detect BroadcastChannel and catch construction failures in both original tab and callback. An unavailable channel preserves the existing strict opener/postMessage transport; do not synthesize source-window events or relax origin/path/state checks. If both transports are lost, the detached callback shows retry guidance and the original attempt terminates through its Cancel/deadline with no ScriptaHub session or action. After cross-origin navigation, `popup.closed` is advisory because it cannot distinguish physical closure from COOP separation. A short acknowledgment confirms delivery only, allowing the callback to close itself or show completion/close guidance; it does not announce authenticated success. This requires no new library. Same-origin top-level tabs can communicate without an opener; partitioned or embedded contexts still require browser tests. [BroadcastChannel constraints](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API).

Add an accessible pending status with **Cancel in the original ScriptaHub tab**, visible from the start of the action through final publication. The current `requireAccount` has no such control after its fallback dialog closes (`src/auth.js:124–150`). Give each attempt an immutable generation ID, one attempt-owned AbortController, an absolute deadline and explicit `pending`, `ready`, `published`, `cancelled` or `expired` state. Cancellation/expiry immediately invalidates it, settles its outward wait, removes its UI/transports and permits retry, even when the popup is detached or a network request has not settled. Abort owned fetches where supported and race non-abortable/shared work against cancellation. Transport abort is best-effort: check current generation, cancellation and remaining lifetime after every await, before further popup navigation, and before every shared-state write or publication. Keep the timer active after callback delivery, throughout code exchange and UserInfo, and while a Continue control is awaiting its real user activation.

Guard failure and cleanup paths by ownership as well as success. A late `current()` error may clear only the exact session snapshot it inspected and only while its attempt is current; old sign-in failures must not clear a newer session. Stale finalizers may release their own resources but must compare identity/generation before clearing shared `pending`, busy state, UI, cache references or session state. These are changes to the existing unconditional `clear()` calls in `src/auth-client.js:99`, `:104`, `:141` and `pending = undefined` in `src/auth.js:147`. Shared configuration/discovery may finish harmlessly after cancellation, but cannot restart the old attempt. Do not cache a client whose fetch closure captures a cancelled attempt's signal; use independent settled metadata or per-attempt request configuration and abort only resources owned by that attempt.

Change `requireAccount(action)` from a bare account result to an opaque one-shot action grant, with a concrete contract such as `{ account, publish(fn), cancel() }`. `signIn()` returns a verified candidate session without writing `memorySession` or sessionStorage. The owning attempt/generation, Cancel control and deadline remain active while the grant is ready; resolving the authentication promise alone must not clear `pending` or run terminal cleanup. The grant keeps its candidate private until synchronous `publish(fn)` rechecks current generation, deadline, cancellation, token expiry and unused status, commits the candidate session, marks the grant published, and invokes the synchronous consumer effect without an intervening await. Mark it consumed before invoking the effect to reject reentrant/duplicate activation; an effect failure does not authorize automatic replay. Invalid grants reject publication without side effects. Cancelling a ready grant discards its candidate; it does not erase an unrelated previously valid session. A grant authorizes exactly one retained action, not any destination supplied later. Duplicate activation of that action may share its attempt; another distinct action must not reuse its grant. Update same-origin parent-frame delegation and every consumer together.

Preserve the captured PDF destination and feedback draft, but move their final effects through that publication gate. Normal PDF replay calls `link.click()` only inside an accepted publication. A modified-click Continue control keeps the grant/deadline alive until actual click or auxclick, prevents default when invalid, and enters the bypass set only during accepted activation; closing it cancels the grant. Feedback in `docs/assets/workflow.js:198–206` rechecks connected form, latest draft, validity and agreement immediately before publishing its mail handoff. Original-tab Cancel stays available while the candidate is ready. A cancelled/expired retained DOM node cannot later navigate or send a handoff. Regenerate `docs/assets/auth.js` and `docs/assets/auth-callback.js` with `build:auth`; edit their source modules, existing auth CSS and the owned workflow consumer instead of hand-editing bundles.

This cancellation contract governs ScriptaHub's local session and retained action. It cannot roll back a Google authorization, UserPersisto account/link, or server session already committed before cancellation. Never claim that original-tab Cancel erases those remote results; the enforceable outcome is no cancelled attempt publishing a ScriptaHub session or action. Reloading or closing the original tab loses the pending action by design in this phase; a server restart while that tab remains open is a required case. Apply this lifecycle to all existing popup sign-in methods, including password, not only Google.

The public HTTPS preview calls a loopback identity service. Chrome's current Local Network Access permission can affect discovery, JWKS, token and UserInfo requests; allow and deny cases must be exercised. Do not prescribe obsolete blanket Private Network Access headers as a compatibility fix. [Chrome Local Network Access](https://developer.chrome.com/blog/local-network-access), [Chrome 142 changes](https://developer.chrome.com/release-notes/142?hl=en).
