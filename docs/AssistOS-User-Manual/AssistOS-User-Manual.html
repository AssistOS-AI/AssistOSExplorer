1. Executive Summary

AssistOS is the integrated working environment that the Achilles IDE project provides for its teams. In a single authenticated browser workspace it unites the activities that a team performs around a shared body of project material: workspace and file management, software development, repository management, documentation, real-time collaboration, project management, resource management, automation, and the controlled use of artificial intelligence. These capabilities are not separate products. They are parts of one environment that shares a single workspace, a single identity and a single working context.

In day-to-day project work, teams often rely on multiple tools and platforms: documents are stored in one place, source code is managed elsewhere, while tasks and discussions are handled through separate applications. AI-based assistance is often provided through yet another set of tools. This fragmentation makes it difficult to maintain a clear overview of the project and requires users to constantly switch between different applications and contexts. Over time, information can become scattered, duplicated, or difficult to connect, while identifying the correct or most up-to-date version of a resource can become a challenge. AssistOS is designed to address this challenge by bringing project activities and resources together within a single digital workspace. It provides a shared environment where users can manage and access documents, files, source code, tasks, discussions, and AI-assisted tools without losing the context of the project when moving from one activity to another.

The central idea behind AssistOS is to make the project itself the common point of reference for all these activities. Relevant information remains connected, the results produced through one activity can be easily carried forward into the next, and the current state of the project remains visible and accessible within the same environment. This supports a more coherent, transparent, and traceable way of working, while reducing the time spent switching between different tools and facilitating collaboration among team members. Through this approach, AssistOS goes beyond simply bringing multiple functionalities into a single application. Its purpose is to provide an integrated working environment in which the information, activities, and tools used throughout a project remain connected, contextualised, and relevant across the entire workflow.

Explorer is the primary access point of AssistOS. Users begin in Explorer, navigate the workspace and select the file, folder or repository they intend to work with. That selection provides the context for everything that follows: the appropriate editor opens, repository controls become available, a collaboration session can be started, confidential resources can be requested, and an assistant can be engaged with the selected location as its working context. Explorer therefore provides both the map of the workspace and the entry point to the components that act on it.

A defining characteristic of AssistOS is that the shared workspace experience is separated from the protected state that each capability owns. Every capability belongs to a component responsible for its own data, permissions and operations. Explorer presents these components together without weakening those boundaries, and each component verifies the identity of the caller and the applicable policy before performing a protected action. This is what allows people and software agents to work on the same material under the same rules, without exposing credentials or protected data.

This manual introduces AssistOS, explains its role within Achilles IDE, and describes the practical challenges it is designed to address. It also provides guidance on how users can use AssistOS components in their day-to-day activities and how these components support the overall project workflow. Each component is described through the work it supports and its connections to the other tools. In this way, the manual provides a clear overview of how AssistOS brings tools, information, and project activities together within a coherent and integrated working environment.

2. Introduction

This manual is the reference document for users of the AssistOS environment. It is intended for the members of a project team who work with files, source code, specifications, documents, repositories and collaborative activities, and for the administrators who configure and monitor the workspace. This includes developers, reviewers, testers, analysts, technical writers and project coordinators, as well as the operators responsible for the day-to-day administration of an installation. The manual assumes that the reader has been granted access to a workspace and has a basic familiarity with files, folders and project repositories; it does not assume knowledge of the underlying runtime.

The Achilles IDE project develops and operates a workspace in which people and software agents work together on the same material. The project requires more than a file browser: it requires a place where the current state of the project is visible, where every participant acts with the same context, and where specialised capabilities can be reached without leaving the working environment. AssistOS is that place. Without it, a team faces a recurring set of practical difficulties. A resource is edited in one application and reviewed in another, so the two are never certain to refer to the same version. A repository is inspected through one interface and its documentation through another, so the relationship between code and documentation is lost. A decision is taken in a discussion service that leaves no trace in the project. An assistant that is not connected to the project answers with generic information or with a version of the project that it cannot verify. Each difficulty has the same root cause: the tools do not share a workspace, and therefore do not share context.

AssistOS addresses these difficulties by providing a single environment in which the project material is organised, reachable and kept consistent. It organises the project as a navigable workspace, so that its material has one discoverable structure. It connects repositories to the workspace, so that source and documentation are developed and synchronised from the same surface. It keeps documentation close to the code it describes. It provides collaborative working sessions, so that discussion and joint work take place beside the material they concern, and it supports the planning of work through backlogs and tasks that remain associated with the project. It manages the extensible resources of the environment, including the agents, repositories and skills that add capabilities, and it supports the automation of repeatable activities. Finally, it integrates artificial-intelligence assistance in a controlled manner, so that assistance is grounded in the selected project context and is subject to the same identity and permission rules as any other operation.

To the user, AssistOS behaves as a single application: the workspace is presented once, the user signs in once, the current location is preserved while the user moves between activities, and the result of each activity appears in the same place. Internally the environment is composed of a shared surface and a set of specialised components. The shared surface is Explorer. The specialised components provide the capabilities that act on the workspace, each according to its own domain and under its own authorization. The sixteen components are documented in Chapter 3; they are described individually there, but they are designed and used as parts of the same environment.

The components are organised into four logical groups, and the functional relationships that matter for understanding how a user works with the environment are presented below. The first group, Workspace and Development, contains the components that allow a user to see and change the project material: Explorer, Git, the Code Editors and the MD Editors. This group is the foundation of the environment, because every other activity begins by selecting something in the workspace. The second group, AI and Automation, contains Copilot, Marketplace, RoboTeam, Observability, Live Sessions, Soul Gateway and Local LLMs, which provide context-aware assistance, manage extensible resources and specialised robots, track workflows, and provide access to model providers. The third group, Collaboration and Project Management, contains WebMeet and the Backlog, which provide real-time collaboration and the organisation of planned work. The fourth group, Security and Administration, contains the DPU Agent Confidential, Settings and the Workspace Monitor, which own confidential resources, configuration and monitoring, and thereby establish the boundaries within which all other activity takes place.

3.1 Explorer

3.1.1 Access and Initial Use

Explorer provides users with a single place from which they can navigate through the entire workspace. In AssistOS, a project is organised as a workspace that brings together directories, source code repositories, documentation, generated materials, and other resources used by the team. Explorer brings these resources into one working environment and passes each operation to the component that handles it. Interaction with the workspace is primarily based on selection. The user selects a file, directory, or another resource, and that selection becomes the starting point for the next action. For example, a file is opened using the appropriate editor, an AI assistant can use the selected directory as its working context, and a terminal can be opened directly in the selected location. Similarly, operations such as repository synchronisation, activity planning, or access to confidential resources start from the context selected by the user. This approach makes Explorer the main entry point to AssistOS. Users can start their work from the workspace and return to the same environment to access the results of activities performed through the other components. Since the workspace may contain project information and resources, access to AssistOS is controlled through authentication. To enter the working environment, users access the Sign in page and must use an account with the permissions required for the relevant workspace. The sign-in page displays the authentication methods available for the particular installation. When Google authentication is configured, users can use it as an access method. Depending on the configuration, users can also sign in using their email address and the authentication method associated with their account, such as a password, an email verification code, a passkey, or an authenticator application. On an unclaimed installation, the first completed account setup becomes the administrator. This can be a completed Google sign-in, an email signup, or the initial-password path. For the initial-password path, enter the intended administrator email, select Next, and enter the literal password admin on the password screen. That password becomes the account's own password and should be changed in My Account after signing in. Later self-registered accounts do not receive Explorer access automatically; an administrator grants it by assigning the user role.

Figure 2. Explorer — Sign in page.

Since a user's permissions determine which components and operations are available, the workspace may provide different capabilities for different accounts. A regular user works with project materials, while an administrator also has access to the administration and monitoring interfaces. Administrator-only entries such as Local LLMs, Soul Gateway management and Workspace Monitor appear for accounts with that role. The operations available in Explorer depend on the workspace configuration and the permissions assigned to the account. Explorer never extends access beyond what has been granted. The workspace root also acts as a default security boundary: standard file system operations are validated against the permitted roots for each request, and paths outside these locations are rejected. A session should be explicitly closed both to protect project materials and to ensure that protected resources are properly released. The account control on the right side of the toolbar opens the account menu, which provides account-level operations: Settings, Logout, and Workspace Monitor. Settings opens the account and workspace configuration, while Workspace Monitor opens the administration monitoring interface. Both are described in their respective component subsections in this chapter and are accessed through this menu because they concern the workspace as a whole.

Figure 3. Explorer — Account menu.

Selecting Logout begins an orderly end to the session. Explorer asks the user to confirm the action so that a session is not terminated by accident; confirming it signs the user out and terminates the information associated with the active session. This confirmation step exists because an accidental logout would interrupt work in progress and discard the context of the current location.

Figure 4. Explorer — Sign-out confirmation.

Once the session has ended, the confirmed state is displayed and the user can sign in again. Ending a session promptly is recommended whenever the user finishes work or leaves the workstation, because an open session allows anyone with access to the browser to act with the user's permissions.

Figure 5. Explorer — Signed-out page.

When a session expires, Explorer returns to the Sign in page while preserving the current location. This allows the user to continue working from the same location after signing in again. To start a session, the user opens the workspace address provided for the installation in a supported browser. On the Sign in page, the user can select Sign in with Google, if this option is available, or enter the email address associated with the account and select Next. The user then completes the authentication method available for the account, which may be a password, a code sent to the registered email address, a passkey, or a code generated by an authenticator application. After successful authentication, Explorer opens the requested workspace destination, or the workspace root when no destination was requested, and the components available to the account become accessible.

3.1.2 User Interface

After a successful sign-in the user is presented with the main Explorer interface. The interface is organised so that the user always sees both the structure of the workspace and the content of the current selection. The current location is displayed as a path at the top left. A toolbar spans the top of the workspace and gives access to navigation, resource creation, search and the integrated components. Below the toolbar, the navigation pane on the left presents the directory and file tree of the active workspace, while the working area on the right presents the content of the selected resource. Until something is selected, the working area indicates that a file must be chosen to display its contents.

Figure 6. Explorer — Home Screen.

The toolbar is the principal control surface of Explorer, and its controls are arranged from left to right so that the interface can be read in the same order. The Up and Refresh controls move within the workspace and reload the displayed tree and content. Upload copies files from the local machine into the current directory. The New menu creates workspace content and offers to create a folder, create a file, add a new repository and clone an existing repository; its operations are described in Section 3.1.3. The Tools menu groups the project-level functions Copilot, Tasks, DPU Research and Builder. Copilot opens assistant access in the context of the current location, Tasks provides the entry point to the project's backlogs and tasks, DPU Research opens the research assistant, and Builder runs project build processes and presents their logs, variables and results.

Figure 7. Explorer — Tools menu showing DPU Research.

Select Tools and then DPU Research to open the research assistant in a new browser tab. You can describe the data you need in everyday language, ask it to search the research sources available to your workspace, and compare results. For example, you might ask for a dataset on a topic and then ask how two results differ in access conditions, licence or origin. You can open the chat even when Research Data has no items yet.

The assistant works with the account you used to sign in, so it only returns information and performs actions that account is allowed to access. The available search sources depend on what a workspace administrator has configured. When you find a resource you want to use, open Confidential and then Research Data to inspect its details and available actions. A resource may offer access requests or acquisition before its files can be used. If an action asks for confirmation, read the information shown before continuing; jobs started through DPU can be followed under Confidential and then Jobs.

Find/Replace in files opens the search and replacement capability described in Section 3.1.5, and the Filter specs (.md) control restricts the displayed material to Markdown specification documents.

To the right of the search controls, the toolbar presents the integrated components. Git manages the selected repository and its synchronisation, Marketplace installs and manages the visible agents and repositories that extend the workspace, Soul Gateway provides access to the AI model providers, WebMeet opens real-time collaboration, and RoboTeam opens the specialised robots, Observability shows workflow activity and questions that need a response, and Live Sessions shows agent runs as they happen. Further to the right are the Confidential entry, which opens the confidential-resource area governed by the DPU Agent, and Help, which opens the contextual guide described in Section 3.1.5. At the far right, the account control opens the account menu described in Section 3.1.1, which provides Settings, Logout and Workspace Monitor.

Explorer organises the workspace as a hierarchical structure similar to a file system. Users navigate through this structure by selecting folders in the navigation panel and using the toolbar controls. Selecting a folder opens it and updates the path, allowing users to see their current location at all times. Selecting a file opens its contents in the working area using the view appropriate for its type. The Up control returns to the parent directory, while Refresh reloads the workspace tree and the displayed content so that changes made by other participants or components become visible. When the page is reloaded, Explorer restores the workspace tree and opens the ancestor folders of the location specified in the address, while keeping the other workspace folders visible. This allows a specific file or directory to be shared or revisited directly and makes it possible to recover the user's position after a page reload or a new session.

The workspace root defines the boundary for regular navigation. Since source repositories, documentation, and generated materials are all contained within the workspace, users can access the entire project without leaving Explorer. Locations managed by another component, such as the Confidential area, are displayed as part of the same structure but are treated as virtual resources. Selecting such a location displays the material authorised by the owning component, while the available operations follow the rules defined by that component. If a requested path no longer exists or cannot be loaded, Explorer returns to the workspace root. The conditions that may occur during workspace navigation are described in Section 3.1.6. Each file and folder in the navigation panel also has a context menu, accessed through the More Options control displayed next to the corresponding entry. The menu provides the operations available for the selected resource and is described in Section 3.1.3. The available controls and menu options are not fixed. They depend on the components enabled for the workspace, the installation configuration, and the permissions assigned to the account. A control that is not available is either hidden or displayed as disabled, while the underlying operation remains subject to authorisation by the component that owns the resource.

The New menu allows users to create resources in the current directory and provides options to create a folder, create a file, add a new repository, or clone an existing repository. The available options adapt to the selected location. For example, in the Confidential area used for managing secrets, the option to create a file is replaced with an option to create a secret. 3.1.4 Documents

The main purpose of the workspace is to allow users to access and modify project materials. Since these materials can have different formats and purposes, Explorer automatically selects the appropriate view for the resource being opened. Text files, source code, and configuration files are opened in the general editor, which also provides syntax highlighting. Markdown documents are opened in the dedicated editor, while media files are displayed using a preview adapted to their content type. Office documents and PDF files are handled through the dedicated integration, while confidential documents are managed through DPU Agent. The general editor and the dedicated Markdown editor provide the two available views for a text resource.

Figure 11. Explorer — Viewing a file in the built-in editor.

Structured workflows are also available for Markdown documents when required. A regular Markdown document is edited directly as text and remains a standard Markdown file. For documents that require additional elements, such as metadata, document nodes, commands, variables, or references, users can explicitly access the structured document workflow. This separation keeps the editing process simple for regular documents while providing advanced functionality when needed. The advanced editing workflow is described in Section 3.7.4.

Figure 12. Explorer — Editing a file with unsaved changes.

Editing follows the same principle across these views. When a user modifies a document, Explorer marks the resource as changed and provides options to save or discard the modifications. When the changes are saved, they are passed to the mechanism appropriate for the resource type. Regular text files are saved through Explorer's file system mechanism, collaborative Markdown documents are saved through the workspace collaboration mechanism, while confidential materials are saved through DPU Agent.

Automatic saving can be enabled from Settings. It is disabled by default and, when enabled, uses a configurable inactivity interval. To prevent changes from being lost or another user's work from being overwritten, Explorer checks whether the file has been modified in the meantime. If an external modification is detected, saving is blocked and Explorer alerts the user to the external change.

Office documents, including text documents, spreadsheets, presentations, and PDF files, open through the OnlyOffice integration. When this integration is configured, opening such a document starts an editing session for the selected file. The changes are then saved in the same workspace or in the Confidential area, as applicable. In this way, Office documents remain part of the project and can be accessed from the same environment without requiring users to download and edit them outside the workspace.

OnlyOffice is an optional component that can be enabled by an administrator from the Marketplace, together with the services required for co-editing, callbacks, and document saving. If the integration is not enabled, Office documents are not opened through an integrated editor. The component is described in this section because users access this functionality by selecting a document in Explorer, even though the configuration and management of editing sessions are handled by the dedicated document editing component.

Explorer also includes mechanisms to protect the integrity of project materials. If a file is modified on disk after the user has started editing it, the user is notified and must reload the file before being allowed to save it again. This prevents changes made by another participant from being overwritten without warning.

For files opened in view-only mode, Explorer keeps the current preview and updates it when the file changes, allowing the user to see the latest available version. For files that are too large to be safely edited in the browser, the editing option is restricted and the user is informed that the file must be opened locally. Similarly, resources that are available only for reading, such as certain history files, cannot be modified. Messages and situations that may occur when opening, previewing, or editing files are described in Section 3.1.6.

3.1.5 Search and Help Tools

As a project grows, locating a resource by browsing becomes impractical, and users need to find material by name or by content and, when maintaining documentation or code, to change it consistently. Explorer provides two complementary search capabilities for this purpose. The first finds files and folders by name. The user opens the search dialog on the Find file view types at least two characters of the name and receives matching paths; selecting a result navigates directly to that location. Comma-separated patterns can be excluded from the results, which allows common sources of noise to be removed from large workspaces. This view is the fastest way to reach a known artefact.

Figure 13. Explorer — Find file view of the search dialog.

The second capability finds and replaces text inside files. The user opens the Find/Replace in files view enters the text to locate and, where required, the replacement text, and can enable case-sensitive, regular-expression or whole-word matching. The search can be limited to a base path, and files can be excluded through patterns. Results retain their file, line, column and surrounding context so that the user can review matches before acting on them. The capability can then replace only the matches the user has selected, or apply the replacement to the whole scope. Because a large replacement affects many files at once, Explorer warns when the visible results are truncated and requires confirmation before a wide change is applied; changed files are refreshed afterwards and any partial failure or timeout remains visible in the result summary. 3.2 Git

3.2.1 Purpose and Access

The project's source code and documentation are stored in remote repositories, while the workspace provides the environment from which they are accessed and used. The Git component allows users to check the status of repositories, record changes, and synchronise them with their remote source without leaving AssistOS or directly using version control commands. At the same time, the component plays an important role in defining responsibilities and protecting sensitive information: the shared workspace does not execute Git commands directly and does not handle user credentials itself.

Explorer passes the user's intent based on the location selected in the workspace and displays the result of the operation, while the Git agent validates the repository involved, manages the required credentials, and executes commands only within the approved workspace paths. This separation keeps repository operations controlled and auditable and reduces the risk of credentials being exposed through the browser state or Git metadata.

The Git component is accessed from the Explorer toolbar, described in Section 3.1.2. Selecting Git opens the Git Management window, which lists the repositories configured in the workspace and displays their current status. Repository authentication, configuration, and synchronisation operations are performed from this window. Since Git operations apply to repositories, the Git Management window shows those available in the workspace regardless of the file selected in Explorer.

3.2.2 Authentication

Remote operations such as push and pull require an authenticated identity. The Git component supports two methods, selected on the Authentication tab: signing in with a GitHub account, or providing a Personal Access Token generated on the Git platform in use. The credentials are delegated to the workspace secret store, where they remain protected and available for later operations.

For GitHub sign-in, selecting the GitHub method displays a unique authentication code and a control that copies the code and opens GitHub. The user completes the sign-in in GitHub, after which the component can access the repositories for which the account has permission.

Users can select Disconnect at any time to end the active connection to the GitHub account. The saved credential stays available for a later connection. Select Clear stored credentials when you also want to remove it from the application.

Figure 17. Git — Connected GitHub account and disconnect controls.

For token authentication, selecting the Token method presents a field for the Personal Access Token. An existing token is displayed in masked form: leaving the field unchanged keeps the stored token, while entering a new value and saving replaces it for all subsequent operations. 3.3 WebMeet

3.3.1 WebMeet in the Workspace

WebMeet provides a dedicated environment for conducting and managing online meetings. In addition to audio and video communication, a meeting may include participant authentication, guest access, screen sharing, chat, shared resources, collaborative notes, and shared visual workspaces. To keep these activities separate from the general workspace functionality, WebMeet manages the state and lifecycle of meetings within a dedicated environment. Explorer provides the entry point to WebMeet and hosts its interface, while WebMeet and its supporting services manage meeting rooms, participants, state synchronisation, audio and video communication, and shared resources. The workspace media service handles the transport of audio, video, screen sharing, and presence information, while WebMeet manages the persistent meeting data and the access rules associated with each room.

WebMeet is accessed from the Explorer toolbar, described in Section 3.1.2. Selecting WebMeet opens the meeting management interface in a new browser tab. Authenticated users can view the meeting rooms they are authorised to access. From this interface, users can join an existing room, create a new room, or open a room using its unique meeting link.

Users who are not authenticated can join a meeting as guests using the room's public link. Before joining, they must provide a display name, which is visible to the other participants. Guest access is limited to the room associated with the link. Having the room link does not provide access to other rooms or grant administrative rights over the room.

Figure 25. WebMeet — Meeting rooms.

3.3.2 Meeting Rooms

Creating a room sets up a new collaboration space. The user selects the option to create a new room and, in the dialog, chooses the room type and provides a title. WebMeet distinguishes two types: a team room, intended for workspace members and accessible only to them, and a public meeting, reachable through a meeting link that may be shared with invited participants. After the room is created it appears in the list and can be joined or shared according to its type.

Figure 26. WebMeet — Create New Room dialog.

A room can be joined from the list or through its link; authenticated users join with their account identity, while guests provide a display name. Administrators of a room additionally reach its settings, which are organised into tabs. The General tab allows the room name to be changed and shows the room link, which can be copied and shared.

Figure 27. WebMeet — Room settings, General tab.

The Lifecycle tab allows users with the appropriate permissions to manage the status of a meeting room. A room can be archived when it is no longer intended for regular use. Archiving does not remove the room or its content. Instead, the room and its resources are kept but are no longer available to regular users or guests. Archived rooms can only be accessed and managed by administrators. If a meeting is still in progress when the room is archived, the connected participants are notified that the meeting has ended and their sessions are closed. A room can also be deleted when it is no longer needed. Unlike archiving, deletion permanently removes the room and its content and cannot be reversed. Participants who are connected at the time of deletion are notified that the meeting has ended and their sessions are closed.

The assistants operate within the permissions of the meeting room and use the operations available to participants. They do not have unrestricted access to the room or to workspace files, which ensures that their actions remain within the same access rules as the meeting participants. 3.3.6 The Blackboard

The Blackboard provides a shared visual workspace within a meeting room. It allows participants to organise and develop ideas visually during the discussion. A Blackboard can contain text, cards, shapes, images, files, embedded content, polls, bullet lists, connectors, and groups. These elements can be arranged across multiple named boards. Documents can also be attached to a Blackboard, making structured content created in the workspace available during the meeting.

WebMeet manages the Blackboard and its access permissions, while Explorer provides the interface for displaying and interacting with it. Workspace files remain managed by Explorer, which also maintains the canonical version of any structured document attached to the Blackboard.

The Blackboard is available during the meeting and is shared by all participants. The active board is synchronised across the room, so participants see the same board and move between boards together. Each participant can also open a personal preview showing all available boards. Because the Blackboard is part of the meeting room, its content is retained with the room. The board is stored in the room's encrypted data and remains available when the room is opened again. It is permanently removed only when the meeting room itself is deleted

The room's assistant can use the same authorised operations, as configured in Section 3.3.3, ensuring that activities such as note-taking and visual organisation follow the same room permissions.

An attached structured document remains a workspace document, with its collaborative state managed by Explorer and its content presented on the board. A group of widgets can be exported as an image when it contains at least two widgets and has finished rendering. The resulting image can then be shared or stored.

3.4 Marketplace

3.4.1 Purpose and Access

The Marketplace provides a central place for managing the agents available in AssistOS and the repositories from which they are obtained. It allows users to view the installed agents, check their current status, change their configuration or availability, and manage the repositories that provide them.

The Marketplace keeps the relationship between agents and repositories clear: each agent listed in the Agents section is provided by one of the installed repositories. When a repository is added or removed, the list of available agents is updated accordingly. The Marketplace is accessed from the Explorer toolbar, described in Section 3.1.2. The interface is organised into two sections: Agents and Repos. A search field at the top of the window can be used to filter agents and repositories by name.

The available actions depend on the user's permissions. Administrators can install or remove repositories and enable or disable agents, while other users can view and use the agents available to them according to their access rights.

3.4.2 Agents

The Agents section lists the installed agents grouped by the repository from which they were installed, so that agents with a common origin are easy to identify. Each entry shows the agent name, its current status, a short description and its availability level. An agent reported as Running is enabled and available for its configured functions. Other reported states include Disabled, Starting up, Stopped, Failed, Paused and Unknown. The list refreshes while the Marketplace is open. Where an agent offers configuration, the Configure control opens its settings only after the agent is verified as Running, so that agent-specific values can be reviewed or changed. Where an agent is no longer required, it can be disabled, after which it remains installed but is not used until it is enabled again.

Figure 42. Marketplace — Agents.

3.4.3 Repositories

In the Repos section, users can add and manage the repositories used to provide agents and other components. To add a repository, the user enters its Git address and can optionally provide a name and select the branch from which the content should be retrieved. The repository can then be installed using the Install action.

To keep the list easy to navigate, installed repositories are grouped into Agent Repos and Others. Skill repositories and skill entries do not appear in Marketplace; the separate skills controls manage those resources.

Each repository entry shows its name, a short description, and information about what will be affected if the repository is removed. For example, the Marketplace indicates how many agents would also be removed. This gives the user the information needed to understand the consequences before confirming the operation.

An installed repository can be uninstalled when it is no longer needed. Its agents are removed at the same time and are no longer available in the Marketplace. Repositories that have not been installed provide an Install action instead. Before removing a repository, users should also check whether any of their projects rely on the agents it provides.

3.5 Copilot

3.5.1 Purpose and Access

Achilles Copilot is an intelligent assistant integrated into the workspace that helps administrators configure and manage websites powered by WebAssist. Its purpose is to make administrative work possible through natural language, so that a user who understands the website does not also need to remember the underlying commands or the internal structure of the platform. Its capabilities are extended through skills: reusable components that provide the assistant with the knowledge and instructions required to perform specific tasks. Based on the request, the assistant identifies the appropriate skills and uses them to produce a response or perform an operation. Copilot is launched from Explorer, where the selected folder becomes the active workspace for the session and is used for all the operations the assistant performs.

Figure 43. Copilot interface

It is used through the WebChat interface: after signing in, an administrator starts a conversation in natural language and requests an administrative operation, and the assistant interprets the request, identifies the required skills and executes the appropriate actions. The relationship with the workspace is therefore the same as elsewhere in AssistOS: the selection supplies the context, and the assistant acts within it.

3.5.2 The Achilles CLI Interface

The Copilot interface is organised around the active workspace and the conversation with the assistant. The top bar displays the agent name and its current status. An online indicator shows when the service is available, while the centre of the bar displays the path of the workspace currently used for the session. The main area contains the conversation between the administrator and Copilot. When a request is being processed, a status indicator shows that Copilot is working on the request before returning a response. At the bottom of the interface, the input field can be used to enter requests in natural language. It also accepts the commands described in Section 3.5.4, allowing the administrator to use either natural-language requests or the available CLI commands depending on the task.

3.5.3 Skills and Repositories

The workspace contains the resources the assistant uses: skills, documentation, configuration files, knowledge bases and other material required for it to operate. All operations performed through the interface are restricted to the active workspace, which provides a controlled environment for project administration. Skills are reusable components that extend the assistant: each contains the instructions, documentation and files required for a specific task, and administrators can create, modify, generate code for and test them directly from the interface.

Figure 44. Copilot workspace

Repositories that contain skills and agents can be added from the prompt. Once a repository has been added, it becomes available in the suggested repositories of the directory's manifest; the user selects the folder containing the manifest in Explorer, opens the manifest, and the repository can then be chosen as a source for the corresponding skills or agents. After changing skills or their documentation, the recommended step is to rebuild them so that the generated components are refreshed.

3.7.1 Purpose and Access

Markdown is the format in which much of the project's documentation and structured material is written, so the workspace must allow it to be both read as rendered content and changed as source.

Figure 56. MD Editor — Edit mode.

Figure 63. SCRIPTA Variants — adding a variant.

The counts beside the controls show the current votes. When available to the viewer, Show voters lists the participants behind the likes and dislikes.

The editor selects it from the votes: the highest likes-minus-dislikes score wins; ties favor more likes, then fewer dislikes, then the earlier variant. The active selection is recalculated after variant and reaction changes.

3.14 Code Editor

3.14.1 Purpose and Access

Source code must be created and changed in the same environment in which the rest of the project is managed, so that it is edited with the project context and saved through the same workspace contract. The Code Editor provides an integrated environment for creating and modifying text and source files directly in the platform. It applies syntax highlighting to JavaScript, JSON, HTML and CSS files and opens other text files as plain text, and it provides editing, code navigation and previewing of web content. Markdown documents are handled by the dedicated editor described in Section 3.7. The Code Editor is reached by opening a supported file in Explorer, as described in Section 3.1.4.

3.14.2 Editing Source Code

When a text file is opened, its contents are displayed in the editor area. The file is shown first in a read-only preview; selecting Edit enables editing and replaces the edit control with Save and Cancel. The editor applies syntax highlighting according to the selected file type, so that keywords, identifiers, strings, comments and the other supported elements are shown in different colours and the code is easier to read and navigate. Line numbers are displayed alongside the source code to provide a reference for identifying lines and discussing changes, and the existing indentation and formatting are preserved while the file is modified.

The Wrap control toggles line wrapping, and pressing Tab inserts two spaces at the cursor. Where a keyboard shortcut for it is configured, the editor can request a completion from the language model at the cursor position. While a file has unsaved changes, the editor marks the document as changed. A very large file is opened as a read-only preview with editing disabled, so that the interface remains responsive.

Figure 99. Code Editor — Editing a source file.

3.14.3 Viewing Modes

For HTML files the preview provides three viewing modes, selected from the controls in the preview header and switchable without closing the document. In Code mode the source code is displayed directly and can be edited. In Web View mode the document is displayed as a rendered web page so you can check the result; the preview can be updated with the Refresh control. In Split mode the source code and the rendered page are displayed at the same time, so that the source can be modified while its result is visible. In split mode the code pane and the preview pane are resized with the divider between them, the preview can be refreshed, and the preview pane can be closed without closing the edited document. The selected file can be opened in a new browser tab with the Open in new tab control in the Explorer toolbar.

3.14.4 Saving and Cancelling Changes

After a source file has been changed, the Save control stores the updated content through the workspace contract, while the Cancel control discards the unsaved changes and returns the file to its preview without applying them. HTML files can be edited in any viewing mode, so the user can move between the source, the rendered page and both at once, save or cancel, and continue working without closing the document. If the file is changed outside the editor while it is open, the editor reports the external change so that the latest version can be reloaded before editing continues.

3.14.5 Error Messages

The Code Editor reports problems through the messages documented in Section 3.1.6 under documents and editing, including failures to load, save or refresh the file and the warning raised when a file is modified externally.

3.15 Soul Gateway

3.15.1 Purpose and Access

The artificial-intelligence components of AssistOS need access to language models and services, and that access must be configured, controlled and monitored rather than left to each component. Soul Gateway is the central component that allows administrators to manage and use the language models and services available in the platform: it configures providers, manages the available models, organises models into tiers, and monitors system activity. It provides a single point from which the configuration required to use models in compatible applications can be managed, and from which problems during request processing can be identified. The management interface requires a Ploinky administrator session and is opened from Settings. Its sections are presented in a navigation bar and include Providers, Models, Tiers, Keys, Logs, Errors, Activity, Usage, Blacklist, Middlewares and Export.

3.15.2 Providers, Models and Tiers

A new installation does not include a local language model. Soul Gateway initially provides a restricted free OpenRouter provider for the fast, code, plan, write, deep, ultra and web-assist tiers. It needs an internet connection, and the bundled credential has a daily quota shared across installations. An administrator can replace that credential in Soul Gateway settings. OpenCode free models may also be available if an administrator enables the optional provider. They are not assigned to a tier automatically and support plain-text chat without tools or images.

The Providers section reviews and manages the providers available in Soul Gateway. The list can be filtered, and each provider shows its name, display name, base address, adapter, authentication strategy, pipeline membership and enabled status. A provider is enabled or disabled with its toggle, and the actions on each row allow it to be edited or deleted and to be tested and synchronised, so that its models are refreshed from the provider. A new provider is added with the Add Provider control; once the required information has been saved, it appears in the list and can be managed from the same section.

Figure 100. Soul Gateway — Providers.

The Models section lists the models available in Soul Gateway. The list can be searched and filtered by enabled state, by whether the model is free, by billing type and by tag, and a new model is added with Add Model.

Figure 101. Soul Gateway — Models.

The Tiers section defines the cascades used to serve a request. A tier has a key, a display name, an ordered list of child models, a maximum number of attempts and an enabled status; a request that uses the tier tries its child models in order until one answers. A tier is created with Add Tier, and an existing tier can be edited, enabled or disabled, or deleted. Because a tier may be referenced by other configurations, it should be checked before it is deleted.

The Keys section lists API keys for users and agents. The list shows each key's label, type, masked key hint, daily budget and spending, requests-per-minute limit (RPM), last use, creation date and status. Select Create user key to issue a key for a user. Enter the owner and key name, then set any limits, budgets or expiry. Copy the full key when it appears; Soul Gateway shows it only at creation. Soul Gateway generates the configuration, which is displayed for review and can be copied or downloaded for later use.

4. Conclusions

AssistOS addresses a problem that project teams recognise immediately: work is spread across many tools, and every movement between them loses context. The environment documented in this manual answers that problem by making the workspace the shared frame of reference. Files, source code, documentation, repositories, collaborative sessions, planned work, extensible resources, automation and artificial intelligence are all reached from the same place, under the same identity and with the same working context. This shared view helps teams move through project work with fewer context switches.

Explorer is the constant of the environment. It is where the user begins, where the material of the project is visible, and where the other components are reached. Its selection-based model is what makes the other capabilities usable without restating the task: the editor opens for the selected file, the repository controls apply to the selected location, the assistant works in the selected directory, and the confidential, collaborative and planning surfaces open around the selected resource. Every component is reached at the point in the user's activity where it becomes useful.

The components themselves are documented as parts of one environment because that is how they are used. Git keeps the project synchronised; the Markdown editors support SCRIPTA paragraph variants and voting; the Code Editor changes source files; the DPU Agent protects confidential resources; WebMeet and the Backlog support collaboration and planning; the Marketplace extends the environment; RoboTeam automates workspace tasks; Observability tracks running and completed workflows; Live Sessions shows agent work as it happens; Copilot, Local LLMs and Soul Gateway bring artificial intelligence into it under control; and Settings and the Workspace Monitor configure and observe the whole.

A second idea runs through the manual: the shared surface is separate from the protected state that each capability owns. Explorer presents the components without taking over their responsibilities, and each component verifies the identity of the caller and the applicable policy before acting. This separation is what allows people and software agents to work on the same material with the same rules, and it is the reason the environment can be extended without weakening its boundaries.

The documentation follows the same principle. Each component states why it exists, which problem it solves and how it is used, and the messages that can appear are documented in the subsection of the component to which they belong. Figures and tables are numbered and referenced so that the manual can be navigated as a reference as well as read as a whole.

AssistOS continues to evolve, and further components and capabilities will be documented in later revisions of this manual, following the structure established here. The objective remains the same: to give a project team one controlled, authenticated workspace in which the work of people and agents is visible, connected and accountable.
