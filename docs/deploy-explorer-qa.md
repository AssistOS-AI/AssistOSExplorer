# Deploy Explorer QA with Ploinky Box

Deployment is operator-controlled. Codex sessions are authorized operators when
the user's task selects the target deployment operation. They may invoke the
tracked GitHub Actions deployment workflows with `gh` or use direct SSH,
Ploinky CLI, container, registry, Cloudflare, DNS, and other remote operations
needed to complete that selected task.

This repository deploys only Explorer QA (`explorer-qa.axiologic.dev`). The
former `skills.axiologic.dev` production deployment and its
`deploy-skills-explorer.yml` and `destroy-explorer.yml` workflows were removed
on 2026-10-20, when its host was reinstalled.

The tracked Ploinky-command workflows `deploy-explorer-qa-ploinky.yml` and `destroy-explorer-qa-ploinky.yml`, the product workflows described under "Product workflows" and `cleanup-explorer-qa-images.yml` (see "Image cleanup") are the supported execution channels. Before dispatch, inspect the workflow at the requested revision and verify its exact inputs, target guards, credentials, branch selection, and fallback behavior against the user's requirements. A workflow name or historical successful run is not evidence that its current implementation satisfies those requirements. If an explicit request forbids `--branch-fallback`, do not dispatch a workflow that injects that option; use an authorized direct channel or update and verify the workflow first.

Explorer QA has five tracked workflows. `deploy-explorer-qa-ploinky.yml` and `destroy-explorer-qa-ploinky.yml` deploy and destroy the Box through Ploinky commands (see "Ploinky-command workflows"). `deploy-explorer-qa-bizanso.yml` and `deploy-explorer-qa-scriptahub.yml` update one product each inside the running Box (see "Product workflows"). `cleanup-explorer-qa-images.yml` removes container images that no container uses (see "Image cleanup"). All five share the concurrency group `deploy-explorer-qa` and take the host operation lock, so no two of them overlap.

The former `deploy-explorer-qa.yml` and `destroy-explorer-qa.yml` workflows changed the host and the workspace directly through their own helper scripts and not through Ploinky commands. They were removed on 2026-11-24, and their helpers and tests with them, so that one workflow family owns the Box. Their selection between an in-place update and a rebuild, the install marker with its crash recovery, the capacity admission, the quiesce helper, the sandboxed Git source checks and the teardown receipts no longer exist, and neither does the deploy test step that ran `tests/smoke/lib/retired-source-absence.test.mjs` on every dispatch; that test still runs through `tests/smoke/scripts/run-playwright.mjs`. The host-storage inspect and cleanup, runtime-verify, recovery and retired-source-absence workflows were removed earlier. The `/home/admin/.qa-deployment-state` directory those workflows used for the parked access policy and the install marker has no owner now (see "Recovery from the removed workflows"). Restoring a removed workflow goes through the normal reviewed and tested change process.

QA Boxes use Ploinky's same-path workspace contract. The host workspace `/home/admin/explorerQaWorkspace` is mounted read-write at that same absolute path inside the Box, is the Box working directory, and is its only `PLOINKY_WORKSPACE_ROOT`. There is no `/workspace` alias. AchillesAgentLib is not a selected repository: the Box image supplies it, and the workflows pin no AgentLib commit and do not verify it (see the table in "Ploinky-command workflows").

The default Explorer graph no longer enables Umami, WebMeet or LiveKit, and no longer installs the `legacy-agents` repository: `UmamiAgent` and `webmeet` stay in `repos` and Marketplace offers `UmamiAgent/umamiAgent` and `webmeet/webmeetAgent`, while `soplangAgent`, `tasksAgent`, `webAssist` and the other `legacy-agents` agents are neither cloned nor started, so the recursive graph has 10 tracked agents with 5 no-wait agents. The no-wait runtimes are RoboTeam, RoboWork, Soul Gateway, Workspace Monitor and `local-llms/local-llm`. RoboWork inherits no-wait execution through RoboTeam even though its own enable entry says `global`; a runtime stays blocking when any path from Explorer reaches it without a no-wait edge. Copilot runs through RoboTeam's ordinary `default` robot; the retired `AchillesCLI/achilles-cli` agent is not a dependency. The default graph excludes the external `OnlyOfficeAgent/onlyOffice` agent, `webmeetAgent`, `liveKitServerAgent`, `webmeetScribeAgent`, and `webmeetStt`; `explorer/manifest.json` installs the `OnlyOfficeAgent` repository through `repos` while leaving the agent disabled. The Ploinky-command deploy requires `running` only for a fixed list in the workflow: nine of these runtimes (all but RoboWork) and the QA products (see "Ploinky-command workflows"). Any other runtime, RoboWork included, fails the run only when `ploinky status` reports it failed. No test compares that list with the recursive graph; `explorer/tests/unit/retiredLocalModelGraph.test.js` checks the graph only for retired local-model edges. Administrators enable optional agents through Explorer Marketplace; a `legacy-agents` agent first needs its repository installed with `ploinky install repo https://github.com/AssistOS-AI/legacy-agents.git`. Meeting Secretary uses final browser SpeechRecognition transcripts and does not depend on the separate STT service.

The QA deployment workflows do not pull, start, or inspect a local model image; the retired `proxies/default-local-llm` agent is not part of the default graph. The local Soul Gateway seeds a restricted free OpenRouter provider on first start with the tiers `fast`, `code`, `plan`, `write`, `deep`, `ultra`, and `web-assist`. Its bundled credential is guarded to free models only and shares one daily quota with every installation using it, so deployments need outbound internet access for these tiers and must not rely on them as unlimited or offline capacity. Administrators replace the credential through the admin-only Soul Gateway settings dashboard. OpenCode's free models are available through the optional `legacy-agents/opencode-free` agent, which `ploinky start explorer` does not enable; its `legacy-agents` repository is not installed by default either, so to add it to a workspace run `ploinky install repo https://github.com/AssistOS-AI/legacy-agents.git` and then `ploinky enable agent legacy-agents/opencode-free` from the workspace root. The agent wraps the unmodified OpenCode CLI; once enabled, Soul Gateway discovers it like any other agent and adds it to no tier by default: plain-text chat only, no tool calls and no images, one answer per request delivered as a single chunk after several seconds, a free quota shared by every installation that uses the bundled key, and prompts subject to the free models' data-use terms. Native OpenCode execution through RoboTeam's installed OpenCode CLI is unchanged.

The `webmeet` repository supplies `webmeet/liveKitServerAgent` alongside WebMeet, and a fresh deployment starts neither: the workflows neither pull the LiveKit image nor gate on LiveKit health; Explorer installs that repository through the `repos` map of `explorer/manifest.json`. Deployment repository lists must not install a separate media-runtime repository or `basic`. LiveKit keeps its immutable image, readiness contract, `.data/liveKitServerAgent/` storage, Router signaling/private Twirp paths, and single UDP `7882` media mux. Its relocation does not change the readiness gate. The image publication workflow in `container-image-builds` must select the `liveKitServerAgent/` build context from the `webmeet` repository. Integrate that source selection and the matching Ploinky listener profile before retiring the previous runtime source.

A workspace that still has the retired media repository must move its LiveKit owner to `webmeet` before startup: disable the old runtime records and repository through Ploinky, confirm no old runtime remains in the Box's nested Podman, and keep `.data/liveKitServerAgent/` throughout. Two owners cannot share the fixed media socket.

Direct operator execution has the same authority and safety boundary. Before a
destructive or externally visible mutation, positively identify the exact host,
workspace, environment, revisions, images, and recovery state. Authorization
for QA or local deployment never authorizes production or unrelated workloads.
Never expose secret values in commands, logs, reports, or artifacts.

## Required sequence

For an explicitly requested QA reset, dispatch `destroy-explorer-qa-ploinky.yml` with `delete_data` checked and then `deploy-explorer-qa-ploinky.yml`; leave the checkbox unchecked to keep the data (see "Destroying QA"). A checked box permanently removes the QA data, so use it only when that reset has been explicitly authorized. Never prune unrelated host resources: the Ploinky-command workflows act on the QA workspace through Ploinky and remove only the unused images described under "Ploinky-command workflows" and "Image cleanup".

Before it changes anything, the Ploinky-command deploy and both product workflows install the SHA-256-pinned official Node.js 24.19.0 archive under `/home/admin/.qa-deployment-tools/` and prepend its `bin` directory only for that run. Existing installs are compared against the verified archive before execution. The shared host Node installation is unchanged. The block is the same text in the three workflows, and `tests/smoke/lib/deploy-qa-product-workflows.test.mjs` pins it byte for byte.

The Ploinky-command deploy sets UserPersisto's public OIDC issuer and allowed redirect origins for `explorer-qa.axiologic.dev` before graph startup, with `ploinky var NAME --stdin`, which stores the values encrypted. It adds the QA origin to the saved `USERPERSISTO_ALLOWED_REDIRECT_ORIGINS` value; an origin held only in the UserPersisto policy store is not merged. The preserved `.data/userPersistoAgent/persisto` snapshot retains accounts, installation ownership, and OIDC clients and keys together with the original workspace encryption identity. Authentication methods and self-registration policy are not changed. An optional repository variable, `EXPLORER_QA_USERPERSISTO_GOOGLE_CLIENT_ID`, can select the QA Google Web client; otherwise an existing client is retained. Without one, Google is unavailable instead of using the distributed localhost client.

Public deployment checks follow the Router's same-origin SSO handoff to the
sign-in wizard shell, confirm that its opening page carries no password field,
and verify OIDC discovery and its exact public issuer. They report only
ownership-complete, registration, and method-availability booleans and never
submit a sign-up or claim the first administrator.
No account is pre-created. On an unclaimed installation, enter the owner's
email, select **Next**, enter the literal password `admin`, and select **Log in**.
This creates the first administrator without email delivery or a verification
code; its email remains unverified. Google sign-in and password signup (verified
or direct) can also claim the installation first. By default **Sign up** creates
the account immediately with an unverified mailbox, so ordinary QA and local
deployments need no mail provider; setting
`USERPERSISTO_SIGNUP_EMAIL_VERIFICATION_REQUIRED=true` on an internet-facing
host restores the emailed-code flow, and **Forgot password?** needs real
delivery. The exception closes permanently after the first claim. Configure
EmailAgent delivery to verify the initial administrator's email and enable
email codes and password reset. Complete the selected owner's setup before inviting restricted users.
When upgrading a running workspace to a release that adds the EmailAgent
`email_send_password_reset` tool, restart the Router afterwards: it registers
agent tools in its tool policy only at startup, so until it restarts
**Forgot password?** answers "We could not send the email" (`502
delivery_failed`). Fresh deployments and direct sign-up are unaffected.
Subsequent public sign-ups receive `selfRegistered` and do not gain Explorer
access automatically. Automated release gates sign in and sign up through the
same screens with the smoke helper described in `tests/smoke/README.md`.

1. Keep application data and its encryption keys in place. A QA redeploy or keep-data destroy must
   retain accounts, documents, local skills, access policies and revocations.
   A requested test-workspace reset is the destroy workflow with `delete_data`
   checked and has its own explicit target.
2. Build or pull the pinned multi-architecture box and dependency images.
3. Configure either explicit local-only mode or a complete dedicated-tunnel
   Cloudflare configuration. Never create a quick tunnel. The Ploinky-command
   deploy reuses the single `explorer-qa` tunnel, creates it through the
   Cloudflare API when it is absent (for example after the destroy workflow
   deleted it), and fails if the name is ambiguous;
   it must preserve the pinned shared `proxies` tunnel and unrelated DNS,
   validate the connector credential against the selected account/tunnel,
   and keep connector and management credentials in separate encrypted handles.
4. Configure the literal public media IPv4 and external relay service.
5. Recreate the Box explicitly under the semantic Box contract.
6. Inspect the real outer container and prove its normalized bindings are
   exactly loopback Router TCP and wildcard LiveKit UDP `7882`.
7. Start the full Explorer graph and validate the topology-aware in-box
   listener gate. Loopback is `required-loopback`; a managed gateway is
   `required-assigned-managed-gateway` only when current Podman and kernel
   evidence prove assignment to the exact reported `network_interface`; an
   unassigned gateway is `inactive-unassigned-managed-gateway`, has no
   listener, and remains inactive and fail-closed.
8. While the graph remains alive, run the fixed Chromium Router/auth baseline
   below with no retry or skip.
9. Run the local Ploinky core WebTTY gate against the exact mounted workspace.
10. Revalidate outer publication and listener ownership.
11. Enable `webmeet/webmeetAgent` in global mode (Marketplace or `ploinky enable agent webmeet/webmeetAgent global`), since the default graph does not start it, then run the real-browser OnlyOffice, Umami, and WebMeet gates. The GPTResearcher gate needs the `legacy-agents` repository, which the default graph no longer installs: run it only after installing that repository for the gate (`ploinky install repo https://github.com/AssistOS-AI/legacy-agents.git`) and enabling `legacy-agents/GPTResearcher`.
12. Clean up and destroy the graph only after all graph-dependent gates finish.

The Ploinky release harness runs this exact baseline after the full graph and
listener gate succeed and before cleanup or graph destruction:

```bash
cd tests/smoke
SMOKE_BASE_URL=http://127.0.0.1:18080 npm test -- --project=chromium specs/00-router-auth.spec.mjs
```

It proves the dashboard, Explorer shell, and routed WebChat shell through
Router. This oracle is distinct from the WebMeet external-network and
ScreenShare gates below; none substitutes for another. A missing or failing
baseline is a release failure and must not be retried, skipped, or weakened.

The local Ploinky core WebTTY gate is:

```bash
cd tests/smoke
SMOKE_BASE_URL=http://127.0.0.1:18080 \
SMOKE_WORKSPACE_ROOT=/absolute/path/to/the/box/workspace \
npm run test:webtty
```

It requires the canonical local `admin` and `user` accounts and a fresh Box.
The gate exercises the local administrator browser-mutation path through the
Explorer-owned target chooser, which requires a robot choice and an
explicit Open. It proves Ploinky Box is first, checks the exact
eligible-agent rows returned for the selected folder, and opens WebTTY only
through an opaque fragment launch. It proves the selected Box or agent working
directory and bidirectional PTY behavior, closes the terminal, and creates a
second terminal through a fresh chooser discovery to prove cleanup did not
disable WebTTY. It also proves launch replay and stale-target rejection,
fragment stripping, UI omission, and page/discovery/session API `403`
responses for the ordinary user. A direct `?dir=` launch, non-loopback target,
missing workspace root, skipped case, or failed assertion is a release failure.

The WebMeet screen gate is:

```bash
cd tests/smoke
SMOKE_BASE_URL=http://127.0.0.1:8080 \
SMOKE_WEBMEET_MEDIA=1 \
SMOKE_WEBMEET_SCREEN=1 \
SMOKE_TEST_TIMEOUT_MS=240000 \
npm test -- --headed --project=chromium specs/30-webmeet-room-chat.spec.mjs
```

This command requires two distinct authenticated accounts. On Linux without a
display, the runner creates a deterministic Xvfb display. Missing accounts,
media, or real infrastructure are hard failures while the screen flag is set.
The local gate removes TURN and requires both browsers to use active non-relay
UDP `7882` pairs during each ScreenShare direction. Exact configured-public-IP
selection is intentionally reserved for the distinct-network native x64/arm64
matrix, which also rejects `7881` and private/discovered alternatives.

Cloudflare, external relay, cross-network, native x64, and native arm64 gates
must use dedicated test resources. A missing prerequisite is reported as
BLOCKED with the reproducible command; it is never treated as a pass.

An inactive managed gateway does not authorize a wider bind, forwarder, direct
target, or alternate authorization path. Ploinky DS004 Question #8 remains the
owner of any architecture change needed to activate that lane.

## Ploinky-command workflows

`deploy-explorer-qa-ploinky.yml` and `destroy-explorer-qa-ploinky.yml` target the pinned host and workspace through Ploinky commands, not through helpers that inspect or change the workspace directly. They share the `deploy-explorer-qa` concurrency group and the host lock with the product workflows and `cleanup-explorer-qa-images.yml`. They refuse to run while `/home/admin/.qa-deployment-state` holds anything, because the workflows that parked the access policy there were removed and no remaining workflow restores it (see "Recovery from the removed workflows"). The deploy runs the dedicated-tunnel, DNS and public verification steps on the runner. `deploy-explorer-qa-ploinky.yml` also prunes unused images before it changes anything and after the readiness checks: on the host only dangling ones whose name history is `docker.io/assistos/ploinky-box`; inside the Box every unused image that is dangling or whose names are all digest references (`repo@sha256:<digest>`) to `docker.io/assistos/scriptahub-agent`, `docker.io/assistos/roboteam-agent` or `docker.io/assistos/bizanso-agent`, each by `podman image rm <id>` with no force, warn-only (podman refuses an image with several names by ID, so such an image is reported and kept). A pull by digest never leaves the image it replaces dangling, so without the digest-only rule every rollout kept the superseded agent image (about 10 GB for ScriptaHub) until the disk gate stopped the next deploy. An unused Box image with any tag, such as `scriptahub-agent:runtime` or `roboteam-agent:runtime`, is kept, because a later start resolves that tag locally, and so is every other digest-pinned image, such as Ploinky's Router authority helper `docker.io/library/node@sha256:...`, which has no container between probes but must stay present. The product workflows share the same prune. It stops before anything moves when the admin home has less than 5 GiB free and warns below 10 GiB.

| Work | Command |
| --- | --- |
| Save the publication document | `ploinky edge set -` |
| Store Cloudflare and UserPersisto values | `ploinky var NAME --stdin`, with values only on SSH stdin |
| Update the repository sources | `ploinky update repo` for each installed repository except the Bizanso and CSV Mail copies and PromotionScoutV2, then a fast-forward of the RoboTeam `link-install` checkouts `AdvancedLanguageAgent` and `DocumentationSkills` at the workspace root (each only when it exists), then `ploinky restart`, on every deploy |
| Start | `ploinky --port 8097 start explorer`, first when the graph is not running and again after the publication is saved |
| Readiness | `ploinky status`, 13 of 13 runtimes ready three times in a row |
| Destroy, keeping data | `ploinky destroy` |
| Destroy, deleting data | `ploinky destroy --delete-data --confirm-workspace /home/admin/explorerQaWorkspace` |

The host work outside Ploinky is the bootstrap it cannot do for itself: the pinned Node, a Ploinky checkout at `/home/admin/.qa-deployment-tools/ploinky` and the workspace directory. The checkout lies outside the workspace because `--delete-data` refuses a checkout inside it and a Box mounts it read-only.

### Unpublished work on QA

Before the full deploy changes any source, it checks the host Ploinky checkout, the workspace repositories it may update or remove, the two link-install checkouts, and the Bizanso and CSV Mail source copies. The product deploys check their own source. A clean checkout can be behind its deployment branch. ### Cloudflare cache rules for Explorer QA

The full Ploinky deploy and the Bizanso product deploy own two zone Cache Rules for `explorer-qa.axiologic.dev`. Both rules use `set_cache_settings`. Cloudflare applies the credential bypass last so a signed-in visitor cannot receive a warm anonymous copy, including CSS and JavaScript.

**Bizanso.** The runner checks out the private Bizanso default branch with the read-only deploy key, extracts `git archive HEAD` and computes the commit, the digest-pinned `container` reference of `bizanso/manifest.json` and a tree digest of the files. The Box pulls that image by digest (the reference is validated again inside the Box), the live tree and the files that decide the reach of the change are read back, and the classifier prints the scope:

| Scope | When | Restart |
| --- | --- | --- |
| `none` | The tree digests are equal and the running container's image ID is the pulled image | None. The run makes no copy and sets no value |
| `whole` | `bizanso/manifest.json` differs outside its `container` field, or `bizanso/mcp-config.json`, `bizanso/package.json`, `package.json` or `package-lock.json` differs or exists on one side only | `ploinky restart`. A missing live or incoming `manifest.json` fails the run |
| `targeted` | Anything else, unless the tree has `deepProofArticle` (see below) | `ploinky restart bizanso/bizanso` |

The Bizanso tree is swapped in by rename, so an agent that is not restarted keeps running from the removed tree. When the live or the incoming tree has `deepProofArticle/manifest.json`, the classifier also reads that file, and any difference (tree digest, image, either manifest or a package file) gives `whole`, never `targeted`; with no difference the scope stays `none`. Neither this workflow nor `deploy-explorer-qa-ploinky.yml` enables the article agent or checks its route.

Unless the scope is `none`, the runner streams `git archive` into the Box with the same private no-git copy program as the Ploinky-command deploy (the previous copy stays at `.ploinky/.qa-private-copy/previous` until the next run), sets `BIZANSO_PUBLIC_LINK_BASE` and proves the live tree equals the source tree before restarting. There is no automatic source rollback: recover by pushing a fix or a revert to Bizanso and dispatching again.

**ScriptaHub.** The runner checks out `Axiologic/ScriptaHubAgent` with full history and resolves registry index digests for `docker.io/assistos/scriptahub-agent:runtime` and `docker.io/assistos/roboteam-agent:runtime`. The sandbox runs skill sources from the mounted checkout, and the dependencies that the image installs (npm modules, Python environments, native libraries, models, notices) are mounted read-only beside them. The image still contains the baked source tree and its source receipt, so that service code from before the change keeps working on a new image; the sandbox never executes them. The gate therefore compares a **dependency fingerprint** instead of source trees. The fingerprint (v1) is the sha256 of the header `scriptahub-dependency-fingerprint-v1\n` followed by one `<git blob id> <path>\n` line per file that `scriptahubAgent/deployment/dependency-inputs.txt` lists at a commit, in file order; the list is strictly ascending by byte, holds only plain paths and lists itself. The image build records it as the label `io.assistos.scriptahub.dependency-fingerprint`. The workflow requires on both `linux/amd64` and `linux/arm64` the revision label (40 hex), the assets image label and the fingerprint label (64 lowercase hex), each equal across platforms. An image with no fingerprint label is refused as predating mounted skill sources, and an invalid or platform-specific label is refused as invalid. The revision must be an ancestor of the selected head, and both the fingerprint computed at the image revision and the one computed at the selected head must equal the label. A change to a dependency input after the image revision (a lockfile of a skill, an installer, a file of `scriptahubAgent/deployment/` that the image build runs, or the list itself) is refused and the error names the changed inputs; a change to any other file, including skill sources, `SKILL.md`, the launchers and `reader.css`, is accepted and moves the checkout. The legacy labels `skills-tree`, `deployment-tree` and `reader-css-blob` stay published for the transition and are no longer read. The shell function that computes the fingerprint is one marked block, `# BEGIN ScriptaHub dependency fingerprint` to `# END ScriptaHub dependency fingerprint`, identical in the resolve step of both workflows, in the product read program and in the pre-restart check of the full deploy; a test pins that and runs it on a fixture whose expected value is `b46a273fb33f3535a42f1244c246494d87596d7214588d45b9bdb74877b40016`. It reads the checkout only through `git` with hooks and fsmonitor off (plus `sort` and a sha256 tool on the text), executes nothing from the checkout, and fails closed wherever the Node reference `dependency-fingerprint.mjs` of ScriptaHubAgent rejects the list: CR or a missing or doubled final newline, blank lines, duplicates, unsorted entries, a path outside `[A-Za-z0-9._-]` segments or with a `.` or `..` segment, a missing self entry, and any entry that is not a regular blob (a symlink, a directory, a submodule or an absent path). Every refusal of the gate happens in the resolve step, before the first pull, tag, merge or restart. The Box pulls both indexes by digest and restores the generic RoboTeam runtime tag. The product workflow fast-forwards a clean checkout only to the selected head, then reads the head and dependency fingerprint of the moved checkout in the Box and requires the selected head and a fingerprint equal to the label (either mismatch is a post-mutation failure; the read before the move prints an empty value for a checkout that predates the list, which no label equals), and restarts the workspace when the checkout or a running image differs. It logs `dependency fingerprint equal`. It verifies the actual image IDs for ScriptaHub, RoboTeam and RoboWork after restart. The Ploinky-command deploy runs the same resolve step and computes the fingerprint of the selected checkout again in the Box, after the repositories are updated and before the restart, and verifies the three running image IDs. The existing source lock must identify a real committed revision; publish the matching agent image before deployment. After a dependency-only change the QA deploy refuses until an image is published from a revision that carries the new fingerprint.

**Restart policy and recovery.** After a targeted Bizanso restart the run requires the product `running`, a ready graph, the three public paths alive, the container on the pulled image and started no earlier than the copy, and then keeps polling the three paths every 15 s for 6 minutes (longer than the 5-minute Box monitor and snapshot intervals); one miss counts as lost. After any whole restart the same checks and the same 6-minute dwell run, and a miss there fails the run.

| Situation | What the run does |
| --- | --- |
| A targeted restart succeeds and every check holds | Done; `restart result: targeted` |
| A targeted restart exits non-zero without a refused drain, the product does not settle, the graph is not ready, the routes are lost, the container check fails or a dwell poll misses | A warning, then one whole-workspace restart with the same checks; `restart result: whole-after-targeted` |

## Image cleanup

`cleanup-explorer-qa-images.yml` (no inputs) frees disk on the QA host by removing container images that no container uses. Inside the running QA Box every image without a running or stopped container goes, named or not, removed name by name (a dangling one by its validated ID) with `podman image rm` and no force; the next start or deploy pulls again what it needs (for example the OnlyOffice image when OnlyOffice is enabled, or the dependency installer image). Two kinds of unused image are kept because nothing pulls them back when Ploinky needs them: Ploinky's Router authority helper (`docker.io/library/node`, pinned by digest, with no container between probes but required present for an agent to be adopted by `ploinky shell`, `ploinky cli` or the watchdog) and the local `:runtime` tags the product deploys create. On the host, which other workspaces such as Soul Gateway share, it removes only dangling images and unused images whose name history is the Ploinky Box image, each with `podman image rm <id>` on a validated ID. It never removes containers, volumes, networks, workspace files or another workspace's images, takes the `deploy-explorer-qa` concurrency group and the host lock, and prints free disk and the image listings before and after, plus a read-only `du` of the largest directories under `/home/admin`. Use it when a deploy stops at a disk gate.

## Destroying QA

`destroy-explorer-qa-ploinky.yml` has one input, the boolean `delete_data` (default unchecked). The dispatch itself is the confirmation; there is no separate confirm box. It takes the host operation lock and runs `ploinky destroy` for the keep-data form or `ploinky destroy --delete-data --confirm-workspace /home/admin/explorerQaWorkspace` for the other.

| Aspect | `delete_data` unchecked (keep data) | `delete_data` checked |
| --- | --- | --- |
| Box and containers | Destroyed by `ploinky destroy` | The same, and the workspace data is deleted |
| Workspace `/home/admin/explorerQaWorkspace` | Stays, with its repositories, regenerated state, enabled agent selections, data and encryption identity | Deleted by Ploinky |
| Dedicated Cloudflare tunnel and DNS | Kept for the next deploy, which reconciles the same tunnel; the hostname answers with a tunnel error until then | Deleted by a runner step that refuses the shared protected `proxies` tunnel ID, deletes DNS before the tunnel, and is idempotent |

## Migrating principal-keyed state after the agent repository split

Moving agents to the `legacy-agents` and `webmeet` repositories, and `soul-gateway` and `roboTeamAgent` into this repository, renames their Ploinky identities. Ploinky derives an agent identity, its principal and its container name from the repository name and the agent name, so a workspace that already ran the earlier layout must be reviewed before it starts the new one. A fresh deployment is not affected.

| State | Old key | New key | Action |
| --- | --- | --- | --- |
| Per-agent data volumes such as `.data/soul-gateway` and `.data/roboTeamAgent` | Agent name | Agent name | Keyed by agent name, so they are expected to survive the move; confirm the mount after the first start |
| DPU agent policy for the search agent | `agent:proxies/searchAgent` | `agent:legacy-agents/searchAgent` | The default policy is added for the new key only when it is absent (`applyFreshDefaultAgentPolicies`). Re-apply a grant an administrator edited under the old key |
| Soul Gateway subject keys and agent provider rows | `agent:proxies/soul-gateway`, `agent:AchillesIDE/<moved agent>` | `agent:AchillesIDE/soul-gateway`, `agent:legacy-agents/<agent>`, `agent:webmeet/<agent>` | Subjects are stored by principal; review the old rows in the Soul Gateway dashboard and remove them once the new subjects work |
| Meeting Secretary write authorization | `agent:AchillesIDE/webmeetScribeAgent` | `agent:webmeet/webmeetScribeAgent` | Defined in the webmeet source (`MEETING_SECRETARY_PRINCIPAL`); no stored state is known to convert, so verify meeting notes after the update |
| RoboTeam principal | `agent:AchillesCLI/roboTeamAgent` | `agent:AchillesIDE/roboTeamAgent` | Re-select any stored reference to the old ref (the Copilot launcher, WebTTY target and tests use the new ref) |
| Ploinky registry and selections (`.ploinky/agents.json`, enabled repositories, routing) | Records `proxies/soul-gateway`, `AchillesCLI/roboTeamAgent`, `AchillesIDE/<moved agent>` and the `proxies` repository entry | `AchillesIDE/soul-gateway`, `AchillesIDE/roboTeamAgent`, `legacy-agents/<agent>`, `webmeet/<agent>` | Records are keyed by repository and agent, so an old record can coexist with the new one or fail the start preflight, and a redeploy or keep-data destroy keeps the registry and the enabled selections, so the old records stay. Disable the old records and repository through Ploinky before the first start, as the LiveKit repository migration does. This change ships no script for it |
| Legacy agents in an existing local workspace | `legacy-agents/soplangAgent`, `legacy-agents/tasksAgent`, `legacy-agents/webAssist` (and any opted-in `legacy-agents` agent) enabled, `.ploinky/repos/legacy-agents` installed | None: the default graph no longer installs `legacy-agents` | Ploinky does not reset existing enablement, so a workspace started before the removal keeps them. Run `ploinky disable agent legacy-agents/soplangAgent`, the same for `tasksAgent`, `webAssist` and any other enabled `legacy-agents` agent, then `ploinky uninstall repo legacy-agents`. A `legacy-agents` checkout placed directly in the workspace root still contributes its IDE plugins, because Explorer also scans workspace-root repositories, until it is removed. Enabling the `copilot-agents/research-agents` bundle installs `legacy-agents` again, since that bundle declares it in `repos` and enables `legacy-agents/GPTResearcher`. This change ships no script for it |
| Containers and repository checkouts | `ploinky_proxies_soul-gateway_*`, `.ploinky/repos/proxies` and the former agent folders | `ploinky_AchillesIDE_*`, `ploinky_legacy-agents_*`, `ploinky_webmeet_*` | Old containers and the unused `proxies` checkout stay until removed with the supported Ploinky commands |

Post-redeploy checklist for QA. A redeploy keeps all durable data in place but does not re-key it, and Soul Gateway creates subject rows on the first signed call. Before the redeploy, export the DPU agent policy and the Soul Gateway subject and provider listings. After the deploy reports the Box ready, review the rows for the old `agent:proxies/soul-gateway`, `agent:AchillesCLI/roboTeamAgent` and `agent:AchillesIDE/<moved agent>` principals and the DPU agent policies, and re-apply any customized limit or grant under the new key. The old keys stay inert. Confirm that an existing user signs in and finds their Explorer files, and that the Soul Gateway settings still list the prior providers and tiers with no tier naming a disabled provider. The migration of principals stays manual: this change ships the reference table above and no migration script. The post-split graph has not been deployed to QA before; the workflows were edited for the new repositories and the first redeploy is their first run.
