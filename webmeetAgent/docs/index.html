WebMeet Collaboration In The Workspace

Workspace participants need rooms, live media, shared resources, collaborative notes, and visual workspaces without moving identity, authorization, or durable meeting state into the Explorer browser shell.

Meeting Collaboration Needs

A meeting is more than a video call. Participants need authenticated and guest entry, synchronized room state, microphone and camera control, screen sharing, chat, attachments, shared Blackboard workspaces, and durable SCRIPTA notes. Implementing those responsibilities directly in Explorer would mix realtime media, protected room state, and meeting-specific authorization with the general workspace user interface.

WebMeet is the domain boundary for meeting collaboration. Explorer opens the experience and hosts its plugin, while WebMeet and its supporting agents retain responsibility for room lifecycle, participant admission, event ordering, media coordination, resources, and meeting automation.

WebMeet Workspace Boundary

webmeetAgent owns workspace meeting rooms, guest invite routing, LiveKit participant token issuance, Ploinky-managed RoboTeam metadata, room resources, and the Explorer WebMeet plugin. It exposes one coordinated meeting experience while keeping LiveKit infrastructure and Meeting Secretary processing in dedicated runtime agents.

The result is a meeting surface that participates in AchillesIDE navigation and identity without turning Explorer into the owner of media transport or meeting-domain state.

Runtime Behavior

Meeting Secretary (webmeetScribeAgent) is optional and disabled by default. An administrator can enable it from Explorer Marketplace before enabling automatic Meeting Notes in room settings. When the settings dialog verifies that the worker is disabled, it explains the required enablement and preserves unsaved edits. Ordinary meetings remain available. The Secretary uses browser SpeechRecognition; the separate webmeetStt service is also optional and disabled by default.

The Explorer toolbar opens WebMeet's room loader directly in a new tab. While an admitted WebMeet runtime is still starting, Ploinky Router serves the shared startup page and reloads the original URL when the runtime is ready. WebMeet then loads its normal dashboard or scoped guest room; initial room-data failures appear through the dashboard's ordinary error reporting.

Explorer opens the WebMeet plugin and supplies the authenticated workspace identity. WebMeet authorizes room access, returns the room projection, obtains short-lived LiveKit join material through the private runtime route, and records durable meeting activity through its configured Model Context Protocol tools.

Participant browsers connect to LiveKit for audio, video, screen sharing, presence, and data transport. WebMeet remains responsible for room roles, authenticated and owner-bound guest chat history, shared Blackboard state, resources, guest scope, and the logical RoboTeam room-agent record. Explorer remains responsible for canonical SCRIPTA files and their Automerge collaboration state.

Development Contract

The design specifications are the source of truth for room access, runtime behavior, media recovery, collaboration state, and Ploinky invariants. DS001-coding-style.md defines coding style, module boundaries, and test organization. Focused regression tests live under tests/unit/, and behavior or browser-service changes are validated with node --test tests/unit/*.test.mjs.

The WebMeet wiki is the canonical source for project terminology. WebMeet does not implement or distribute a local product skill catalog, so this documentation set remains focused on the agent and its active runtime contracts.
