# DS010-blackboard-agentic-diagrams

### DS010 - Blackboard Agentic Diagrams

## Introduction

The [WebMeet](wiki.html#definition-webmeetagent) [Blackboard](wiki.html#definition-blackboard) is the authoritative home for widgets, geometry, groups, attached connections, shared semantic focus, and bounded history. Room infrastructure supplies authorization, serialized persistence, and realtime transport but does not duplicate this functional state.

## Core Content

The persisted [Blackboard](wiki.html#definition-blackboard) is a `BlackboardWorkspace` containing a workspace revision, one shared active board id, ordered board ids, a bounded global history, and one or more generic boards. Each board contains its own `boardId`, title, monotonically increasing revision, widgets, theme, and `interactionContext`. There is no single-board storage shape or fixed [RoboTeam](wiki.html#definition-roboteam) board id. `webmeet_blackboard_workspace_get` exposes the shared structure and `webmeet_blackboard_get` exposes one filtered board projection. Workspace and board revisions independently order realtime projections and are never client preconditions.

### Serialization and viewer filtering

[Blackboard](wiki.html#definition-blackboard) realtime delivery uses two nested text envelopes. The outer envelope is the standard [WebMeet](wiki.html#definition-webmeetagent) event encoding:

```text
<roomId>:blackboard.updated:<base64url(event JSON)>
```

Its event payload carries routing and mutation metadata such as `boardId`, `blackboardRevision`, `changeType`, `targetType`, `targetRef`, and `objectKind`. When a direct [Blackboard](wiki.html#definition-blackboard) projection or invalidation is available, the payload also carries `blackboardMessage` with this inner encoding:

```text
blackboard:<from>:<to>:<base64(payload JSON)>
```

`from` records the emitting actor address, normally `user:<participantId>` for browser publication or `service:<id>` for a service publication. Current [Blackboard](wiki.html#definition-blackboard) publishers use `to = ALL`. The codec can split `user:<id>`, `agent:<id>`, `widget:<id>`, `service:<id>`, and `policy:<id>` destination forms, but the current receiver does not use `to` for authorization or recipient filtering and no current publisher emits a directed [Blackboard](wiki.html#definition-blackboard) projection. Room admission, the outer event route, `roomId`, `boardId`, viewer-filtered [MCP](wiki.html#definition-mcp) reads, and server-side mutation authorization remain the security boundaries. A parsed destination is transport metadata and must never be interpreted as proof that the receiving actor may view or mutate the object.

The inner payload contains the following fields:

| Field | Contract |
| --- | --- |
| `kind` | `blackboard` or `widget`; transient [SCRIPTA](wiki.html#definition-scripta) draft presentation is delivered separately within the same payload shape. |
| `roomId` | Required meeting identity and checked against the connected room. |
| `boardId` | Required board identity and checked against the adapter's current board. |
| `messageId` | Unique inner-envelope identifier used for deduplication. |
| `revision` | Board revision carried by the projection or invalidation. This is not an independent widget version. |
| `visibility` | Visibility metadata associated with the projected object. It does not replace authenticated viewer filtering. |
| `object` | Complete public-safe board or widget projection, or `null` when the message is an invalidation. |
| `presentation` | Optional non-persistent [SCRIPTA](wiki.html#definition-scripta) draft presentation; absent from ordinary final projections. |
| `timestamp` | Inner-envelope production time. |

The payload also retains board ownership metadata used by the room integration. Runtime DOM references, local drafts, pointer state, caches, and privileged history never enter either envelope.

The receiver first validates and deduplicates the outer `blackboard.updated` event, then validates the inner room and board identities and deduplicates `messageId`. A revision lower than the currently applied board revision is ignored. An equal revision is accepted when it has a distinct message id because a command response and its realtime delivery may represent the same accepted revision through separate envelopes; exact duplicate ids remain ignored. Revisions order projections but are not optimistic concurrency preconditions.

Ordinary mutations may carry a complete public-safe object and are applied directly without reconstructing a patch. Workspace changes carry an invalidation and reload the workspace plus its active board. [SCRIPTA](wiki.html#definition-scripta) final changes, [SCRIPTA](wiki.html#definition-scripta) objects containing viewer-relative permissions or votes, private objects that have no public projection, and other messages with `object: null` are invalidations: the receiving browser reloads the board through the authenticated [WebMeet](wiki.html#definition-webmeetagent) tool boundary. A locally applied [SCRIPTA](wiki.html#definition-scripta) revision may consume its matching invalidation without a redundant render while still synchronizing the Explorer collaboration replica.

The public realtime projection and the authenticated [MCP](wiki.html#definition-mcp) projection are deliberately different. Realtime publication to `ALL` is built with an unauthenticated public viewer context and may omit private widgets, participant-specific fields, protected aggregate results, workspace editor links, ownership capabilities, and votes. `webmeet_blackboard_get` and `webmeet_blackboard_workspace_get` build a new projection for the authenticated caller and are the authority whenever resynchronization is required. Realtime transport accelerates rendering or signals invalidation; it does not grant access and does not replace the persisted, viewer-filtered [WebMeet](wiki.html#definition-webmeetagent) state.

The participant-facing workspace projection contains `id`, `roomId`, `revision`, `activeBoardId`, ordered `boardOrder`, a `boards` summary array, and the filtered `activeBoard`. Each board summary contains `boardId`, `title`, `purpose`, `systemManaged`, `revision`, and `widgetCount`. The participant-facing board projection contains `boardId`, `revision`, shared `interactionContext`, safe metadata, and a `widgets` array. Safe board metadata contains only the selected theme id; full metadata and history are never part of this projection.

Each participant-facing widget contains `id`, `type`, filtered `properties`, `groupId`, `visibility`, `locked`, `createdBy`, `updatedBy`, `createdAt`, `updatedAt`, and `timestamp`. Runtime references are never serialized. The privileged persistent representation additionally contains workspace history; board identity, ownership, visibility, full metadata, and board history; unfiltered widget properties; and widget provenance. Widget collections are arrays in both projections even though the runtime model indexes them internally by id. Widgets do not carry an independent version: workspace and board revisions provide ordering.

Widget visibility is evaluated against the authenticated viewer context. `all` admits every room viewer; `participants` admits human participants and privileged viewers; `moderators` and `privileged` admit only privileged viewers; `owner` matches `visibility.ownerId`; `participantsList` matches an id in `visibility.participantIds`; and `user:<id>` or `agent:<id>` matches that exact actor kind and id. `policy:<id>` and every unknown mode are visible only to privileged viewers. Privileged viewers include authorized agents, administrator, moderator, agent, or evaluator roles, and viewers explicitly authorized to moderate the [Blackboard](wiki.html#definition-blackboard) or inspect all participant data.

Properties containing participant responses or aggregate results are filtered after widget visibility. `resultsVisibility` values `public` and `live` expose aggregation immediately; `afterSubmit` and `afterPoll` expose it after the current viewer has submitted; `afterClose` exposes it after the widget closes; `moderatorsOnly` restricts it to privileged viewers; and `hidden` suppresses it. A non-privileged viewer receives only their own `participantData` while aggregation is hidden. When non-anonymous results are visible, the participant rows are visible with the aggregation; an anonymous widget removes all participant rows from non-privileged projections and exposes only the permitted aggregation. `correctAnswer` and `scoring` remain privileged fields. The poll owner receives the privileged property projection, and `canManagePoll` states whether the current viewer is that owner or a privileged viewer.

[SCRIPTA](wiki.html#definition-scripta) projections apply the same viewer-relative rule. Guests and viewers without an authenticated workspace user do not receive `editorUrl` or `documentId`; `canBrowseWorkspace` is true only for an authenticated non-guest workspace user. Private vote maps and variant owner hashes are removed and replaced with the current viewer's vote and viewer-relative `ownedByViewer`, `canEdit`, and `canDelete` capabilities.

All participants can create, rename, reorder, activate, and delete shared boards, but the final board cannot be deleted. The same operations are available to natural `/robo` commands. Robo resolves explicit board titles case-insensitively when unique and resolves participant-facing workspace or tab ordinals against the synchronized order; the emitted canonical event carries only an existing `targetBoardId`. Rename, delete, reorder, and activate therefore operate on the resolved board rather than implicitly on the active board. Board activation is durable shared navigation, is not an undo step, and produces no chat audit entry. Every content or board-structure mutation enters one global chronological history. A cross-board transfer removes from the active source and inserts into the resolved destination as one serialized command and one Undo/Redo step.

`webmeet_event_command` accepts canonical JSON, deterministic `/event <action> [JSON object]`, and natural `/event` or `/robo` text. Natural input creates an isolated `MainAgent` for one bounded round with internal skills disabled and only the `blackboard-event` skill available. Its context contains the instruction, logical content bounds, safe widget semantics and capabilities, transient global widget ordinals, shared focus, last affected widget ids, and the complete ordered workspace catalog with each board's exact id, title, ordinal, item count, and active state. It excludes viewport state, room revision, participant-private data, paths, editor URLs, audit identifiers, and transport identifiers.

Every [Blackboard](wiki.html#definition-blackboard) interpretation, correction, and semantic-verification call uses provider-native Structured Outputs with one strict JSON Schema generated from the canonical action, widget, property, connection, Poll/Bullets, [SCRIPTA](wiki.html#definition-scripta), and semantic-error definitions. Follow-up [SCRIPTA](wiki.html#definition-scripta) document-content generation and paragraph reformulation use their own strict content schema through the same transport. Chat Completions transports use `response_format.json_schema`; Responses transports use `text.format`. Nullable transport fields are removed before canonical validation, and dynamic Poll answer entries are converted back to the canonical question-id map. The server never treats Markdown or unconstrained model prose as an executable event. Runtimes that do not yet expose the Achilles structured helper send the same strict `response_format` through the existing prompt API, so they do not silently downgrade to free-form JSON.

The canonical public actions are `create`, `update`, `delete`, `group`, `ungroup`, `clear`, `undo`, `redo`, `show`, `hide`, `board-create`, `board-rename`, `board-reorder`, `board-delete`, `board-activate`, `board-transfer`, and declared widget-domain actions. `focus` and `board-copy` are internal and UI-only. `add`, `lock`, and `unlock` are invalid. Events never contain server-generated widget ids, event ids, command ids, revisions, participant ids, or provenance. A multi-event result uses `{events:[...]}`; create events may declare a command-local `ref`, which later ordered targets and connection endpoints may resolve. Duplicate and forward references fail the entire command.

[Blackboard](wiki.html#definition-blackboard) content, semantic focus, and revisions are shared, but whether the [Blackboard](wiki.html#definition-blackboard) surface is open or enlarged is local browser layout state. Selecting the [RoboTeam](wiki.html#definition-roboteam) participant card or the [Blackboard](wiki.html#definition-blackboard) toolbar button toggles that surface only for the current participant, exactly like focusing any other participant card. The open [Blackboard](wiki.html#definition-blackboard) surface also exposes a visible Close control in its header; it uses the same local toggle and restores the participant layout without publishing room state. `show` and `hide` return a requester-local visibility result and are never published as room realtime state. Peers continue to receive `blackboard.updated` invalidations while hidden and render the current projection only when they choose to open their own [RoboTeam](wiki.html#definition-roboteam) card. [SCRIPTA](wiki.html#definition-scripta) and `/robo` mutations never force another participant's [Blackboard](wiki.html#definition-blackboard) surface open.

The shared tab strip activates the same board for every participant with mouse or ARIA keyboard navigation. A double-click on a tab enters its inline rename field; the tab template has no dedicated rename button. Enter or focus leaving the input commits a changed non-empty title and exits edit mode immediately, while Escape cancels. Open clients animate the ordered direction as a horizontal slide, while reduced-motion clients switch without movement. A local filmstrip mode displays incrementally loaded previews for every board; each preview projects the real widget geometry, type, visual style, image, and compact semantic content instead of substituting generic placeholder rectangles. A rigid group keeps all member miniatures visible inside one labelled outline; hover and drag belong to that complete outline, while standalone widgets remain individually interactive. Choosing a preview activates that board for the room. Dropping a miniature item, multi-selection, or complete group anywhere in a workspace preview maps the exact pointer position into that board's logical coordinate space and preserves the original grab offset, clamped only to keep the moved bounds visible. A drop back onto the source preview repositions the complete selection in the same board as one atomic `board-reposition` history entry; a drop onto a different preview transfers it. When a standalone dragged item belongs to the active multi-selection, the whole selection moves. During a full-size widget, group, or multi-selection drag, dwelling over another tab for 450 ms activates that shared tab without ending the pointer gesture. Pointer capture continues at document scope, a bounded selection outline follows the pointer on the destination canvas, and releasing inside that canvas transfers the complete selection at the exact indicated position while preserving the original grab offset. Releasing before activation or outside the destination canvas does not transfer. Both filmstrip paths use the canonical `board-transfer` command, which distinguishes same-board repositioning from cross-board transfer by the board ids. Relative geometry, stable ids, groups, and internal attached connections are preserved; cross-board connections crossing the selection boundary are removed. A cross-board destination becomes the shared active board before the continued destination-placement gesture. Ctrl/Cmd+C captures the current widget, complete rigid group, or multi-selection into a browser-local [Blackboard](wiki.html#definition-blackboard) clipboard, while Ctrl/Cmd+X captures the same complete selection as a pending move. Right-clicking a selection exposes declarative WebSkel Copy and Cut actions. Whenever either clipboard mode is populated, right-clicking a full-size board or a filmstrip preview exposes Paste here and maps that pointer to the exact logical destination coordinate. Keyboard paste copies into the active tab in normal mode; in filmstrip mode each miniature and workspace card is keyboard-focusable, so paste targets the focused card without activating or closing it. Copy uses the UI-only canonical `board-copy` action, which generates new widget and group ids on the server, remaps internal attached connections, preserves the source, and records the complete copy as one global Undo/Redo entry. Cut defers mutation until Paste here or keyboard paste succeeds, then uses one atomic `board-transfer`. Every successful Copy or Cut paste clears the browser-local [Blackboard](wiki.html#definition-blackboard) clipboard, so another paste requires a new Copy or Cut action. A failed paste leaves both the source and local clipboard intact. Complete groups and internal attached connections are expanded into the clipboard selection so no copied or moved connection can retain invalid endpoint references. The workspace-backed singleton [SCRIPTA](wiki.html#definition-scripta) projection cannot be copied as an independent [Blackboard](wiki.html#definition-blackboard) widget.

One command is validated and applied on one working board, persisted only when every event succeeds, recorded as one history entry, and undone as one unit. The server generates ids, resolves references, attaches provenance, updates shared focus, increments revision once, saves, and publishes `blackboard.updated`. Each durable event audit stores the relevant board id and a human-readable workspace-title snapshot so Full chat can identify the board for every canonical event line without exposing opaque ids; this snapshot remains intelligible after a later rename or deletion. [RoboTeam](wiki.html#definition-roboteam) mutations use `agent_robo_team` as technical author and retain the authorized participant only as private provenance. UI mutations use the authorized participant and `source: "ui"`; caller-supplied authorship is rejected.

Visible widget geometry defines logical content bounds. An empty board uses `0,0,1200,800`; generated layouts use a default 40-pixel gap and never depend on browser viewport, zoom, or scrolling. Free lines store endpoints. A line or arrow endpoint may be attached independently, so `properties.connection.from/to` is either `null` for a free endpoint or identifies exactly one widget, rigid group, or ordered command-local reference plus a `left`, `right`, `top`, or `bottom` anchor. Starting the line tool or dragging an existing endpoint reveals four fine connection points on every eligible standalone widget and one axis-aligned set around each complete group. Each indicator is centered along its side and sits immediately outside, tangent to the target border, while the canonical line endpoint remains exactly on the border. An endpoint snaps within 18 logical pixels, shows the current snap target, and may be dragged away to become free without disturbing the other endpoint. The renderer derives attached coordinates from current target geometry and rotation, so connections follow widget move, resize, and rotation and group move, resize, and rotation during the pointer gesture as well as after persistence. Ungrouping materializes a group-attached endpoint at its last visible position before removing the group reference. Deleting a widget endpoint removes its dependent connection; deleting a group removes connections targeting that group. Connections cannot cross workspace tabs. Copy, cut, paste, same-tab reposition, and cross-tab transfer include complete internal connectors and remap both widget and group targets; filmstrip previews project the same current connector geometry.

Semantic context exposes each widget's current canonical rotation. “Rotate by N degrees” adds N to that value, while “rotate to N degrees” sets an absolute value. Rotation preserves the widget center and does not rewrite free-line endpoints merely to achieve a rendered rotation.

Widgets share a flat, server-generated `groupId`; nested group objects are unnecessary because regrouping composes existing rigid groups into one new rigid group. Participants form or merge groups with modifier-click or a canvas marquee. Selecting any member for a composite selection expands that selection to every member of its existing group, so independent widgets, one or more complete groups, or both can be merged atomically. Once grouped, clicking or dragging anywhere inside the common bounding box, including empty space between members, selects or moves one strict block. Member editing and individual resize remain unavailable until `ungroup`. The group projection owns one contextual menu with Move, Rotate, Export, Delete, and Ungroup, while resize is exposed only through the eight handles on the group outline. Export is a local visual snapshot and offers transparent PNG or PNG with the solid board theme background. It includes every visible group widget plus attached connections whose endpoints are both group members, uses 16 px padding and 2x output (bounded to 8192 px per side and 32 megapixels), and excludes selection UI, menus, handles, Robo ordinals, fullscreen controls, admin actions, and edit controls. Visual resources are embedded before rendering, and the locally vendored html2canvas renderer runs without SVG `foreignObject` so the output canvas remains origin-clean. Export never calls the network adapter and does not create history or increment revision. Canonical group mutations target `{type:"group",groupId}`: translation moves every member by one delta, rotation moves member centers around the common center and increments their rotations, and resize maps member geometry into an authoritative target bounding box. Resize handles scale axes independently, while Shift preserves the group aspect ratio. Geometry and free-line endpoints scale, but fonts, strokes, and internal controls do not. Minimum widget dimensions still apply. Group creation and merging, group deletion, and ungrouping are each single history commands; Undo restores the exact previous group memberships. A connector may itself join a rigid group only when both endpoints are attached and every endpoint target is included; a hybrid connector with a free endpoint remains outside the group and follows its attached target normally. Shape text uses `properties.label` and is centered in the shape SVG rather than represented by a second text widget.

Validated uploads create Explorer-backed `image` or `file` widgets. The chat composer exposes attachments through a left-aligned plus control whose WebSkel menu contains one declarative `Add file` action; stable templates, menu, drop overlay, and input-shell structure remain in component HTML, while presenter actions own state and commands. File-picker selection, clipboard file paste, and file drag-and-drop over the composer enter one ordered upload queue. Files may also be pasted or dropped directly onto the full [Blackboard](wiki.html#definition-blackboard) canvas or an exact logical position inside any filmstrip workspace preview. Those direct gestures emit one semantic component event to the dashboard and therefore use the same canonical chat publisher: every successful file creates both its chat message and its widget on the explicitly targeted board. Multiple files are processed sequentially in source order, with independent failures that do not block later files.

Explorer recognizes supported images from their byte signatures, not their declared MIME metadata. Images store safe source metadata, intrinsic dimensions, alt text, style, and geometry. Every other accepted file stores safe source metadata and geometry and renders through a reusable file-card template showing name, extension, MIME type, and size. Every upload is stored under the canonical [SCRIPTA](wiki.html#definition-scripta) room folder's `assets/` child, so the Markdown documents and their chat, [Blackboard](wiki.html#definition-blackboard), and [SCRIPTA](wiki.html#definition-scripta) resources share one room-owned root. One asset is exactly one directory and one real file: `assets/<assetId>/<sanitized-original-name.ext>`. No permanent metadata sidecar or paired payload exists; Explorer derives the projection from the single file and rejects asset directories containing anything else. A standalone file card's contextual menu intentionally contains Download, Move, and Delete but no Settings or Rotate actions; Download is a declarative WebSkel action and is not rendered inside the card content. File widgets have a canonical minimum size of 160 by 100 logical pixels, matching the card's minimum layout, so resize previews, persisted geometry, and selection bounds cannot become smaller than their content. File cards participate in ordinary move, resize, grouping, deletion, history, workspace drag/move, and one-shot Copy/Cut/Paste behavior, including cross-tab and filmstrip operations. A containing group may still be transformed as one unit. Chat publication creates the attachment and widget atomically after Explorer accepts the staged bytes. After that mutation succeeds, the uploader's browser opens and focuses its local [Blackboard](wiki.html#definition-blackboard) surface when necessary and immediately applies the returned projection; this local layout transition is not published to peers. Selecting any chat attachment opens the corresponding board and widget, while a file attachment also offers direct download. Contextual insertion of an image into [SCRIPTA](wiki.html#definition-scripta) reuses its asset. Contextual or `/robo` insertion of a group uses the existing origin-clean browser renderer, commits the resulting PNG, and invokes the canonical [SCRIPTA](wiki.html#definition-scripta) media mutation.

`interactionContext` stores `focusedWidgetId`, `lastAffectedWidgetIds`, `updatedBy`, and `updatedAt`. The latest create, manual selection, move, resize, or edit updates global focus; plural follow-up language uses the last affected ids. Missing focused widgets are cleared. Focus changes do not create undo steps.

The interpreter returns either `{events:[...]}` or `{error:{code,message}}`. Ambiguous or unsafe intent returns a precise natural-language error in the instruction language and executes no events. The audit entry transitions directly from `pending` to `success` or `error`; no clarification state or popup exists.

As soon as the chat composer starts with `/robo`, the local browser shows deterministic global ordinal badges over semantic targets, allowing references such as “line 3”. Each ungrouped widget consumes one ordinal. Each rigid group consumes one ordinal displayed as `G<number>` over the group bounds, while its member widgets display no separate ordinals. The safe interpreter context exposes these targets through `board.widgets` and `board.groups`; a group ordinal or a focused member of that group must resolve to `{type:"group",groupId}` so movement, resize, rotation, deletion, and ungroup apply atomically to the entire block. Browser push-to-talk inserts the prefix on microphone press, before the first speech result, so ordinals are visible while the participant formulates the command. Interim speech text remains a local composer projection; release submits the finalized `/robo` text through the same command path as keyboard input. The badges remain active during execution, disappear when the prefix is removed or the command reaches a terminal result, and are transient DOM overlays that never become widget properties or history. A realtime-only `blackboard.command_status` event lets all participants see who is editing after submission. Terminal success remains visible for four seconds, terminal errors for ten seconds, and stale active status expires after the interpreter timeout plus fifteen seconds.

The selected-group overlay is a browser-only projection expanded by eight logical pixels on every side of the current member bounds. Its border and resize handles therefore remain visually separated from member content. Resize previews reapply the same gap while the canonical transform continues to use the unpadded group bounds, so selection spacing never changes persisted geometry, export bounds, or undo history.

Line widgets expose pointer hit-testing only through a transparent 12-pixel interaction band centered on the visible segment. Their rectangular SVG layout bounds do not receive pointer events, so a connector crossing or ending at another widget never consumes the first drag gesture intended for that widget. Endpoint handles and the selected-line contextual menu remain independently interactive. An unselected movable widget is selected and begins its pointer drag in the same first press-and-hold gesture; shared semantic focus is published only after a click is released or through the completed move, so a focus projection cannot replace the pointer-capturing node mid-gesture. Group connection bounds are computed from members with authoritative geometry; attached connectors are derived from their endpoints and therefore never expand or displace those bounds, while free line members still contribute normally. A complete group made only from free lines remains a valid connection target.

### Browser projection and DOM reconciliation

The latest board projection accepted from the network adapter is the confirmed client model. The rendered widget node is normally a projection of that model, but it may temporarily contain a local DOM draft while the current participant is typing or performing a pointer gesture. A DOM draft is transient interaction state only: it is not a second board model, is not sent as a complete board snapshot, and does not prevent the adapter from accepting a newer projection. The final local action sends only its narrow widget patch. Server-side room serialization and board revisions continue to define last-edit-wins ordering.

The browser reconciles the confirmed projection by stable widget id. Runtime maps associate each widget id with its current DOM node and render key; they are rendering caches and are never serialized. Reconciliation applies the following rules:

| Projection change | DOM reconciliation |
| --- | --- |
| Create | Render the new widget node, cache it by widget id, and place it at the position defined by the confirmed widget order. |
| Update | Replace only the changed widget node when its render key differs. Unchanged nodes retain their identity, focus, and local browser state. |
| Delete | Remove the missing widget node and its cached render key immediately. A confirmed deletion is authoritative and does not preserve an obsolete local draft. |
| Reorder | Move the existing widget nodes into confirmed order without recreating otherwise unchanged nodes. |

After widget reconciliation, transient connection anchors, group hit areas, selection overlays, and ordinal decorations are rebuilt from the confirmed model. During an active group gesture, the group interaction overlay is retained until that gesture ends so the pointer target is not invalidated. Attached connection geometry remains derived from the current projected endpoint geometry.

A widget node is protected from replacement while it owns an inline text draft, an active drag, resize, or rotation, or belongs to an active group drag, group resize, or group rotation. Widgets carried by an active cross-workspace drop are protected by the same rule. A widget is also protected when one of its `input`, `textarea`, `select`, or editable content elements owns document focus. Protection preserves the live node and its draft or pointer capture; it does not reject, buffer, or rewrite the confirmed board projection.

When a protected node differs from the confirmed projection, rendering for that node is marked pending. An inline text node is reconciled after commit, cancellation, or an unchanged edit exits. Pressing the primary pointer anywhere on the [Blackboard](wiki.html#definition-blackboard) outside the active editable content explicitly blurs and commits that draft before the canvas or another widget handles the gesture; this remains reliable even when drag or marquee handling suppresses the browser's default focus transition. A pointer gesture is reconciled from the authoritative response when it completes, or immediately from the already accepted projection when it is cancelled. A focused form control is reconciled after focus leaves the control and no protected interaction remains. Group decorations are rebuilt after the group gesture completes. These flush points apply the newest confirmed projection available at that moment, so a later accepted local patch or remote patch remains the last edit that wins.

Complete board reconstruction is the recovery path only when the [Blackboard](wiki.html#definition-blackboard) surface is newly mounted or its runtime DOM caches have been reset during teardown. The next render then treats every confirmed widget as a create and reconstructs transient decorations from the confirmed model. Ordinary create, update, delete, reorder, selection, and realtime projection changes must use incremental reconciliation and must not clear or replace the complete board DOM.

### Decisions & Questions

### Question #1: Why is revision not an optimistic concurrency precondition?

Response: The room mutation lock already supplies a deterministic server order. Revision is required only to discard stale realtime projections; making it a client precondition would reject valid last-edit-wins collaboration and require unnecessary read/retry cycles.

### Question #2: Why is focus shared board state?

Response: Follow-up commands such as “move it” and “align them” must resolve identically for every participant. Persisting focus and last affected targets on the board provides that deterministic semantic context without relying on participant viewport or DOM selection.

### Question #3: Why are file widgets created only by the attachment publisher?

Response: The publisher receives a validated Explorer asset and can safely project its stable URL and sanitized metadata. Allowing a generic event or model-generated command to create file widgets would permit invented asset ids or paths. Once created through the specialized path, the file widget uses the ordinary canonical geometry, grouping, transfer, history, and clipboard operations.

[Blackboard](wiki.html#definition-blackboard) commands remain deterministic and secure while server order defines last-edit-wins behavior, canonical event lists execute atomically, ambiguous instructions fail without mutation, and collaboration status stays transient.
