# Copilot workflow delegation gate

C4 now uses the current `launch-workflow` skill and `roboflow_start_flow` background task. The test defines one run-owned ordinary workflow with one terminal node and no edges. Its canonical source/skill requirement must match exactly one newly created Codex-only worker. The worker's defaults are not seeded, and the existing default robot's settings, registration and selected front backend remain unchanged.

The front Copilot submits one self-contained objective through its browser composer. Setup creates the workflow definition and worker source only. The test never starts the tested flow through an administrative API. `SMOKE_C4_FRONT_BACKEND` records the existing front backend separately; the child ALA backend must be `codex` regardless of the front backend.

Enabled live execution remains absolutely refused in `beforeAll` until the reviewed phase6 credential/preflight runner and independently verified B+C setup are integrated. Test discovery and offline checks do not launch browsers or native backends. C4 does not supply C5, H1, X1 or final deployment acceptance.

The proof follows the current durable records. The front session turn identifies its background task by task ID, assistant message ID and turn ID. The task's details link identifies the flow. The captured flow supplies its objective, graph and single instance; that instance identifies the actual runtime task. The runtime request supplies its objective context and child ALA session. Folder `.roboteam` metadata and the pinned ALA transcript API then prove the child's Codex backend and completed final challenge. The task description omits objective, so matching filenames or markers in task-card descriptions cannot substitute for this join.

The worker uses one generated helper through its actual Ploinky symlink. The helper checks a noncredential marker inside its newly owned home and the exact installed source. It writes the requested marker plus newline and an exclusive receipt beneath the run-owned `.set2-c4-proof/` directory. The receipt records its invocation, source, helper hash, file hash and source proof value. Task, workflow and session correlation stays in the external observer because the native sandbox masks `.roboteam` empty and read-only. Direct execution from the front home, copied helpers and replayed writes fail. The observer requires the sole receipt, managed link revision and actual Codex child evidence; a file alone cannot satisfy the gate.

The browser must show a `COMPLETED` task card, the current RoboTeam task details and marker log, and the matching workflow page with one completed worker phase. Explorer must display the requested file, and its raw contents must equal the marker plus one newline. User-file inventory permits exactly that file change; runtime `.roboteam`, `.agents`, `.claude` and the sole `.set2-c4-proof/` receipt are checked separately. Existing user files and directories remain unchanged.

The observer reuses the reviewed Box/runtime/source binding guards and pins every RoboTeam `.mjs` source before its imports. SQLite is opened read-only, and official record composition is used. Front continuation identity follows the selected backend: Codex thread ID, OpenCode session ID, or Pi session ID and session file. The child must retain a Codex thread ID. Child prompt equality is checked privately; composed user messages expose a comparison boolean and identifiers without prompt text or a prompt digest. Intermediate output, tools and runtime logs stay inside the reader. Missing child publication remains incomplete evidence and cannot satisfy the gate.

Offline tests exercise the pinned launch-workflow action, graph normalization, canonical matching, RoboFlow service, task-description contract, Ploinky links, generated Node helper and ALA recorder with disposable sources and database files. They reject duplicate or wrong workers, backend/home/folder switches, mismatched objectives or task associations, extra phases, direct front-file receipts, fabricated file-only success, stale source and unrelated user-file changes. These are synthetic native-turn records, not deployed model turns.

Cleanup cancels the front turn, pauses owned active flows, checks native quiescence, closes views, removes the owned workflow and source links, unregisters/deletes the owned worker, and removes owned folders. Ambiguous resource creation, unfinished native work, foreign cleanup targets or any failed cleanup retains ownership and fails the test. Credential cleanup and recovery remain reserved for phase6.
