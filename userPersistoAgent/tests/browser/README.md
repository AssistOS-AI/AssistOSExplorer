# Opt-in Google browser regression

`google-resume.mjs` exercises actual Chromium native form navigation with the controlled signed Google provider, the real UserPersisto OIDC engine and a separate local relying party. It first establishes password login and application consent, then requires Google collision reauthentication and explicit linking. Before Google authorization it holds the deferred interaction script, verifies an early click cannot submit or navigate, then releases the script and completes the same attempt. It also verifies the browser-generated POST Origin, the cross-origin callback redirect chain, independent downstream PKCE/state/nonce/signature verification, unchanged local subject/roles and exactly one binding.

Run with a supported Node LTS release, the installed UserPersisto dependencies, and an existing Playwright package and Chromium installation. No global install or download occurs. Set the absolute path to that package's `index.mjs` explicitly:

```sh
GOOGLE_BROWSER_PLAYWRIGHT_MODULE=/absolute/path/to/playwright/index.mjs \
  node userPersistoAgent/tests/browser/google-resume.mjs
```

An existing browser executable can be selected with `GOOGLE_BROWSER_EXECUTABLE=/absolute/path/to/chromium`; otherwise Playwright uses its installed Chromium. Set `GOOGLE_BROWSER_HEADED=true` for a visible browser. The runner is intentionally separate from `npm test`.

Set `GOOGLE_BROWSER_LINK_METHOD=totp` or `GOOGLE_BROWSER_LINK_METHOD=passkey` to select the Google collision credential; the default is `password`. Each run has fresh accounts and persistence, and first establishes ordinary password login/application consent. TOTP setup uses a random fixture secret through the existing enrollment functions, then submits an actual browser form and verifies counter consumption. Passkey setup loads a random fixture P-256 credential into Chromium's CDP virtual authenticator and persists only its public key. The production browser script performs `navigator.credentials.get`, and the runner checks the authenticator assertion event and server-side signature counter advancement. No hardware, real user credential or mocked authentication result is used. Every method separately proves that reauthentication alone creates no binding/application success, then explicitly clicks **Link Google and continue** and verifies the existing local ID and roles downstream.

Passkey fixtures default to `localhost`; password/TOTP fixtures default to `127.0.0.1`. `GOOGLE_BROWSER_HOST` explicitly selects either value and consistently configures the fixture's issuer, callback, cookie host and virtual credential. Chromium 148 rejects WebAuthn on the numeric `127.0.0.1` origin with a relying-party domain `SecurityError`, even when the browser options omit an explicit IP `rpId`. Setting `GOOGLE_BROWSER_LINK_METHOD=passkey GOOGLE_BROWSER_HOST=127.0.0.1` reproduces that known failing boundary and checks that no binding or Google application login results. Passing localhost fixtures do not establish passkey support for a deployed numeric-IP route or authorize changing a deployment's registered origins.

Set `GOOGLE_BROWSER_HTTPS=true` to run the same roundtrip behind an ephemeral local HTTPS reverse proxy. This mode requires an existing OpenSSL executable (`GOOGLE_BROWSER_OPENSSL` can select its absolute path), creates a one-day self-signed certificate with a loopback IP subject alternative name, and enables certificate-error bypass only in the disposable Chromium context. The Node relying party trusts that certificate only for the exact fixture origin. Both modes verify the host-only, HttpOnly, SameSite=Lax service-path proof cookie and its removal; HTTPS additionally requires `Secure` and the `__Secure-` name prefix. No production TLS configuration is relaxed.

The fixture chooses dynamic loopback ports, creates temporary persistence, uses test identities, and closes its browser/servers and removes persistence in `finally`, including after failed checks. It writes no screenshots, traces, credentials or callback-query artifacts. Normal output includes only the browser version and check result, apart from existing service initialization diagnostics. It does not use a Ploinky workspace or an actual Google account. Router deployment, Google Console acceptance, popup transport, Firefox and Safari remain separate acceptance checks.
