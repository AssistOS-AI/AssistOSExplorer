Deployment and Operations

Soul Gateway has one production deployment model: a Ploinky-managed agent behind the Ploinky Router. The manifest selects the Node 24 agent image, mounts persistent data at /data, starts startup.sh, and publishes inference, management, and health paths with different access rules.

Startup contract

The manifest pins the shared Ploinky Node image by digest. Node 24 on Debian Trixie supplies the built-in SQLite API and a maintained Git/libcurl stack; native amd64 and arm64 Git/npm checks gate image adoption.

install.sh creates persistent data and credential directories, connects the Ploinky-prepared dependency cache when needed, optionally installs Chromium for headless search, and creates DATA_DIR/encryption.key with owner-only permissions. startup.sh repeats dependency and browser readiness checks, exports the data paths and listener values, and runs node src/index.mjs.

The application validates configuration, fails closed when required signed-subject authentication values are absent, initializes SQLite, installs catalogs and services, and reconciles Ploinky agents. Next it installs the first-start free model defaults when they have not been installed yet, refreshes provider model catalogs, bootstraps auto tag tiers once (recorded by the initial-tag-tiers marker), reconciles compatibility aliases, loads the runtime snapshot, starts maintenance jobs, and registers HTTP and WebSocket routes. A failed free-defaults install is logged and retried on the next start; it does not stop startup.

src/config/env.mjs is the executable source for parsed defaults. The Ploinky manifest supplies DATA_DIR=/data, CREDENTIALS_DIR=/data/credentials, and SQLITE_PATH=/data/soul-gateway.sqlite3 for the managed agent deployment. A direct process start must explicitly set all three paths beneath the selected workspace .data/soul-gateway root and fails closed when any is absent; there is no relative data-directory default.

Persistence and credential recovery

The SQLite file and encryption key must persist together. Provider API secrets are encrypted with the application key, and managed OAuth credential files use the same protected runtime boundary. Losing the encryption key makes existing encrypted secret material unusable even if the database remains available.

Schema initialization applies the idempotent schema in src/db/schema/sqlite-current.sql. The one-time free model defaults described below and the one-time auto tag-tier bootstrap each record completion in gateway_bootstrap_state, so they run once per database file. Existing configuration is loaded into an immutable runtime snapshot so the request hot path does not query configuration tables at every stage.

First start and free model defaults

On the first start with FREE_MODELS_ENABLED left at true, Soul Gateway installs, in one database transaction, the free-only provider openrouter-free, one encrypted provider account, nine baseline free models, and the compatibility tiers named in LLM_DEFAULT_TIERS (fast, code, plan, write, deep, ultra, and web-assist by default). The transaction also writes a bootstrap marker, so the install happens once. An interrupted start writes nothing, and the next start retries. After the install, a GET /v1/models call lists the tiers, and a request to fast is answered by a free OpenRouter model. The later catalog refresh adds the rest of the free OpenRouter catalog; models that are not free, and guard, moderation, safety, or embedding models, are never stored on this provider. Every model on it runs with one attempt and bounded first-output deadlines, including models the refresh adds later. Two models measured as unfit, nvidia/nemotron-3.5-lightning:free and openrouter/free, stay callable by their direct model key but never join a tier.

The install runs on any database that has no bootstrap marker yet, including an existing gateway that already has its own providers and tiers, for example a production deployment upgraded to this version. Start such a gateway with FREE_MODELS_ENABLED=false if the free provider and tiers are not wanted there.

If OPENROUTER_API_KEY is set when the install runs, that key is stored instead of the bundled key. Setting it later has no effect on an installed gateway; replace the key from the dashboard as described below.

Starting without internet access

The tier records and baseline models are written before any catalog request, so the gateway starts, reports healthy, lists every tier, and serves the management dashboard without internet access. The provider catalog refresh fails and leaves the baseline models in place. Requests to the tiers fail until the gateway can reach openrouter.ai over HTTPS, because the free models run at OpenRouter; Soul Gateway performs no local inference by default.

A network that accepts connections and then stalls does not keep the gateway from starting. Model discovery gives up after 10 seconds per provider, and the startup refresh walks providers one after another, so a start with two stalled providers reaches its listening state after about 20 seconds. Each load of the external pricing directory gives up after PRICING_DIRECTORY_TIMEOUT_MS (default 5000, clamped to at most 2147483647); a timed-out directory load is logged as a warning and the catalog is stored without directory metadata. A failed load is remembered for the refresh interval, at most a minute, so while the directory is unreachable the model list and further catalog syncs answer immediately instead of waiting for the timeout again, and the warning is logged once per window rather than once per caller. Test harnesses and restart-heavy scripts should point PRICING_DIRECTORY_URL at a local server, because every start with a non-empty catalog loads the directory.

Shared quota and quota exhaustion

The bundled key belongs to a dedicated free-tier OpenRouter account with a zero credit limit and a guardrail that allows only free models. Its daily free-model allowance, currently 50 requests per day on OpenRouter's free tier, is shared by every installation that uses the bundled key, and failed attempts may not count. The key expires on 2027-03-20. The free defaults are a working first start, not unlimited, guaranteed, or private capacity.

When the daily allowance is spent, OpenRouter answers with HTTP 429 and a daily-limit signal. Soul Gateway classifies this as an account-scoped failure: the account is marked quota_exhausted until the reset time reported by OpenRouter in x-ratelimit-reset (at most 26 hours; when no reset is reported, at most 15 minutes, after which the account is tried again), and the remaining free children are skipped without further upstream calls. Callers receive HTTP 429 with error type provider_quota_exhausted on the first failing request and provider_accounts_exhausted on later requests until the reset, not tier_exhausted. The management account data for the openrouter-free account reports status quota_exhausted and the reset time in quotaResetAt, and the audit log records the error type of each failed request. The scheduled quota-reset sweep reactivates the account after the reset time. Replacing the key clears the lock immediately. A per-minute rate limit from OpenRouter is not treated as quota exhaustion: it only cools the affected model down briefly while the other free children stay available.

Replacing the bundled key

An administrator replaces the bundled key from the management dashboard by editing the openrouter-free provider and entering a new API key; the dashboard sends PATCH /management/providers/:providerId with apiKey. The new key is encrypted in place of the old one, the account becomes active, the stored quota reset and the running gateway's in-memory exhaustion record are both cleared, and the account no longer carries the bundled-key and expiry metadata, so the new key is used on the next request without a restart. The provider keeps its free_only setting, so it still serves only free models; configure a separate provider for paid models. The key is never shown back in the dashboard or returned by any API.

If the catalog request made with the new key returns an empty list, the stored models are kept, because an empty list can mean an outage; if it returns HTTP 404 on the provider's discovery path, the key update reports the failure and the stored models are kept. Only a catalog that lists models of which none is free disables the stored free models. The same rules apply to Sync models and to the periodic refresh.

Turning the free defaults off

Set FREE_MODELS_ENABLED=false before the first start to skip the install. No provider, key, models, tiers, or marker are written, so the gateway has no compatibility tiers until an administrator configures providers and cascades. Setting the variable back to true on a later start installs the defaults then. Any tier, alias, or provider that an administrator created in the meantime under a default name is kept as it is: the install creates only the tier names that are still free and adds no models or credentials to an administrator's provider named openrouter-free. Setting it to false after the install has completed does not remove anything; disable or delete the provider, models, or tiers from the dashboard instead. A disabled or deleted default is never recreated: the installer never runs again, a disabled model stays disabled through every catalog refresh, and deleting a model that a catalog sync created records a model tombstone, so later refreshes and restarts skip that model even though OpenRouter still lists it. To bring a deleted model back, create it again from the dashboard with the same model key; that removes its tombstone and makes the model manual. A manual model leaves no tombstone when it is deleted, so deleting that re-created model lets the next catalog refresh add it again as a synced model; delete it once more after that refresh to keep it away. Deleting the provider removes its tombstones.

Restarts and administrator changes

The free defaults are installed exactly once per database. The install and its bootstrap marker are written in one transaction: if the process stops during the first start, nothing is written and the next start installs the defaults again. After the marker exists, restarts never re-run the install, and catalog refreshes honour model deletions and disables, so a tier, model, provider account, or provider that an administrator reorders, disables, edits, or deletes stays that way. The startup log entry free model defaults installed lists the created and kept tiers.

Monitoring and maintenance

Use the Router-published /healthz/ path for readiness checks. The response includes ok, database reachability, snapshot generation, and uptime. The management dashboard exposes system metrics, cost and token aggregation, errors, activity, sessions, audit logs, live streams, and exports.

Maintenance intervals do not overlap with another run of the same job. Failures are logged and do not terminate the process. Provider discovery and pricing refresh use direct network access only as lifecycle/catalog operations; request-time vendor LLM generation remains inside AchillesAgentLib. Authenticated Ploinky-agent capability calls use their signed exact-byte Router transport.

Shutdown and verification

On SIGTERM or SIGINT, the process stops accepting connections, marks the application as draining, stops background and discovery timers, closes live log subscribers, waits up to SHUTDOWN_GRACE_MS for active work, flushes audit updates, shuts down backend generations, and closes SQLite. A second signal forces exit.

Run npm test before deployment. After a restart, verify the Router health path, the agent container status, and the presence of the configured SQLite file inside the container. Production state changes should use the repository's deployment and administrative workflows; direct host access is reserved for read-only diagnosis unless the operation explicitly requires otherwise.
