API and Management

Soul Gateway exposes inference, model discovery, health, and administrative interfaces through the agent-port path assigned by the Ploinky Router. The Router removes the external prefix before dispatching to the internal service, so route definitions in src/ begin with /v1, /management, or /healthz.

Public model interface

Method and internal pathBehavior
POST /v1/chat/completionsAccepts OpenAI Chat Completions input and returns OpenAI-compatible buffered JSON or server-sent events.
POST /v1/messagesAccepts Anthropic Messages input and serializes the canonical response as Anthropic JSON or events.
POST /v1/responsesAccepts OpenAI Responses input and returns Responses-compatible JSON or events.
POST /v1/embeddingsNormalizes embedding input, resolves a direct model, and calls a backend that advertises embedding support.
GET /v1/modelsLists addressable direct models, cascade models, and aliases with additive pricing, context, tag, free-model, and cascade metadata.

Every public model route requires a signed-subject key. Agent callers send the raw signed value. User callers send the sk-soul- wrapper issued through Ploinky. A valid signature creates or reuses the deterministic API-key row for that subject; revoked or expired rows remain denied.

Request and response behavior

Completion requests must provide a model name and messages valid for their ingress protocol. The gateway resolves normalized names and aliases against the bound runtime snapshot. Unknown models return a structured model-not-found response. The stream flag selects protocol-specific streaming; non-streaming requests buffer the canonical events before serialization.

Errors use the caller's protocol where an error frame exists. Provider failures are classified into authentication, quota, rate-limit, content-policy, model-not-found, bad-request, timeout, and availability categories. Classification controls HTTP status, retry eligibility, cascade eligibility, and cooldown behavior. An upstream client error other than those categories, such as an invalid parameter, returns HTTP 400 with error type provider_bad_request and the upstream message, without retrying or trying another model.

When a tier's children fail because of the provider account rather than the models, the caller receives that account-scoped failure: HTTP 429 provider_quota_exhausted or provider_accounts_exhausted for an exhausted daily quota, or HTTP 502 provider_auth_error for a rejected key. A generic HTTP 503 tier_exhausted means the children failed for model-specific reasons. A tier that exceeds its tier budget before any child answers returns HTTP 504 provider_timeout.

A streaming request receives no response bytes until a model has produced its first text or tool-call delta, so failures before that point are handled like buffered failures and return an ordinary JSON error when no model answers. A model response that contains no text and no tool call, for example a reasoning-only answer cut off by the token limit, is treated as an empty response (HTTP 502 provider_server_error, "Provider returned an empty response") and the next tier child is tried. If the model fails after streaming has started, the stream ends with the protocol's error event; it is not silently cut off and is never continued by another model.

Management interface

The dashboard at /management/ and every management API route require a verified Ploinky protected-route invocation whose authenticated user has the admin role. Soul Gateway verifies the signed invocation surface and replay protection; caller-supplied identity headers do not grant management access.

The management API groups operations by purpose:

  • API keys: list, provision user keys, inspect, update, revoke, and delete.
  • Models and tiers: create or modify direct and cascade models, manage children, reorder cascades, and enable or disable tiers. Deleting a synced model keeps later catalog syncs from recreating it until the model is created again manually.
  • Providers: create provider records, test connectivity, discover or synchronize models, run OAuth flows, and manage provider accounts. A synchronization whose upstream catalog came back empty reports emptySkipped and changes nothing, so all-zero counters after an outage are not mistaken for an unchanged catalog.
  • Middleware: rescan catalogs and manage gateway, model, and provider bindings.
  • Policy state: manage blacklist rules and clear model cooldowns.
  • Observability: inspect logs, sessions, agent trees, usage and cost metrics, export JSON or CSV, and subscribe to live logs over SSE or WebSocket.

The Explorer integration exposes the admin-only soul-gateway-settings settings entry and the soul-gateway-tool-button toolbar button, and both open the agent-served dashboard in a maximized Explorer modal that embeds the Router-prefixed /management/ URL in an iframe. The dashboard reuses Explorer's shared UI styles and light or dark theme. It does not create an independent settings store, theme store, or authentication flow.

Connect a SuperGrok subscription

Administrators can connect an eligible SuperGrok subscription from Providers → Add Provider by choosing xAI SuperGrok and creating the provider. Open Manage → Add Account, follow the verification link, and enter the displayed code if requested. Sign in using the account that owns the subscription, including Google sign-in when applicable, and approve access. The browser can run on another computer; no localhost callback or port forwarding is needed.

The dashboard waits for approval, then lists the connected account. The gateway saves encrypted OAuth tokens, refreshes them before expiry, and synchronizes the available models. Use the provider's model synchronization action if a later catalog refresh is needed. Available models and usage limits depend on the subscription. An expired or denied authorization displays an error; use Add Account to try again.

The xAI SuperGrok template uses the OpenAI-compatible provider backend at https://api.x.ai/v1. The xAI (Grok) template uses an API key. See xAI's subscription integration announcement for the supported account authorization workflow.

Health and CLI

GET /healthz and GET /healthz/ return gateway liveness, SQLite reachability, runtime snapshot generation, and uptime. The Ploinky manifest publishes health without login. cli.sh exposes status, health, keys, models, and logs [n]; management commands forward PLOINKY_AUTH_COOKIE to the Router.
