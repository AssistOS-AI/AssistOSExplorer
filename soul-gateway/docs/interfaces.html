API and Management

Soul Gateway exposes inference, model discovery, health, and administrative interfaces through the agent-port path assigned by the Ploinky Router. The Router removes the external prefix before dispatching to the internal service, so route definitions in src/ begin with /v1, /management, or /healthz.

Public model interface

Method and internal pathBehavior
POST /v1/chat/completionsAccepts OpenAI Chat Completions input and returns OpenAI-compatible buffered JSON or server-sent events.
POST /v1/messagesAccepts Anthropic Messages input and serializes the canonical response as Anthropic JSON or events.
POST /v1/responsesAccepts OpenAI Responses input and returns Responses-compatible JSON or events.
POST /v1/embeddingsNormalizes embedding input, resolves a direct model, and calls a backend that advertises embedding support.
GET /v1/modelsLists addressable direct models, cascade models, and aliases with additive pricing, context, tag, free-model, and cascade metadata.

Every public model route requires a signed-subject key. Agent callers send the raw signed value. User callers send the sk-soul- wrapper issued through Ploinky. A valid signature creates or reuses the deterministic API-key row for that subject; revoked or expired rows remain denied.

Request and response behavior

Completion requests must provide a model name and messages valid for their ingress protocol. The gateway resolves normalized names and aliases against the bound runtime snapshot. Unknown models return a structured model-not-found response. The stream flag selects protocol-specific streaming; non-streaming requests buffer the canonical events before serialization.

Errors use the caller's protocol where an error frame exists. Provider failures are classified into authentication, quota, rate-limit, content-policy, model-not-found, timeout, and availability categories. Classification controls HTTP status, retry eligibility, cascade eligibility, and cooldown behavior.

Management interface

The dashboard at /management/ and every management API route require a verified Ploinky protected-route invocation whose authenticated user has the admin role. Soul Gateway verifies the signed invocation surface and replay protection; caller-supplied identity headers do not grant management access.

The management API groups operations by purpose:

  • API keys: list, provision user keys, inspect, update, revoke, and delete.
  • Models and tiers: create or modify direct and cascade models, manage children, reorder cascades, and enable or disable tiers.
  • Providers: create provider records, test connectivity, discover or synchronize models, run OAuth flows, and manage provider accounts.
  • Middleware: rescan catalogs and manage gateway, model, and provider bindings.
  • Policy state: manage blacklist rules and clear model cooldowns.
  • Observability: inspect logs, sessions, agent trees, usage and cost metrics, export JSON or CSV, and subscribe to live logs over SSE or WebSocket.

The Explorer integration exposes the admin-only soul-gateway-settings entry and opens the same Router-protected dashboard. It does not create an independent settings store or authentication flow.

Health and CLI

GET /healthz and GET /healthz/ return gateway liveness, SQLite reachability, runtime snapshot generation, and uptime. The Ploinky manifest publishes health without login. cli.sh exposes status, health, keys, models, and logs [n]; management commands forward PLOINKY_AUTH_COOKIE to the Router.
