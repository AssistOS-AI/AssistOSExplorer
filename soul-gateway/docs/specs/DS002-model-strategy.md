## Introduction

Soul Gateway presents direct models, aliases, and cascade tiers through one model namespace. The model strategy determines which provider execution path runs while keeping caller protocols independent from provider configuration.

## Core Content

### Addressable model namespace

Every enabled [direct model](../wiki.html#definition-direct-model), [cascade model](../wiki.html#definition-cascade-model), and alias must have a unique addressable name in the [runtime snapshot](../wiki.html#definition-runtime-snapshot). Model-name normalization may remove supported compatibility prefixes and resolve aliases, but it must not silently select an unrelated model when the requested name is absent.

<code>GET /v1/models</code> must enumerate addressable models and aliases in an OpenAI-compatible list. Gateway metadata may add pricing, context, tag, free-model, billing-type, and cascade child-count fields without changing the base model fields expected by compatible clients.

### Direct execution

A direct model must reference one provider and one provider model identifier. Execution must apply its concurrency and queue limits, retry and request timeouts, provider middleware, and a temporary [credential lease](../wiki.html#definition-credential-lease). A vendor LLM [provider backend](../wiki.html#definition-provider-backend) must use AchillesAgentLib for request-time inference. A Ploinky-agent backend may use its signed exact-byte Router capability transport. Every backend must normalize its result into the [canonical stream](../wiki.html#definition-canonical-stream).

### Cascade execution

A cascade model must contain ordered child references and must not own provider credentials. It must try the highest-priority enabled child that is not excluded by a current cooldown or an earlier failed attempt. Only a classified error with <code>cascade=true</code> may advance to another child. A classified cooldown error must persist cooldown state and request a snapshot refresh without delaying the in-flight attempt transition.

A child failure classified as an [account-scoped failure](../wiki.html#definition-account-scoped-failure), such as a rejected provider key or an exhausted daily provider quota, must exclude every remaining child on the same provider for the rest of that request, because those children share the failed account. When the walk ends for that reason, the caller must receive the account-scoped error, for example <code>provider_quota_exhausted</code> or <code>provider_auth_error</code>. A tier-exhausted error is returned when the children failed for model-specific reasons or no eligible child remains for another reason.

Each <code>model_children.settings</code> record may tune how one tier uses one child without duplicating the model row. The supported keys are <code>requestTimeoutMs</code>, a <code>retryPolicy</code> object merged over the child model's own retry policy (including <code>firstEventTimeoutMs</code>, <code>firstContentTimeoutMs</code>, and <code>streamIdleTimeoutMs</code>, and taking precedence over the free-model execution policy of a free-only provider), and <code>requestParams</code>, from which only <code>reasoning</code> and <code>reasoning_effort</code> reach the provider request. Identity, provider, and pricing always come from the child model record.

A request that contains image parts must skip children whose recorded capabilities declare <code>supportsVision=false</code>, and a request that declares tools must skip children that declare <code>supportsTools=false</code>. Children with unknown capabilities remain eligible. If this filtering would leave no child, the unfiltered list is used so an operator-configured tier still reaches its upstream and reports the provider's own error.

A cascade whose metadata sets <code>cascadeBudgetMs</code> must bound the whole child walk by that [tier budget](../wiki.html#definition-tier-budget). When the budget expires before a child returns a committed response, the in-flight attempt is aborted, no further child is tried, and the caller receives a provider timeout (HTTP 504). The budget stops applying once a child has committed a response, so a long streamed answer is limited only by that child's own stream deadlines.

The cascade must stop after its configured maximum attempts or when no eligible child remains. It must preserve the successful child's response and attach attempt, model, account, retry, and queue metadata used by observability.

### Standard tiers and reconciliation

The public [compatibility tiers](../wiki.html#definition-compatibility-tier) are <code>fast</code>, <code>code</code>, <code>plan</code>, <code>write</code>, <code>deep</code>, <code>ultra</code>, and <code>web-assist</code>. <code>LLM_DEFAULT_TIERS</code> lists the tier names that the free defaults create; its default is <code>fast,code,plan,write,deep,ultra,web-assist</code>. The free defaults create only names from that list that have a built-in free definition, and a name added to the list after the first start is created on the next start.

On first start, Soul Gateway installs the free model defaults once: the [free-only provider](../wiki.html#definition-free-only-provider) <code>openrouter-free</code>, one encrypted provider account, nine baseline free models, and one cascade per requested tier. The definitions live in <code>src/bootstrap/free-model-catalog.mjs</code> and the one-time install in <code>src/bootstrap/free-model-defaults.mjs</code>. Every child is a free OpenRouter model. The child lists and per-tier deadlines come from measured requests against the free catalog, which changes over time; they are defaults, not a promise that any given model stays available.

Each child has two pre-output deadlines. The silence window (<code>firstEventTimeoutMs</code>) ends an attempt whose upstream sends nothing for that long; it restarts on model reasoning and on nothing else, so a reasoning model that is visibly working is not abandoned while a trickle of other events cannot keep a silent one alive. The first-content cap (<code>firstContentTimeoutMs</code>) ends an attempt that has not produced its first answer token or tool call within that time from the attempt start, however much it reasons. SSE keepalive comments do not restart the silence window, because a router sends them while its model does nothing. The tier budget bounds the whole fallback walk. The values are written into the tier child settings once at install, so they apply to databases installed with this version.

The silence window therefore also bounds the queue phase, in which the model has been accepted upstream but has not started. A model that queues longer than its silence window before sending its first model event is abandoned even though it would have answered, and the shared-quota request it was holding is spent. This is the deliberate cost of not treating router keepalive comments as liveness: a comment proves only that the router is alive. One capture on 21 September 2026 showed a free reasoning model sending nothing but keepalive comments for 47 seconds before its first reasoning delta; after that first delta its reasoning arrived at most 2 seconds apart, well inside every window above. Sizing a window is therefore a trade between abandoning a slow queue and holding a request that will never answer.

Some free models are kept out of every tier, because a tier fallback must return an ordinary assistant answer. Classifiers, rerankers and embedding models are never stored for a free-only provider: their identifier carries one of the tokens <code>safety</code>, <code>shield</code>, <code>guard</code>, <code>moderation</code>, <code>embed</code>, <code>rerank</code>, <code>classif</code>, or <code>reward</code> (see DS009). Two models measured as unfit are stored, stay callable by their direct model key, and never join a tier: <code>nvidia/nemotron-3.5-lightning:free</code> answered HTTP 200 and then sent no events for 45 seconds in repeated measurements, and <code>openrouter/free</code> routed a plain coding prompt to a safety classifier and returned a verdict instead of an answer. The list lives next to the baseline as <code>TAG_TIER_EXCLUDED_MODEL_IDS</code>. Every catalog sync of a free-only provider marks those rows with the model metadata flag <code>excludeFromTagTiers</code>, matching the identifier without regard to letter case, and recomputed on each sync because a sync replaces the metadata of enabled rows; the tag-tier code reads only that flag and knows no provider or model name. A sync that writes the flag on a row that already exists also removes that model from every auto tag tier, so an exclusion list that reaches a model after its row exists still takes effect; operator cascades and compatibility tiers keep the model. Models restricted to specific agent harnesses are left out of the baseline for the same reason.

Every direct model on a free-only provider runs with the free-model execution policy for each field its row does not set: one attempt, a 30 s silence window, a 120 s first-content cap, a 60 s idle deadline for a committed stream, a 60 s cooldown, and <code>lengthWithoutContentFails</code>, so inside a cascade a reply that the token limit cut off before any content fails over to the next child like an empty answer, while a direct request to the model keeps the length finish (DS007). A committed stream is bounded twice: the idle deadline every event restarts, and a content gap of <code>max(streamIdleTimeoutMs, firstContentTimeoutMs)</code> that only content restarts, so a stream that commits and then reasons without end ends at 120 s under this policy instead of lasting as long as the upstream reasons (DS007). The policy is resolved once when the runtime snapshot is loaded, keyed on the provider's <code>free_only</code> setting, so a model a later sync adds or recreates is bounded exactly like the baseline, and tier child settings still override it. Without it a synced row would fall back to the 120 s row timeout and three attempts, which measured 364 s and three shared-quota requests for one stalled request.

The install creates the provider, its account, and the baseline models at most once per database, creates each tier at most once, and never overwrites records it finds. A tier name that already exists as a model or alias is kept, and an administrator's provider named <code>openrouter-free</code> is used as found without adding models or credentials to it. The provider, account, and baseline models are installed only by the first install, so when an administrator's provider held that key then, they are never installed later, even after that provider is deleted. This matters when <code>FREE_MODELS_ENABLED=false</code> is later changed to <code>true</code>: tiers, aliases, and providers the administrator created in the meantime stay as they are, and only the missing tier names are created. Its [bootstrap marker](../wiki.html#definition-bootstrap-marker) records every tier the install has handled, created or kept, so a tier, account, or provider that an administrator later reorders, disables, edits, or deletes is never recreated by the installer. A requested tier none of whose children is an enabled model of the free provider is not created, because an empty cascade would answer every request with <code>tier_exhausted</code> and, once handled, would never be filled; it stays pending, like a tier name added to <code>LLM_DEFAULT_TIERS</code> after the first start, and a later start creates it once one of its children is available. A tier created with only some of its children tries at most that many. Catalog syncs keep the same promise for models: a disabled model stays disabled, and a synced model that an administrator deletes through the management interface leaves a [model tombstone](../wiki.html#definition-model-tombstone), so no later sync or restart recreates it (DS008). Creating that model manually brings it back.

The install runs on any database that lacks the <code>free-model-defaults</code> marker, including an existing gateway that already has its own providers and tiers. Such a deployment should start with <code>FREE_MODELS_ENABLED=false</code> when it does not want the free provider and tiers.

Tag-tier reconciliation may create or update cascade models derived from predefined tags. An auto tag tier contains exactly the enabled direct models that carry its tag; it has no generic fallback child, so a tag with no tagged model yields an empty tier. The initial bootstrap runs once per database, recorded by the <code>initial-tag-tiers</code> [bootstrap marker](../wiki.html#definition-bootstrap-marker); later catalog synchronizations may append newly tagged models. Bootstrap and append operations must modify only auto-generated tag tiers (<code>metadata.autoTagTier</code> or <code>metadata.seededBy='tag-tier-bootstrap'</code>); a compatibility tier such as <code>fast</code> or an operator cascade that shares a tag name keeps its own children and order. Tag reconciliation never creates an auto tag tier under a public compatibility tier name (<code>fast</code>, <code>code</code>, <code>plan</code>, <code>write</code>, <code>deep</code>, <code>ultra</code>, <code>web-assist</code>), even when a predefined tag has that name, so a start with the free defaults disabled cannot pre-empt those tiers. Reconciliation must request a new runtime snapshot after material catalog changes.

### Metadata and pricing

Model metadata may combine provider discovery, curated metadata, and an external pricing directory. Explicit stored values must retain precedence where the classifier contract requires them. Pricing may be token-based, request-based, free, or externally resolved. Budget enforcement must not invent a cost when the selected model lacks sufficient pricing evidence.

### Transport boundary

Soul Gateway may own direct HTTP for connectivity checks and model discovery because those operations validate or synchronize provider state. It must not use those lifecycle paths to serve completion or generation results. A new vendor LLM protocol family must first exist in AchillesAgentLib. The exact-byte Ploinky-agent capability route is limited to authenticated Router delegation, and a new search backend must remain behind the standard model interface.

Soul Gateway contains no OpenCode-specific upstream code. OpenCode's hosted API refuses free-tier inference from any client other than OpenCode (HTTP 403 <code>FreeTierError</code>), so the <code>opencode-zen</code> and <code>opencode-go</code> presets serve paid keys only, and the gateway does not imitate a client. Any agent that exposes the OpenAI chat-completions surface, including one that wraps a native client, is consumed through the generic Ploinky agent provider path like every other agent.
