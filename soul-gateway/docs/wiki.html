Soul Gateway Wiki

This page is the canonical terminology source for Soul Gateway documentation and specifications. Each entry describes the term's role, users, relationships, and governing boundary.

Account-scoped failure
An account-scoped failure is a provider error that describes the provider account used for the attempt, not the model that was called. The OpenAI-compatible classifier marks HTTP 401 (rejected key), HTTP 402 (no credit), and an HTTP 429 that signals an exhausted daily or billing quota as account-scoped. A 429 counts as a quota signal only for the error types insufficient_quota or billing_hard_limit_reached, x-ratelimit-remaining: 0 with a reset more than five minutes away, or, on a free-only provider only, a message that names a per-day or daily limit, free-models-per-day, insufficient credits, or billing, because only there does every model draw on one account allowance; a per-minute limit or a message that only says "quota" stays a model-level rate limit; the credential lease middleware does the same when a provider that needs credentials has no eligible account (provider_accounts_exhausted). Such an error is never retried and never cools down a model. Within a cascade model, it removes every remaining child on the same provider from the current request, because those children share the failed account and would fail the same way while spending shared quota. The account is then marked quota_exhausted until the x-ratelimit-reset time reported by the upstream, clamped to between one minute and 26 hours. Without a reset header the lock lasts at most 15 minutes (or until the next UTC midnight if that is sooner), after which the account is tried again, so a misclassified error cannot block the account for long. The scheduled quota-reset sweep restores the account after the lock expires, and replacing the account key clears the lock immediately. When every candidate failed for an account reason, the caller receives that error, for example HTTP 429 provider_quota_exhausted or HTTP 502 provider_auth_error, instead of a generic tier_exhausted, so an operator can tell an exhausted shared quota from unavailable models. A momentary per-model HTTP 429 is not account-scoped; it cools that one model down briefly.
AchillesAgentLib
AchillesAgentLib is the runtime library that owns request-time vendor LLM provider transport. Soul Gateway selects the backend family, leases credentials, supplies model and provider settings, and converts the library's stream events into the gateway canonical stream. Provider lifecycle checks and model discovery may use direct vendor HTTP because they do not return an inference result to a caller. The Ploinky-agent backend owns an authenticated Router capability call because its signed request hash must cover the exact serialized bytes; this does not authorize vendor LLM backends to bypass AchillesAgentLib. Provider-specific search implementations may own search transport behind the same model-facing contract.
Agent-port path
An agent-port path is the Ploinky Router prefix that maps an external HTTP request to a port exposed by a named agent. Soul Gateway uses /base-agent-additional-server/soul-gateway/7000/. The manifest assigns separate access modes beneath that prefix: inference is available to guests at the Router layer but still requires a Soul Gateway signed-subject key, management requires an authenticated Ploinky identity, and health is public.
Bootstrap marker
A bootstrap marker is a row in the SQLite table gateway_bootstrap_state that proves a one-time initialization step completed. Two steps use one: the first-start free model defaults (key free-model-defaults, version 1) and the initial auto tag-tier bootstrap (key initial-tag-tiers), whose marker is written after its tiers exist so an interrupted start simply reruns that idempotent step. The install writes the provider, encrypted account, baseline models, tiers, and the marker in one BEGIN IMMEDIATE transaction, so an interrupted start leaves neither the records nor the marker and the next start retries. Once the marker exists the provider install never runs again, and a tier that the marker's JSON metadata lists as created or kept is never created again, which keeps administrator changes (a disabled tier, a deleted model, a replaced key) from being undone on restart. A later start only creates tiers that are still pending: a name added to LLM_DEFAULT_TIERS, or a tier that had no enabled free model among its children and was therefore not created empty; it adds them to the metadata in the same transaction. FREE_MODELS_ENABLED=false skips the install without writing a marker, so enabling the setting later still installs the defaults; tiers, aliases, and providers that an administrator created in the meantime under default names are kept, and only missing tier names are created. A third key, free-model-defaults-tag-tiers, records that the free provider's models were appended once to the matching auto tag tiers; it is written only after models joined, so a start at which the provider has no enabled model leaves the join for a later start.
Canonical request
The canonical request is the internal representation shared by all completion protocols. Ingress normalizers translate OpenAI Chat, Anthropic Messages, and OpenAI Responses fields into this representation before validation, model policy, or provider execution. It preserves messages, selected model, streaming intent, tool definitions, token controls, and provider options that downstream code supports. Protocol serializers later convert the canonical result back to the caller's wire format.
Canonical stream
The canonical stream is Soul Gateway's protocol-independent sequence of model events. Backend adapters emit message-start, text-delta, tool-call-delta, usage, error, and completion events. Gateway and provider middleware can inspect or transform these events without depending on OpenAI or Anthropic wire syntax. Egress serializers translate the events to the selected streaming protocol, while buffered requests collect them into a completed response.
Cascade model
A cascade model is an addressable model whose children are other enabled models ordered by priority. It lets callers select one stable model name while the gateway tries eligible children until one succeeds or the configured attempt limit is exhausted. Only classified errors marked for cascade advance to another child; cooldown-marked failures also create persistent cooldown state. A cascade has no provider account of its own because each child retains its direct-model provider boundary.
Compatibility tier
A compatibility tier is a stable public model name such as fast, code, plan, write, deep, ultra, or web-assist that callers use without knowing which provider model answers. Each tier is a cascade model whose ordered children are tried until one answers. On first start, Soul Gateway creates the tiers listed in LLM_DEFAULT_TIERS from the free model defaults: every child is a free model of the free-only provider openrouter-free, with per-child deadlines and a tier budget chosen for the tier's purpose, such as an 11-second budget for fast. Tiers are ordinary configuration records: administrators can reorder, replace, or disable their children, and the one-time install never overwrites those changes. Tag-tier reconciliation maintains separate cascades for predefined model tags, each containing exactly the enabled direct models with that tag, and does not modify compatibility tiers.
Credential lease
A credential lease is the temporary right to use one eligible provider account for a single backend attempt. The credential manager selects an account, decrypts or refreshes its secret material, and returns a lease containing the account identity and authentication data. Execution releases the lease in a finally block on success or failure. Quota state and account rotation can exclude an account without exposing its secret to callers.
Direct model
A direct model maps one public model_key to a provider, provider model identifier, execution backend, concurrency and timeout controls, pricing metadata, capabilities, and policy overrides. Direct execution acquires concurrency, retries classified failures, leases credentials, compiles provider middleware, and invokes a backend. Every enabled direct model requires both a provider and provider model identifier in the SQLite schema.
Free-only provider
A free-only provider is a provider record whose settings.free_only is true. Soul Gateway only stores and runs models on it that are provably free. The first-start defaults create one, openrouter-free, which uses the OpenAI-compatible backend at https://openrouter.ai/api/v1, discovers models from /models/user, and holds the bundled restricted OpenRouter key or an administrator's replacement. Catalog synchronization admits an entry only when its identifier ends in :free as its only variant (or is openrouter/free), every listed price is an explicit zero, and its declared modalities are text in and text out; repriced or removed models are disabled. Before each request, the gateway rejects a non-free model identifier and forces zero OpenRouter price ceilings while removing request options that could add paid fallback models, routes, plugins, or web search. Embedding requests are refused. The upstream key itself has a zero credit limit and a free-models-only guardrail, which blocks paid models independently. A free-only provider does not make free service unlimited: the bundled key's daily free-request allowance is shared by every installation that uses it, and the key expires on 2027-03-20.
Liveness event
A liveness event is the internal canonical stream event activity, emitted when an upstream proves it is working without producing answer content, for example while a model streams its reasoning. It carries no client content and exists only for deadlines: it restarts the pre-commit silence window and a committed stream's idle deadline, and it never restarts the pre-commit first-content cap or a committed stream's content-gap deadline, so an upstream that only reasons is still bounded. Stream priming consumes every liveness event, so buffered responses, streamed responses, response capture, and callers never see one.
Middleware catalog
The middleware catalog is the generation-scoped registry of enabled built-in and extension middleware. It resolves bindings by gateway, model, and provider scope and composes them through the shared kernel. Administrative rescans create a new generation while previous generations receive a grace period for in-flight work. The catalog defines availability and ordering; each middleware module defines its own settings and observable policy effect.
Model tombstone
A model tombstone is a row in model_tombstones that records a provider-synced model key an administrator deleted through the management interface. Model rows are hard-deleted, so without it the next catalog sync would recreate a model that the provider still lists. A catalog sync never creates a tombstoned key. While some row holds that key the tombstone is suspended — the row is synchronized normally — but it stays recorded and applies again once the key is free, so moving a row onto the key and off it again cannot undo the deletion. Creating the model manually with the same key is the only action that removes a tombstone; deleting the provider removes all of its tombstones.
Ploinky agent model
A Ploinky agent model represents an OpenAI-compatible model route discovered from another enabled Ploinky agent. Discovery uses the Router's authenticated agent-discovery interface and reconciles provider and model records before a runtime snapshot loads. Agent identity, route ownership, and request hashes prevent ambiguous delegation. The local Soul Gateway remains the model hub and owns the aliases and tier policy presented to its callers.
Ploinky Router
The Ploinky Router is the host process that exposes agent-port routes, applies path-level access policy, forwards authenticated user metadata, and signs protected HTTP invocations. Soul Gateway depends on the Router for management identity and route reachability but performs its own signed-subject authentication for public inference. Management requests must include both an administrator role and a verified, replay-protected invocation surface.
Provider backend
A provider backend is a catalog entry with a validated manifest and an execute() terminal used for one provider protocol family. The manifest declares its key, authentication strategy, supported formats, streaming and tool support, plus lifecycle functions such as connectivity testing or model discovery. Vendor LLM backends adapt execution context to AchillesAgentLib and normalize results; lifecycle functions may contact vendor metadata endpoints directly. The Ploinky-agent backend is a distinct Router capability backend that signs and sends its exact serialized body.
Provider middleware
Provider middleware runs around one provider attempt after a direct model and credential lease are selected. Bindings can inject prompts, compact context, filter responses, or compress output for a specific provider without changing the public model interface. The provider middleware registry combines built-ins and extension modules, and the execution chain resolves the active binding set for each attempt.
Runtime snapshot
The runtime snapshot is an immutable, generation-numbered in-memory view of configuration used by request processing. It contains providers, models, aliases, tiers, cascade children, API-key policy, blacklist rules, cooldowns, and middleware bindings loaded from SQLite. Each request pins one snapshot so administrative updates cannot change its routing halfway through execution. Mutating management operations request a refresh that replaces the snapshot for later requests.
Signed-subject key
A signed-subject key proves either a Ploinky agent identity in the form agent:<repo>/<agent> or a Ploinky user identity in the form user:<id>. Ploinky signs the exact subject bytes with Ed25519, and Soul Gateway verifies the signature with PLOINKY_AGENT_API_PUBLIC_KEY. Agent keys travel in raw <subject>|<signature> form. User keys must be wrapped as canonical base64url with the sk-soul- prefix. A deterministic SQLite API-key row carries limits, budget, revocation, and expiry state for the verified subject.
Stream priming and commit
Stream priming is the step inside each model attempt that pulls the provider's stream until the first text delta or tool-call delta arrives. Backends start the upstream request lazily, so without priming a streamed attempt would count as successful before the provider answered, and a rejected, rate-limited, or silent upstream could no longer fall back to another model. With priming, those failures happen inside the attempt, where retry and the cascade model can still act on them, and two deadlines bound the wait for the first content event: retryPolicy.firstEventTimeoutMs is a silence window that restarts on a liveness event and on nothing else, and retryPolicy.firstContentTimeoutMs caps the time from the attempt start to the first text or tool call. SSE keepalive comments do not restart the silence window. A stream that ends, or reports completion, without any text or tool call, such as an empty HTTP 200 stream, is an empty response: the attempt fails with provider_server_error ("Provider returned an empty response"), is not retried, and the cascade moves to the next child. A reply that the token limit cut off before any content (finish reason length) is instead returned with that finish reason, so the caller can raise its limit, unless the model's retry policy sets lengthWithoutContentFails, as the free-model execution policy does; then it fails over like an empty response. Usage and completion events alone never commit. The first text or tool-call delta commits the response: the events already pulled are replayed to the caller, and from then on a failure ends the caller's stream with a protocol error event instead of switching to another model's output. A committed stream is also watched by two deadlines: an idle deadline (retryPolicy.streamIdleTimeoutMs, falling back to STREAM_IDLE_TIMEOUT_MS) that every event restarts, and a content-gap deadline of max(streamIdleTimeoutMs, firstContentTimeoutMs) that only content restarts. The stream is aborted when it falls silent, and also when it produces nothing but liveness for the content gap.
Tier budget
A tier budget is the maximum time, in milliseconds, that a cascade model may spend trying its children, stored as metadata.cascadeBudgetMs on the cascade record. It exists because each child also has its own timeout, and a slow first child could otherwise consume a caller's whole deadline before a faster sibling was tried. When the budget expires before any child has committed a response, the in-flight attempt is aborted, no further child is tried, and the caller receives a provider timeout (HTTP 504). After a child commits a response the budget no longer applies, so a long streamed answer is limited only by that child's stream deadlines. The free defaults set 11 seconds for fast, 60 seconds for web-assist, 240 seconds for code, plan, and write, and 300 seconds for deep and ultra. A cascade without the field has no overall budget.
