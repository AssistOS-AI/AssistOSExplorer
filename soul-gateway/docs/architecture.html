Soul Gateway Architecture

Soul Gateway separates the caller-facing protocol from provider-specific execution. A request enters through the Ploinky Router, passes a fixed route chain, and reaches either one direct model or a prioritized cascade model. The same kernel composition contract runs route, gateway, model, provider, and backend middleware.

Canonical route chain

runRouteRequest() creates one request context and composes error handling, JSON parsing, signed-subject authentication, caller identity, snapshot binding, ingress normalization, audit setup, validation, model resolution, agent-loop protection, session resolution, response serialization, and gateway dispatch. OpenAI Chat, Anthropic Messages, and OpenAI Responses inputs become one canonical request before policy and routing inspect them.

The request binds one immutable runtime snapshot. That snapshot contains enabled providers, direct models, cascade children, aliases, tiers, active cooldowns, API-key policy data, blacklist rules, and middleware bindings. Administrative mutations request a new snapshot generation; in-flight requests retain the generation they already bound.

Execution and provider ownership

A direct model acquires its concurrency slot, enters retry and timeout control, leases one provider account, compiles provider middleware, and invokes the selected backend. The credential lease is released in a finally path. Request-time vendor LLM transport belongs to AchillesAgentLib; Soul Gateway supplies the model, credential, base URL, headers, and provider settings, then converts Achilles stream events to the gateway's canonical stream. The Ploinky-agent backend separately signs the exact serialized request bytes for an authenticated Router capability call.

Inside one direct-model attempt the chain runs in this order: retry control, the attempt timeout, the credential lease, provider middleware, stream priming, and the backend. The timeout step gives each attempt a deadline linked to the caller's connection, so a client disconnect or an expired tier budget aborts the upstream request. Stream priming pulls the backend's lazy stream until the first text or tool-call delta, so an upstream rejection, rate limit, or silence fails inside the attempt where retry and cascade can act, in streamed and buffered mode alike. Before that delta, a silence window that restarts on liveness events and nothing else, and a first-content cap measured from the attempt start, bound the wait. Model reasoning arrives from the Achilles bridge as a content-free liveness event: it restarts the silence window and the idle timer but neither the first-content cap nor the content-gap deadline below, and stream priming consumes it so no caller ever receives it. A stream that ends without text or a tool call, such as a reasoning-only answer cut off by the token limit, fails the attempt as an empty response (provider_server_error), which is not retried but moves the cascade to the next child. When a streamed attempt returns, the timeout step hands its deadline to the stream: the whole-attempt timer stops and two timers take over. An idle timer restarts on every event, liveness included, and a content-gap timer of max(streamIdleTimeoutMs, firstContentTimeoutMs) restarts only on content, so a committed stream is aborted when it falls silent, when it produces nothing but reasoning for the content gap, or when the caller stops reading. A buffered attempt holds no such lease: it completes inside the whole-attempt deadline.

Retry, deadlines, and cooldowns read one effective retry policy per direct model. The runtime snapshot resolves it when it loads: a model of a free-only provider gets the free-model execution policy for every field its row does not set, and cascade child settings override it for that tier.

A cascade model orders enabled children by priority and invokes one child at a time. It first drops children that cannot serve the request, such as a child that declares no image input for a request with images, and applies per-child timeouts and reasoning settings stored on the cascade link. A classified error may permit another child, may place a model in cooldown, or may fail the request immediately. An account-scoped failure, such as an exhausted shared quota, removes the failed provider's remaining children and is returned to the caller when no other provider remains. The first text or tool-call delta commits the response; after that a failure ends the caller's stream with a protocol error event and never switches to another model. The gateway persists cooldowns asynchronously and refreshes the snapshot so later requests avoid unavailable children.

Startup order

src/bootstrap.mjs prepares configuration in a fixed order so the first runtime snapshot already contains usable tiers. After SQLite and services are ready, it reconciles discovered Ploinky agents. It then installs the first-start free model defaults (a free-only provider, an encrypted account, baseline free models, and the compatibility tiers) in one transaction guarded by a bootstrap marker. Only then does it refresh provider model catalogs over the network, bootstrap auto tag tiers once (recorded by the initial-tag-tiers bootstrap marker), reconcile compatibility aliases, and load the first snapshot. Because the free tiers and baseline models exist before any catalog request, a start without internet access still has every tier; a failed catalog refresh leaves them in place.

Middleware and policy

The middleware catalog loads built-in and extension middleware into generation-scoped registries. Bindings apply at gateway, model, or provider scope and merge default, binding, request, model, key, and provider settings according to the relevant middleware contract. Built-ins cover rate and token limits, budgets, content blocking, response filtering, session context, prompt injection, request logging, response caching, context compression, output compression, and loop detection.

Persistence and background coordination

Embedded SQLite stores provider and account configuration, models and cascade children, aliases, middleware records and bindings, API-key subjects and limits, blacklist rules, cooldowns, sessions, audit logs, and persistent session state. Provider API secrets use the generated encryption key; managed OAuth credentials use encrypted credential files beneath CREDENTIALS_DIR.

Background jobs remove expired cooldowns, maintain audit partitions and retention, refresh OAuth tokens, reset provider quotas, clean spend caches, and refresh provider model catalogs. A separate Ploinky discovery timer reconciles agent model routes. Graceful shutdown stops ingress and jobs, closes live subscribers, waits for active requests, flushes audits, shuts down backend generations, and closes SQLite.
