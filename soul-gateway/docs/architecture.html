Soul Gateway Architecture

Soul Gateway separates the caller-facing protocol from provider-specific execution. A request enters through the Ploinky Router, passes a fixed route chain, and reaches either one direct model or a prioritized cascade model. The same kernel composition contract runs route, gateway, model, provider, and backend middleware.

Canonical route chain

runRouteRequest() creates one request context and composes error handling, JSON parsing, signed-subject authentication, caller identity, snapshot binding, ingress normalization, audit setup, validation, model resolution, agent-loop protection, session resolution, response serialization, and gateway dispatch. OpenAI Chat, Anthropic Messages, and OpenAI Responses inputs become one canonical request before policy and routing inspect them.

The request binds one immutable runtime snapshot. That snapshot contains enabled providers, direct models, cascade children, aliases, tiers, active cooldowns, API-key policy data, blacklist rules, and middleware bindings. Administrative mutations request a new snapshot generation; in-flight requests retain the generation they already bound.

Execution and provider ownership

A direct model acquires its concurrency slot, enters retry and timeout control, leases one provider account, compiles provider middleware, and invokes the selected backend. The credential lease is released in a finally path. Request-time vendor LLM transport belongs to AchillesAgentLib; Soul Gateway supplies the model, credential, base URL, headers, and provider settings, then converts Achilles stream events to the gateway's canonical stream. The Ploinky-agent backend separately signs the exact serialized request bytes for an authenticated Router capability call.

A cascade model orders enabled children by priority and invokes one child at a time. A classified error may permit another child, may place a model in cooldown, or may fail the request immediately. The gateway persists cooldowns asynchronously and refreshes the snapshot so later requests avoid unavailable children.

Middleware and policy

The middleware catalog loads built-in and extension middleware into generation-scoped registries. Bindings apply at gateway, model, or provider scope and merge default, binding, request, model, key, and provider settings according to the relevant middleware contract. Built-ins cover rate and token limits, budgets, content blocking, response filtering, session context, prompt injection, request logging, response caching, context compression, output compression, and loop detection.

Persistence and background coordination

Embedded SQLite stores provider and account configuration, models and cascade children, aliases, middleware records and bindings, API-key subjects and limits, blacklist rules, cooldowns, sessions, audit logs, and persistent session state. Provider API secrets use the generated encryption key; managed OAuth credentials use encrypted credential files beneath CREDENTIALS_DIR.

Background jobs remove expired cooldowns, maintain audit partitions and retention, refresh OAuth tokens, reset provider quotas, clean spend caches, and refresh provider model catalogs. A separate Ploinky discovery timer reconciles agent model routes. Graceful shutdown stops ingress and jobs, closes live subscribers, waits for active requests, flushes audits, shuts down backend generations, and closes SQLite.
