Operational Need

The regular Explorer filesystem model is not enough for secrets, confidential files, or permission-driven collaboration. Those flows need actor-aware access checks, separate storage rules, and encrypted persistence for sensitive values. If Explorer stored this data directly as ordinary files, it would blur the security boundary and force user interface code to guess at storage and access control list (ACL) semantics that belong on the server side.

Service Boundary

`dpuAgent` exposes Model Context Protocol (MCP) surfaces for secrets, confidential objects, research resources, data sources, jobs, confirmations, provenance, audit, and permission checks. Explorer stays responsible for navigation and interaction flow, while the agent owns identity resolution, access control enforcement, metadata storage, encrypted value storage, provider orchestration, and confidential blob handling.

In practice, requests enter through tools/dpu_tool.sh and tools/dpu_tool.mjs, then dispatch into lib/dpu-store.mjs. Storage and access control list details are delegated further into lib/dpu-store-internal/, where the locking, manifest, and encryption helpers live.

Runtime Behavior

The agent exposes /Confidential with an actor-owned My Space folder and the named Shared, Secrets, Research Data, and Jobs projections. Users can create additional nested files and folders beneath their confidential folder tree; each child is linked to its containing folder by parentId. Research Data and Jobs remain specialized record projections rather than an exhaustive list of permitted directory names. Secret values are stored separately from metadata, confidential file bodies are encrypted, and provider operations run outside the short storage commit lock.

Scope note: DPU records are not normal filesystem entities. Explorer can present them in file-like views, but persistence and permission rules come from DPU, not from the regular workspace filesystem.
