Ploinky and Explorer Integration

gitAgent is integrated as a Ploinky Model Context Protocol (MCP) agent and consumed by Explorer-facing user interface (UI) flows as a backend Git mediator.

Ploinky Runtime Integration

Agent lifecycle is controlled by gitAgent/manifest.json, while tool contracts come from gitAgent/mcp-config.json. AgentServer executes those tool commands in workspace context and returns normalized MCP responses to clients, which keeps Git execution policy centralized in the agent.

AssistOSExplorer Integration

Explorer integration uses the internal AssistOSExplorer repository. Frontend code calls callAgentTool("gitAgent", ...) and relies on this agent for Git operations, conflict checks, push/pull flows, and repository overview behavior.

The Explorer New menu exposes two Git actions: Add new repository creates a GitHub remote or initializes a local repository from an editable remote URL, while Clone repository clones a selected GitHub repository or manual remote. Both actions are contextual: inside a repository they open Add Git submodule and accept only an existing GitHub repository or manual remote URL.

Explorer remains the interaction surface, while gitAgent remains the operational boundary for Git process execution.

IDE-plugins Channel

The folder gitAgent/IDE-plugins/git-tool-button/ provides user interface plugin bundles inserted in Explorer toolbar slot file-exp:toolbar. Plugin dependencies include the Git panel, repo tree, diff viewer, conflict helper, status bar, and auth prompt components.

The Git toolbar opens git-panel inside Explorer's shared expanded modal, initially fullscreen. Explorer owns resize, fullscreen, Escape and close controls. Reactive properties preserve repository and conflict selection; removal clears panel polling and listeners and refreshes toolbar indicators. Branch and stash dialogs open above the panel.

Repository Visibility is a draft confined to the credentials dialog. The Git changes list continues using saved visibility, including during background refreshes. Save persists the preference before applying it to the list; Cancel restores the saved checkbox without changing the list. An unsuccessful Save leaves both the saved preference and Git changes list unchanged.

The Git panel first loads a compact repository overview with aggregate counts. Dirty repositories remain automatically expanded, and Explorer requests their complete git_status independently with bounded concurrency. Repository details are cached until Refresh, while loading and failure states are displayed inside the affected repository row. Repository discovery skips dot-directories and node_modules directories. Quick overview checks use a five-second deadline, while complete status enumeration has a separate 120-second deadline for large repositories.

Generating an AI commit message uses a busy overlay scoped to the Git panel. The Git content remains visible beneath the overlay, duplicate generation requests are disabled, and the panel returns to its interactive state when generation succeeds or fails.

Commit and Commit & Push capture the chosen files, folder selections and exclusions when the action starts. After checking remote updates, they wait for complete status from each selected repository, stage the resolved files, verify staged status, commit and then push. Sync also resolves its selection against complete status. Background tree loading and display row limits do not determine which files are submitted; the process uses request completion without additional timers or polling.

For Commit and Commit & Push, if no selected changes remain, no commit or push is performed and the selection and draft remain available. Failed or aborted operations also retain that input. A batch clears only repositories that committed and preserves skipped selections and their draft. Completion messages report actual operations: checking an up-to-date remote is not a pull, and completing an existing merge is reported separately.

AutoSync pulls before committing and pushing. If a concurrent remote update causes an explicit non-fast-forward push rejection, it synchronizes through the existing Git tool contract and retries the push once. Conflicts or a second rejection stop AutoSync; the plugin never force-pushes.

Before pulling, Commit, Commit & Push, Sync, Pull, and AutoSync refresh the current upstream through git_fetch and check for incoming commits. No incoming commits means no pull or stash. If both incoming commits and uncommitted local work exist, a warning identifies the repository and incoming commit count and offers Stash & pull or Abort. Closing the warning also aborts. Abort stops the operation for that repository without changing working files or staging, and stops the AutoSync timer. Approval permits one stash and pull, followed by stash restoration; conflicts require review.

Stash temporarily removes local changes and can interrupt a coding agent using the same folder. The warning asks the user to pause that agent before continuing. This confirmation does not lock the repository against concurrent writers. Credential validation fetches remote metadata without pulling, and the direct git_pull tool explicitly disables Git's configured autostash.

A resolved merge remains an active Git operation until its merge commit is created. The Git status contract exposes both this state and Git's prepared merge message. Explorer pre-fills the commit field for manual Commit and Commit & Push, preserving user edits, while Sync and AutoSync use the prepared message automatically.

Commit and Push require confirmation for Git file content of at least 50 MiB. The warning lists paths and sizes and offers Continue commit or Continue push, and Abort. Commit checks added or modified staged versions, not unstaged working files. Push checks local history not known through the target remote's tracking references, including a large file added in an earlier commit and deleted later. This is an application warning threshold, not a remote provider limit. Stale tracking references and matching pushes can produce conservative warnings.

Abort, closing the warning, and Escape stop the pending operation and AutoSync without deleting files, undoing staging, or removing existing commits. In Commit & Push, a commit created before a push warning remains local if the push is aborted. Nothing is automatically added to Git LFS. Confirmation applies only to the displayed blob versions; newly discovered large versions require another confirmation. The backend checks again before execution, and the frontend checks before creating or changing a remote. Confirmation is not a repository lock, and other writers or Git hooks can still change the repository.

Artifact Role
IDE-plugins/git-tool-button/config.json Registers plugin metadata, toolbar location, and component dependencies.
IDE-plugins/git-tool-button/git-tool-button.js Hosts button presenter and binds controller lifecycle to Explorer host context.
IDE-plugins/git-tool-button/git-tool-button-controller.js Calls MCP tools via Explorer API and orchestrates autocommit/pull/push/conflict UI logic.

Shared expanded panels cancel superseded launches, retain one close promise when reused, and forward updated properties without recreating the Git panel. Fullscreen restore preserves the previous size within the viewport; Help uses the shared window controls.

Closing a loading panel cancels its startup requests, polling, timers and pending mount. Late shared imports or already submitted server operations cannot resume the closed panel.

Modal cleanup is owned directly by the presenter. Close stops HTTP probes and timers; ordinary asynchronous component loading checks whether the modal is closed before continuing. Hosted components clean up in afterUnload.
